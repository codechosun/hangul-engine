## 0. 왜 이 장이 먼저인가

앞으로 이 교재를 진행하는 내내 같은 질문을 반복하게 됨.

> **"내가 짠 게 맞나?"**

글자 빈도표가 맞는지, 확률 계산이 맞는지, 나중에는 역전파 그래디언트가 맞는지, 트랜스포머가 뱉은 값이 맞는지.

여기서 중요한 차이가 하나 있음. **틀렸을 때 티가 나는 코드가 있고, 티가 안 나는 코드가 있음.**

- 문장을 **생성**하는 코드가 틀리면 → 출력이 쓰레기가 됨. 바로 앎.
- 모델을 **훈련**하는 코드가 틀리면 → 손실이 *조금* 내려감. 모델이 *그럭저럭* 돌아감.

두 번째가 무서운 쪽. 그래디언트 한 항이 틀려도 훈련은 진행됨. 그냥 더 나쁘게 될 뿐. **조용히 틀림.**

그래서 순서를 뒤집음. 모델을 만들기 전에 **모델이 맞는지 재는 자**부터 만듦. 이 장에서 만드는 도구는 마지막 장까지 그대로 씀.

분량은 짧음. 하지만 여기서 정한 규칙이 이후 전부를 지배하므로 대충 넘기지 말자.

## 1. 폴더 구조

전체 저장소는 이렇게 생김.

```
hangul-engine/
├─ common/                 교재 도구. 엔진에는 안 들어감
│  ├─ Test.h
│  ├─ Test.c
│  └─ Types.h
├─ lib/                    엔진이 될 코드. 장을 거치며 자란다
│  └─ (A1부터 채워짐)
├─ ch-A00-skeleton/        이 장
│  └─ Main.c
├─ ch-A01-utf8/            다음 장
│  └─ Main.c
├─ tools/                  파이썬 스크립트 (데이터 준비, 시각화)
├─ CONVENTION.md           코딩 컨벤션
└─ README.md
```

### 세 갈래로 나누는 기준

| 어디에 | 무엇을 | 예 |
|---|---|---|
| `common/` | 교재를 진행하는 **도구**. 최종 엔진에는 안 들어감 | 검증 매크로, 타입 규약 |
| `lib/` | **엔진이 될 코드.** 여러 장이 쓰고 마지막에 엔진이 됨 | UTF-8 처리, 해시맵, 텐서 |
| `ch-XXX/` | 그 장의 **실습 코드.** 이해했으면 역할이 끝남 | `Main.c` |

핵심은 가운데 줄임. **이 교재의 최종 산출물은 30개의 예제 프로그램이 아니라 하나의 엔진**이고, 그 엔진이 바로 `lib/`임.

지금은 비어 있지만 다음 장 A1에서 UTF-8 처리기가 들어가고, 이후 장마다 부품이 하나씩 얹힘. 마지막 장에 가면 이 폴더가 그대로 **쓸 수 있는 물건**이 됨.

### 장은 여전히 혼자 돌아간다

폴더를 나눠도 **각 장은 독립적으로 빌드되고 실행됨.** `common/`과 `lib/`이 포함 경로에 들어가 있으므로(2.4 참고) 독자가 중간 장부터 열어봐도 바로 돌아감.

장 폴더에는 **그 장에서 실험하는 코드만** 둠. 다시 쓸 코드는 `lib/`으로 보냄. 그래서 같은 파일을 여러 장에 복사할 일이 없음.

### 코딩 컨벤션

저장소 루트의 **`CONVENTION.md`**에 이름 규칙과 서식이 정리되어 있음. 기반은 **언리얼 코딩 컨벤션**이되 언리얼 전용 요소는 뺀 범용 부분만 씀.

지금 당장 알아야 할 것은 셋뿐.

| 규칙 | 예 |
|---|---|
| 함수·변수는 **PascalCase** | `CountBytes()`, `CharCount` |
| 전역 변수는 **`G`** 접두사 | `GCheckCount` |
| 중괄호는 **Allman** (여는 괄호가 새 줄에) | |

기존 세 권이 이미 PascalCase를 쓰고 있었으므로 새로 익힐 것은 사실상 `G` 접두사 하나임. 나머지는 필요해질 때 해당 장에서 다시 짚음.

## 2. 빌드 설정

프로젝트를 새로 만드는 방법 자체는 C 교재 `1.4`에 있으므로 생략. 여기서는 **이 교재에서만 다르게 잡아야 하는 것** 네 가지만 봄.

### 2.1 C 표준을 C11로

프로젝트 속성 → `C/C++` → `언어` → `C 언어 표준`에서 **C11**을 고름.

MSVC는 기본적으로 C 표준을 느슨하게 잡음. 명시해두면 컴파일러가 더 엄격하게 검사해줘서 실수를 일찍 잡을 수 있음.

### 2.2 플랫폼은 x64

상단 툴바의 플랫폼을 **x64**로. 기본값이 `x86`(32비트)인 경우가 있음.

이유는 나중에 드러남. 뒤로 가면 배열 하나가 수백 MB가 되는데, 32비트에서는 주소 공간이 부족해서 아예 돌아가지 않음.

### 2.3 소스 인코딩을 UTF-8로

프로젝트 속성 → `C/C++` → `명령줄` → `추가 옵션`에 다음을 넣음.

```
/utf-8
```

이게 없으면 소스에 한글 주석이나 한글 문자열을 넣었을 때 컴파일러가 깨진 글자로 읽음.

> 여기서 미리 감을 잡아두자. **컴파일러도 "이 바이트들이 어떤 글자인지"를 따로 알려줘야 앎.** 바이트와 글자는 다른 것이고, 그 사이를 잇는 규칙이 필요함. 그 규칙이 UTF-8이고, 다음 장 A1의 주제임.

### 2.4 common 과 lib 을 포함 경로에 추가

프로젝트 속성 → `C/C++` → `일반` → `추가 포함 디렉터리`에 **두 폴더**를 넣음.

```
common
lib
```

이러면 각 장에서 이렇게 쓸 수 있음.

```c
#include "Test.h"      // 상대 경로 ../common/Test.h 를 쓰지 않아도 됨
#include "Utf8.h"      // lib/ 도 마찬가지 (A1부터)
```

그리고 `common/Test.c`를 프로젝트에 **소스 파일로 추가**해야 함. 헤더만 포함시키면 링커 에러가 남 (C 교재 `11.5` 참고). `lib/` 의 소스도 장마다 필요한 것을 같은 방식으로 추가함.

## 3. 첫 실행 — A0-1

설정이 맞는지부터 확인하자.

```c
// A0-1
#include <stdio.h>

int main(void)
{
    printf("한글이 깨지지 않으면 성공.\n");
    printf("포인터 크기: %zu 바이트\n", sizeof(void*));
    return 0;
}
```

실행 결과.

```
한글이 깨지지 않으면 성공.
포인터 크기: 8 바이트
```

**확인할 것 두 가지.**

- 한글이 안 깨짐 → `/utf-8`이 먹었음
- 포인터가 **8바이트** → x64로 빌드됐음 (4바이트면 32비트이므로 2.2로 돌아갈 것)

둘 중 하나라도 틀리면 여기서 고치고 가자. 뒤로 갈수록 고치기 번거로워짐.

## 4. 검증 도구를 직접 만든다

### 4.1 assert로는 왜 부족한가

C에는 이미 `assert`가 있음. 그런데 이 교재에는 안 맞는 지점이 셋 있음.

**첫째, 첫 실패에서 죽음.** 검사를 열 개 걸어놨는데 세 번째가 실패하면 나머지 일곱 개는 결과를 못 봄. 우리가 알고 싶은 건 "**몇 개 중 몇 개**가 맞나"임.

**둘째, Release 빌드에서 사라짐.** `NDEBUG`가 정의되면 `assert`는 통째로 없어짐. 그런데 뒤로 가면 속도 때문에 Release로 돌릴 일이 많아짐. 그때 검증이 조용히 꺼져 있으면 곤란함.

**셋째, 우리가 원하는 걸 못 함.** 실수를 비교하려면 "허용 오차 안에 있나"를 물어야 하는데 `assert`는 참/거짓만 봄.

그래서 직접 만듦. 어차피 짧음.

> `assert`를 안 쓴다는 뜻은 아님. **용도가 다름.**
> - `CHECK` — 결과가 맞는지 **검증**. 틀려도 계속 진행하고 마지막에 집계
> - `assert` — 프로그래머 실수를 잡는 **함정**. 예를 들어 널 포인터가 들어오면 안 되는 자리
>
> 이 교재의 규칙: **검증은 CHECK, 있을 수 없는 상황은 assert.**

### 4.2 CHECK 매크로 — A0-2

먼저 헤더.

```c
// common/Test.h
#ifndef TEST_H
#define TEST_H

extern int GCheckCount;
extern int GFailCount;

#define CHECK(Expr) \
    CheckImpl((Expr) ? 1 : 0, #Expr, __FILE__, __LINE__)

int CheckImpl(int Ok, const char* Expr, const char* File, int Line);
int ReportResult(void);

#endif
```

구현.

```c
// common/Test.c
#include "Test.h"
#include <stdio.h>

int GCheckCount = 0;
int GFailCount = 0;

int CheckImpl(int Ok, const char* Expr, const char* File, int Line)
{
    GCheckCount++;

    if (Ok)
    {
        return 1;
    }

    GFailCount++;
    printf("[실패] %s(%d)\n", File, Line);
    printf("       CHECK(%s)\n", Expr);
    return 0;
}
```

`GCheckCount`와 `GFailCount`는 전역 변수임 (C 교재 `6.5`). 여러 파일에서 같은 값을 봐야 하므로 헤더에는 `extern`으로 선언만 하고, `.c` 파일에서 실제로 정의함.

### 4.3 왜 함수가 아니라 매크로인가

여기가 이 장에서 제일 중요한 대목.

이걸 그냥 함수로 만들었다고 해보자.

```c
void Check(int Ok);          // 이렇게 만들면?

Check(Add(2, 2) == 5);       // 호출하는 쪽
```

`Check` 함수가 받는 건 **`0`이라는 값 하나**뿐임. `Add(2, 2) == 5`라는 **식 자체**는 함수 안에서 볼 방법이 없음. 그러면 실패했을 때 "뭐가 실패했는지" 출력할 수가 없음. `실패!`라고만 찍고 끝남.

매크로는 다름. 매크로는 컴파일 **전에** 글자 단위로 치환되므로, 식을 **글자 그대로** 붙잡을 수 있음.

| 문법 | 하는 일 | 결과 |
|---|---|---|
| `#Expr` | 매크로 인자를 **문자열로** 바꿈 | `Add(2, 2) == 5` → `"Add(2, 2) == 5"` |
| `__FILE__` | 이 줄이 있는 **파일 이름** | `"...\Main.c"` |
| `__LINE__` | 이 줄의 **줄 번호** | `28` |

`#`은 **문자열화 연산자**임 (C 교재 `11.4`). 이 셋을 합치면 이렇게 치환됨.

```c
CHECK(Add(2, 2) == 5);

// 전처리기가 아래로 바꿈
CheckImpl((Add(2, 2) == 5) ? 1 : 0, "Add(2, 2) == 5", "...\\Main.c", 28);
```

이제 실패했을 때 **어느 파일 몇 번째 줄에서 어떤 식이** 실패했는지 전부 출력 가능.

> 매크로 인자를 괄호로 감싼 것(`(Expr)`)에 주의. 이걸 빼먹으면 `CHECK(a || b)` 같은 걸 넣었을 때 연산자 우선순위가 꼬임. 매크로 함수를 만들 때의 기본 습관임 (C 교재 `11.4`).

### 4.4 실수 비교 — CHECK_NEAR — A0-3

실수는 `==`로 비교하면 안 됨. 확인해보자.

```c
// A0-3
#include <stdio.h>

int main(void)
{
    float Sum = 0.0f;
    for (int i = 0; i < 10; i++)
    {
        Sum += 0.1f;
    }

    printf("%.10f\n", Sum);
    printf("1.0과 같은가? %s\n", (Sum == 1.0f) ? "예" : "아니오");
    return 0;
}
```

```
1.0000001192
1.0과 같은가? 아니오
```

`0.1`을 열 번 더했으니 `1.0`이어야 할 것 같지만 아님. `0.1`은 2진수로 정확히 표현할 수 없어서(10진수로 `1/3`을 적을 수 없는 것과 같음) 매번 아주 작은 오차가 생기고, 열 번 쌓이면 `1.0000001`이 됨.

### 더 고약한 점

그렇다고 **항상 틀리는 것도 아님.** 이건 되는지 맞혀보자.

```c
float Ratio = 1.0f / 3.0f;
printf("%s\n", (Ratio * 3.0f == 1.0f) ? "같음" : "다름");
```

`1/3`은 2진수로 더 정확히 못 담는데도 결과는 **`같음`**임. 나누면서 생긴 오차와 곱하면서 생긴 오차가 우연히 상쇄되어 정확히 `1.0`으로 반올림되기 때문.

**이게 실수 비교가 위험한 진짜 이유임.** 되기도 하고 안 되기도 하는데, 어느 쪽인지는 해보기 전엔 모름. 그래서 `==`를 아예 안 쓰는 쪽으로 규칙을 정함.

실수는 **"충분히 가까운가"**로 물어야 함.

```c
#define CHECK_NEAR(A, B, Tol) \
    CheckNearImpl((double)(A), (double)(B), (double)(Tol), \
                  #A, #B, __FILE__, __LINE__)
```

```c
int CheckNearImpl(double A, double B, double Tol,
                  const char* ExprA, const char* ExprB,
                  const char* File, int Line)
{
    GCheckCount++;

    double Diff = fabs(A - B);
    if (Diff <= Tol)
    {
        return 1;
    }

    GFailCount++;
    printf("[실패] %s(%d)\n", File, Line);
    printf("       CHECK_NEAR(%s, %s)\n", ExprA, ExprB);
    printf("       %.17g 와 %.17g 의 차이 %.17g (허용 %.17g)\n",
           A, B, Diff, Tol);
    return 0;
}
```

실패했을 때 **두 값과 실제 차이까지** 찍는 게 핵심. 허용 오차를 얼마로 잡아야 할지는 해보기 전엔 모름. 차이가 찍혀야 "아, 1e-6은 너무 빡빡했구나"를 알 수 있음.

`fabs`는 절댓값 함수이므로 `<math.h>`가 필요함.

> 이 `CHECK_NEAR` 하나가 뒤에서 아주 큰 역할을 함. 역전파를 구현할 때 **손으로 유도한 미분값**과 **수치적으로 구한 미분값**을 비교하게 되는데, 그 비교가 정확히 이 함수임. 그때까지는 그냥 실수 비교 도구로 쓰면 됨.

### 4.5 결과 집계

마지막으로 몇 개 중 몇 개가 통과했는지 출력.

```c
int ReportResult(void)
{
    int PassCount = GCheckCount - GFailCount;

    printf("\n검사 %d개 중 %d개 통과", GCheckCount, PassCount);
    if (GFailCount > 0)
    {
        printf(", %d개 실패", GFailCount);
    }
    printf("\n");

    return (GFailCount == 0) ? 0 : 1;
}
```

**반환값에 주의.** 전부 통과면 `0`, 하나라도 실패하면 `1`을 돌려줌. 이걸 `main`에서 그대로 반환하면 프로그램의 종료 코드가 됨.

지금은 눈으로 확인하면 되지만, 나중에 여러 장을 한꺼번에 검사하고 싶을 때 종료 코드만 보면 되므로 편해짐.

## 5. 숫자 타입 규약

파일 하나 더 만들고 끝.

```c
// common/Types.h
#ifndef TYPES_H
#define TYPES_H

#ifdef USE_DOUBLE
typedef double Real;
#else
typedef float Real;
#endif

#endif
```

앞으로 실수를 쓸 때는 `float`이나 `double`을 직접 쓰지 않고 **`Real`**을 씀.

이유는 이것. **실행할 때와 검증할 때 원하는 게 다름.**

| | 원하는 것 | 맞는 타입 |
|---|---|---|
| 실행 | 빠르고 메모리 적게 | `float` (4바이트) |
| 검증 | 오차가 작아서 판정이 명확 | `double` (8바이트) |

지금은 와닿지 않겠지만, 나중에 역전파를 수치미분으로 검증할 때 `float`의 오차가 너무 커서 **통과인지 실패인지 구분이 안 되는** 상황이 옴. 그때 `USE_DOUBLE`만 켜서 돌리면 됨.

미리 `Real`로 써두지 않으면 그때 가서 코드 전체를 뒤져야 함. 한 줄 규칙으로 막아두는 것.

`#ifdef`는 조건부 컴파일임 (C 교재 `11.4`).

## 6. 오류 처리 규약

이 교재는 **예외를 쓰지 않음.** C에는 없고, 뒤에서 C++로 넘어가서도 안 씀. 성능이 중요한 코드에 잘 안 맞고, 무엇보다 이미 배운 것만으로 충분함.

대신 두 가지로 나눔.

| 상황 | 방법 | 예 |
|---|---|---|
| **일어날 수 있는** 오류 | 반환값으로 알림 | 파일이 없음, 메모리 할당 실패 |
| **일어나면 안 되는** 상황 | `assert`로 즉시 중단 | 널 포인터가 들어옴, 인덱스가 범위 밖 |

두 번째는 사용자 잘못이 아니라 **프로그래머 잘못**임. 조용히 넘어가면 안 되고 그 자리에서 죽어야 원인을 찾기 쉬움.

```c
#include <assert.h>

int CountBytes(const char* Text)
{
    assert(Text != NULL);   // 널이 들어오는 건 호출한 쪽 잘못
    ...
}
```

## 7. 전부 돌려보기 — A0-4

```c
// ch-A00-skeleton/Main.c
//
// A0-4. 검증 도구가 제대로 동작하는지 확인한다.
// 마지막 검사는 일부러 실패시켜서 실패 출력이 어떻게 생겼는지 본다.

#include "Test.h"
#include "Types.h"

#include <stdio.h>

int Add(int A, int B)
{
    return A + B;
}

int main(void)
{
    printf("A0. 프로젝트 골격과 검증 도구\n\n");

    // 통과하는 검사
    CHECK(Add(2, 3) == 5);
    CHECK(Add(-1, 1) == 0);

    // 실수 비교. 1/3 을 세 번 더해도 정확히 1 이 되지는 않는다.
    Real Ratio = (Real)1 / (Real)3;
    CHECK_NEAR(Ratio * 3, 1.0, 1e-6);

    // 일부러 실패시킨다. 이 줄을 지우면 종료 코드가 0 이 된다.
    CHECK(Add(2, 2) == 5);

    return ReportResult();
}
```

실행 결과.

```
A0. 프로젝트 골격과 검증 도구

[실패] ...\ch-A00-skeleton\Main.c(29)
       CHECK(Add(2, 2) == 5)

검사 4개 중 3개 통과, 1개 실패
```

마지막 검사를 **일부러 실패**시킨 이유는, 실패 출력이 어떻게 생겼는지 한 번은 봐야 하기 때문. 도구를 만들었으면 **도구가 고장을 제대로 알리는지**도 확인해야 함.

확인할 것.

- 실패한 줄 번호가 실제 줄과 맞는가
- 실패한 **식이 그대로** 찍히는가
- 실패가 있어도 앞의 검사들이 멈추지 않고 집계됐는가

29행의 `CHECK(Add(2, 2) == 5);`를 지우고 다시 돌리면 `검사 3개 중 3개 통과`가 나오고 종료 코드는 `0`이 됨.

## 정리

이 장에서 만든 것.

| 파일 | 내용 |
|---|---|
| `common/Test.h` · `Test.c` | `CHECK`, `CHECK_NEAR`, `ReportResult` |
| `common/Types.h` | `Real` 타입 별칭 |

정한 규칙.

- 장마다 폴더를 나누고, 전 장이 공유하는 것만 `common/`에 둠
- 빌드는 **C11 / x64 / `/utf-8`**
- 실수는 `Real`로 씀. 검증할 때는 `USE_DOUBLE`로 전환
- **검증은 `CHECK`, 있을 수 없는 상황은 `assert`**
- 예외는 쓰지 않음

배운 문법.

- 매크로의 **문자열화 연산자 `#`** — 식을 글자 그대로 붙잡는 유일한 방법
- `__FILE__`, `__LINE__` — 미리 정의된 매크로
- `extern` 전역 변수로 파일 간 상태 공유
- `#ifdef` 조건부 컴파일로 타입 전환

## 연습문제

**1.** `CHECK_NEAR(Sum, 1.0, 1e-6)`의 허용 오차를 `0.0`으로 바꿔 돌려보자. 출력에 찍히는 실제 차이는 얼마인가?

<details>
<summary>해답</summary>

약 `1.19e-07`이 찍힘.

`float`는 `0.1`을 정확히 담지 못하므로 더할 때마다 아주 작은 오차가 생기고, 열 번 쌓이면 그만큼 벌어짐. 이 숫자가 바로 **허용 오차를 얼마로 잡아야 할지**를 알려주는 값임. 그래서 `CHECK_NEAR`가 실패할 때 차이를 찍어주도록 만든 것.

</details>

**2.** 일부러 실패시킨 줄을 지우고 빌드한 뒤, 명령 프롬프트에서 실행하고 종료 코드를 확인해보자.

```
Main.exe
echo %ERRORLEVEL%
```

<details>
<summary>해답</summary>

`0`이 나옴. 실패한 검사가 있으면 `1`.

`ReportResult`가 `(GFailCount == 0) ? 0 : 1`을 돌려주고 `main`이 그걸 그대로 반환하기 때문. 나중에 여러 장을 한꺼번에 돌려서 **화면을 안 보고도 통과 여부를 판단**할 때 쓰게 됨.

</details>

**3.** `CheckImpl`은 `int`를 돌려주는데 지금은 아무도 그 값을 쓰지 않음. 어디에 쓸 수 있을까?

<details>
<summary>해답</summary>

**앞 검사가 통과했을 때만 다음 검사로 가야 할 때.**

```c
if (CHECK(Ptr != NULL))
{
    CHECK(Ptr->Value == 3);   // 널이 아닐 때만 역참조
}
```

`CHECK`가 실패해도 프로그램이 멈추지 않으므로, 이 보호가 없으면 널 포인터를 역참조해서 진짜로 죽어버림. 검증 도구가 프로그램을 죽이면 안 되니까 반환값을 남겨둔 것.

</details>

## 다음 장

**A1. UTF-8과 한글 코드포인트.**

이 장 2.3에서 `/utf-8` 옵션을 넣으며 잠깐 스친 문제를 정면으로 다룸.

한글 한 글자는 **3바이트**임. 그래서 `"안녕"`의 `strlen`은 2가 아니라 6임. 글자를 세려면 바이트를 세면 안 되고, 바이트열을 읽어서 **어디서 한 글자가 끝나는지** 판단해야 함.

여기서 C 교재 `2.4`(비트 연산)와 `7.5`(포인터와 연산자)가 처음으로 실전이 됨. 그리고 이 장에서 만든 `CHECK`로 **한글 11,172자를 전부 왕복시켜 하나도 안 깨지는지** 검증함.
