# A1. UTF-8과 한글 코드포인트

> **선행** · C 교재 `1.10` ASCII / `2.4` 비트 논리·이동 연산자 / `7.5` 포인터와 연산자 / `1.8` 자료형
> **만드는 것** · `Utf8Encode`, `Utf8Decode`, `Utf8Length`
> **예제** · A1-1 ~ A1-7

---

## 0. strlen("안녕")은 왜 6인가

직접 돌려보자.

```c
// A1-1
#include <stdio.h>
#include <string.h>

int main(void)
{
    printf("%zu\n", strlen("Hi"));      // 2
    printf("%zu\n", strlen("안녕"));    // ?
    return 0;
}
```

`안녕`은 두 글자인데 `strlen`은 **6**을 돌려줌.

`strlen`이 틀린 게 아님. **`strlen`은 글자를 세는 함수가 아니라 바이트를 세는 함수**임. 영어는 한 글자가 1바이트라 둘이 우연히 같았을 뿐이고, 한글은 한 글자가 3바이트임.

이 장의 목표는 이것.

> **바이트열을 받아서 "여기서 한 글자가 어디까지인지" 판단하는 코드**를 짠다.

왜 이게 첫 장인가. 앞으로 이 교재는 계속 한국어 텍스트를 다룸. 글자 빈도를 세고, 두 글자 조합을 세고, 나중에는 토큰으로 자름. 그 전부가 **"글자 하나를 어떻게 떼어내는가"** 위에 얹힘. 여기가 틀리면 뒤가 전부 틀림.

## 1. 글자와 바이트는 다르다

### 1.1 ASCII — 글자에 번호를 매기다

C 교재 `1.10`에서 본 것. 컴퓨터는 글자를 직접 저장하지 못하므로 **글자마다 번호를 매긴 표**를 씀. `A`는 65, `a`는 97.

ASCII는 번호가 0~127뿐임. 7비트면 충분하니 **한 글자 = 1바이트**로 딱 떨어졌음.

### 1.2 유니코드 — 세상의 모든 글자에 번호를

한글·한자·이모지까지 담으려면 128개로는 어림도 없음. 그래서 **유니코드**(Unicode)는 번호 공간을 훨씬 크게 잡음. 0부터 0x10FFFF까지.

이 번호 하나를 **코드포인트**(code point)라고 부르고 `U+AC00` 식으로 적음.

| 글자 | 코드포인트 |
|---|---|
| `A` | U+0041 |
| `가` | U+AC00 |
| `한` | U+D55C |

### 1.3 인코딩 — 번호를 바이트로 바꾸는 규칙

여기서 한 단계가 더 필요함. 코드포인트는 **번호**일 뿐이고, 그 번호를 **어떤 바이트로 저장할지**는 따로 정해야 함. 그 규칙을 **인코딩**(encoding)이라고 함.

`U+AC00`은 16비트짜리 숫자임. 이걸 그냥 2바이트로 저장하면 안 되나?

안 됨. 이유 둘.

- **ASCII와 호환이 깨짐.** 기존 영어 문서가 전부 못 쓰게 됨
- **`0x00` 바이트가 섞임.** C 문자열은 `0x00`을 끝으로 보는데, 코드포인트 중간에 `0x00`이 나오면 문자열이 거기서 잘림

**UTF-8**은 이 둘을 피하도록 설계된 규칙임. 그래서 바이트 수가 글자마다 다름.

## 2. UTF-8의 규칙

코드포인트 크기에 따라 1~4바이트를 씀.

| 코드포인트 | 바이트 | 패턴 |
|---|---|---|
| U+0000 ~ U+007F | 1 | `0xxxxxxx` |
| U+0080 ~ U+07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800 ~ U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000 ~ U+10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

`x` 자리에 코드포인트의 비트를 채워 넣음. 앞의 `0`, `110`, `1110`, `11110`과 `10`은 **표식**임.

### 이 설계가 영리한 이유

**① ASCII가 그대로 살아남음.** 1바이트 패턴이 `0xxxxxxx`이므로 0~127은 예전과 똑같은 한 바이트. 영어만 있는 파일은 ASCII이면서 동시에 UTF-8임.

**② 첫 바이트만 보면 길이를 앎.** 위쪽 비트가 몇 개나 연속으로 `1`인지 세면 그게 바이트 수임.

| 첫 바이트 | 뜻 |
|---|---|
| `0xxxxxxx` | 1바이트짜리 글자 |
| `110xxxxx` | 2바이트짜리 글자의 시작 |
| `1110xxxx` | 3바이트짜리 글자의 시작 |
| `11110xxx` | 4바이트짜리 글자의 시작 |
| `10xxxxxx` | **글자의 시작이 아님.** 이어지는 바이트 |

**③ 중간에서도 경계를 찾을 수 있음.** 파일 한가운데로 뛰어들어도 `10xxxxxx`가 아닌 바이트가 나올 때까지 앞으로 가면 글자 시작을 찾음.

**④ `0x00`이 안 섞임.** 첫 바이트든 이어지는 바이트든 최상위 비트 패턴 때문에 `0x00`이 될 수 없음(ASCII의 널 문자 제외). C 문자열이 안 잘림.

> **한글은 전부 3바이트임.** 완성형 한글이 U+AC00 ~ U+D7A3인데, 이 범위가 통째로 U+0800~U+FFFF 안에 들어가기 때문. 예외 없음.

## 3. 손으로 한 번 풀어보기 — A1-3

`가`(U+AC00)를 직접 바이트로 바꿔보자. 비트 연산 감각을 잡는 데는 손으로 한 번 해보는 게 제일 빠름.

**1단계. 코드포인트를 2진수로.**

```
0xAC00 = 1010 1100 0000 0000      (16비트)
```

**2단계. 3바이트 패턴에 자리가 몇 개인지 센다.**

```
1110xxxx  10xxxxxx  10xxxxxx
    ^^^^    ^^^^^^    ^^^^^^
     4비트    6비트     6비트   = 16비트
```

마침 16비트임. 딱 맞음.

**3단계. 16비트를 4 / 6 / 6 으로 자른다.**

```
1010110000000000
────┬─────┬─────
1010 110000 000000
```

**4단계. 표식을 앞에 붙인다.**

```
1110 + 1010   = 11101010 = 0xEA
  10 + 110000 = 10110000 = 0xB0
  10 + 000000 = 10000000 = 0x80
```

**`가` = `EA B0 80`**

실행해서 확인해보자.

```
[A1-3] 글자별 바이트
  가 : EA B0 80  -> U+AC00
  한 : ED 95 9C  -> U+D55C
  A : 41  -> U+0041
```

`A`는 1바이트 그대로고, 한글은 셋씩임.

## 4. unsigned char를 써야 하는 이유 — A1-2

코드를 쓰기 전에 반드시 짚어야 할 함정 하나. **바이트를 `char`로 다루면 안 됨.**

MSVC에서 `char`는 **부호 있는** 타입임. 즉 `-128 ~ 127`. 그런데 UTF-8 바이트는 `0 ~ 255`를 다 씀.

```c
// A1-2
char          Signed   = (char)0xEA;
unsigned char Unsigned = (unsigned char)0xEA;

printf("%d\n", Signed);     // -22
printf("%d\n", Unsigned);   // 234
```

같은 비트 `0xEA`인데 **값이 다르게 읽힘.** `char`로 읽으면 최상위 비트를 부호로 해석해서 음수가 됨.

이게 실제로 어디서 터지는가.

```c
// "3바이트짜리 글자의 시작인가?" 를 보려고 0xE0 과 비교하면
if (Signed >= 0xE0)      // -22 >= 224  ->  거짓 (!)
if (Unsigned >= 0xE0)    // 234 >= 224  ->  참
```

`char`로 비교하면 **정수로 승격될 때 부호가 확장되어**(sign extension) `-22`가 되고, `224`보다 작다고 판정됨. 한글을 통째로 놓침.

실행 결과.

```
[A1-2] 부호 있는 char 의 함정
  char          0xEA -> -22
  unsigned char 0xEA -> 234
  0xE0 이상인가?  char: 아니오(!)   unsigned char: 예
```

> **이 교재의 규칙: 바이트를 값으로 다룰 때는 반드시 `unsigned char`.**
> 문자열을 받을 때는 `const char*`로 받되, 안에서 바로 캐스팅함.
>
> ```c
> const unsigned char* Bytes = (const unsigned char*)Text;
> ```

## 5. 디코더 — 바이트열에서 코드포인트 읽기

이제 규칙을 코드로 옮김. 하는 일은 둘.

1. 첫 바이트의 위쪽 비트를 보고 **길이를 판단**
2. 각 바이트에서 **`x` 자리만 뽑아 이어 붙임**

### 5.1 길이 판단 — 마스크와 비교

"위쪽 3비트가 `110`인가"를 어떻게 묻는가. **관심 있는 비트만 남기고 나머지를 지운 뒤** 비교하면 됨.

```c
if ((First & 0xE0u) == 0xC0u)   // 위쪽 3비트가 110 인가?
```

`0xE0` = `11100000`. `&` 연산은 양쪽이 다 1일 때만 1이므로, 이걸 씌우면 **위쪽 3비트만 남고 나머지는 0**이 됨. 그 결과가 `0xC0`(`11000000`)이면 패턴이 맞는 것.

| 검사 | 마스크 | 기댓값 |
|---|---|---|
| 1바이트 `0xxxxxxx` | `0x80` | `0x00` |
| 2바이트 `110xxxxx` | `0xE0` | `0xC0` |
| 3바이트 `1110xxxx` | `0xF0` | `0xE0` |
| 4바이트 `11110xxx` | `0xF8` | `0xF0` |
| 이어지는 바이트 `10xxxxxx` | `0xC0` | `0x80` |

**순서가 중요함.** 1바이트부터 차례로 검사해야 함. `0xE0` 검사를 먼저 하면 4바이트 선행 바이트가 걸려들 수 있음.

### 5.2 비트를 뽑아 이어 붙이기

3바이트 글자라면 `4 + 6 + 6`비트를 모아야 함.

```c
*OutCode = ((uint32_t)(First    & 0x0Fu) << 12)   // 위쪽 4비트를 12칸 밀고
         | ((uint32_t)(Bytes[1] & 0x3Fu) << 6)    // 가운데 6비트를 6칸 밀고
         |  (uint32_t)(Bytes[2] & 0x3Fu);         // 마지막 6비트는 그대로
```

- `& 0x0F` — 아래 4비트만 남김 (표식 `1110`을 지움)
- `& 0x3F` — 아래 6비트만 남김 (표식 `10`을 지움)
- `<<` — 자기 자리로 밀어 올림
- `|` — 겹치지 않으니 그대로 합침

`가`로 확인해보자.

```
First    = 0xEA = 11101010  ->  & 0x0F = 1010      -> << 12 = 1010 000000 000000
Bytes[1] = 0xB0 = 10110000  ->  & 0x3F = 110000    -> << 6  =      110000 000000
Bytes[2] = 0x80 = 10000000  ->  & 0x3F = 000000    ->               000000
                                                      합치면 1010110000000000 = 0xAC00
```

### 5.3 전체 코드

> **이 장의 코드는 `lib/`에 들어감.** 장 폴더가 아님.
>
> A0에서 정한 기준대로임 — UTF-8 처리는 앞으로 **거의 모든 장이 쓰고**, 최종적으로 엔진의 일부가 됨. 토크나이저(tokenizer)가 바이트열을 다루려면 반드시 필요하기 때문.
>
> 지금 비어 있던 `lib/`에 첫 부품이 들어가는 순간임. 여기서부터 엔진이 자라기 시작함.

```c
// lib/Utf8.c
int Utf8Decode(const char* Text, uint32_t* OutCode)
{
    assert(Text != NULL);
    assert(OutCode != NULL);

    const unsigned char* Bytes = (const unsigned char*)Text;
    unsigned char First = Bytes[0];

    // 1바이트: 0xxxxxxx
    if ((First & 0x80u) == 0x00u)
    {
        *OutCode = First;
        return 1;
    }

    // 2바이트: 110xxxxx
    if ((First & 0xE0u) == 0xC0u)
    {
        if ((Bytes[1] & 0xC0u) != 0x80u) return 0;

        *OutCode = ((uint32_t)(First    & 0x1Fu) << 6)
                 |  (uint32_t)(Bytes[1] & 0x3Fu);
        return 2;
    }

    // 3바이트: 1110xxxx
    if ((First & 0xF0u) == 0xE0u)
    {
        if ((Bytes[1] & 0xC0u) != 0x80u) return 0;
        if ((Bytes[2] & 0xC0u) != 0x80u) return 0;

        *OutCode = ((uint32_t)(First    & 0x0Fu) << 12)
                 | ((uint32_t)(Bytes[1] & 0x3Fu) << 6)
                 |  (uint32_t)(Bytes[2] & 0x3Fu);
        return 3;
    }

    // 4바이트는 같은 방식이므로 생략 — 전체는 Utf8.c 참고

    return 0;   // 선행 바이트가 아니다
}
```

**반환값이 바이트 수임.** 이게 중요함. 부르는 쪽이 이 값만큼 포인터를 앞으로 밀면 다음 글자로 감. 실패하면 `0`을 돌려주므로(결정: 반환 코드 + assert) 무한 루프에 빠지지 않음.

### 5.4 문자열 끝을 넘어 읽지 않는가

3바이트 글자라고 해놓고 뒤가 잘려 있으면?

```c
Utf8Decode("\xEA\xB0", &Code);   // 3바이트인데 2개뿐
```

안전함. `Bytes[1]`은 `0xB0`이라 통과하지만, `Bytes[2]`는 **널 종료 문자 `0x00`**임. `(0x00 & 0xC0) != 0x80`이므로 거기서 `0`을 돌려주고 멈춤. **널 문자를 넘어 읽기 전에 반드시 걸림.**

이건 우연이 아니라 UTF-8 설계 덕분임. 이어지는 바이트는 `10xxxxxx`라 절대 `0x00`이 될 수 없음.

## 6. 인코더 — 코드포인트를 바이트열로

디코더를 거꾸로 하면 됨.

```c
// 3바이트: 1110xxxx 10xxxxxx 10xxxxxx
if (Code <= 0xFFFFu)
{
    Bytes[0] = (unsigned char)(0xE0u | (Code >> 12));
    Bytes[1] = (unsigned char)(0x80u | ((Code >> 6) & 0x3Fu));
    Bytes[2] = (unsigned char)(0x80u | (Code & 0x3Fu));
    return 3;
}
```

- `>>` 로 원하는 자리를 맨 아래로 내림
- `& 0x3F` 로 6비트만 남김
- `|` 로 표식을 씌움

`Bytes[0]`에는 `& 0x0F`가 없음. `Code <= 0xFFFF`이므로 `Code >> 12`가 이미 4비트 이하라서 필요 없음.

## 7. 글자 수 세기 — A1-5

이제 처음 질문에 답할 수 있음.

```c
int Utf8Length(const char* Text)
{
    int Count = 0;

    while (*Text != '\0')
    {
        uint32_t Code = 0;
        int Len = Utf8Decode(Text, &Code);

        if (Len == 0)
        {
            return -1;   // 깨진 바이트열
        }

        Text += Len;     // 읽은 만큼 앞으로
        Count++;
    }

    return Count;
}
```

**`Text += Len`이 이 장의 포인터 산술임** (C 교재 `7.5`). 한 글자가 몇 바이트인지 미리 알 수 없으므로, 읽어보고 나온 길이만큼 민다.

실행 결과.

```
[A1-5] strlen 과 Utf8Length
  "안녕" : strlen=6, Utf8Length=2
  "Hi안녕" : strlen=8, Utf8Length=4
```

`Hi안녕`은 영어 2바이트 + 한글 6바이트 = 8바이트지만 글자로는 4개임.

## 8. 11,172자 왕복 검증 — A1-6

이제 A0에서 만든 `CHECK`를 쓸 차례.

### 왜 11,172인가

완성형 한글은 U+AC00부터 U+D7A3까지임. 세어보면 `0xD7A3 - 0xAC00 + 1 = 11172`.

이 숫자가 어디서 나오는가.

```
초성 19개  ×  중성 21개  ×  종성 28개(없음 포함)  =  11,172
```

한글이 조합 문자라서 모든 조합을 미리 만들어 표에 넣어둔 것임. 코드포인트 순서도 이 규칙을 따름.

### 여기서 직관이 한 번 배신한다

`끥`, `쭃` 같은 조합은 표에만 있고 실제 글에는 안 나올 것 같음. 그래서 **"실제로 쓰이는 글자는 11,172개보다 훨씬 적겠지"**라고 짐작하기 쉬움.

이 교재가 쓸 한국어 위키백과 코퍼스(약 6억 글자)로 직접 세어보면 그렇지 않음.

> **11,172자가 전부 등장함. 하나도 빠짐없이 100%.**

6억 글자쯤 되면 아무리 희귀한 조합도 어딘가에는 한 번씩 나옴.

대신 **분포가 극단적으로 치우쳐 있음.**

| 상위 | 한글 사용량에서 차지하는 비중 |
|---|---|
| 100자 | 65.5% |
| **500자** | **96.6%** |
| 1,000자 | 99.7% |

즉 *"쓰이는 글자가 적다"*가 아니라 **"전부 나오지만 500자가 거의 다 먹는다"**가 맞음.

이 차이가 뒤에서 결정적이 됨. A4에서 빈도표를 어떤 자료구조에 담을지 정해야 하는데, **배열로 하면 11,172칸을 전부 잡아야 하지만 실제 부하는 500칸 근처에 몰려 있음.** 그때 이 숫자를 다시 꺼냄.

> 짐작을 적어놓고 넘어갔다면 A4의 근거가 통째로 틀어졌을 것임. **세어보기 전에는 모름** — 이 교재가 장마다 검증을 붙이는 이유이기도 함.

### 검증

전부 인코딩했다가 다시 디코딩해서 **원래 코드포인트로 돌아오는지** 봄.

```c
int RoundTripFail = 0;
int NotThreeBytes = 0;
int HangulCount   = 0;

for (uint32_t Code = HANGUL_FIRST; Code <= HANGUL_LAST; Code++)
{
    char     EncBuffer[8] = { 0 };
    uint32_t Decoded      = 0;

    int EncLen = Utf8Encode(Code, EncBuffer);
    int DecLen = Utf8Decode(EncBuffer, &Decoded);

    if (EncLen != 3 || DecLen != 3) NotThreeBytes++;
    if (Decoded != Code)            RoundTripFail++;

    HangulCount++;
}

CHECK(HangulCount == 11172);
CHECK(NotThreeBytes == 0);
CHECK(RoundTripFail == 0);
```

**`CHECK`를 루프 안에 넣지 않은 이유.** 11,172번을 걸면 통과해도 집계 숫자가 만 단위가 되고, 실패하면 출력이 화면을 넘김. **실패만 세어두고 밖에서 한 번 검사**하는 쪽이 나음. 앞으로도 대량 검사는 이 형태로 감.

실행 결과.

```
[A1-6] 완성형 한글 왕복 검증
  검사한 글자 수 : 11172
  3바이트가 아닌 것 : 0
  왕복이 깨진 것 : 0
```

### 깨진 입력도 확인 — A1-7

제대로 된 입력만 처리하는 건 절반임. **틀린 입력을 거부하는지**도 봐야 함.

```c
CHECK(Utf8Decode("\xEA\xB0", &Dummy) == 0);       // 3바이트인데 2개뿐
CHECK(Utf8Decode("\xEA\x41\x80", &Dummy) == 0);   // 이어지는 바이트가 아님
CHECK(Utf8Decode("\x80", &Dummy) == 0);           // 선행 바이트가 아님
CHECK(Utf8Length("\xEA\xB0") == -1);
```

최종 출력.

```
검사 15개 중 15개 통과
```

## 정리

만든 것.

| 함수 | 하는 일 |
|---|---|
| `Utf8Encode` | 코드포인트 → 바이트열. 쓴 바이트 수 반환 |
| `Utf8Decode` | 바이트열 → 코드포인트. 읽은 바이트 수 반환 |
| `Utf8Length` | 바이트가 아니라 **글자** 수 |
| `Utf8IsHangul` | 완성형 한글 범위인지 |

알아둘 것.

- **글자 ≠ 바이트.** `strlen`은 바이트를 셈
- **한글은 UTF-8에서 3바이트**, 예외 없음
- 첫 바이트의 위쪽 비트가 **길이를 알려줌**
- **바이트를 값으로 다룰 때는 `unsigned char`.** `char`는 부호가 있어서 0x80 이상이 음수가 됨
- 완성형 한글은 **19 × 21 × 28 = 11,172자**
- 실제 글에는 **11,172자가 전부 등장하지만, 상위 500자가 한글 사용량의 96.6%**를 차지함

쓴 문법.

- `&` 마스크로 **관심 있는 비트만 남기기**
- `<<` `>>` 로 비트를 자리로 밀기
- `|` 로 겹치지 않는 비트 합치기
- `Text += Len` — **길이를 모를 때의 포인터 산술**
- `unsigned char` 캐스팅으로 부호 확장 차단

## 연습문제

**1.** 이모지 `😀`(U+1F600)를 `Utf8Encode`에 넣고 바이트를 찍어보자. 몇 바이트가 나오는가?

<details>
<summary>해답</summary>

`F0 9F 98 80` — **4바이트**임.

U+1F600은 U+FFFF를 넘으므로 4바이트 패턴 `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx`를 씀. 담을 비트가 `3 + 6 + 6 + 6 = 21`개라 U+10FFFF까지 들어감.

한글은 전부 3바이트인데 이모지는 4바이트라는 점에서, **"한 글자 = 몇 바이트"를 미리 가정하면 안 된다**는 걸 다시 확인할 수 있음.

</details>

**2.** `Utf8Length`가 `-1`을 돌려주는 입력을 하나 더 만들어보자.

<details>
<summary>해답</summary>

여러 가지가 있음.

```c
Utf8Length("\xEA\xB0\x41");   // 세 번째가 이어지는 바이트가 아님
Utf8Length("\xF8\x80");       // 11111xxx 은 정의된 선행 바이트가 아님
Utf8Length("\xBF");           // 10xxxxxx 는 글자의 시작이 될 수 없음
```

공통점은 **`Utf8Decode`가 `0`을 돌려주는 상황**임. 길이가 `0`이면 포인터를 못 밀어서 무한 루프에 빠지므로, 거기서 `-1`로 빠져나오게 만들어 둔 것.

</details>

**3.** `힣`(U+D7A3)의 UTF-8 바이트를 3절의 방법대로 손으로 계산한 뒤, 코드로 확인해보자.

<details>
<summary>해답</summary>

```
0xD7A3 = 1101 0111 1010 0011

4 / 6 / 6 으로 자르면
1101 | 011110 | 100011

표식을 붙이면
1110 + 1101   = 11101101 = 0xED
  10 + 011110 = 10011110 = 0x9E
  10 + 100011 = 10100011 = 0xA3
```

**`힣` = `ED 9E A3`**

`힣`은 완성형 한글의 **마지막** 글자임(`HANGUL_LAST`). 첫 글자 `가`가 `EA B0 80`이었으니, 11,172자가 이 사이에 늘어서 있는 셈.

</details>

**A2. 빈도 집계와 정렬.**

이제 글자를 하나씩 떼어낼 수 있으므로, 세기 시작함. 한국어 텍스트를 통째로 읽어서 **어떤 글자가 몇 번 나오는지** 집계하고 순위를 매김.

여기서 C 교재 `7.9`의 **함수 포인터**가 처음 실전이 됨 — `qsort`에 "무엇을 기준으로 정렬할지"를 넘겨야 하기 때문. 그리고 결과가 맞는지는 **파이썬으로 같은 집계를 돌려 완전히 일치하는지**로 검증함. 이 교재가 검증할 때 쓰는 기본 수법임.
