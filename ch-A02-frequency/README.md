## 0. 1위가 글자가 아니었다

한국어 위키백과 전체에서 글자 빈도를 세면 이렇게 나온다.

```
 1. 공백    20.25%
 2. 줄바꿈   3.20%
 3. 이       1.77%
 4. 다       1.41%
 5. 의       1.41%
```

**전체의 5분의 1이 공백이다.** 글자를 세려고 했는데 1·2위가 글자가 아니다.

이게 왜 중요한가. 뒤에서 우리는 "다음에 올 글자"를 예측하는 모델을 만든다. 그 모델이 가장 많이 마주칠 것은 **한글이 아니라 공백**이다. 띄어쓰기를 어디에 넣을지가 모델의 가장 큰 일감이 된다. A7에서 문장을 생성해보면 실감하게 된다.

이 장에서 할 일은 단순하다.

> **6억 글자를 세고, 순위를 매기고, 그 결과가 맞는지 증명한다.**

세 번째가 이 장의 진짜 주제다.

## 2. 무엇으로 셀 것인가

글자마다 카운터가 하나씩 필요하다. 가장 단순한 방법은 **코드포인트를 그대로 배열 인덱스로 쓰는 것**이다.

```c
// 유니코드는 0 부터 0x10FFFF 까지
uint64_t* Counts = calloc(0x110000, sizeof(uint64_t));

Counts[Code]++;   // 찾을 필요 없이 바로 접근
```

크기를 계산해보자.

```
0x110000 칸 × 8바이트 = 1,114,112 × 8 = 약 8.9MB
```

**8.9MB면 충분히 감당된다.** 게다가 찾는 비용이 0이다. 인덱스로 바로 접근하니까.

### 왜 uint64 인가

`uint32` 로 하면 42억까지 센다. 우리 코퍼스의 최대 빈도는 공백의 1억 2천만이니 넉넉하다.

그런데 코퍼스를 열 배로 키우면? 공백이 12억, 스무 배면 24억. **42억은 생각보다 가깝다.** 카운터는 넘치면 조용히 0부터 다시 세기 시작하므로 알아채기도 어렵다. 8바이트를 쓰는 값이 있다.

### 그런데 낭비다

실제로 등장하는 글자는 **27,663종**뿐이다. 1,114,112칸 중 2.5%만 쓰고 나머지는 0으로 남는다.

지금은 8.9MB니까 넘어간다. 하지만 A5에서 **두 글자 조합**을 세기 시작하면 이 방식이 무너진다. 그 얘기는 A4에서 한다.

## 3. 큰 파일을 나눠 읽기 — A2-1

1.3GB를 한 번에 메모리에 올릴 수는 없다. 조각내서 읽어야 한다.

```c
#define CHUNK_SIZE (1u << 20)   // 1MB 씩

while (1)
{
    size_t Read = fread(Buffer, 1, CHUNK_SIZE, File);
    if (Read == 0) break;

    // Buffer 를 해석한다...
}
```

여기서 **A1을 하지 않았으면 못 보고 지나쳤을 함정**이 하나 있다.

### 경계에서 글자가 잘린다

한글은 3바이트다. 1MB 경계가 하필 글자 한가운데를 지나가면?

```
청크 1 끝  ...  EA B0        <- "가" 의 앞 두 바이트만 들어옴
청크 2 시작      80  ...     <- 나머지 한 바이트
```

이걸 그냥 해석하면 두 청크 모두에서 깨진 바이트가 된다. 1.3GB를 1MB로 나누면 경계가 **1,300번** 생기니, 조용히 1,300글자가 틀어진다.

### 몇 바이트가 필요한지 먼저 묻는다

해결하려면 **"이 글자가 몇 바이트짜리인가"를 읽기 전에** 알아야 한다. A1에서 본 대로 그건 **첫 바이트만 보면 안다.**

`lib/Utf8` 에 함수 하나를 추가한다.

```c
// lib/Utf8.c  (A2 에서 추가)
int Utf8SequenceLength(unsigned char First)
{
    if ((First & 0x80u) == 0x00u) return 1;   // 0xxxxxxx
    if ((First & 0xE0u) == 0xC0u) return 2;   // 110xxxxx
    if ((First & 0xF0u) == 0xE0u) return 3;   // 1110xxxx
    if ((First & 0xF8u) == 0xF0u) return 4;   // 11110xxx

    return 0;   // 10xxxxxx 이거나 정의되지 않은 패턴
}
```

A1의 디코더에서 길이를 판단하던 부분만 떼어낸 것이다. 마스크와 기댓값 표는 A1 5.1절에 있다.

이제 경계를 처리할 수 있다.

```c
int Need = Utf8SequenceLength(First);

if (Need == 0)
{
    Pos++;                          // 선행 바이트가 아니다. 한 바이트 버린다.
    continue;
}

if (Pos + (size_t)Need > Filled)
{
    break;                          // 잘렸다. 다음 청크와 이어 붙인다.
}
```

잘린 꼬리는 버퍼 앞으로 당겨두고 다음 청크를 그 뒤에 읽어 붙인다.

```c
Leftover = Filled - Pos;
memmove(Buffer, Buffer + Pos, Leftover);
```

그래서 `fread` 가 `Buffer + Leftover` 부터 채우는 것이다.

> 버퍼를 `CHUNK_SIZE + 8` 로 잡은 이유가 이것이다. 최대 3바이트가 남을 수 있으므로 여유를 둔다.

> **저장소 현재 코드 안내.** 이 루프는 A2 시점에 `lib/Freq.c` 안에 있었지만, A4에서 같은 것이 또 필요해져서 `lib/Scan` 으로 옮겼다. A2 당시의 코드를 그대로 보려면 `git checkout ch-A02` 를 쓰면 된다. 왜 옮겼고 그 대가로 무엇을 잃었는지는 A4 본문에 있다.

## 4. 정렬 — 함수 포인터가 필요한 이유

세고 나면 순위를 매겨야 한다. 정렬 알고리듬은 이미 배웠으니(자료구조 교재 `2.2`) 직접 짜지 않고 표준 라이브러리를 쓴다.

```c
qsort(Table, Count, sizeof(FCharCount), FreqCompare);
```

### 4.1 qsort 는 무엇을 모르는가

`qsort` 는 **어떤 타입이든** 정렬할 수 있다. 정수든 구조체든 문자열이든.

그러려면 두 가지를 모른 채로 동작해야 한다.

- 원소가 **무엇인지** → 그래서 `void*` 와 `sizeof` 를 받는다
- 둘 중 **뭐가 앞인지** → 그래서 **비교하는 방법을 함수로 받는다**

두 번째가 함수 포인터다 (C 교재 `7.9`).

```c
void qsort(void* Base, size_t Count, size_t Size,
           int (*Compare)(const void*, const void*));
//         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
//         "int 를 돌려주고 const void* 둘을 받는 함수의 주소"
```

**정렬 순서를 데이터가 아니라 코드로 넘긴다.** 이게 함수 포인터의 쓸모다.

비교 함수는 규칙이 정해져 있다.

| 돌려주는 값 | 뜻 |
|---|---|
| 음수 | A 가 앞 |
| 0 | 순서 상관없음 |
| 양수 | B 가 앞 |

### 4.2 빼서 돌려주면 안 된다

흔히 이렇게 쓴다.

```c
return Right->Count - Left->Count;   // 내림차순... 처럼 보이지만
```

**우리 경우엔 틀린다.** `Count` 가 `uint64_t` 이기 때문이다.

부호 없는 정수끼리 빼면 음수가 나오지 않는다. 밑으로 넘쳐서 **거대한 양수**가 된다. 그걸 `int` 로 자르면 값이 제멋대로가 된다.

공백(1억 2천만)과 어떤 희귀 글자(1)를 비교해보자.

```
Right->Count - Left->Count  =  1 - 123320760
                            =  (uint64 로 넘쳐서) 18446744073586230857
                            →  int 로 자르면 예측 불가
```

그래서 **빼지 말고 비교한다.**

```c
if (Left->Count > Right->Count) return -1;
if (Left->Count < Right->Count) return 1;
```

> 빼기가 통하는 건 **작은 `int` 끼리**일 때뿐이다. 습관처럼 쓰다가 타입이 커지면 조용히 깨진다.

### 4.3 동점 처리가 없으면 검증이 불가능하다

여기가 이 장에서 제일 중요한 대목이다.

빈도만으로 정렬하면 **빈도가 같은 글자들의 순서가 정해지지 않는다.** 27,663종 중 상당수가 동점이고, 특히 꼬리 쪽에는 **빈도 1짜리가 수천 개** 몰려 있다.

`qsort` 는 **안정 정렬이 아니다.** 동점인 원소의 순서를 보장하지 않고, 구현에 따라 달라진다. 그러면 같은 코드를 같은 데이터로 돌려도 **줄 순서가 달라질 수 있다.**

그러면 정답표와 한 줄씩 비교하는 게 불가능해진다.

해법은 **2순위 기준을 두어 동점을 없애는 것**이다.

```c
// 1순위: 빈도 내림차순
if (Left->Count > Right->Count) return -1;
if (Left->Count < Right->Count) return 1;

// 2순위: 코드포인트 오름차순  <- 이게 없으면 검증이 불가능하다
if (Left->Codepoint < Right->Codepoint) return -1;
if (Left->Codepoint > Right->Codepoint) return 1;

return 0;
```

코드포인트는 글자마다 다르므로 **여기까지 오면 동점이 남지 않는다.** 순서가 하나로 확정된다.

`tools/make_expected.py` 도 똑같은 규칙으로 정렬한다.

```python
sorted(Freq.items(), key=lambda Item: (-Item[1], ord(Item[0])))
```

**양쪽이 같은 규칙을 쓰기로 합의**했기 때문에 비교가 성립한다. 이건 파일 포맷만큼이나 중요한 약속이다.

## 5. 골든 파일로 검증하기 — A2-3

이제 결과가 맞는지 증명할 차례다.

파이썬으로 같은 집계를 돌려 그 결과를 저장소에 커밋해두었다. 이런 걸 **골든 파일**(golden file) 이라고 부른다. 현업에서 출력이 복잡한 코드를 검증할 때 흔히 쓰는 방법이다.

```
data/expected.csv

Codepoint,Count
32,123320760
10,19477661
51060,10764068
...
```

27,663줄이다. C 프로그램은 자기가 만든 표를 이 파일과 **한 줄씩** 맞춰본다.

```c
for (int i = 0; i < Limit; i++)
{
    if (Rows[i].Key != Table[i].Codepoint || Rows[i].Value != Table[i].Count)
    {
        Mismatch++;
    }
}

CHECK(Mismatch == 0);
```

### CHECK 를 루프 안에 넣지 않는다

A1에서 쓴 방식 그대로다. 27,663번을 걸면 통과해도 집계가 만 단위가 되고, 실패하면 화면이 넘친다. **틀린 것만 세어두고 밖에서 한 번** 검사한다.

대신 처음 몇 개는 내용을 찍어준다. 개수만 알면 고칠 수가 없기 때문이다.

```c
if (Mismatch < 3)
{
    printf("  [다름] %d번째 줄\n", i + 1);
    printf("         정답표 U+%04X %llu\n", ...);
    printf("         내 결과 U+%04X %llu\n", ...);
}
```

### 줄바꿈이 검증을 깨뜨릴 뻔했다

`expected.csv` 는 저장소에 `.gitattributes` 로 **변환 금지**를 걸어두었다.

```
data/expected.csv -text
```

이게 없으면 윈도우에서 체크아웃할 때 git 이 `LF` 를 `CRLF` 로 바꾼다. 그러면 C 가 읽은 줄 끝에 `\r` 이 붙어 파싱이 틀어진다. **눈으로는 똑같아 보이는데 값만 안 맞는**, 찾기 고약한 버그가 된다.

## 7. MSVC 경고 하나

빌드하면 이런 경고가 뜬다.

```
warning C4996: 'sscanf': This function or variable may be unsafe.
               Consider using sscanf_s instead.
```

`sscanf` 는 **표준 C 함수이고 아무 문제 없다.** MSVC 가 자기네 확장(`sscanf_s`)을 쓰라고 권하는 것뿐이다.

`sscanf_s` 는 마이크로소프트 전용이라 다른 컴파일러에서 안 돌아간다. 표준을 쓰는 게 맞다. 경고만 끄면 된다.

프로젝트 속성 → `C/C++` → `전처리기` → `전처리기 정의` 에 추가한다.

```
_CRT_SECURE_NO_WARNINGS
```

`fopen`, `strcpy` 등에서도 같은 경고가 나오므로 한 번 켜두면 끝이다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Freq.h` · `Freq.c` | 빈도 집계와 정렬 |
| `common/Golden.h` · `Golden.c` | 정답표 읽기 |
| `lib/Utf8` | `Utf8SequenceLength` 추가 |

알아둘 것.

- 한국어 텍스트에서 **가장 흔한 글자는 공백**이다 (20.25%)
- 큰 파일을 나눠 읽으면 **경계에서 글자가 잘린다.** 첫 바이트로 길이를 먼저 판단할 것
- **부호 없는 정수는 빼서 비교하면 안 된다.** 넘쳐서 부호가 뒤집힌다
- **동점 처리 규칙이 없으면 결과를 검증할 수 없다.** `qsort` 는 동점 순서를 보장하지 않는다
- 골든 파일은 **양쪽이 같은 정렬 규칙에 합의**해야 성립한다

쓴 문법.

- **함수 포인터** — `qsort` 에 "비교하는 방법"을 넘긴다
- `void*` 와 `sizeof` 로 타입에 무관한 함수 만들기
- `fread` 로 나눠 읽기, `memmove` 로 꼬리 당기기
- `calloc` 으로 0 초기화된 큰 배열 잡기

`이`(1.77%)가 1위가 되고 `다`, `의` 가 뒤를 잇는다. 마침표와 숫자가 상위권에 그대로 남는다.

여기서 한 가지 판단할 거리가 생긴다. **공백을 세야 하는가?**

글자 통계만 보려면 빼는 게 맞아 보인다. 하지만 우리 목적은 **다음 글자를 예측하는 모델**이고, 그 모델은 띄어쓰기도 맞혀야 한다. 공백을 빼고 배우면 띄어쓰기 없는 글을 뱉게 된다.

그래서 이 교재는 **공백도 구두점도 세지 않고 빼지 않는다.** 있는 그대로 전부 센다. A7에서 문장을 생성할 때 이 선택이 값을 한다.

</details>

**2.** `FreqCompare` 의 1순위 비교를 뺄셈으로 바꿔보자. 실제로 깨지는가?

```c
return (int)(Right->Count - Left->Count);
```

<details>
<summary>해답</summary>

깨진다. 정답표 대조가 실패하고 `OrderBroken` 도 0이 아니게 된다.

`uint64_t` 끼리 빼면 음수가 나올 수 없다. 밑으로 넘쳐서 아주 큰 양수가 되고, `int` 로 자르면 상위 32비트가 버려져 부호가 제멋대로 결정된다.

흥미로운 점은 **작은 값끼리는 우연히 맞는다**는 것이다. 빈도 1과 2를 비교하면 `2 - 1 = 1` 로 정상 동작한다. 그래서 작은 데이터로 테스트하면 통과하고, 실제 데이터에서 터진다. 이런 버그가 제일 찾기 어렵다.

</details>

**3.** 청크 크기(`lib/Scan.h` 의 `SCAN_CHUNK`)를 `4` 로 바꿔보자. 결과가 달라지는가?

<details>
<summary>해답</summary>

**달라지지 않는다.** 서로 다른 글자 27,663종, 전체 609,022,912개, 검사 5개 전부 통과. 숫자 하나 안 바뀐다.

한글이 3바이트이므로 4바이트 청크에서는 거의 매번 경계에 글자가 걸린다. 그런데도 결과가 같다는 것이 **경계 처리가 제대로 동작한다는 증거**다.

느려지기는 한다.

| 청크 크기 | 시간 |
|---|---|
| 1MB | 3.40초 |
| 4바이트 | 8.38초 |

`fread` 호출이 3억 번 넘게 일어나는데도 2.5배밖에 안 느려진다. 표준 라이브러리가 내부에 버퍼를 두고 있어서 매번 디스크까지 가지는 않기 때문이다.

**청크 크기는 정확성이 아니라 속도에만 영향을 준다** — 경계 처리가 맞다면. 이렇게 **파라미터를 극단으로 밀어서 결과가 안 변하는지 보는 것**은 불변식을 확인하는 좋은 방법이다.

</details>

## 다음 장

**A3. 확률과 샘플링.**

빈도표가 생겼으니 이제 **글자를 뽑을** 수 있다. 빈도를 확률로 바꾸고, 그 확률대로 글자를 하나씩 꺼내본다. 언어 모델의 가장 작은 형태다.

여기서 **난수**를 처음 다룬다. 그런데 기존 세 권 어디에도 난수가 나오지 않는다 — 새로 배워야 한다. 그리고 C 표준의 `rand()` 를 그냥 쓰면 **같은 글자만 반복해서 나오는** 함정에 빠진다. 그 함정을 직접 재현해본 뒤, 결과가 항상 똑같이 재현되는 난수 생성기를 직접 만든다.
