## 0. 이미 모델이다

A2에서 만든 빈도표를 다시 보자.

```
공백   20.25%
줄바꿈  3.20%
이      1.77%
다      1.41%
```

이건 그냥 통계표가 아니다. **확률 분포**다. "다음 글자가 무엇일까?"라는 질문에 "20%의 확률로 공백, 1.8%의 확률로 `이`"라고 답할 수 있다.

답할 수 있으면 모델이다. 앞을 하나도 안 보는, 세상에서 가장 멍청한 언어 모델.

이 장에서는 그 모델을 **실제로 굴려본다.** 분포에서 글자를 뽑아 이어 붙이면 이런 게 나온다.

```
어는히  어청  교 2" 어여받т도성다가대번 클포마영시선중  죽어행경  T축는더 출2浩했조 )    시 대
```

말이 안 된다. 당연하다. 그런데 **엉터리인 방식이 정확하다.** 공백이 5분의 1쯤 섞여 있고, 한글이 대부분이고, 숫자와 한자와 라틴 문자가 가끔 끼어든다. 한국어 위키백과의 겉모습 그 자체다.

A4에서 "앞 글자 하나"를 보게 하는 순간 이 글은 눈에 띄게 한국어에 가까워진다. 그 변화를 느끼려면 **출발점이 얼마나 형편없는지**를 먼저 봐야 한다. 그게 이 장이다.

## 1. 첫 번째 함정 — `rand()`

빈도대로 뽑는 방법은 간단하다. 6억 개의 글자를 일렬로 늘어놓고 **아무 데나 하나 찍는다.** 공백이 1억 2천만 개 있으면 찍힐 확률도 그만큼 높다.

그러니까 `0 ~ 609,022,911` 사이의 수 하나가 필요하다. C 표준에는 `rand()` 가 있다.

```c
uint64_t Target = (uint64_t)rand() % Total;
```

이걸로 10만 번 뽑아보면,

```
[A3-1] rand() 로 100000 번 뽑아보기
  RAND_MAX           = 32767
  뽑아야 할 범위     = 0 ~ 609022911
  1등 글자가 가진 칸 = 0 ~ 123320759
  뽑은 값의 최대값   = 32767 (전체의 0.00538%)
  나온 글자 종류     = 1 가지 (공백)
```

**10만 번을 뽑았는데 공백만 나왔다.**

이유는 `RAND_MAX` 한 줄에 다 있다. MSVC에서 `rand()` 는 **0부터 32,767까지**밖에 못 만든다. 6억 짜리 자에 32,767짜리 눈금을 대고 있는 셈이다.

그런데 1등인 공백이 차지한 구간만 해도 `0 ~ 123,320,759` 다. 32,767은 그 안에 **완전히** 들어간다. 그래서 뽑을 때마다 예외 없이 공백이다. 천만 번을 뽑아도 결과는 같다.

> `% Total` 이 범위를 넓혀줄 거라고 생각하기 쉽다. 나머지 연산은 **큰 값을 작게 만들 뿐** 없는 값을 만들어내지 못한다. 32,767을 6억으로 나눈 나머지는 그냥 32,767이다.

`rand()` 를 쓰지 않는 이유는 하나 더 있다. **구현마다 결과가 다르다.** MSVC의 `RAND_MAX` 는 32,767이지만 glibc는 2,147,483,647이다. 같은 씨앗을 심어도 다른 수열이 나온다. 그러면 이 교재에 적힌 숫자를 독자가 재현할 수 없다.

재현되지 않는 숫자는 검증할 수 없다. A0에서 자를 먼저 만든 이유가 여기서도 걸린다.

그래서 **난수 생성기를 직접 만든다.**

## 2. xorshift64 — 세 줄짜리 난수

`lib/Random.c` 의 알맹이는 이게 전부다.

```c
uint64_t RandomNext(FRandom* Rng)
{
    uint64_t X = Rng->State;
    X ^= X << 13;
    X ^= X >> 7;
    X ^= X << 17;
    Rng->State = X;

    return X;
}
```

밀고(`<<`, `>>`) 뒤집기(`^`)를 세 번. C 교재 `2.4` 에서 배운 비트 연산자 두 종류만 쓴다.

동작 원리는 이렇다. 시프트는 비트를 통째로 옮기고, XOR은 옮긴 것과 원래 것을 섞는다. 섞는 순간 **한 비트의 변화가 옆 비트로 번진다.** 이걸 세 번 반복하면 64비트가 골고루 뒤엉킨다. 13, 7, 17이라는 숫자는 주기가 최대(`2^64 - 1`)가 되도록 고른 값이다.

### `State` 가 0이면 안 된다

```c
void RandomSeed(FRandom* Rng, uint64_t Seed)
{
    // 0 은 쓸 수 없다. xorshift 는 0 에서 영원히 0 만 만든다.
    Rng->State = (Seed == 0) ? 0x9E3779B97F4A7C15ull : Seed;
}
```

0을 아무리 밀어도 0이고, 0끼리 XOR해도 0이다. 한 번 0에 빠지면 영원히 0만 나온다. **유일한 금지 상태**이므로 씨앗을 심을 때 한 번 걸러준다.

바꿔 넣는 값 `0x9E3779B97F4A7C15` 는 황금비를 64비트로 표현한 상수다. 비트가 고르게 섞여 있어서 이런 자리에 관습적으로 쓴다.

### 씨앗은 고정한다

```c
#define BOOK_SEED 20260914ull
```

`time(NULL)` 을 쓰지 않는다. **돌릴 때마다 같은 결과가 나와야** 교재의 숫자와 독자의 숫자가 맞는다. 실제 제품에서는 시간을 넣지만, 교재와 테스트에서는 고정이 원칙이다.

A3-3은 그걸 확인한다. 같은 씨앗으로 생성기 두 개를 만들어 1,000번 비교한다.

```c
CHECK(Same == 1);
```

효과는 바로 나타난다.

```
[A3-2] xorshift64 로 100000 번 뽑아보기
  뽑은 값의 최대값   = 609020246 (전체의 100.00%)
```

10만 번 만에 6억 범위의 끝까지 닿았다.

### 나머지 연산의 미세한 치우침

```c
uint64_t RandomBelow(FRandom* Rng, uint64_t Limit)
{
    return RandomNext(Rng) % Limit;
}
```

엄밀히 말하면 이 코드는 완전히 균등하지 않다. `2^64` 를 `Limit` 으로 나누면 딱 떨어지지 않기 때문에, 앞쪽 값 몇 개가 한 번씩 더 나온다.

우리 경우로 계산해보자.

```
2^64         = 18446744073709551616
Total        =           609022912
2^64 / Total = 30289080  ... 나머지 22661120
```

앞쪽 22,661,120개의 값은 30,289,081번 나올 기회를 갖고, 나머지는 30,289,080번이다. **차이가 3천만분의 1이다.** 확률로 따지면 `1.2 × 10^-12`.

천만 번 뽑아서 생기는 통계적 흔들림이 뒤에 나올 `0.009%p` 수준인 것과 비교하면, 치우침은 그보다 **1억 배쯤 작다.** 측정이 불가능하다.

> 암호용 난수라면 이야기가 다르다. 공격자는 `10^-12` 짜리 편향도 긁어모은다. 하지만 우리는 글자를 뽑는 중이다. **어디까지가 충분한가**를 판단하는 것도 엔지니어링이다.

## 3. 두 번째 함정 — 매번 처음부터 세기

이제 `0 ~ 609,022,911` 중 하나를 뽑았다. 이게 몇 번째 글자인지 어떻게 찾는가?

가장 순진한 방법.

```c
uint64_t Sum = 0;
for (int i = 0; i < Count; i++)
{
    Sum += Table[i].Count;
    if (Sum > Target) return Table[i].Codepoint;
}
```

뽑을 때마다 **더하기를 다시 시작한다.** 한 번 뽑는 데 27,663번까지 갈 수 있다.

더하기는 한 번만 하면 된다. 결과를 **누적합 배열**로 남겨두는 것이다.

```c
uint64_t Running = 0;
for (int i = 0; i < Count; i++)
{
    Running += Table[i].Count;
    Cumulative[i] = Running;
}
```

| i | 글자 | 빈도 | `Cumulative[i]` | 담당 구간 |
|---|---|---|---|---|
| 0 | 공백 | 123,320,760 | 123,320,760 | 0 ~ 123,320,759 |
| 1 | 줄바꿈 | 19,477,... | 142,798,... | 123,320,760 ~ ... |
| 2 | 이 | 10,761,... | 153,559,... | ... |

`Cumulative` 는 **오름차순으로 정렬된 배열**이다. 정렬되어 있으면 이진 탐색을 쓸 수 있다.

## 4. 이진 탐색 — 다만 모양이 다르다

자료구조 교재 `2.4` 의 이진 탐색은 이렇게 생겼다.

```c
while (Left <= Right)
{
    Mid = (Left + Right) / 2;
    if (InKey < InData[Mid])       Right = Mid - 1;
    else if (InKey == InData[Mid]) return Mid;
    else                           Left = Mid + 1;
}
```

**정확히 같은 값**을 찾는다. 없으면 실패다.

우리 문제는 다르다. `Target = 5억` 이라는 값이 `Cumulative` 배열에 들어 있을 이유가 없다. 우리가 원하는 것은 **"Target을 처음으로 넘어서는 자리"** 다.

```c
int Low = 0;
int High = Sampler->Count - 1;

while (Low < High)
{
    int Mid = Low + (High - Low) / 2;

    if (Sampler->Cumulative[Mid] > Target)
    {
        High = Mid;          // Mid 도 후보다. 버리지 않는다
    }
    else
    {
        Low = Mid + 1;       // Mid 는 확실히 아니다
    }
}

return Sampler->Table[Low].Codepoint;
```

세 군데가 다르다.

| | 교재의 이진 탐색 | 여기의 이진 탐색 |
|---|---|---|
| 반복 조건 | `Left <= Right` | `Low < High` |
| 찾으면 | `return Mid` 즉시 탈출 | 탈출하지 않는다 |
| 좁힐 때 | `Right = Mid - 1` | `High = Mid` |

**조건을 만족해도 멈추지 않는 것**이 핵심이다. `Cumulative[Mid] > Target` 이어도 그보다 더 왼쪽에 조건을 만족하는 칸이 있을 수 있다. 그래서 `Mid` 를 후보로 남긴 채 범위만 줄인다. 구간이 한 칸으로 줄어들면 그게 답이다.

이 모양을 **lower bound** 라고 부른다. C++ STL에 `std::lower_bound` 라는 이름으로 들어 있고, B파트에서 다시 만난다.

### `(Low + High) / 2` 가 아닌 이유

```c
int Mid = Low + (High - Low) / 2;   // (Low+High)/2 는 넘칠 수 있다
```

`Low` 와 `High` 가 둘 다 크면 `Low + High` 가 `int` 범위를 넘는다. 우리는 27,663개라 절대 안 넘치지만, 이 버그는 **자바 표준 라이브러리의 이진 탐색에서 9년 동안 살아남았다.** 습관으로 굳혀두는 편이 낫다.

`High - Low` 는 항상 원래 범위 안이므로 넘칠 수 없고, 거기에 `Low` 를 더한 값은 `High` 를 넘지 않는다.

## 5. 확률대로 뽑혔는지 확인하기

천만 번 뽑아서 실제 비율을 센다.

```c
for (int i = 0; i < DRAW_COUNT; i++)
{
    uint32_t Code = SamplerPick(&Sampler, &Rng);
    Drawn[IndexOf[Code]]++;
}
```

`IndexOf` 는 코드포인트를 표의 자리로 되돌리는 역인덱스다. A2에서 썼던 `0x110000` 짜리 직접 배열을 한 번 더 쓴다. 4.5MB를 써서 되찾기를 `O(1)` 로 만든다.

결과.

```
[A3-4] 10000000 번 뽑는 중...

  순위      이론      실제      차이  글자
     1   20.249%   20.258%  0.0092%p  공백
     2    3.198%    3.196%  0.0022%p  줄바꿈
     3    1.767%    1.765%  0.0024%p  이
     4    1.410%    1.419%  0.0092%p  다
     5    1.405%    1.408%  0.0024%p  의
     6    1.350%    1.351%  0.0007%p  .
     7    1.288%    1.286%  0.0016%p  1
     8    1.167%    1.167%  0.0002%p  에
     9    1.012%    1.014%  0.0019%p  0
    10    1.009%    1.007%  0.0023%p  ,

  가장 큰 차이 = 0.0092%p
```

```c
CHECK(WorstGap < 0.05);
```

이론과 실제가 소수점 둘째 자리까지 맞는다. **샘플러가 제대로 동작한다는 증거**이자 동시에 **큰 수의 법칙**의 실물이다.

> **글자 칸을 왜 맨 뒤에 뒀는가.** `printf("%-8s", "공백")` 은 칸을 맞춰주지 못한다. `%-8s` 의 8은 **바이트 수**이고 한글은 3바이트이기 때문이다. "공백"은 6바이트라 2칸만 채워지고, 화면에서는 4칸을 차지한다. A1에서 본 "바이트와 글자는 다르다"가 여기서도 튀어나온다. 폭이 들쭉날쭉한 칸은 **맨 뒤로 보내면 문제가 사라진다.**

## 정리

만든 것.

- `lib/Random` — xorshift64. 씨앗이 같으면 어디서 돌려도 같은 수열
- `lib/Sample` — 누적합 + lower bound 이진 탐색

피한 함정.

- **`rand()` 는 범위를 못 채운다** — MSVC 기준 32,767까지. 6억 범위에서는 1등만 나온다
- **`% Total` 은 범위를 넓혀주지 않는다** — 큰 값을 작게 만들 뿐
- **`(Low + High) / 2` 는 넘칠 수 있다** — `Low + (High - Low) / 2`
- **정렬 순서가 알고리듬보다 크게 먹힐 수 있다** — 연습문제 2

쓴 문법.

- 시프트(`<<`, `>>`)와 XOR(`^`) — C 교재 `2.4`
- `uint64_t` 의 자연스러운 순환 (부호 없는 정수는 넘쳐도 정의된 동작)
- 이진 탐색의 lower bound 변형 — 자료구조 교재 `2.4` 의 사촌

이제 **분포에서 글자를 뽑는 기계**가 생겼다. A4부터는 그 분포를 "앞 글자"에 따라 바꾼다. 그러려면 `(앞 글자, 다음 글자)` 쌍을 세야 하고, 그 쌍은 `0x110000` 짜리 배열로는 감당이 안 된다. 해시맵이 필요해진다.

## 연습문제

**1.** `RandomSeed` 의 0 처리를 지우고 `RandomSeed(&Rng, 0)` 으로 돌려보자. 무슨 일이 벌어지는가?

<details>
<summary>해답</summary>

검사 10개 중 2개가 실패하고 `[A3-5]` 는 **공백 60개**를 뱉는다.

```
     1   20.249%  100.000% 79.7510%p  공백
     2    3.198%    0.000%  3.1982%p  줄바꿈

[실패] Main.c(219)
       CHECK(WorstGap < 0.05)
검사 10개 중 8개 통과, 2개 실패
```

`State` 가 0이면 `0 << 13` 도 0, `0 ^ 0` 도 0이다. `RandomNext` 는 영원히 0만 돌려주고, `RandomBelow` 도 0, `SamplerFind(S, 0)` 은 항상 1등 글자를 준다.

**증상이 A3-1과 똑같다.** 원인은 정반대인데(난수 범위가 너무 좁아서 vs. 난수가 아예 안 만들어져서) 화면에 보이는 것은 구분이 안 된다. 그래서 `CHECK` 를 특정 값이 아니라 **성질**에 걸어두는 게 중요하다. 여기서는 `CHECK(MyBiggest > Total / 2)` 가 둘 다 잡아낸다.

xorshift 계열은 이 금지 상태가 **유일한** 약점이다. 그래서 실무에서도 씨앗을 그대로 믿지 않고 한 번 걸러 쓴다.

</details>

**2.** `SamplerFind` 의 이진 탐색을 선형 탐색으로 바꾸면 얼마나 느려질까? 예상한 뒤 재어보자.

<details>
<summary>해답</summary>

**거의 안 느려진다.** 천만 번 뽑기 기준.

| 방식 | 시간 |
|---|---|
| 이진 탐색 | 0.266초 |
| 선형 탐색 | 0.299초 |

12% 차이다. `O(log N)` 과 `O(N)` 인데 왜 이런가.

빈도표가 **내림차순으로 정렬되어 있기 때문**이다. 앞에서부터 훑으면 확률이 높은 글자를 먼저 만난다. 기대 비교 횟수를 계산해보면,

```
Σ (i+1) × p_i = 116.5 번
```

27,663이 아니라 116이다. 이진 탐색의 `log2(27663) ≈ 14.8` 번과 8배밖에 차이가 안 나고, 그마저도 **순차 접근이라 캐시가 다 먹어치운다.** 선형 탐색은 메모리를 앞에서 뒤로 훑으므로 CPU가 미리 읽어둘 수 있지만, 이진 탐색은 배열 여기저기를 건너뛴다.

진짜 차이는 **정렬 순서를 바꿨을 때** 나온다.

| 정렬 | 이진 탐색 | 선형 탐색 |
|---|---|---|
| 빈도 내림차순 | 0.266초 | 0.299초 |
| 코드포인트 오름차순 | 0.267초 | **23.275초** |

코드포인트순으로 정렬하면 기대 비교 횟수가 116.5에서 **12,047번**으로 뛴다. 자주 나오는 글자가 배열 곳곳에 흩어지기 때문이다. 78배 느려졌다.

이진 탐색은 정렬 순서에 **전혀** 영향받지 않는다(0.266 vs 0.267).

읽어낼 것이 두 가지다.

1. **A2에서 빈도순으로 정렬해둔 것이 여기서 공짜 이득이 됐다.** 정렬은 순위를 보려고 한 것이었는데, 탐색 비용까지 78배 줄여줬다.
2. 그럼에도 이진 탐색을 쓰는 이유는 **최악의 경우가 보장되기 때문**이다. 선형 탐색의 0.299초는 "이 분포가 마침 치우쳐 있어서" 나온 숫자다. 분포가 평평해지면 바로 무너진다. D파트에서 다룰 트랜스포머의 출력 분포는 훈련 초기에 거의 균등하다.

</details>

**3.** `DRAW_COUNT` 를 바꿔가며 "가장 큰 차이"가 어떻게 줄어드는지 보자. 규칙이 보이는가?

<details>
<summary>해답</summary>

| 뽑은 횟수 | 가장 큰 차이 |
|---|---|
| 100 | 1.8018%p |
| 1,000 | 1.0490%p |
| 10,000 | 0.6510%p |
| 100,000 | 0.1830%p |
| 1,000,000 | 0.0401%p |
| 10,000,000 | 0.0092%p |
| 100,000,000 | 0.0040%p |

횟수를 100배 늘리면 오차가 **약 10배** 줄어든다. `1,000,000 → 100,000,000` 구간에서 `0.0401 → 0.0040` 으로 정확히 10분의 1이다.

오차가 `1/√N` 에 비례하기 때문이다. 이 관계는 몬테카를로 방법 전반에 걸쳐 나타난다.

실무에서 이게 왜 아픈가. **정확도를 한 자리 올리려면 표본을 100배 늘려야 한다.** 100번 뽑아서 1.8%p였던 것을 0.004%p로 만드는 데 백만 배가 들었다. C파트에서 데이터를 늘려도 성능이 기대만큼 안 오르는 현상의 뿌리가 여기 있다.

`CHECK(WorstGap < 0.05)` 의 `0.05` 라는 문턱도 이 표를 보고 정한 것이다. 천만 번이면 0.0092가 나오니 5배 여유를 뒀다. **너무 빡빡하면 우연히 실패하고, 너무 헐거우면 버그를 못 잡는다.**

</details>
