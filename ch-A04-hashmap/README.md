## 0. 배열은 몇 칸이 필요한가

A3까지는 글자 하나를 셌다. 유니코드 코드포인트를 그대로 배열 인덱스로 쓰면 끝이었다.

```c
uint64_t* Counts = calloc(0x110000, sizeof(uint64_t));   // 8.9MB
```

이제 **글자 쌍**을 센다. 같은 방식이면 2차원 배열이다.

```c
Counts[Prev][Next]++;
```

칸이 몇 개나 필요한지 계산해보자.

```
[A4-1] 글자 쌍을 2차원 배열로 세면
  한글끼리만 (11,172^2)       124813584 칸       952 MB
  코퍼스의 글자끼리           765241569 칸       5.7 GB
  유니코드 전체               1.241e+12 칸         9 TB
```

한글만 세겠다고 타협해도 **1GB에 육박한다.** 코퍼스에 실제로 나온 27,663종을 다 받으려면 5.7GB다. A6에서 세 글자로 넘어가면 여기에 다시 27,663을 곱해야 한다. 곱셈 한 번에 끝난다.

그런데 **실제로 나타나는 쌍은 1,227,989개**다. 2차원 배열이 준비했을 칸의 **0.16%**.

> 6억 개의 글자를 이어 붙이면 쌍도 6억 개다. 그 6억 개가 고작 123만 종류로 수렴한다. 한국어가 아무 글자 뒤에 아무 글자나 오는 언어가 아니기 때문이다. 이 **희소성**이 언어 모델이 성립하는 근거이고, 동시에 이 장에서 해시맵이 필요한 이유다.

빈 칸에 메모리를 쓰지 않는 자료구조가 필요하다. 해시맵이다.

## 1. 교재의 해시맵을 꺼내 온다

자료구조 교재 `1.7` 에서 만든 것을 그대로 가져와 실행해본다.

```c
#define BOOK_SLOTS 7

typedef struct
{
    const char* Keys[BOOK_SLOTS];
    int Values[BOOK_SLOTS];
} FBookMap;
```

여덟 개를 넣어보면,

```
[A4-2] 자료구조 교재 1.7 의 해시맵에 8개를 넣으면
  칸 수 = 7, 넣으려 한 개수 = 8
  들어간 개수 = 7, 처음 실패한 것 = 8번째 ("Jung")
```

이건 버그가 아니다. **의도된 설계다.** 교재의 해시맵은 해시 충돌과 선형 탐사를 눈으로 보여주려고 칸을 일부러 7개로 잡았다. 일곱 칸짜리 표에 여덟 개가 안 들어가는 건 당연하다.

우리가 넣어야 할 것은 **123만 개**다. 고칠 곳이 네 군데다.

| | 교재 `1.7` | 이 장의 `lib/Map` | 이유 |
|---|---|---|---|
| 키 | `const char*` | `uint64_t` | 글자 쌍은 숫자다. `strcmp` 가 필요 없다 |
| 칸 수 | 7 고정 | 자란다 | 몇 개가 들어올지 미리 모른다 |
| 칸 수의 성질 | 소수 (`% 7`) | 2의 거듭제곱 (`& Mask`) | 3절에서 잰다 |
| 값 | 덮어쓴다 | 더한다 | 세는 게 목적이다 |
| 삭제 | 있다 | **없다** | 안 지우면 `DELETED` 상태도 필요 없다 |

마지막 줄은 기능을 줄여서 얻은 이득이다. 교재도 주석으로 짚어두었다.

> 실제 Linear Probing 기반 해시 자료구조는 삭제된 위치를 NULL로 만들면 탐색이 끊어질 수 있어서 EMPTY, USED, DELETED 상태를 별도로 관리함. — 자료구조 교재 `1.7`

우리는 코퍼스를 세기만 하고 지우지 않는다. **필요 없는 기능을 안 만들면 그에 딸린 복잡도도 안 생긴다.**

## 2. 키를 숫자 하나로 묶기

글자 두 개를 어떻게 키 하나로 만드는가. 코드포인트는 21비트면 충분하고(`0x10FFFF`), 우리에겐 64비트가 있다.

```c
static uint64_t PackPair(uint32_t Prev, uint32_t Next)
{
    return ((uint64_t)Prev << 32) | (uint64_t)Next;
}
```

위쪽 32비트에 앞 글자, 아래쪽 32비트에 뒤 글자. **정보를 하나도 잃지 않는다.** 되꺼내는 것도 시프트와 마스크 한 번씩이다.

```c
uint32_t Prev = (uint32_t)(Key >> 32);
uint32_t Next = (uint32_t)(Key & 0xFFFFFFFFu);
```

이걸로 문자열 키가 사라졌다. `strcmp` 도, `malloc` 으로 키를 복사해두는 일도 없다. 키 비교가 `==` 한 번이 된다.

> `(Prev << 21) | Next` 로 42비트에 욱여넣을 수도 있다. A6에서 세 글자를 다룰 때 그게 필요해진다. 지금은 읽기 쉬운 쪽을 고른다.

## 3. 해시 함수는 무엇을 하는가

칸 번호는 이렇게 고른다.

```c
uint64_t Slot = MapHash(Key) & (Capacity - 1);
```

`MapHash` 를 빼고 `Key & (Capacity - 1)` 로 하면 어떻게 될까. 실제로 해보면,

```
[A4-3] 키 1227989개를 칸 2097152개(2^21)에 뿌리면
  방식                   쓰인 칸   최대 무더기
  키 그대로                27663         11037
  MapHash 로 섞기         929375             7
```

**27,663.** 어디서 본 숫자다. A2에서 센 "코퍼스에 나온 글자의 종류"다.

이유는 `PackPair` 를 보면 바로 나온다. 키의 아래쪽 32비트는 **뒤 글자 그대로**다. 210만 칸을 마스크로 자르면 아래 21비트만 남고, 그건 뒤 글자의 코드포인트다. 앞 글자가 무엇이든 **뒤 글자가 같으면 같은 칸에서 출발한다.**

209만 칸을 마련했는데 2만 7천 칸만 쓴다. 한 칸에서 11,037개가 출발한다.

실제로 자리를 잡아보면 값이 얼마나 벌어지는지 보인다.

```
  키 100000개로 실제 탐사 횟수를 재면 (칸 262144개, 적재율 0.38)
  방식                 평균 탐사          최악      시간
  키 그대로             20072.93         83289     0.451s
  MapHash 로 섞기           1.31            18     0.001s
```

한 번 찾는 데 **평균 2만 칸**을 들여다본다. 해시맵이라고 이름만 붙었을 뿐, 사실상 배열을 처음부터 훑는 것보다 나쁘다. 키 10만 개에 0.45초면 123만 개로는 **한 시간 단위**가 된다.

`MapHash` 를 통과시키면 평균 1.31칸이다. **15,000배 차이**가 자료구조가 아니라 함수 하나에서 나온다.

### `MapHash` 가 하는 일

```c
uint64_t MapHash(uint64_t Key)
{
    uint64_t X = Key;

    X ^= X >> 33;
    X *= 0xFF51AFD7ED558CCDull;
    X ^= X >> 33;
    X *= 0xC4CEB9FE1A85EC53ull;
    X ^= X >> 33;

    return X;
}
```

교재의 65599 해시와 **발상이 같다.**

```c
// 자료구조 교재 1.7, Ex010703
HashValue = 65599 * HashValue + InKey[i];
...
return HashValue ^ (HashValue >> 16);
```

큰 수를 곱해 넘치게 만들고(곱셈은 아래쪽 비트의 영향을 위쪽으로 밀어 올린다), 시프트와 XOR로 위쪽 비트를 아래로 끌어내린다. 이걸 두 번 반복한 것뿐이다. 상수가 64비트에 맞게 크고, 섞는 횟수가 많다.

이 함수의 이름은 splitmix64 finalizer 이고, Java 의 `HashMap`, Rust 의 `HashMap`, 리눅스 커널이 모두 사촌뻘 되는 함수를 쓴다. 우리가 만든 것이 장난감이 아니라는 뜻이다.

> **왜 섞어야 하는가.** 해시 함수의 일은 "값을 줄이는 것"이 아니라 **"입력의 규칙성을 지우는 것"** 이다. 우리 키는 규칙적이다 — 아래 21비트가 곧 뒤 글자다. 규칙적인 입력을 규칙적으로 자르면 규칙적으로 뭉친다.

## 4. 소수인가 2의 거듭제곱인가

교재는 칸 수를 **소수**로 잡으라고 했다.

> 배열의 크기가 소수인 경우 약수가 2개임. 일정한 패턴을 가진 입력 값이 들어온다해도 약수가 적으니, 인덱스가 겹치는 현상도 합성수에 비해 적어짐. — 자료구조 교재 `1.7`

맞는 말이다. 그런데 **전제가 있다.** "일정한 패턴을 가진 입력 값"이 들어올 때의 이야기다. 앞 절에서 우리는 그 패턴을 `MapHash` 로 이미 지웠다.

그러면 소수가 아직도 필요한가. 재어보자.

```
[A4-4] 나머지 연산과 비트 마스크 (키 1227989개, 10번 반복 평균)
  방식                     칸 수   평균 탐사      시간
  & 마스크               2097152        1.710     0.010s
  % 나머지 (소수)        2097169        1.703     0.015s
  % 가 & 보다 1.47 배 걸린다
```

평균 탐사 횟수는 **1.710 대 1.703.** 차이가 없다. 잘 섞인 값은 아래 비트만 잘라도 고르게 퍼진다.

시간은 `%` 쪽이 1.47배 걸린다. 정수 나눗셈은 CPU에서 가장 느린 산술 명령이고(곱셈의 5~10배), `&` 는 1사이클이다.

**섞기 전에는 소수가 필요하고, 섞은 뒤에는 필요 없다.** 교재의 규칙이 틀린 게 아니라, 규칙이 성립하는 조건이 사라진 것이다.

2의 거듭제곱을 고르면 따라오는 이득도 있다.

```c
Slot = (Slot + 1) & Mask;   // 표 끝에서 자동으로 0 으로 돌아온다
```

`% Slots` 없이 한 바퀴가 돈다. 표를 두 배로 늘리는 것도 `Capacity << 1` 이다.

## 5. 표를 늘리기

몇 개가 들어올지 모르므로 작게 시작해 자라게 한다.

```c
#define MAP_MAX_LOAD 0.7

if ((double)(Map->Count + 1) > (double)Map->Capacity * MAP_MAX_LOAD)
{
    Grow(Map);
}
```

**적재율**(load factor)이 0.7을 넘으면 두 배로 늘린다. 늘릴 때 기존 항목을 그냥 복사하면 안 된다. 칸 수가 바뀌면 `Hash & Mask` 의 결과가 바뀌므로 **전부 다시 넣어야 한다.**

```c
static int Grow(FMap* Map)
{
    FMap Bigger;
    MapInit(&Bigger, Map->Capacity * 2);

    for (uint64_t i = 0; i < Map->Capacity; i++)
    {
        if (Map->Used[i] != 0)
        {
            InsertFresh(&Bigger, Map->Keys[i], Map->Values[i]);
        }
    }

    free(Map->Keys); free(Map->Values); free(Map->Used);
    *Map = Bigger;
    return 1;
}
```

`InsertFresh` 는 `MapAdd` 와 다르다. **"이미 있는 키인가"를 검사하지 않는다.** 새 표에 중복이 있을 리 없기 때문이다. 옮기는 동안 잠깐 두 표가 함께 존재하므로 메모리가 1.5배까지 부푼다.

리해싱은 비싸 보이지만 그렇지 않다. 16칸에서 시작해 200만 칸까지 가는 동안 리해싱은 **17번** 일어나고, 옮긴 항목의 총합은 `16 + 32 + ... + 1048576 < 2 × 1048576` 이다. 항목 하나당 평균 두 번 옮겨지는 셈이다. 넣기 한 번의 비용을 길게 평균 내면 여전히 상수다. (**분할 상환 분석**, amortized analysis)

A4-6이 그걸 확인한다.

```
[A4-6] 16칸으로 시작해 5,000개를 넣으면
  칸 수           = 8192
  들어간 수       = 5000
  전부 되찾았는가 = 예
```

16칸으로 시작해 9번 자라는 동안 **하나도 잃어버리지 않았다.**

## 6. 파일을 훑는 코드를 꺼내다

글자 쌍을 세려면 코퍼스를 다시 한 글자씩 읽어야 한다. A2의 `lib/Freq.c` 안에 그 루프가 이미 있다 — 청크로 나눠 읽고, 경계에서 잘린 글자를 이어 붙이는 그 코드다.

같은 것이 두 번째로 필요해졌다. **두 번째가 되면 옮긴다.**

```c
// lib/Scan.h
FScanner Scanner;
ScanOpen(&Scanner, Path);

uint32_t Code;
while (ScanNext(&Scanner, &Code))
{
    ...
}
ScanClose(&Scanner);
```

`lib/Freq.c` 도 이걸 쓰도록 고쳤다. `FreqCountFile` 의 본문이 60줄에서 20줄로 줄었다.

### 그 대가

공짜가 아니었다. A2를 옮기기 전과 후로 재보면,

| | 시간 |
|---|---|
| A2 당시 (루프가 `Freq.c` 안에) | 2.60초 |
| `lib/Scan` 으로 뺀 뒤 | 3.39초 |

**30% 느려졌다.** 글자마다 함수를 한 번씩 부르는데, `ScanNext` 는 다른 `.c` 파일에 있어서 컴파일러가 인라인할 수 없다. 6억 번의 함수 호출이 그대로 비용이 된다.

재사용성과 성능이 맞붙었다. 보통은 한쪽을 포기하지만, 이 경우엔 **컴파일러 설정 하나로 둘 다 가진다.**

프로젝트 속성에서 두 가지를 켠다.

| 설정 | 위치 |
|---|---|
| **전체 프로그램 최적화** (`/GL`) | `C/C++` → `최적화` → `전체 프로그램 최적화` = `예` |
| **링크 타임 코드 생성** (`/LTCG`) | `링커` → `최적화` → `링크 타임 코드 생성` = `예` |

이걸 켜면 컴파일러가 **`.c` 파일 경계를 넘어서 인라인한다.** 각 파일을 따로 기계어로 번역하는 대신, 중간 표현을 들고 있다가 링크할 때 한꺼번에 최적화한다.

| | 시간 |
|---|---|
| A2 당시 | 2.60초 |
| `lib/Scan` (`/GL` 없이) | 3.39초 |
| `lib/Scan` + `/GL /LTCG` | **2.55초** |

옮기기 전보다 오히려 빠르다. **A4부터는 이 두 설정을 켠 상태를 기준으로 한다.**

> 빌드가 느려지는 대가가 있다. 링크할 때 전체를 다시 최적화하므로 큰 프로젝트에서는 링크가 몇 배로 길어진다. 그래서 보통 Release 에만 켠다.

## 7. 6억 개를 세다

준비가 끝났다. 코퍼스를 훑으며 이웃한 글자 쌍을 전부 센다.

```c
while (ScanNext(&Scanner, &Code))
{
    if (HasPrev)
    {
        MapAdd(&Pairs, PackPair(Prev, Code), 1);
    }
    Prev = Code;
    HasPrev = 1;
}
```

```
[A4-5] 글자 쌍 세기 결과
  글자 수        = 609022912
  쌍의 개수      = 609022911
  서로 다른 쌍   = 1227989
  표의 칸 수     = 2097152 (2^21)
  적재율         = 0.586
  평균 탐사 횟수 = 1.017
  메모리         = 34 MB
  걸린 시간      = 5.43 초
  2차원 배열이라면 필요했을 칸의 0.1605% 만 씀
```

**34MB.** 2차원 배열이었다면 5.7GB였다. 168분의 1이다.

평균 탐사 1.017회는 **여섯 번에 다섯 번은 첫 칸에서 바로 찾았다**는 뜻이다. 이게 해시맵이 `O(1)` 이라고 불리는 실제 모습이다.

### 검증

숫자가 맞는지 증명해야 한다. 세 가지를 건다.

```c
CHECK(PairTotal == Chars - 1);       // 쌍은 글자보다 정확히 하나 적다
CHECK(Sum == PairTotal);             // 모든 값을 더하면 센 횟수
CHECK(Distinct == Pairs.Count);      // Used 를 세면 Count 와 같다
```

첫 번째가 특히 값을 한다. 6억 개의 글자를 이으면 쌍은 **정확히** 6억 하고 하나 적은 개수여야 한다. `609,022,912` 와 `609,022,911`. 경계에서 하나를 더 세거나 덜 세는 실수는 이 검사에 바로 걸린다.

두 번째는 표 전체를 다시 훑어 값을 더한다. 리해싱을 17번 하는 동안 **값이 하나라도 새거나 겹쳤으면** 합이 어긋난다.

### 무엇이 흔한가

```
  가장 흔한 쌍 열 개
    1. 의 -> 공백         7519110 번
    2. 다 -> .            6405397 번
    3. 줄바꿈 -> 공백     6210850 번
    4. , -> 공백          5826849 번
    5. 는 -> 공백         5756150 번
    6. 줄바꿈 -> 줄바꿈   4620278 번
    7. . -> 공백          4324908 번
    8. 을 -> 공백         4087949 번
    9. 에 -> 공백         3795129 번
   10. 공백 -> 1          3699201 번
```

열 개 중 여섯 개가 **공백으로 끝난다.** 그리고 그 앞에 오는 것은 `의` `는` `을` `에` — 전부 조사다. 2위 `다 -> .` 는 종결어미와 마침표다.

A2에서 "공백이 전체의 20%"라는 걸 봤을 때는 그냥 통계였다. 이제 그 공백이 **어디에 붙어 있는지**가 보인다. 한국어는 조사와 어미가 어절 끝에 붙고, 그 뒤에 띄어쓰기가 온다. 우리 표가 그 규칙을 **배운 적 없이 세기만 해서** 잡아냈다.

A5에서 이 표를 확률로 바꾸면, 모델은 `의` 다음에 공백을 찍을 줄 알게 된다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Map.h` · `Map.c` | 64비트 키 해시맵. 자라고, 더하고, 안 지운다 |
| `lib/Scan.h` · `Scan.c` | A2의 청크 루프를 꺼낸 것 |
| `common/Pretty.h` · `Pretty.c` | 한글이 섞인 표를 반듯하게 찍기 |

교재 `1.7` 에서 바꾼 것.

- 문자열 키 → 64비트 정수 키 (`strcmp` 와 키 복사가 사라짐)
- 고정 7칸 → 적재율 0.7에서 두 배로 자람
- 소수 `%` → 2의 거듭제곱 `&` (**섞은 뒤에는** 소수가 필요 없다)
- 덮어쓰기 → 더하기
- 삭제 제거 → `DELETED` 상태도 제거

알아둘 것.

- **해시 함수의 일은 규칙성을 지우는 것이다.** 안 지우면 15,000배 느려진다
- **분할 상환.** 리해싱은 비싸 보이지만 항목당 평균 두 번 옮기는 값이다
- **`/GL` `/LTCG`.** 파일 경계를 넘는 인라인. 재사용의 대가를 되돌려준다
- **희소성.** 실제로 나타나는 쌍은 가능한 조합의 0.16%다

쓴 문법.

- 비트 시프트와 마스크로 두 값을 하나에 담기 — C 교재 `2.4`
- `malloc` / `calloc` / `free` 와 소유권 — C 교재 `8.1` `8.2`
- 구조체를 통째로 대입해 표를 갈아끼우기 (`*Map = Bigger;`)

## 연습문제

**1.** `MAP_MAX_LOAD` 를 바꿔보자. 메모리와 속도가 어떻게 움직이는가?

<details>
<summary>해답</summary>

| `MAP_MAX_LOAD` | 최종 칸 수 | 메모리 | 평균 탐사 | 세는 시간 |
|---|---|---|---|---|
| 0.5 | 4,194,304 | 68 MB | 1.010 | 6.44초 |
| **0.7** | 2,097,152 | 34 MB | 1.017 | 6.22초 |
| 0.9 | 2,097,152 | 34 MB | 1.039 | 6.13초 |
| 0.95 | 2,097,152 | 34 MB | 1.066 | 6.04초 |
| 0.99 | 2,097,152 | 34 MB | 1.250 | 6.12초 |

(`/GL` 없이 잰 값이다. 켜면 전부 0.8초쯤 줄어든다.)

두 가지가 눈에 띈다.

**최종 칸 수가 0.7 이상에서 모두 같다.** 123만 개를 209만 칸에 담으면 적재율이 0.586이라, 문턱이 0.7이든 0.99든 마지막 리해싱 지점이 똑같기 때문이다. 달라지는 것은 **자라기 전에 얼마나 버티느냐**이고, 그게 평균 탐사(1.017 → 1.250)에 나타난다.

**그런데 시간은 거의 안 변한다.** 0.5는 메모리를 두 배 쓰고도 오히려 제일 느리다(큰 표는 캐시에 안 들어간다). 나머지는 측정 오차 안에 있다.

이유는 간단하다. 6초 중 대부분이 **파일을 읽고 UTF-8을 푸는 데** 쓰인다. 해시맵은 병목이 아니다. 평균 탐사를 1.017에서 1.250으로 23% 악화시켜도 전체 시간은 안 움직인다.

**고치기 전에 재라**는 말이 이런 뜻이다. 적재율 0.7은 교과서적인 기본값이고 여기서도 무난하지만, 이 프로그램에서는 **어떤 값을 골라도 상관없었다.**

</details>

**2.** `lib/Map` 에 삭제 기능을 넣으려면 무엇이 필요한가? `Used[Slot] = 0` 으로 두면 왜 안 되는가?

<details>
<summary>해답</summary>

**탐색이 끊어진다.** 자료구조 교재 `1.7` 이 주석으로 남긴 바로 그 문제다.

키 A, B, C가 모두 5번 칸에서 출발했다고 하자. 선형 탐사로 5, 6, 7번에 자리를 잡는다. 여기서 B(6번)를 지우고 `Used[6] = 0` 으로 두면, C를 찾을 때 5번을 보고 6번을 보는데 **빈 칸이므로 "없다"고 판단하고 멈춘다.** 7번에 멀쩡히 있는데도 못 찾는다.

해결책은 **묘비**(tombstone)다. 상태를 셋으로 늘린다.

```c
enum { SLOT_EMPTY, SLOT_USED, SLOT_DELETED };
```

- 찾을 때: `DELETED` 를 만나면 **계속 간다** (여기 있었을 수도 있으니)
- 넣을 때: `DELETED` 를 만나면 **거기 넣어도 된다** (단, 뒤에 같은 키가 있는지 끝까지 확인한 뒤에)

여기서 새 문제가 생긴다. **묘비는 쌓인다.** 넣고 지우기를 반복하면 표가 묘비로 가득 차서, 실제 항목은 몇 개 없는데 탐사가 끝없이 길어진다. 그래서 실무 구현은 "묘비 비율이 일정 수준을 넘으면 리해싱"이라는 규칙을 하나 더 둔다.

기능 하나를 넣었더니 상태 하나, 분기 두 개, 리해싱 조건 하나가 따라왔다. **우리가 삭제를 안 만든 것은 게을러서가 아니라, 필요 없는 기능의 복잡도를 거절한 것이다.**

B파트에서 `std::unordered_map` 을 쓰면 이 전부가 이미 들어 있다. 직접 만들어봤기 때문에 그 안에 무엇이 들었는지 알게 된다.

</details>

**3.** 가장 흔한 쌍 열 개에서 무엇을 읽어낼 수 있는가? A5의 모델이 어떤 글을 쓸지 예상해보자.

<details>
<summary>해답</summary>

**열 개 중 여섯 개가 공백으로 끝나고, 그중 넷은 조사 뒤의 공백이다.**

| 쌍 | 정체 |
|---|---|
| `의 → 공백` `는 → 공백` `을 → 공백` `에 → 공백` | 조사 + 띄어쓰기 |
| `다 → .` | 종결어미 + 마침표 |
| `. → 공백` `, → 공백` | 구두점 + 띄어쓰기 |
| `줄바꿈 → 줄바꿈` | 문단 사이 빈 줄 |
| `공백 → 1` | 띄어쓰기 뒤 숫자 (연도·날짜) |

A5의 바이그램 모델은 앞 글자 하나만 본다. 그래서 이런 일이 벌어질 것이다.

- **띄어쓰기를 꽤 잘 맞춘다.** `의` `는` `을` 을 쓰고 나면 공백을 찍을 확률이 높다
- **어절 하나 정도는 그럴듯해진다.** `하` 다음에 `는`, `다` 다음에 `.` 같은 이음새를 배운다
- **문장은 여전히 말이 안 된다.** 두 글자 앞을 못 보므로 주어와 서술어가 이어지지 않는다

A3의 출력과 비교하면 차이가 극적이겠지만, 한국어라고 부를 수는 없는 물건이 나온다. **얼마나 뒤를 봐야 말이 되는가**가 A6의 질문이고, 결국 D파트에서 트랜스포머가 답한다.

</details>

## 다음 장

**A5. 바이그램과 특수 토큰.**

표는 만들었다. 이제 확률로 바꾼다. `의` 다음에 올 글자의 분포를 꺼내고, A3의 샘플러로 하나 뽑고, 그걸 다시 앞 글자로 삼아 반복한다. **첫 문장이 나오는 장이다.**

새 문제가 둘 생긴다.

**시작을 어떻게 하는가.** 앞 글자가 없는 상태에서 첫 글자를 뽑아야 한다. 그리고 **끝을 어떻게 아는가.** 모델은 영원히 글자를 뱉을 수 있다. 문장의 시작과 끝을 나타내는 **특수 토큰**을 글자 집합에 새로 끼워 넣어야 하고, 그 순간 "글자"와 "토큰"이 갈라진다. A8의 BPE로 가는 첫걸음이다.

검증도 한 단계 올라간다. A5부터는 파이썬으로 같은 계산을 하는 참조 구현을 두고 **확률표를 자릿수까지 맞춰본다.**
