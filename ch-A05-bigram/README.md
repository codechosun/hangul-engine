## 0. 첫 문장

A3의 출력은 이랬다.

```
의전서배 생선  1범의있민무생그 로 ,두-르 림일 표은실N남군관국 ,장의
```

이 장이 끝나면 이렇게 된다.

```
출신 이주인간)와의 m21320년대모(郭陽驛)이 해 동자수 죽음과의해도쿄코드- 19년에시칸센터

```

여전히 말이 안 된다. 하지만 **읽을 수 있는 조각이 생겼다.** `출신`, `죽음과`, `선명으로 냈다.` — 어절이 만들어지고, 조사가 붙고, 마침표로 끝난다. 바뀐 것은 딱 하나다. **앞 글자 하나를 본다.**

이 장에서 할 일.

1. 문장의 시작과 끝을 나타내는 **특수 토큰**을 만든다
2. 앞 글자별 다음 글자 분포를 **꺼낼 수 있는 모양**으로 담는다
3. 파이썬 참조 구현과 **숫자를 한 줄씩 맞춘다**

## 1. 시작과 끝을 어떻게 아는가

A4의 표에는 `(앞 글자, 뒤 글자)` 쌍의 횟수가 들어 있다. 이걸로 글을 쓰려면 두 가지가 없다.

**첫 글자를 무엇으로 뽑는가.** 앞 글자가 있어야 표를 찾는데, 첫 글자에는 앞이 없다. 글자 전체 빈도에서 뽑으면 될 것 같지만 — 그게 맞는지는 3절에서 재본다.

**언제 멈추는가.** 계속 뽑으면 영원히 뽑을 수 있다. 어디서 문장이 끝나는지 모델이 알아야 한다.

답은 **없는 글자를 만들어 넣는 것**이다.

```c
#define TOKEN_BOS   (CODEPOINT_LIMIT)        // 0x110000
#define TOKEN_EOS   (CODEPOINT_LIMIT + 1u)   // 0x110001
#define VOCAB_LIMIT (CODEPOINT_LIMIT + 2u)   // 0x110002
```

유니코드 코드포인트는 `0x10FFFF` 까지다. 그 **위는 영원히 빈다.** 유니코드 표준이 상한을 그렇게 못박아 두었기 때문에, `0x110000` 은 앞으로 어떤 글자도 차지하지 않는다.

이건 흔한 기법이다. **값의 범위 밖에 표지를 놓는다.** C 교재에서 `EOF` 가 `-1` 인 것과 같은 발상이다 — `getchar()` 가 0~255를 돌려주니 `-1` 은 "글자가 아니다"라는 뜻으로 쓸 수 있다.

> **왜 0을 안 쓰는가.** `U+0000` 은 진짜 코드포인트다. 코퍼스에 없더라도 "없다"는 보장이 아니라 "아직 못 봤다"일 뿐이다. 범위 밖은 보장이다.

여기서 **글자와 토큰이 갈라진다.** 지금까지 우리가 센 것은 전부 글자였다. BOS와 EOS는 글자가 아니면서 모델이 다루는 단위다. A8에서 BPE를 하면 `"습니다"` 같은 덩어리가 토큰 하나가 되면서, 토큰은 글자와 완전히 다른 것이 된다. 그 분리가 여기서 시작된다.

### 문장을 어떻게 나누는가

코퍼스는 위키백과 문서를 줄바꿈으로 이어 붙인 것이다. **줄 하나를 문장 하나로 본다.**

```
"한국어\n"  ->  [BOS] 한 국 어 [EOS]
```

줄바꿈 자체는 세지 않는다. **EOS와 BOS로 갈아 끼운다.**

```c
while (ScanNext(&Scanner, &Code))
{
    if (Code == '\n')
    {
        MapAdd(&Counts, PackPair(Prev, TOKEN_EOS), 1);
        Prev = TOKEN_BOS;
    }
    else
    {
        MapAdd(&Counts, PackPair(Prev, Code), 1);
        Prev = Code;
    }
}
```

이 규칙에서 **쌍의 개수는 글자 수와 정확히 같아진다.** 줄바꿈 하나가 빠지고 EOS 하나가 들어오기 때문이다. 검증할 것이 하나 공짜로 생겼다.

```c
CHECK(Chars == Model.Total);   // 609,022,912 == 609,022,912
```

## 2. 해시맵으로는 글을 못 쓴다

A4의 `lib/Map` 은 `"이 쌍이 몇 번 나왔나"` 에 답한다. 그런데 글을 쓰려면 다른 질문이 필요하다.

> **`의` 다음에 올 수 있는 글자를 전부 달라.**

해시맵은 이걸 못 한다. 키가 흩어져 있어서 `의` 로 시작하는 것만 모아 볼 방법이 없다. 표 전체를 훑으면 한 글자 뽑는 데 200만 칸을 보게 된다.

후보가 **한 자리에 모여 있어야** 한다. 그리고 A3에서 배운 대로, 확률에 비례해 뽑으려면 **누적합**이 필요하다.

### 압축 행 저장 (CSR)

```c
typedef struct
{
    uint32_t* Next;         // 모든 쌍의 '뒤 글자'. 앞 글자별로 모여 있다
    uint64_t* Cumulative;   // 같은 자리의 누적 빈도. 구간마다 0 에서 다시 쌓는다
    uint32_t* Start;        // Start[Prev] ~ Start[Prev+1] 이 그 앞 글자의 구간
    ...
} FBigram;
```

그림으로 보면 이렇다.

```
Prev:      ...    '의'                    '이'          ...
                   |                        |
Start:  [ ... , 812340 ,              813243 , ... ]
                   |                        |
Next:   [ ... , 공백, 가, 견, 결, ... , 갈, 감, ... ]
Cumul:  [ ... , 7519110, 7519152, ... 8558982 | 42, 77, ... ]
                                      ^구간의 끝 = '의' 가 나온 총 횟수
```

`Start` 는 길이 `0x110002 + 1` 짜리 배열이다. 4.5MB를 고정으로 쓰지만, 그 대가로 **앞 글자에서 구간까지 `O(1)`** 이다. A2에서 코드포인트를 그대로 인덱스로 쓴 것과 같은 거래다.

구간 끝의 누적값이 곧 그 앞 글자의 총 횟수이므로, **따로 저장할 필요가 없다.**

```c
uint64_t BigramContextTotal(const FBigram* Model, uint32_t Prev)
{
    uint32_t To = Model->Start[Prev + 1];
    ...
    return Model->Cumulative[To - 1];
}
```

### 해시맵에서 CSR로 옮기기

세 단계다.

**1단계.** `lib/Map` 으로 쌍을 센다. (A4가 한 일 그대로)

**2단계.** 표를 배열로 쏟아내고 `(앞, 뒤)` 순으로 정렬한다.

```c
static int ComparePairRow(const void* A, const void* B)
{
    if (Left->Prev < Right->Prev) return -1;
    if (Left->Prev > Right->Prev) return 1;
    if (Left->Next < Right->Next) return -1;
    if (Left->Next > Right->Next) return 1;
    return 0;
}
```

A2의 `FreqCompare` 와 같은 이야기다. **2순위가 없으면** 해시맵을 훑은 순서가 그대로 남는다. 표의 칸 수가 조금만 달라져도 결과가 달라지고, 그러면 파이썬과 대조할 수가 없다.

**3단계.** 앞 글자별 개수를 세어 누적하면 `Start` 가 나온다.

```c
for (uint64_t i = 0; i < RowCount; i++)
{
    Start[Rows[i].Prev + 1]++;     // 한 칸 밀어서 센다
}

for (uint32_t i = 0; i < VOCAB_LIMIT; i++)
{
    Start[i + 1] += Start[i];      // 누적
}
```

**한 칸 밀어서 세고 누적하는 것**이 요령이다. 이러면 한 번도 안 나온 앞 글자는 `Start[p] == Start[p+1]` 이 되어 자동으로 "빈 구간"이 된다. 예외 처리가 필요 없다.

### 뽑기

A3의 `SamplerPick` 과 같다. 다르다면 **배열 전체가 아니라 구간 안에서만** 찾는다는 것뿐이다.

```c
uint64_t Target = RandomBelow(Rng, Model->Cumulative[To - 1]);

uint32_t Low = From;
uint32_t High = To - 1;

while (Low < High)
{
    uint32_t Mid = Low + (High - Low) / 2;
    if (Model->Cumulative[Mid] > Target) High = Mid;
    else                                 Low = Mid + 1;
}

return Model->Next[Low];
```

완성된 모델은 이렇다.

```
[A5-1] 만들어진 모델
  문장 수        = 19477661
  쌍의 개수      = 609022912
  서로 다른 쌍   = 1227989
  메모리         = 18 MB
  걸린 시간      = 5.27 초
```

**18MB.** 1,900만 문장, 6억 개의 글자에서 뽑아낸 모델이 18MB다.

## 3. 파이썬과 숫자를 맞춘다

여기서부터 검증이 한 단계 올라간다. A2에서는 글자 빈도 27,663줄을 대조했다. 이번엔 **조건부 분포**를 대조한다.

문제가 하나 있다. 서로 다른 쌍이 123만 개라 전부 적으면 파일이 수십 MB가 된다. 그래서 **앞 글자 여섯 개만 고르되, 그 여섯 개에 대해서는 빠짐없이 전부** 적는다.

|---|---|---|
| BOS | 4,685종 | 19,477,661 |
| 공백 | 12,353종 | 123,320,760 |
| `.` | 1,598종 | 8,223,019 |
| `의` | 903종 | 8,558,982 |
| `다` | 1,226종 | 8,584,827 |

`data/bigram_expected.csv` 는 21,720줄, 283KB다. 일부만 맞는 구현은 통과할 수 없다.

> **공백의 총 횟수 123,320,760** 은 A2에서 잰 공백의 **글자 빈도와 정확히 같다.** 모든 공백은 무언가의 앞에 있기 때문이다(줄 끝의 공백이면 EOS 앞). 서로 다른 방법으로 센 두 숫자가 맞아떨어지는 것은 좋은 신호다.

### 파이썬 쪽은 다르게 센다

같은 알고리듬을 옮겨 적으면 검증이 아니다. 같은 버그를 두 번 쓰게 된다. 파이썬 쪽은 **정규식**으로 센다.

```python
Pattern = re.compile("(?<=" + re.escape(Context) + ")(.)", re.S)
Tally[Key].update(Pattern.findall(Text))
```

뒤돌아보기(lookbehind)는 폭이 0이라 다음 글자를 소비하지 않는다. `"의의의"` 에서도 두 쌍을 다 잡는다. 청크 경계는 앞 청크의 마지막 글자를 이어 붙여 해결한다 — A2에서 C로 했던 일과 똑같은 문제를 다른 언어로 푸는 셈이다.

44초면 끝난다. 그리고 이 파일은 저장소에 커밋되므로 **독자는 파이썬 없이도 검증할 수 있다.**

### 결과

```
[A5-2] 파이썬 참조 구현과 대조
  문장 수     파이썬     19477661   C     19477661
  쌍의 개수   파이썬    609022912   C    609022912
  쌍 정답표 21720줄 대조 → 어긋난 줄 0개
```

**21,720줄이 전부 일치했다.** 특수 토큰 처리, 줄 경계, 빈 줄, 청크 경계 — 어긋날 자리가 많았는데 하나도 어긋나지 않았다.

여기에 세 가지를 더 건다.

```c
CHECK(Chars == Model.Total);                          // 쌍 개수 == 글자 수
CHECK(BigramCount(&Model, TOKEN_EOS, TOKEN_BOS) == 0); // 없는 쌍은 0
CHECK(Sum == BigramContextTotal(&Model, Contexts[k])); // 구간 합계
```

마지막 것이 CSR 구조를 직접 겨눈다. 정답표에서 `앞 == 공백` 인 줄의 값을 전부 더한 것과, 모델의 `Cumulative[To-1]` 이 같아야 한다. **누적합을 잘못 쌓았으면 여기서 걸린다.**

## 4. 직관이 또 한 번 배신한다

문장의 첫 글자를 무엇으로 뽑아야 할까. "글자 전체 빈도에서 뽑으면 되지 않나" 싶다. 재보자.

```
[A5-3] 문장의 첫 글자는 아무 글자가 아니다

  'BOS' 다음 (후보 4685종, 총 19477661번)
     1. 공백       6210850   31.89%
     2. EOS        4620278   23.72%
     3. 1           579364    2.97%
     4. 2           503631    2.59%
     5. 외          277281    1.42%

  글자 전체 빈도 상위 5종
     1. 공백     123320760   20.25%
     2. EOS       19477661    3.20%
     3. 이        10764068    1.77%
     4. 다         8584827    1.41%
     5. 의         8558982    1.41%
```

이 장을 쓰면서 나는 **"공백은 문장 첫 글자로는 드물 것"** 이라고 예상하고 그렇게 검사를 걸었다. **틀렸다.** 공백은 첫 글자로 31.89%다 — 전체 빈도 20.25%보다 **오히려 높다.**

데이터를 보면 이유가 나온다.

- **EOS가 2위, 23.72%.** 네 줄 중 하나가 **빈 줄**이다. 위키백과 문서에서 문단 사이의 빈 줄이다
- **공백이 1위.** 위키백과 본문에는 들여쓴 줄이 많다. 목록, 인용, 표 조각
- **`1` 과 `2` 가 3·4위.** 연도로 시작하는 줄이 그만큼 많다
- **`외` 가 5위.** `외부 링크` 라는 절 제목이다

"문장"이라고 불렀지만 우리가 나눈 것은 **줄**이다. 위키백과의 줄에는 본문만 있는 게 아니다. 데이터가 그렇게 생겼다.

### 얼마나 다른가를 숫자로

두 분포가 다르다는 것을 눈으로만 말하면 검사를 걸 수가 없다. **총변동거리**(total variation distance)로 재면 숫자 하나가 된다.

```
TVD = 0.5 × Σ |p_i - q_i|
```

0이면 완전히 같고, 1이면 겹치는 데가 하나도 없다.

```
  두 분포의 총변동거리 = 0.458
```

```c
CHECK(Distance > 0.2);
```

**0.458.** 절반 가까이 다르다. BOS를 따로 둔 것이 헛일이 아니었다는 뜻이고, 동시에 **검사를 특정 값이 아니라 성질에 거는 방법**이기도 하다. 내 예상(`공백 < 5%`)은 코퍼스가 조금만 달라도 깨지는 검사였지만, "두 분포가 다르다"는 어느 코퍼스에서나 성립한다.

> 분포 사이의 거리를 재는 건 여기서 끝이 아니다. B파트에서 **퍼플렉서티**를 만들고, C파트에서 **교차 엔트로피**를 손실 함수로 쓴다. 전부 "두 분포가 얼마나 다른가"를 재는 서로 다른 자다.

## 5. 앞 글자가 정해지면

이게 이 장의 핵심이다.

```
  '의' 다음 (후보 903종, 총 8558982번)
     1. 공백       7519110   87.85%
     2. 해          122583    1.43%
     3. 원           96841    1.13%

  '다' 다음 (후보 1226종, 총 8584827번)
     1. .          6405397   74.61%
     2. 공백        285255    3.32%
     3. 고          206418    2.40%

  '한' 다음 (후보 955종, 총 4102041번)
     1. 공백       2219215   54.10%
     2. 다          678716   16.55%
     3. 민          480226   11.71%
     4. 국          237090    5.78%
```

**`의` 다음은 87.85%가 공백이다.** 아무 정보도 없을 때 공백일 확률은 20.25%였다. 앞 글자 하나를 아는 것만으로 **네 배**가 됐다.

`다` 다음은 74.61%가 마침표다. 한국어의 종결어미다.

`한` 이 재미있다. 공백(54%)·`다`(16%)·`민`(11%)·`국`(5%) — `한 `, `한다`, `한민(국)`, `한국`. 조사·어미·고유명사가 한 줄에 섞여 있다. 모델은 문법을 배운 적이 없고 **그냥 셌을 뿐이다.**

이게 언어 모델이다. 조건을 하나 붙일 때마다 분포가 뾰족해진다. D파트의 트랜스포머가 하는 일도 결국 같다 — **앞의 것을 더 많이, 더 멀리 보고 분포를 더 뾰족하게 만드는 것.**

## 6. 글을 쓰게 하기

```c
int BigramGenerate(const FBigram* Model, FRandom* Rng,
                   uint32_t* Out, int MaxLength)
{
    uint32_t Prev = TOKEN_BOS;
    int Length = 0;

    while (Length < MaxLength)
    {
        uint32_t Code = BigramPick(Model, Prev, Rng);

        if (Code == TOKEN_EOS)
        {
            break;
        }

        Out[Length++] = Code;
        Prev = Code;
    }

    return Length;
}
```

BOS에서 시작해서 EOS가 나올 때까지 뽑는다. **모델이 스스로 멈춘다.**

`MaxLength` 는 안전장치다. EOS를 안 뽑고 계속 갈 수 있으므로 200자에서 끊는다. 실제로 몇 번은 여기에 걸린다.

```
   1. AFiviss:lioour(중종회를 기타이토리고 시 초 민도면의 다가대학교육재판하였으로
   3.  2회

   7. 출신 이주인간)와의 m21320년대모(郭陽驛)이 해 동자수 죽음과의해도쿄코드- 19년에시칸센터 선명으로 냈다.
   8.  기에서를 사학원점함께 남리, 시 되어
  10.  すく(GCO승

  평균 길이 46.8 글자
```

무엇이 생겼는가.

- **어절이 생겼다.** `출신`, `자치`, `대학교육`, `죽음과`
- **띄어쓰기가 그럴듯하다.** 조사 뒤에서 잘 띈다
- **문장이 스스로 끝난다.** `냈다.` 뒤에서 EOS를 뽑았다
- **길이가 그럴듯하다.** 평균 46.8자

무엇이 없는가.

- **두 글자 앞을 못 본다.** `AFiviss:lioour` — `A` 다음에 `F` 가 올 수 있고, `F` 다음에 `i` 가 올 수 있다. 각 이음새는 전부 합법인데 전체는 아무 뜻이 없다
- **주어와 서술어가 이어지지 않는다.** 문장 전체를 관통하는 것이 아무것도 없다

같은 씨앗으로 A3 방식과 나란히 놓으면 차이가 분명하다.

```

   1. 의전서배 생선  1범의있민무생그 로 ,두-르 림일 표은실N남군관국 ,장의
```

**앞 글자 하나가 이만큼을 했다.** 그리고 이게 거의 전부다 — 앞 글자를 둘로 늘리면 얼마나 더 나아질까? 그게 A6의 질문이다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Bigram.h` · `Bigram.c` | 바이그램 모델. CSR 저장, 조건부 샘플링, 문장 생성 |
| `tools/make_bigram_expected.py` | 정규식으로 세는 파이썬 참조 구현 |
| `common/Golden` | 세 칸짜리 정답표 읽기 추가 |
| `data/bigram_expected.csv` | 21,720줄. 앞 글자 6종에 대한 전수 |
| `data/bigram_summary.csv` | 글자 수·문장 수·쌍 개수 |

알아둘 것.

- **범위 밖에 표지를 놓는다.** 유니코드는 `0x10FFFF` 가 상한이므로 그 위는 영원히 안전하다
- **해시맵은 "전부 달라"에 답하지 못한다.** 뽑으려면 후보가 한 자리에 모여야 한다 (CSR)
- **한 칸 밀어서 세고 누적하면** 빈 구간이 저절로 처리된다
- **참조 구현은 다른 방법으로 짜야** 검증이 된다. 옮겨 적으면 같은 버그를 두 번 쓴다
- **검사는 값이 아니라 성질에 건다.** `공백 < 5%` 는 틀렸고 `TVD > 0.2` 는 맞다
- **조건을 붙이면 분포가 뾰족해진다.** 20.25% → 87.85%

쓴 문법.

- 구조체로 자료구조 묶기 — C 교재 `9.1`
- `qsort` 와 다중 키 비교 함수 — 자료구조 교재 `2.2`
- 구간 안에서의 lower bound 이진 탐색 — 자료구조 교재 `2.4`
- 누적 배열(prefix sum)로 구간 경계 만들기

## 연습문제

**1.** 빈 줄이 전체 문장의 23.72%다. 빈 줄을 빼고 모델을 만들면 무엇이 달라질까? 예상한 뒤 고쳐보자.

<details>
<summary>해답</summary>

`BigramBuild` 에서 `Prev == TOKEN_BOS` 인 채로 줄바꿈을 만나면 (= 빈 줄이면) 아무것도 세지 않고 넘기면 된다.

```c
if (Code == '\n')
{
    if (Prev != TOKEN_BOS)          // 빈 줄은 건너뛴다
    {
        MapAdd(&Counts, PackPair(Prev, TOKEN_EOS), 1);
        Total++;
        Lines++;
    }
    Prev = TOKEN_BOS;
}
```

바뀌는 것.

- 문장 수가 1,948만에서 **1,486만**으로 준다
- `BOS → EOS` 쌍이 사라지므로, 모델이 **빈 문장을 만들지 않는다**
- BOS 다음 분포에서 EOS(23.72%)가 빠지고 나머지가 그만큼 올라간다
- 그런데 **공백이 여전히 1위**다. 들여쓴 줄은 빈 줄과 다른 이야기이기 때문이다

여기서 판단할 거리가 생긴다. **빈 줄을 빼는 게 맞는가?**

모델의 목적이 "문장 쓰기"라면 빼는 게 낫다. 빈 문장은 쓸모가 없다. 하지만 목적이 "이 코퍼스를 그대로 흉내내기"라면 빼면 안 된다 — 위키백과 텍스트에는 실제로 빈 줄이 그만큼 있다.

이 교재는 **빼지 않는다.** A2에서 공백을 안 뺀 것과 같은 이유다. 데이터를 손대기 시작하면 어디까지 손댈지 기준이 없어지고, 무엇보다 **정답표와 어긋난다.** 전처리는 선택이 아니라 기록해야 할 결정이다.

</details>

**2.** `ComparePairRow` 의 2순위 비교(`Next` 비교)를 지우면 무엇이 깨지는가?

<details>
<summary>해답</summary>

**정답표 대조가 깨진다.** 그런데 깨지는 방식이 고약하다.

`BigramCount` 는 구간 안에서 **이진 탐색**을 한다. 이진 탐색은 정렬되어 있다는 가정 위에서만 동작한다. 2순위가 없으면 같은 앞 글자 안에서 뒤 글자의 순서가 `qsort` 구현과 해시맵을 훑은 순서에 따라 제멋대로가 된다.

결과는 **어떤 쌍은 찾고 어떤 쌍은 못 찾는다.** 21,720줄 중 일부만 어긋나므로, 적은 데이터로 테스트하면 우연히 통과할 수도 있다. A2 연습문제 2의 뺄셈 비교와 같은 종류의 버그다 — **작은 입력에서는 숨고 큰 입력에서 나온다.**

`BigramPick` 은 더 은밀하다. 누적합은 순서와 무관하게 총합이 같으므로 **뽑기는 여전히 정확히 동작한다.** 확률 분포가 맞다. 다만 같은 씨앗에서 다른 문장이 나온다. 즉 **"틀리지는 않았는데 재현이 안 되는"** 상태가 된다.

A0에서 "훈련 코드는 조용히 틀린다"고 한 것이 이런 모습이다. 정렬 순서 하나로 (1) 조회가 깨지고 (2) 샘플링은 멀쩡하고 (3) 재현성만 사라진다. 세 증상이 따로 논다.

</details>

**3.** `의` 다음에 공백이 올 확률은 87.85%다. 그럼 `의` 다음 글자를 예측하는 문제는 얼마나 쉬운가? 숫자로 말해보자.

<details>
<summary>해답</summary>

"가장 흔한 것을 찍는다"는 전략으로 **87.85%를 맞힌다.** 후보가 903종인데도 그렇다.

비교해보자.

| 조건 | 1위의 비율 | 후보 수 |
|---|---|---|
| 아무것도 모를 때 | 20.25% (공백) | 27,663 |
| `의` 다음 | 87.85% (공백) | 903 |
| `다` 다음 | 74.61% (`.`) | 1,226 |
| `한` 다음 | 54.10% (공백) | 955 |
| BOS 다음 | 31.89% (공백) | 4,685 |

앞 글자 하나가 정답률을 20%에서 **50~88%** 로 올린다.

그런데 이 숫자는 **속임수**이기도 하다. 맞히기 쉬운 이유가 "한국어를 이해해서"가 아니라 **"공백이 워낙 흔해서"** 다. `의` `한` 뒤에서 공백을 찍는 것은 띄어쓰기 규칙을 아는 것이지 의미를 아는 것이 아니다.

그래서 **"몇 %를 맞혔나"는 언어 모델의 자를 만들 때 쓰지 않는다.** 대신 "정답에 얼마나 높은 확률을 줬나"를 본다. 공백에 87%를 주고 실제로 공백이 나오면 좋은 점수, 다른 글자가 나오면 나쁜 점수다. 그걸 전체 문장에 걸쳐 평균낸 것이 **퍼플렉서티**이고, B2에서 만든다.

지금 이 모델의 퍼플렉서티가 얼마인지는 B2에서 잰다. 그 숫자가 A6·A7·A8을 거치며 어떻게 내려가는지가 A파트 후반의 이야기다.

</details>

## 다음 장

**A6. N 일반화.**

앞 글자 하나로 이만큼 왔다. 둘이면? 셋이면?

`lib/Bigram` 은 `(앞, 뒤)` 두 글자에 못박혀 있다. 키를 만드는 `PackPair` 도, CSR의 `Start` 배열도 전부 "앞 글자 하나"를 전제한다. 이걸 **N개**로 일반화한다.

문제가 셋 생긴다.

**키가 64비트에 안 들어간다.** 글자 하나가 21비트이므로 세 개면 63비트로 아슬아슬하고, 네 개면 넘친다. **가변 길이 키**를 해시맵에 넣어야 하고, 그러면 키를 누가 소유하는지(`malloc` 한 메모리를 언제 `free` 하는지)가 문제가 된다.

**`Start` 배열을 못 쓴다.** 앞 글자가 하나일 때는 4.5MB 배열로 `O(1)` 조회가 됐지만, 앞 글자가 셋이면 그 세제곱이다.

**표가 폭발한다.** N을 올릴수록 서로 다른 조합이 급격히 늘고, 대부분은 **한 번씩만** 나타난다. 그 지점에서 모델은 "외우기" 시작한다. A7에서 그 한계를 직접 본다.
