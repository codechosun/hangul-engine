## 0. 하나 더 보면 얼마나 나아지는가

앞 글자 **하나**를 보게 했더니 어절이 생겼다. 둘이면? 다섯이면?

같은 데이터, 같은 씨앗으로 N만 바꿔 문장을 쓰게 하면 이렇게 된다.

```
N=1   널선년이리사였 지 라 제배  을프방사 알기 서회1종 세에역안란울대0

N=2   그가수 연을 군인 -캐쳐서 적 이언급된 것을 1987년 공화민국의의점에서 하의 함락하는 4일 25.

N=3   그는 직접 기념관이 상하게 자장면 대한민국의 명주도권에 스타인의 소창에 좋지 않을 확실하게
      '사회주의는 경험이 있으며, 폴링은 남극에도 했지만, 백신을 사용하는 역

N=4   그는 기원전 50,000원 정복되었으며, 행렬은 행시와 활쏘기를 하거나 저작권을 가리키며, 움직인다.

N=5   그는 여러 차례 만나 그와 다른 장점이 있다. 이 때부터 소련의 붕괴가 되어 편찬된 동국여지승람》
      및 그의 모든 버전에 이르러서야 "리소르지멘토 움직임은 계산(community)들로 변환

N=6   그는 여성에게도 자유가 없는 것 같은 그의 전역병 약 150 kb 내외이다.
```

N=6은 **읽힌다.** 문법이 맞고, 조사가 맞고, 문장이 끝난다.

그런데 이게 좋은 소식일까. N=6 모델이 만든 저 문장에서 ` 약 150 kb 내외이다.` 라는 **15글자는 코퍼스에 그대로 들어 있다.** 모델은 6글자밖에 못 보는데 15글자를 원문대로 이어 붙였다.

무슨 일이 벌어진 것인지가 이 장의 마지막 이야기다.

## 1. 키가 64비트에 안 들어간다

A4에서 글자 두 개를 64비트 하나에 담았다.

```c
return ((uint64_t)Prev << 32) | (uint64_t)Next;
```

코드포인트는 21비트면 충분하다(`0x10FFFF`). 그러면 몇 개까지 되는가.

```
[A6-1] 글자 N 개를 64비트 키 하나에 담을 수 있는가
  코드포인트 하나 = 21비트 (0x10FFFF 까지)

  N      필요한 비트    64비트에
  1              21     들어간다
  2              42     들어간다
  3              63     들어간다
  4              84       넘친다
  5             105       넘친다
  6             126       넘친다
```

**3개까지다.** 63비트로 아슬아슬하게 들어간다.

여기서 선택지가 셋이다.

| 방법 | 되는가 |
|---|---|
| 어휘를 다시 번호 매기기 (27,663종 → 15비트) | N=4까지 늘어난다. 여전히 한계가 있다 |
| 128비트 정수 | 표준 C에 없다. MSVC는 `__int128` 도 없다 |
| **키를 배열로 다룬다** | 된다. N에 제한이 없다 |

세 번째로 간다. 대신 해시맵이 바뀐다.

## 2. 가변 길이 키 해시맵

키가 값 하나가 아니라 배열이 되면 세 가지가 달라진다.

| | A4 `lib/Map` | A6 `lib/GramMap` |
|---|---|---|
| 키 비교 | `Keys[Slot] == Key` | `memcmp(Stored, Key, ...)` |
| 해시 | `MapHash(Key)` | 토큰을 굴리며 섞기 |
| **키를 어디에 두는가** | 슬롯 안에 | **따로 둬야 한다** |

세 번째가 진짜 문제다. 키가 배열이면 슬롯 안에 못 넣는다. 길이가 바뀌면 슬롯 크기도 바뀌어야 하니까.

### 아레나

키의 실제 내용은 **한 덩어리 배열**에 이어 붙여 담는다. 이런 저장소를 아레나(arena)라고 부른다.

```c
typedef struct
{
    int KeyLength;

    uint32_t* Keys;         // 모든 키의 토큰을 이어 붙인 것
    uint64_t  KeyCount;
    uint64_t  KeyCapacity;

    uint64_t* Index;        // 0 이면 빈 칸, 아니면 (키 번호 + 1)
    uint64_t* Values;
    ...
} FGramMap;
```

해시표는 **키를 담지 않는다.** 아레나의 몇 번째 키인지만 담는다.

```
Index:   [ 0 , 0 , 3 , 0 , 1 , 0 , 2 , ... ]     <- 키 번호 + 1
                 |       |       |
Keys:    [ 한 국 어 | 국 어 를 | 어 를 배 | ... ]
            0번        1번        2번
```

`+1` 을 하는 이유는 `0` 을 "빈 칸"으로 쓰기 때문이다. A4에서는 별도의 `Used` 배열을 뒀는데, 여기서는 `Index` 하나가 두 일을 겸한다.

### 포인터를 저장하면 안 되는 이유

아레나도 자란다. 꽉 차면 `realloc` 으로 두 배로 늘린다.

```c
uint32_t* Keys = (uint32_t*)realloc(Map->Keys, NewCapacity * KeyLength * sizeof(uint32_t));
```

`realloc` 은 **주소를 옮길 수 있다.** 자리가 모자라면 새 자리를 잡고 내용을 복사한 뒤 옛 자리를 반납한다. 그 순간 옛 주소를 가리키던 포인터는 전부 **끊어진 포인터**(dangling pointer)가 된다.

그래서 `Index` 에 **포인터가 아니라 번호**를 담는다.

```c
// realloc 이 성공하면 옛 주소는 무효다.
// 우리는 포인터가 아니라 번호를 저장했으므로 고칠 것이 없다.
Map->Keys = Keys;
```

번호는 주소가 어디로 가든 그대로다. 이건 자료구조 교재 `1.3` Dynamic Array 에서 배열이 자랄 때 겪는 문제와 **똑같은 문제**다. 거기서는 배열 원소를 가리키는 포인터를 들고 있으면 안 된다고 했다. 여기서는 그 규칙을 설계로 못박은 것이다.

헤더에도 적어두었다.

```c
// **주의.** 이 포인터는 다음 GramMapAdd 까지만 유효하다.
// 아레나가 자라면서 realloc 되면 주소가 통째로 바뀐다.
// 오래 들고 있어야 하면 포인터가 아니라 번호를 저장할 것.
const uint32_t* GramMapKeyAt(const FGramMap* Map, uint64_t Index);
```

**소유권이 어디 있는지 문서에 쓰는 것**도 C 프로그래머의 일이다. 컴파일러가 대신 막아주지 않는다. C++의 스마트 포인터(`CPP 10`)와 이동 시맨틱(`CPP 11`)이 바로 이 문제를 언어 차원에서 다루려는 시도이고, B파트에서 다시 만난다.

### 표가 자랄 때는 아레나를 건드리지 않는다

```c
static int GrowTable(FGramMap* Map)
{
    ...
    // 아레나는 건드리지 않는다. 자리표만 다시 만든다.
    for (uint64_t i = 0; i < Map->Capacity; i++)
    {
        if (Map->Index[i] == 0) continue;

        uint64_t KeyIndex = Map->Index[i] - 1;
        const uint32_t* Key = Map->Keys + KeyIndex * Map->KeyLength;
        ...
    }
}
```

키를 다시 복사하지 않는다. **번호만 옮긴다.** 아레나와 해시표의 수명이 분리되어 있어서 가능한 일이다.

### 여러 토큰을 하나의 해시로

```c
uint64_t GramHash(const uint32_t* Key, int Length)
{
    uint64_t Hash = 0xCBF29CE484222325ull;

    for (int i = 0; i < Length; i++)
    {
        Hash ^= (uint64_t)Key[i];
        Hash *= 0x100000001B3ull;
    }

    return MapHash(Hash);
}
```

앞에서부터 굴리며 섞는다. 자료구조 교재 `1.7` 의 65599 해시가 문자열에 하던 일과 **같은 모양**이다.

```c
HashValue = 65599 * HashValue + InKey[i];   // 교재
```

곱하는 상수만 64비트에 맞게 키웠고(FNV-1a의 상수다), 마지막에 A4의 `MapHash` 를 한 번 더 통과시킨다. A4에서 봤듯 **곱셈만으로는 아래 비트가 덜 섞이기** 때문이다.

## 3. 모델도 일반화한다

`lib/Bigram` 은 "앞 글자 하나"에 못박혀 있었다. 두 군데가 문제다.

**`Start` 배열을 못 쓴다.** A5에서는 `Start[Prev]` 로 `O(1)` 에 구간을 찾았다. 문맥이 다섯 글자면 그 배열은 `0x110002^5` 칸이다.

대신 **그램을 사전순으로 정렬한다.** 그러면 같은 문맥을 가진 그램들이 저절로 붙어 있다.

```
[BOS][BOS] 가
[BOS][BOS] 각
...
대 한 민
대 한 민          <- '대한' 문맥의 구간
대 한 반
```

문맥을 찾는 것은 **구간의 이진 탐색**이 된다. `O(1)` 이 `O(log C)` 가 됐지만, 메모리는 `0x110002^(N-1)` 에서 실제 문맥 수로 줄었다.

**qsort에 N을 넘길 수가 없다.**

```c
static int CompareGramRow(const void* A, const void* B)
{
    for (int i = 0; i < GSortOrder; i++)   // <- 이 값을 어떻게 받는가
    ...
}
```

`qsort` 의 비교 함수는 인자가 둘뿐이다. "토큰을 몇 개까지 비교할 것인가"를 넘길 자리가 없다.

표준 C에는 방법이 없다. **파일 범위 변수**를 쓴다.

```c
static int GSortOrder = 0;
...
GSortOrder = Order;
qsort(Rows, RowCount, sizeof(FGramRow), CompareGramRow);
```

보기 좋지 않다. 멀티스레드에서는 위험하기까지 하다. POSIX에 `qsort_r`, MSVC에 `qsort_s` 가 있지만 **인자 순서가 서로 다르다.** 이식성을 포기하거나 전역을 쓰거나다.

C++에서는 이 문제가 아예 없다.

```cpp
std::sort(Rows.begin(), Rows.end(),
          [Order](const auto& A, const auto& B) { ... });   // Order 를 잡아간다
```

람다가 `Order` 를 **캡처**한다. B파트에서 이 코드를 실제로 바꿔 쓴다.

### memcmp 를 쓰면 안 되는 곳

정렬 순서와 탐색 순서가 같아야 이진 탐색이 동작한다. 그런데 `memcmp` 로 비교하면 순서가 달라진다.

```c
// 리틀 엔디언에서 uint32_t 0x100 과 0x2 를 memcmp 로 비교하면
//   0x100 -> 00 01 00 00
//   0x002 -> 02 00 00 00
// 첫 바이트가 00 < 02 이므로 0x100 이 작다고 나온다. 숫자 순서와 반대다.
```

**같은지만 볼 때는 `memcmp` 로 충분하다.** 순서를 볼 때는 직접 세야 한다. `lib/Ngram.c` 에 두 함수를 따로 둔 이유다.

```c
static int SameContext(const uint32_t* A, const uint32_t* B, int Length);   // memcmp
static int CompareTokens(const uint32_t* A, const uint32_t* B, int Length); // 한 칸씩
```

### 창 굴리기의 함정

문장 하나는 이렇게 만든다.

```
N=3, "한국"  ->  [BOS][BOS] 한 국 [EOS]
```

창(window)을 한 칸씩 밀면서 그램을 뽑는다. 자료구조 교재 `2.5` 의 슬라이딩 윈도우 그대로다.

```c
for (int i = 0; i < Order - 1; i++)
{
    Window[i] = Window[i + 1];
}
Window[Order - 1] = Token;
```

문장이 끝나면 창을 BOS로 되돌려야 하는데, 여기서 **한 칸을 틀렸다.**

```c
// 틀린 코드
for (int i = 0; i < Order - 1; i++)   // 0 ~ Order-2 만 채운다
{
    Window[i] = TOKEN_BOS;
}
```

맨 뒤 칸(`Window[Order-1]`)에는 방금 넣은 EOS가 그대로 남는다. 다음 글자가 들어오면서 한 칸 밀면 **그 EOS가 문맥 안으로 딸려 들어온다.** 다음 문장의 첫 그램이 `[BOS][EOS] 그` 가 되는 것이다.

증상이 고약했다.

- 서로 다른 그램의 **개수**는 거의 안 변했다 (N=3에서 698,438 대 698,440)
- `'대한민국'` 문맥 정답표는 **전부 통과했다** (문장 중간은 멀쩡하므로)
- BOS 문맥 정답표만 4,340줄이 어긋났다
- 문장 생성은 **전부 빈 문자열**이 나왔다 ([BOS][BOS] 문맥이 표에 없으므로)

개수가 맞고 중간이 맞으니 "거의 맞는" 것처럼 보였다. **정답표가 없었으면 못 찾았을 버그다.** 고치면 이렇게 된다.

```c
// 창 전체를 BOS 로 채운다
for (int i = 0; i < Order; i++)
{
    Window[i] = TOKEN_BOS;
}
```

## 4. N=1부터 6까지, 같은 데이터로

N을 올리면 표가 폭발하므로 전체 코퍼스는 못 쓴다. **앞 20만 줄**로 고정한다. N마다 같은 데이터를 쓰므로 비교는 공정하다.

```
[A6-2] N=1 부터 6 까지 같은 데이터로 만든다 (앞 200000줄)

  N     서로 다른 그램     한 번만    비율     문맥 수    메모리    시간
  1              5534        1155    20.9%           1       0 MB   0.08s
  2            136127       47819    35.1%        5534       2 MB   0.21s
  3            698438      341163    48.8%      135259      14 MB   0.57s
  4           1941781     1192683    61.4%      687463      50 MB   1.39s
  5           3377252     2487500    73.7%     1911722     105 MB   2.27s
  6           4545006     3688208    81.1%     3329580     164 MB   2.75s

  BOS 문맥 정답표 9874줄, '대한민국' 문맥 정답표 5963줄
  어긋난 줄 = 0 + 0
```

**820만 글자에서 454만 개의 서로 다른 6그램이 나온다.** 글자 수의 절반이 넘는다.

그리고 그중 **81.1%가 딱 한 번씩만** 나왔다.

| N | 한 번만 나온 비율 |
|---|---|
| 1 | 20.9% |
| 2 | 35.1% |
| 3 | 48.8% |
| 4 | 61.4% |
| 5 | 73.7% |
| 6 | **81.1%** |

한 번만 나온 그램은 **확률이 아니다.** `대한민국의 헌법` 이라는 6그램이 코퍼스에 한 번 있었다면, 모델은 `대한민국의 헌` 다음에 `법` 이 올 확률을 100%로 안다. 그게 통계일까, 아니면 그냥 **그 문장을 외운 것**일까.

### 파이썬 쪽은 다르게 센다

C는 창을 굴리며 해시맵에 넣는다. 파이썬은 문자열을 통째로 만들고 슬라이스로 센다.

```python
Sequence = MARK_BOS * (Order - 1) + Line + MARK_EOS
Tally.update(Sequence[i:i + Order] for i in range(len(Sequence) - Order + 1))
```

자리표로 무엇을 쓸지도 한 번 걸렸다. 처음에는 유니코드 사용자 영역(`U+E000`)을 쓰려 했는데, **코퍼스에 실제로 들어 있었다.** A2가 만든 `data/expected.csv` 로 확인하고 `\x00` / `\x01` 로 바꿨다. 있는 데이터를 확인하고 고른 것이지 짐작한 것이 아니다.

```c
CHECK(Model.Total == WantGrams);      // 8,433,046 — N 이 무엇이든 같다
CHECK(Model.GramCount == ...);        // 서로 다른 그램 수
CHECK(Model.OnceCount == ...);        // 한 번만 나온 그램 수
CHECK(Model.ContextCount == ...);     // 문맥 수
```

첫 줄이 좋은 불변식이다. **그램의 개수 = 글자 수 + 문장 수** 이고, N에 무관하다. N-1개의 BOS를 붙이고 EOS를 하나 붙였으니 창이 지나가는 자리가 항상 같기 때문이다.

## 5. 문맥이 길어지면 선택지가 사라진다

`" 대한민국"` 을 꼬리부터 잘라 문맥으로 주면 이렇게 된다.

```
[A6-3] 문맥이 길어지면 다음 글자가 정해진다

  N   문맥             다음 후보     본 횟수
  2   국                    281       64897
  3   민국                   43       23721
  4   한민국                 36       23164
  5   대한민국               36       23161
  6    대한민국              33       22300
```

`국` 다음에 올 수 있는 글자는 **281종**이다. `민국` 으로 늘리면 **43종**으로 떨어진다. `대한민국` 이면 36종.

동시에 **본 횟수도 줄어든다.** 64,897 → 22,300. 문맥이 길어질수록 그 문맥을 본 적이 적어진다. 확률을 믿을 근거가 얇아진다는 뜻이다.

이 두 곡선이 N-그램 모델의 전부다.

```
문맥을 늘린다 ──> 선택지가 좁아진다 (좋다)
              └─> 본 적이 줄어든다 (나쁘다)
```

`민국` 에서 `한민국` 으로 갈 때 43 → 36으로 줄었지만 횟수는 23,721 → 23,164로 거의 안 줄었다. 남는 장사다. 그런데 코퍼스 전체로 보면 **N=6에서 81%의 문맥이 딱 한 번씩만** 나타난다. 그 문맥들에서는 선택지가 1종이고 확률이 100%다.

D파트의 트랜스포머가 푸는 문제가 정확히 이것이다. **문맥을 길게 보면서도 "본 적 없음"에 빠지지 않는 방법.** 세는 대신 배우면 된다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/GramMap.h` · `.c` | 토큰 여러 개를 키로 쓰는 해시맵. 아레나 + 번호 |
| `lib/Ngram.h` · `.c` | N-그램 모델. 사전순 정렬 + 문맥 구간 이진 탐색 |
| `tools/make_ngram_expected.py` | 문자열 슬라이스로 세는 파이썬 참조 구현 |
| `data/ngram_*.csv` | N=1~6 요약 + 두 문맥의 전수 분포 |

알아둘 것.

- **21비트 × 4 = 84비트.** 글자 넷부터는 64비트에 안 들어간다
- **아레나에는 번호로 접근한다.** `realloc` 이 주소를 옮기면 포인터는 끊어진다
- **`memcmp` 는 같은지만 본다.** 리틀 엔디언에서 순서는 뒤집힌다
- **`qsort` 에는 값을 못 넘긴다.** 전역을 쓰거나 이식성을 포기하거나
- **창을 되돌릴 때는 전체를 되돌린다.** 한 칸이 남으면 문맥을 오염시킨다
- **N을 올리면 한 번만 나온 그램이 81%가 된다.** 확률이 아니라 기억이다

쓴 문법.

- `realloc` 과 소유권 — C 교재 `8.1` `8.2`, 자료구조 교재 `1.3`
- 포인터 산술로 2차원 배열 흉내내기 (`Grams + i * Order`) — C 교재 `7.10`
- `qsort` 와 다중 키 비교 — 자료구조 교재 `2.2`
- 슬라이딩 윈도우 — 자료구조 교재 `2.5`

## 연습문제

**1.** `lib/GramMap` 의 `Index` 에 번호 대신 `const uint32_t*` 포인터를 담으면 무슨 일이 생기는가? 언제 터지는가?

<details>
<summary>해답</summary>

**아레나가 자라는 순간 전부 끊어진다.** 그런데 언제 터질지가 고약하다.

`realloc` 은 자리가 남아 있으면 **주소를 안 옮기고 늘려준다.** 그래서 작은 데이터로 테스트하면 통과한다. 어느 크기에서 옮기는지는 할당자와 그때그때의 힙 상태에 달렸다. **같은 프로그램을 두 번 돌려도 다를 수 있다.**

터지는 방식도 두 가지다.

- **운이 나쁘면 죽는다.** 반납된 메모리를 읽다가 접근 위반
- **운이 더 나쁘면 안 죽는다.** 반납된 자리에 다른 데이터가 들어와 있으면, 키 비교가 조용히 틀린 답을 낸다. 같은 그램이 두 번 들어가거나 다른 그램이 합쳐진다

두 번째가 무섭다. A0에서 말한 **"조용히 틀리는"** 버그의 전형이다. 정답표가 있으면 잡히고, 없으면 못 잡는다.

Debug 빌드에서는 MSVC가 반납된 메모리를 `0xDD` 로 채워주므로 **터질 확률이 올라간다.** 그래서 "Debug에서는 되는데 Release에서 안 된다"가 아니라 **"Release에서는 되는데 Debug에서 죽는다"** 가 더 흔하다. 후자가 훨씬 다행이다.

</details>

**2.** `CompareTokens` 를 `memcmp` 로 바꾸면 무엇이 깨지는가? 정답표는 통과할까?

<details>
<summary>해답</summary>

**정렬은 `CompareGramRow` 가 하고 탐색은 `NgramFindContext` 가 한다.** 둘의 순서 기준이 어긋나면 이진 탐색이 엉뚱한 곳을 짚는다.

`memcmp` 로 바꾸면 리틀 엔디언에서 순서가 뒤집힌다. 예를 들어 `가`(U+AC00)와 `힣`(U+D7A3)을 비교하면,

```
U+AC00 -> 00 AC 00 00
U+D7A3 -> A3 D7 00 00
```

첫 바이트가 `00 < A3` 이므로 `memcmp` 는 `가` 가 작다고 답한다. 이 경우는 우연히 맞다. 그런데 `힣`(U+D7A3)과 `一`(U+4E00)을 비교하면,

```
U+D7A3 -> A3 D7 00 00
U+4E00 -> 00 4E 00 00
```

`A3 > 00` 이므로 `memcmp` 는 `힣` 이 크다고 답한다. 숫자로는 `0xD7A3 > 0x4E00` 이니 이것도 맞다. **한글끼리, 한자끼리는 자주 맞는다.**

틀리는 것은 하위 바이트가 상위 바이트를 뒤집는 경우다. `U+0100` 과 `U+0002` 같은 조합에서 어긋난다.

그래서 **정답표를 일부는 통과하고 일부는 실패한다.** 문맥 하나를 못 찾으면 그 문맥의 모든 줄이 0으로 나오므로, 어긋난 줄 수가 0이 아니게 된다. 어느 줄이 어긋나는지는 **어떤 글자를 썼느냐에 달려 있다.**

이런 버그를 잡는 실용적인 방법이 하나 있다. 정렬 직후에 **정말 정렬되어 있는지 한 번 훑는 것**이다.

```c
for (uint64_t i = 1; i < RowCount; i++)
{
    CHECK(CompareGramRow(&Rows[i - 1], &Rows[i]) <= 0);
}
```

`O(N)` 한 번이면 `O(N log N)` 정렬의 전제를 검증한다. 비싸지 않다.

</details>

**3.** N=6에서 한 번만 나온 그램이 81%다. 이 모델이 쓴 문장은 코퍼스에 있는 문장과 얼마나 다를까? 재어보자.

<details>
<summary>해답</summary>

생성된 문장에서 **코퍼스에 그대로 들어 있는 가장 긴 조각**을 찾아보면 이렇다.

| N | 문장 길이 | 최장 일치 | 그 조각 |
|---|---|---|---|
| 3 | 91글자 | 8글자 | `면 대한민국의 ` |
| 4 | 60글자 | 9글자 | ` 정복되었으며, ` |
| 5 | 136글자 | 15글자 | `에 이르러서야 "리소르지멘토` |
| 6 | 42글자 | **15글자** | ` 약 150 kb 내외이다.` |
| 6 | 28글자 | **12글자** | `하는 사용자들이 있다.` |

N=6에서 **15글자가 통째로 원문이다.** 그런데 모델은 6글자밖에 못 본다. 어떻게 15글자를 이어 붙였는가.

**결정적인 문맥이 연쇄하기 때문**이다. 문맥 `약 150 kb 내` 를 코퍼스에서 한 번 봤고 그때 다음 글자가 `외` 였다면, 모델은 그 문맥에서 `외` 를 100% 확률로 뽑는다. 그러면 문맥이 `150 kb 내외` 가 되고, 그것도 한 번짜리면 다음 글자도 정해져 있다. **한 번 이 궤도에 들어서면 원문을 끝까지 따라간다.** 6글자 창으로 10번 연속 미끄러진 것이 15글자다.

전체를 베끼는 것은 아니다. 문장의 35~42%가 한 조각으로 원문에서 온다. 나머지는 여러 문서의 조각을 이어 붙인 것이다. **문장이 잘 읽히는 이유가 모델이 한국어를 알아서가 아니라, 한국어로 쓰인 조각을 외워서** 다.

이게 왜 문제인가.

1. **일반화가 안 된다.** 본 적 없는 문맥이 나오면 아무것도 못 한다. N=6에서 문맥 332만 개 중 대부분이 한 번짜리이므로, 조금만 다른 문맥이 들어와도 길을 잃는다
2. **원문이 새어나온다.** 학습 데이터를 그대로 뱉는 모델은 실제 대형 언어모델에서도 논쟁거리다

A8의 **백오프**가 1번을 다룬다. 긴 문맥에서 못 찾으면 짧은 문맥으로 물러서는 방법이다. 이 표를 그때 다시 재서, 베낀 조각이 얼마나 줄었는지 본다.

근본적인 해결은 C파트부터다. 세는 대신 **가중치를 배우면**, 본 적 없는 문맥도 비슷한 문맥으로부터 추측할 수 있다.

</details>

## 다음 장

**A7. 문장 생성과 대용량 I/O.**

지금까지 코퍼스를 읽을 때마다 `lib/Scan` 으로 처음부터 훑었다. A6에서는 N을 여섯 번 바꾸느라 **같은 파일을 여섯 번 읽었다.** 앞 20만 줄이라 괜찮았지만, 전체 코퍼스에 N=5를 걸면 읽는 데만 30초가 넘고 메모리는 수십 GB가 필요하다.

A7에서는 두 가지를 한다.

**모델을 파일로 저장한다.** 한 번 만든 모델을 디스크에 쓰고 다음에는 읽기만 한다. 바이너리 파일 형식을 직접 설계하면서 `fwrite` / `fread` 와 엔디언·정렬(alignment)을 다룬다.

**대용량 스트림을 제대로 다룬다.** 지금 `lib/Scan` 은 1MB씩 읽는다. 읽기와 처리를 겹치게 하면 얼마나 빨라지는가, 버퍼 크기는 어디가 최적인가 — 재보고 정한다.

그리고 자료구조 교재 `2.5` 의 **슬라이딩 윈도우**가 사실 A6에서 이미 나왔다는 것을 짚는다. 창을 굴리는 그 코드가 투 포인터의 사촌이다.
