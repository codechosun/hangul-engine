## 0. 30초가 문제다

A6에서 N을 여섯 번 바꾸며 모델을 만들었다. 앞 20만 줄이라 한 번에 3초 미만이었다.

전체 코퍼스로 3그램을 세면 **29.5초**다.

한 번이면 참을 만하다. 그런데 이 장 다음부터는 이 모델을 계속 쓴다. A8의 백오프는 N을 여러 개 동시에 쓰고, B파트의 퍼플렉서티는 같은 모델을 반복해서 두드린다. **실험 한 번에 30초씩 붙으면 실험을 안 하게 된다.**

답은 뻔하다. 한 번 세고 **파일로 구워둔다.**

```

  굽기       0.13 초
  읽기       0.05 초   <- 567배 빠르다
```

이 장에서는 그 파일 형식을 직접 설계한다. 그리고 그 김에 지금까지 대충 정해둔 것 하나를 재본다 — **버퍼 크기.**

## 1. 청크 크기는 얼마가 좋은가

A2부터 `lib/Scan` 은 1MB씩 읽어왔다. 왜 1MB인가? 그때는 **아무 근거가 없었다.** 재보자.

먼저 크기를 실행 중에 바꿀 수 있어야 한다.

```c
int ScanOpenSized(FScanner* Scanner, const char* Path, size_t Chunk);
int ScanOpen(FScanner* Scanner, const char* Path);   // SCAN_CHUNK 로 부른다
```

`#define` 을 고치고 다시 빌드하는 대신 **인자로 받는다.** A2의 연습문제에서 `CHUNK_SIZE` 를 `4` 로 바꾸려면 다시 빌드해야 했는데, 이제 한 번 빌드해서 일곱 가지를 잰다.

```
[A7-1] 청크 크기를 바꿔가며 코퍼스 전체를 훑는다

        청크    fread 횟수      시간        초당
       1 KB       1300073      3.01s       422 MB
       4 KB        325019      2.95s       431 MB
      64 KB         20314      2.56s       496 MB
     256 KB          5079      2.55s       498 MB
       1 MB          1270      2.52s       504 MB
       4 MB           318      2.55s       498 MB
      16 MB            80      2.57s       494 MB
```

**차이가 19%밖에 안 난다.** `fread` 를 130만 번 부르나 80번 부르나 3.0초 대 2.6초다.

예상과 다르다면 이유는 하나다. **표준 라이브러리가 이미 버퍼를 두고 있다.** `fread(Buffer, 1, 1024, File)` 를 부르면 운영체제까지 가는 게 아니라, `FILE` 안의 내부 버퍼(보통 4KB)에서 긁어온다. 우리 청크는 **그 위에 한 겹 더 쌓은 버퍼**일 뿐이다.

그래도 무릎(knee)이 보인다. **4KB에서 64KB 사이**에서 좋아지고 그 뒤로는 평평하다. 4KB가 `FILE` 의 내부 버퍼 크기와 비슷하기 때문이다. 그보다 작으면 우리 호출이 내부 버퍼를 여러 번 건드리고, 그보다 크면 내부 버퍼를 건너뛰고 바로 `memcpy` 가 된다.

16MB에서 다시 느려지는 것도 이유가 있다. **L3 캐시를 넘는다.** 읽어온 16MB를 처리할 때쯤이면 앞부분이 이미 캐시에서 밀려나 있다.

**1MB는 우연히 괜찮은 값이었다.** 무릎을 한참 넘겼고 캐시 안에 있다. 근거 없이 고른 값이 맞았다고 해서 재보지 않아도 되는 건 아니다 — 이제는 근거가 생겼다.

> **결과는 안 바뀐다.** 어느 크기에서나 글자 수가 `609,022,912` 로 같다. A2 연습문제 3의 결론이 여기서도 성립한다. **청크 크기는 정확성이 아니라 속도에만 영향을 준다.**

```c
CHECK(Count == FirstCount);   // 일곱 번 전부
```

## 2. 파일 형식을 설계한다

모델을 파일로 어떻게 담을 것인가.

### CSV로 담으면 안 되는가

정답표는 CSV로 만들었다. 사람이 읽을 수 있고 git diff가 되니까. 모델은 다르다.

| | CSV | 이진 |
|---|---|---|
| 크기 | 약 270MB (숫자를 글자로 적으므로) | **180MB** |
| 쓰기 | `fprintf` 로 3천만 번 | `fwrite` 세 번 |
| 읽기 | `sscanf` 로 3천만 번 | `fread` 세 번 |
| 사람이 읽는가 | 읽는다 | 못 읽는다 |

정답표는 **사람이 검증하는 것**이라 CSV가 맞다. 모델은 **프로그램이 쓰는 것**이라 이진이 맞다. 목적이 형식을 정한다.

### 구조체를 통째로 쓰면 안 된다

가장 짧게 쓰는 방법은 이렇게 보인다.

```c
fwrite(Model, sizeof(FNgram), 1, File);   // 절대 하지 말 것
```

두 가지가 틀렸다.

**포인터를 쓰게 된다.** `FNgram` 안에는 `Grams`, `Cumulative` 같은 포인터가 있다. 주소를 파일에 적어봐야 다음 실행에서는 아무 의미가 없다.

**채움(padding)이 섞여 들어간다.** 컴파일러는 구조체 멤버를 정렬 경계에 맞추려고 사이사이에 빈 바이트를 넣는다. 얼마나 넣을지는 **컴파일러와 옵션에 따라 다르다.** 통째로 쓰면 "내 컴퓨터에서만 읽히는" 파일이 된다.

그래서 필드를 하나씩, **크기를 못박은 타입으로** 쓴다.

```c
static int WriteU64(FILE* File, uint64_t Value)
{
    return fwrite(&Value, sizeof(uint64_t), 1, File) == 1;
}
```

`uint64_t` 는 어느 컴파일러에서나 정확히 8바이트다. C++ 교재 `9.7` 의 고정 폭 정수가 왜 있는지가 여기서 나온다.

### 헤더

```
 0  "HGNG"             4바이트  우리 파일인가
 4  0x01020304         4바이트  바이트 순서가 같은가
 8  버전               4바이트
12  Order              4바이트
16  GramCount          8바이트
24  ContextCount       8바이트
32  Total              8바이트
40  OnceCount          8바이트
48  LineCount          8바이트
56  CharCount          8바이트
64  Grams[]            GramCount * Order * 4바이트
    Cumulative[]       GramCount * 8바이트
    ContextStart[]     (ContextCount+1) * 8바이트
```

**매직 넘버.** 앞 4바이트가 `HGNG` 가 아니면 우리 파일이 아니다. 사용자가 엉뚱한 파일을 지정했을 때 쓰레기를 읽고 수 GB를 `malloc` 하려 드는 대신 깔끔하게 거절한다.

**바이트 순서 표시.** `0x01020304` 를 그대로 쓴다. 리틀 엔디언 기계에서는 파일에 `04 03 02 01` 로 적힌다. 빅 엔디언 기계가 이 파일을 읽으면 `0x04030201` 이 나와서 안 맞는다.

```c
if (!ReadU32(File, &OrderMark) || OrderMark != NGRAM_ORDERMARK)
{
    fclose(File);
    return 0;   // 바이트 순서가 다른 기계에서 구운 파일이다
}
```

우리는 x64만 쓰므로 실제로 걸릴 일은 없다. 그래도 **조용히 틀린 답을 내는 것보다 거절하는 게 낫다.** 이게 이 교재가 계속 하는 이야기다.

**버전 번호.** 나중에 형식을 바꾸면 옛 파일이 남아 있다. 버전이 없으면 옛 파일을 새 코드로 읽다가 알 수 없는 곳에서 터진다.

### 검증

구운 것과 읽은 것이 같은지 **바이트 단위로** 확인한다.

```c
Same = Same && (memcmp(Loaded.Grams, Built.Grams,
                       GramWords * sizeof(uint32_t)) == 0);
```

그리고 망가진 파일을 거절하는지도 본다.

```c
FILE* Broken = fopen("data/broken.bin", "wb");
fwrite("XXXX", 1, 4, Broken);
fclose(Broken);

FNgram Junk;
CHECK(NgramLoad(&Junk, "data/broken.bin") == 0);
```

**실패하는 경우를 테스트하는 것**이 성공하는 경우를 테스트하는 것만큼 중요하다. 거절해야 할 것을 받아들이는 코드는 성공 테스트만으로는 절대 안 잡힌다.

**567배.** 0.05초에 180MB를 읽었으니 초당 3.6GB다. 이건 SSD의 속도가 아니라 **운영체제 파일 캐시**의 속도다. 방금 쓴 파일이라 메모리에 그대로 있다.

**서로 다른 숫자가 맞아떨어지는 것**은 두 코드가 같은 세상을 보고 있다는 신호다.

## 4. 슬라이딩 윈도우는 이미 나왔다

자료구조 교재 `2.5` 의 투 포인터·슬라이딩 윈도우를 기억할 것이다. 배열 위에서 `Left` 와 `Right` 를 움직이며 구간을 훑는 기법이다.

A6의 이 코드가 바로 그것이다.

```c
for (int i = 0; i < Order - 1; i++)
{
    Window[i] = Window[i + 1];
}
Window[Order - 1] = Token;
```

크기가 `Order` 로 **고정된** 창이 스트림 위를 한 칸씩 미끄러진다. 교재의 슬라이딩 윈도우와 다른 점은 둘이다.

| | 교재 `2.5` | N-그램 |
|---|---|---|
| 무엇 위를 움직이는가 | 배열 (전부 메모리에 있다) | **스트림** (앞을 못 본다) |
| 창의 크기 | 조건에 따라 늘었다 줄었다 | 항상 `Order` |

**스트림**이라는 것이 중요하다. 1.3GB 파일 전체를 메모리에 올릴 수 없으므로, 창은 **지나간 것을 기억할 수 없다.** `Window` 배열 `Order` 칸이 우리가 가진 기억의 전부다.

이 제약이 N-그램 모델의 정체이기도 하다. **N개 앞까지만 기억한다.** 트랜스포머가 하는 일은 이 창을 수천 칸으로 늘리면서도 메모리와 시간을 감당하는 것이다.

### 전체 코퍼스가 문장을 바꾸는가

```
[A7-4] 전체 코퍼스 3그램이 쓴 문장

   1. Acre V리그 다음해 발매했다. 나가 있지만 일본인 쇼쿠' 2006년 이념적이었고 학폭 5 시장 개칭
   2.
   3.
   4. 비상 사단의 철수하였고 있는 위해 '특기를 다룬다.
   5. 허리 앞에는 한동안 항 센서, 낙하산 정지법인 수훈자
   6.  목록
   7.  1호를 마츠다의 가능성은 기준)
   8. 「서양 악진

  평균 길이 22.2 글자
```

여덟 개 중 **두 개가 빈 문장**이다. 버그가 아니다. A5에서 쟀듯 코퍼스의 **23.7%가 빈 줄**이므로, 모델이 `[BOS][BOS]` 에서 바로 EOS를 뽑는 것은 데이터를 정확히 따른 결과다.

데이터가 74배 늘었는데 문장이 A6의 20만 줄 3그램보다 눈에 띄게 좋아지지는 않았다. 3그램은 앞 두 글자만 보므로, **데이터를 늘려도 볼 수 있는 창이 그대로**다. 더 나아지려면 N을 올려야 하고, N을 올리면 A6에서 본 대로 표가 폭발하고 원문을 외운다.

이 막다른 골목이 A8과 C파트의 출발점이다.

## 정리

만든 것.

| 것 | 내용 |
|---|---|
| `ScanOpenSized` | 청크 크기를 실행 중에 정한다 |
| `NgramSave` · `NgramLoad` | 이진 모델 파일. 매직·바이트순서·버전 검사 |
| `data/ngram3.bin` | 전체 코퍼스 3그램 모델 180MB (커밋하지 않는다) |

알아둘 것.

- **청크 크기는 생각만큼 중요하지 않다.** `FILE` 이 이미 버퍼를 두고 있다. 무릎은 4~64KB
- **구조체를 통째로 `fwrite` 하지 않는다.** 포인터와 채움이 섞여 들어간다
- **매직 넘버, 바이트 순서 표시, 버전**은 이진 형식의 기본 세 가지다
- **거절해야 할 것을 거절하는지 테스트한다.** 성공 테스트만으로는 안 잡힌다
- **슬라이딩 윈도우가 스트림 위에 있으면** 창 크기가 곧 기억의 한계다

쓴 문법.

- `fopen("wb")` / `fwrite` / `fread` — C 교재 `11.1` `11.2`
- `fseek` / `ftell` 로 파일 크기 재기
- 고정 폭 정수(`uint32_t`, `uint64_t`)로 형식 못박기
- 슬라이딩 윈도우 — 자료구조 교재 `2.5`

**2.** `NgramSave` 를 `fwrite(Model, sizeof(FNgram), 1, File)` 한 줄로 바꾸면 어떻게 되는가?

<details>
<summary>해답</summary>

**파일이 64바이트쯤 되고, 읽으면 죽는다.**

`FNgram` 은 포인터 셋과 정수 몇 개다. `sizeof(FNgram)` 은 64바이트 정도이고, 배열의 **내용은 하나도 안 들어간다.** 파일에 적히는 것은 `Grams` 가 가리키던 **주소**다.

읽을 때 그 주소를 그대로 `Model->Grams` 에 넣으면, 다음 실행에서는 아무 관계 없는 메모리를 가리킨다. 운이 좋으면 접근 위반으로 죽고, 운이 나쁘면 쓰레기를 읽어 **조용히 틀린 답**을 낸다.

여기에 더해 **채움**이 있다. `FNgram` 의 첫 멤버가 `int Order` 이고 다음이 `uint32_t* Grams` 인데, 64비트에서 포인터는 8바이트 경계에 놓여야 하므로 `Order` 뒤에 **4바이트의 쓰레기**가 들어간다. 그 4바이트에 무엇이 들었는지는 아무도 모른다 — 스택에 있던 옛 값일 수도 있다.

그래서 구조체를 통째로 쓰면 **같은 프로그램을 두 번 돌려도 파일이 다를 수 있다.** 재현성이 사라진다.

규칙은 간단하다. **파일에는 값만 쓴다. 주소는 절대 쓰지 않는다.** 그리고 **채움이 끼어들 자리를 만들지 않는다** — 필드를 하나씩 쓰면 채움은 애초에 없다.

</details>

**3.** 모델 파일이 180MB다. 절반으로 줄일 수 있겠는가?

<details>
<summary>해답</summary>

**줄일 수 있다.** 지금 무엇을 담고 있는지 보자.

| 배열 | 칸 수 | 칸 크기 | 합계 |
|---|---|---|---|
| `Grams` | 8,967,467 × 3 | 4바이트 | 103 MB |
| `Cumulative` | 8,967,467 | 8바이트 | 68 MB |
| `ContextStart` | 1,222,919 | 8바이트 | 9 MB |

**`Cumulative` 의 8바이트가 과하다.** 이건 문맥 구간 **안에서의** 누적이다. 한 문맥이 나온 최대 횟수가 전체 그램 수(6억)를 넘을 수 없지만, 실제로는 훨씬 작다. 가장 흔한 3그램 문맥이 몇 번 나왔는지 재보면 `uint32_t`(42억)로 충분한지 알 수 있다. 넘어가면 그 문맥만 따로 처리하면 된다. → **34MB 절약.**

**`Grams` 의 앞 두 칸은 안 담아도 된다.** 배열이 사전순으로 정렬되어 있고 `ContextStart` 가 구간을 알려주므로, 문맥은 **구간마다 한 번만** 적으면 된다. 지금은 구간 안의 모든 그램이 같은 문맥을 반복해서 들고 있다.

- 문맥: 1,222,919 × 2칸 × 4바이트 = 9 MB
- 다음 글자: 8,967,467 × 1칸 × 4바이트 = 34 MB
- 합계 **43MB** (지금 103MB)

둘을 합치면 180MB → **86MB.** 절반 이하다.

더 줄일 수도 있다. 어휘를 27,663종의 촘촘한 번호로 다시 매기면 글자 하나가 **15비트**면 된다. 여기서부터는 압축의 영역이고, 실제 N-그램 도구들이 하는 일이다.

**그럼 왜 안 했는가.** 지금 180MB는 문제가 아니기 때문이다. 읽는 데 0.05초 걸린다. 줄여서 얻는 것(디스크 90MB)보다 잃는 것(코드 복잡도, 버그 자리)이 크다. **필요해지면 그때 한다** — A4의 적재율 실험에서 배운 것과 같은 판단이다.

</details>

## 다음 장

**A8. 백오프.**

N=6 모델은 `[BOS][BOS][BOS][BOS][BOS] 한` 같은 문맥은 잘 안다. 그런데 생성 도중에 **본 적 없는 문맥**에 빠지면 어떻게 되는가. 지금 `NgramPick` 은 이렇게 한다.

```c
if (Index < 0)
{
    return TOKEN_EOS;   // 본 적 없는 문맥. 문장을 닫는다.
}
```

**포기한다.** 그래서 A6의 N=4 출력에 빈 문장이 섞였다.

백오프는 다르게 한다. 6글자 문맥에서 못 찾으면 **5글자로 물러서고**, 그것도 없으면 4글자로 물러선다. 끝까지 가면 글자 빈도만 보는 A3의 모델이 받아준다. 그러면 모델은 절대 막히지 않는다.

문제는 **얼마나 물러설 것인가**다. 짧은 문맥은 안전하지만 멍청하다. 긴 문맥은 똑똑하지만 자주 막히고 원문을 외운다. 그 사이를 재는 방법(할인, discounting)을 만들고, A6 연습문제 3에서 잰 **"베낀 조각의 길이"가 얼마나 줄었는지** 숫자로 확인한다.

재귀도 처음 쓴다 — 백오프는 "짧은 문맥으로 같은 질문을 다시 하는 것"이라 재귀가 자연스럽다. C 교재 `6.1` 과 자료구조 교재 `1.2` 가 그 자리에서 쓰인다.
