# A8. 백오프

> **선행** · C 교재 `6.1` 함수와 재귀 · 자료구조 교재 `1.2` 재귀함수
> **만드는 것** · `lib/Backoff`
> **예제** · A8-1 ~ A8-5

## 0. 내가 틀린 가정으로 시작한 장

이 장을 시작할 때 나는 이렇게 생각했다.

> N=6 모델은 본 적 없는 문맥에 자주 빠질 것이다. A6에서 빈 문장이 많이 나온 게 그 증거다. 백오프를 켜면 안 막히게 된다.

검사를 그렇게 걸었다.

```c
CHECK(PlainBlockedCount > 0);   // 6그램 단독은 막힌 적이 있을 것이다
```

**실패했다.** 200문장을 쓰는 동안 6그램 모델은 **한 번도 막히지 않았다.**

왜인지는 증명할 수 있다. 모델은 자기가 본 그램만 따라간다. 방금 `(t1 t2 t3 t4 t5 t6)` 을 뽑았다면 그 여섯 글자는 코퍼스 어딘가에 있었고, 다음 문맥은 `(t2 t3 t4 t5 t6)` 이다. 그 다섯 글자도 코퍼스에 있었으니, **그 뒤에 무언가가 따라왔다.** 문장은 반드시 EOS로 끝나므로 `t6` 가 EOS가 아닌 한 다음 글자가 존재한다. 그러므로 문맥은 항상 표 안에 있다.

**모델은 자기가 만든 문맥에서 절대 길을 잃지 않는다.**

그럼 백오프가 왜 필요한가. 두 가지 답이 있고, 둘 다 이 장에서 잰다.

1. **바깥에서 문맥을 받으면** 막힌다 (1절)
2. 막히지 않더라도, 백오프는 **원문 베끼기를 줄인다** (4절)

---

## 1. 프롬프트를 주면 막힌다

모델이 스스로 쓰게 두지 않고, **다섯 글자를 주고 이어 쓰라**고 해보자. 실제 언어모델을 쓰는 방식이 이쪽이다.

```
[A8-1] 문맥을 바깥에서 주면

  문맥            아는 최고 차수    6그램 단독  백오프가 이어 쓴 글
   대한민국                   6           된다  의 방송연예인 한재석, 장혁 등의 수
  여성에게도                  6           된다   자유국이 우크라이나의 전 축구 선수
  국의 역사                   6           된다  가 에릭 홉스봄. (~2019년 -
  힣힣힣힣힣                  0         막힌다   사건으로 보이며, 규모 7.09.2
```

`힣힣힣힣힣` 은 **어느 차수도 모른다.** 6그램은 물론이고 2그램에서조차 `힣` 다음에 온 글자를 본 적이 없다. 6그램 단독이면 여기서 끝이다.

백오프는 계속 쓴다. 아무것도 모르는 문맥이면 **글자 빈도만 보고** 뽑는다 — A3의 모델이 바닥에서 받아준다.

세 번째 예가 재미있다. `국의 역사` 다음에 쓴 것이 `가 에릭 홉스봄...` 이다. 앞뒤가 안 맞는다. 문맥을 아는데도 이상한 이유는 코퍼스가 **위키백과 문서의 줄**이고, "역사가 에릭 홉스봄"이라는 조각이 실제로 거기 있었기 때문이다. 모델이 틀린 게 아니라 데이터가 그렇다.

## 2. 백오프는 재귀다

"짧은 문맥으로 같은 질문을 다시 한다." 이 문장이 곧 재귀의 정의다.

```c
uint32_t BackoffPick(FBackoff* Backoff, const uint32_t* Context, int Length,
                     FRandom* Rng)
{
    const FNgram* Model = &Backoff->Orders[Length + 1];

    // ---- 바닥 ----
    if (Length == 0)
    {
        ... 글자 빈도에서 뽑는다 ...
        return ...;
    }

    int64_t Index = NgramFindContext(Model, Context);

    // ---- 문맥 자체가 없다. 한 글자 줄여 다시 묻는다 ----
    if (Index < 0)
    {
        return BackoffPick(Backoff, Context + 1, Length - 1, Rng);
    }

    ...
}
```

자료구조 교재 `1.2` 의 재귀 3요소가 그대로 있다.

| 재귀의 요소 | 여기서는 |
|---|---|
| 바닥 조건 | `Length == 0` — 1그램은 물러설 곳이 없다 |
| 문제를 줄이기 | `Length - 1` — 문맥을 한 글자 줄인다 |
| 자기 호출 | `BackoffPick(..., Context + 1, Length - 1, ...)` |

`Context + 1` 이 요령이다. 문맥은 **최근 글자가 뒤**에 오도록 담겨 있으므로, 앞쪽 한 칸을 버리면 그대로 한 글자 짧은 문맥이 된다. 배열을 새로 만들 필요가 없다 — **포인터를 한 칸 옮기기만 한다.** C 교재 `7.5` 의 포인터 산술이 여기서 값을 한다.

재귀 깊이는 최대 `TOP_ORDER` = 6이다. 스택이 넘칠 걱정이 없다.

## 3. 할인 — 못 찾을 때만 물러서는 게 아니다

문맥을 찾았다고 그 확률을 그대로 믿으면 안 된다.

`대한민국의 헌` 이라는 문맥을 **한 번** 봤고 그때 다음 글자가 `법` 이었다고 하자. 그대로 믿으면 `법` 이 나올 확률이 **100%** 다. 한 번 본 것을 확실하다고 말하는 셈이다. A6에서 본 대로 6그램의 81%가 한 번짜리이므로, 이런 일이 대부분이다.

그래서 **후보마다 일정한 양을 떼어** 짧은 문맥에 넘긴다. 이것을 **절대 할인**(absolute discounting)이라고 한다.

```
후보가 m 개, 문맥을 본 횟수가 T 라면
    떼어낼 양   = D * m
    짧은 문맥에 넘길 확률 = D * m / T
```

후보가 많을수록(= 문맥이 다양한 것을 봤을수록) 많이 뗀다. 뒤집어 말하면 **한 가지만 본 문맥은 조금만 뗀다.**

### 소수를 쓰지 않는다

`D = 0.75` 는 실무에서 흔한 값이다. 그런데 `double` 로 계산하면 반올림이 끼어들고, 컴파일러 최적화에 따라 결과가 달라질 수 있다. **같은 씨앗에서 같은 문장이 나와야 한다**는 규칙을 A3에서 세웠다.

그래서 분수로 둔다.

```c
#define BACKOFF_NUM 3u
#define BACKOFF_DEN 4u
```

전부 `DEN` 배로 키우면 정수만 남는다.

```
전체    = DEN * T
넘길 몫 = NUM * m
남는 몫 = DEN * T - NUM * m
```

```c
uint64_t Scale = (uint64_t)BACKOFF_DEN * Total;
uint64_t Reserved = (uint64_t)BACKOFF_NUM * Choices;

uint64_t Draw = RandomBelow(Rng, Scale);

if (Draw < Reserved)
{
    return BackoffPick(Backoff, Context + 1, Length - 1, Rng);   // 물러선다
}
```

남는 몫 안에서 뽑을 때는 각 후보의 몫이 `DEN * Count - NUM` 이다. 횟수는 1 이상이므로 `4*1 - 3 = 1` 이상, **항상 양수**다. 누적합도 여전히 증가하므로 A3의 이진 탐색이 그대로 돌아간다.

```c
uint64_t Cum = (uint64_t)BACKOFF_DEN * Model->Cumulative[Mid]
             - (uint64_t)BACKOFF_NUM * (Mid - From + 1);
```

넘칠 걱정도 없다. `4 × 6억 = 24억` 이고 `uint64_t` 는 1800경까지 담는다.

> 엄밀히 말하면 이 방식은 **보간**(interpolation)이다. 정통 Katz 백오프는 짧은 문맥으로 물러설 때 긴 문맥이 이미 본 글자를 제외하고 다시 정규화한다. 우리는 제외하지 않는다. 계산이 훨씬 간단하고, 실제로 Kneser-Ney 같은 현대 기법도 보간 쪽을 쓴다.

## 4. 얼마나 덜 베끼는가

이 장의 검증은 **"원문을 얼마나 그대로 뱉는가"** 다. 재는 방법이 필요하다.

A6 연습문제에서는 파이썬으로 최장 일치를 찾았다. 여기서는 C 안에서 끝낸다. **8그램 모델을 자로 쓴다.**

```c
// 문장 안의 8글자 조각이 코퍼스에 그대로 있는가
if (NgramCount(Probe, Tokens + i) > 0)
```

8그램 표에 있다는 것은 그 여덟 글자가 코퍼스 어딘가에 **그대로 있었다**는 뜻이다. 정확하고, 조회가 `O(log N)` 이다. 모델을 자로 쓰는 셈이다.

연속한 창이 전부 원문이면 조각이 길게 이어진다. 창 `k` 개가 연속이면 `8 + k - 1` 글자다.

```
[A8-2] 백오프 없이 6그램으로 200문장
  평균 길이        = 49.9 글자
  빈 문장          = 43개
  문맥을 못 찾아 멈춘 문장 = 0개 (0.0%)
  8글자 조각 8982개 중 원문 그대로 = 6281개 (69.9%)
  가장 길게 베낀 조각 = 68 글자

[A8-3] 백오프를 켜고 같은 씨앗으로 200문장
  평균 길이        = 33.1 글자
  빈 문장          = 51개
  막힌 문장        = 0개 (백오프는 막히지 않는다)
  8글자 조각 5629개 중 원문 그대로 = 2669개 (47.4%)
  가장 길게 베낀 조각 = 47 글자
```

| | 6그램 단독 | 백오프 |
|---|---|---|
| 8글자 조각이 원문인 비율 | 69.9% | **47.4%** |
| 가장 길게 베낀 조각 | 68글자 | **47글자** |

**베끼기가 3분의 1 줄었다.** 그리고 68글자짜리 통째 복사가 사라졌다.

```c
CHECK((double)BackCopied / (double)BackWindows
      < (double)PlainCopied / (double)PlainWindows);
```

### 대가

공짜가 아니다.

| | 6그램 단독 | 백오프 |
|---|---|---|
| 평균 길이 | 49.9글자 | 33.1글자 |
| 빈 문장 | 43개 | 51개 |

**문장이 3분의 1 짧아졌다.** 이유는 분명하다. 짧은 문맥으로 물러설 때마다 EOS를 뽑을 확률이 올라간다. 1그램에서 EOS의 비율은 문장 수 / 글자 수이므로 꽤 높다.

베끼기를 줄이는 것과 문장을 길게 쓰는 것이 **맞바꿈 관계**에 있다. 할인율 `D` 가 그 저울이다. `D` 를 0에 가깝게 두면 6그램 단독에 수렴하고, 1에 가깝게 두면 짧은 문맥에 가까워진다. 연습문제 2에서 직접 돌려본다.

## 5. 실제로 몇 차수를 썼는가

```
[A8-4] 글자 하나를 뽑을 때 실제로 쓴 차수

      차수     뽑은 횟수      비율
        6          4533      66.5%
        5          1297      19.0%
        4           701      10.3%
        3           237       3.5%
        2            48       0.7%
        1             0       0.0%

  물러선 이유
    문맥이 아예 없어서 = 792 번
    할인된 몫에 걸려서 = 2810 번
```

**3분의 2는 6그램에서 뽑는다.** 물러서는 일이 생각보다 적다.

그리고 물러선 이유의 **78%가 할인** 때문이다. 문맥을 못 찾아서 물러선 것은 792번뿐이다. 백오프를 "못 찾았을 때의 대비책"이라고만 생각하면 절반을 놓친다. **주로 하는 일은 확신을 깎는 것**이다.

1그램까지 내려간 적이 한 번도 없다. 2그램 문맥(= 앞 글자 하나)은 거의 항상 표에 있기 때문이다. 그럼에도 1그램 바닥이 필요한 이유는 A8-1의 `힣힣힣힣힣` 같은 경우다. **한 번 일어날 일도 처리해두지 않으면 그때 죽는다.**

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Backoff.h` · `.c` | 1~N그램을 동시에 들고, 재귀로 물러서며 뽑는다 |

알아둘 것.

- **모델은 자기가 만든 문맥에서 길을 잃지 않는다.** 막히는 것은 바깥 문맥을 받았을 때다
- **백오프의 주된 일은 확신을 깎는 것**이다. 못 찾았을 때의 대비책이 아니다
- **할인은 분수로 한다.** 정수만 쓰면 어느 기계에서나 같은 수열이 나온다
- **모델을 자로 쓸 수 있다.** 8그램 표는 "이 조각이 원문인가"에 `O(log N)` 으로 답한다
- **베끼기를 줄이면 문장이 짧아진다.** 할인율이 그 저울이다

쓴 문법.

- 재귀 — C 교재 `6.1`, 자료구조 교재 `1.2`
- 포인터 산술로 부분 배열 넘기기 (`Context + 1`) — C 교재 `7.5`
- 분수 연산으로 부동소수점 피하기

## 연습문제

**1.** `BackoffPick` 의 재귀를 반복문으로 바꿔보자. 어느 쪽이 읽기 좋은가?

<details>
<summary>해답</summary>

바꿀 수 있다. 이 재귀는 **꼬리 재귀**(tail recursion)이기 때문이다 — 자기를 부른 결과를 그대로 돌려주고 그 뒤에 하는 일이 없다.

```c
uint32_t BackoffPickLoop(FBackoff* Backoff, const uint32_t* Context, int Length,
                         FRandom* Rng)
{
    while (Length > 0)
    {
        const FNgram* Model = &Backoff->Orders[Length + 1];
        int64_t Index = NgramFindContext(Model, Context);

        if (Index >= 0)
        {
            ... 할인 판정 ...
            if (Draw >= Reserved)
            {
                return ...;      // 여기서 뽑는다
            }
        }

        Context++;               // 재귀 호출 대신 인자를 고친다
        Length--;
    }

    ... 1그램에서 뽑는다 ...
}
```

**어느 쪽이 나은가.** 성능은 차이가 없다시피 하다. 깊이가 최대 6이고, MSVC는 `/O2` 에서 꼬리 재귀를 대개 반복문으로 바꿔준다.

읽기는 **재귀 쪽이 낫다.** "못 찾으면 한 글자 줄여 같은 질문을 다시 한다"는 설명이 코드와 한 줄씩 대응한다. 반복문 버전은 `Context++` 와 `Length--` 가 무슨 뜻인지 한 번 더 생각해야 한다.

반대로 재귀가 불리한 경우도 있다. 깊이가 데이터에 따라 정해지면(예: 트리 탐색) 스택이 넘칠 수 있다. 여기서는 깊이가 `TOP_ORDER` 로 **고정**이라 그 위험이 없다. **재귀를 쓸지 말지는 깊이가 유계인가로 판단한다.**

</details>

**2.** 할인율 `BACKOFF_NUM / BACKOFF_DEN` 을 바꿔보자. 베끼기와 문장 길이가 어떻게 움직이는가?

<details>
<summary>해답</summary>

`0/4`(할인 없음), `1/4`, `3/4`, `7/8` 로 돌려보면 저울의 양 끝이 보인다.

**`0/4` 로 두면** 백오프는 "못 찾았을 때만" 동작한다. 스스로 쓸 때는 절대 못 찾는 일이 없으므로(0절) **6그램 단독과 완전히 같아진다.** 베끼기 69.9%, 평균 49.9글자.

**할인을 올릴수록** 짧은 문맥으로 자주 물러서므로 베끼기가 줄고 문장이 짧아진다. 극단으로 밀면 거의 1그램이 되어 A3의 출력에 가까워진다.

두 가지를 읽어낼 수 있다.

첫째, **`D` 는 "얼마나 외울 것인가"를 돌리는 손잡이**다. 0이면 통째로 외우고, 1에 가까우면 아무것도 기억하지 못한다.

둘째, **좋은 값을 고르려면 자가 있어야 한다.** 지금 우리에게는 "베낀 비율"과 "평균 길이" 두 숫자뿐인데, 이 둘은 서로 반대로 움직이므로 **어느 쪽이 더 나은 모델인지 말해주지 못한다.** 하나의 숫자로 모델의 좋고 나쁨을 말하는 자가 필요하다.

그게 **퍼플렉서티**이고 B2에서 만든다. 0.75가 실무에서 흔히 쓰이는 값인 것도 누군가 그 자로 재본 결과다.

</details>

**3.** 8그램 모델을 "자"로 쓰는 것은 정확한가? 무엇을 놓치는가?

<details>
<summary>해답</summary>

**8글자 단위로는 정확하다.** 8그램 표에 있다는 것은 그 여덟 글자가 코퍼스에 그대로 있었다는 뜻이고, 없다는 것은 없었다는 뜻이다. 거짓 양성도 거짓 음성도 없다.

놓치는 것은 **8글자보다 짧은 베끼기**다. 7글자를 그대로 옮겨도 창에 안 잡힌다. 그래서 우리 숫자는 **베끼기를 과소평가**한다.

그리고 "연속한 창 `k` 개 → `8 + k - 1` 글자"라는 계산에도 빈틈이 있다. 창 두 개가 연속으로 원문이라고 해서 **같은 위치의 원문**이라는 보장이 없다. 서로 다른 문서에서 온 8글자 조각 두 개가 한 글자 겹쳐 이어졌을 수 있다. 그러면 9글자가 통째로 원문인 것은 아니다.

그래서 이 자는 **양쪽으로 틀린다.**

- 8글자 미만의 베끼기를 못 본다 → 과소평가
- 창을 이어 붙일 때 같은 위치라는 보장이 없다 → 과대평가

정확한 값이 필요하면 A6 연습문제처럼 코퍼스 원문에서 직접 찾아야 한다.

그럼에도 이 자를 쓰는 이유는 **비교가 목적**이기 때문이다. 같은 느슨함을 양쪽에 똑같이 적용하면, 69.9% 대 47.4%라는 **비교는 유효하다.** 절대값이 필요 없고 상대값이면 되는 자리에서는, 싸고 일관된 자가 정확한 자보다 낫다.

이건 실험 설계의 기본이다. **자가 완벽할 필요는 없다. 양쪽에 똑같이 틀리기만 하면 된다.**

**A9. Kiwi 링크 — C++로 가는 다리.**

여기까지 A파트는 **글자**를 단위로 삼았다. `한국어를` 은 네 글자다. 그런데 한국어에서 의미의 단위는 글자가 아니라 **형태소**다 — `한국/어/를`.

A9에서는 한국어 형태소 분석기 **Kiwi** 를 붙여 토큰 단위를 바꾼다. 같은 N-그램 모델을 형태소 위에서 돌리면 얼마나 달라지는지 잰다.

그런데 Kiwi 본체는 **C++** 로 쓰여 있다. 여기서 문제가 시작된다.

- C에서 C++ 라이브러리를 어떻게 부르는가 (`extern "C"`, ABI)
- vcpkg로 의존성을 어떻게 관리하는가
- Debug/Release 런타임이 섞이면 왜 죽는가

이걸 다루다 보면 **"그냥 C++로 쓰는 게 낫지 않나"** 라는 결론에 자연스럽게 도착한다. B파트로 넘어가는 전환이 억지가 아니라 필연이 되는 자리다.
