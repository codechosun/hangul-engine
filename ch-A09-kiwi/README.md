## 0. 글자가 단위인 게 맞는가

A1부터 A8까지 우리는 **글자**를 단위로 삼았다. 이유는 단순했다 — 글자는 UTF-8만 알면 자를 수 있고, 외부 의존성이 하나도 없다.

그런데 한국어에서 의미의 단위는 글자가 아니다.

```
[A9-2] 같은 문장을 글자로 자를 때와 형태소로 자를 때

  원문     한국어를 배우는 사람들이 늘고 있다.
  글자 20개  한 국 어 를   배 우 는   사 람 들 이   늘 고   있 다 .
  형태소 12개  한국어/NNP 를/JKO 배우/VV 는/ETM 사람/NNG 들/XSN 이/JKS 늘/VV 고/EC 있/VX 다/EF ./SF
```

`한국어` 는 세 글자지만 **의미 단위로는 하나**다. `한` `국` `어` 로 쪼개는 순간 모델은 "한국어"라는 낱말을 배울 기회를 잃는다.

A6에서 본 문제를 떠올려보자. 6그램 모델의 창은 여섯 글자였고, 그건 한국어로 **어절 하나 반**이다. 같은 창을 형태소로 채우면 훨씬 멀리 본다.

이 장에서는 형태소 분석기 **Kiwi** 를 붙여 그 차이를 잰다. 그리고 붙이는 과정 자체가 이 장의 절반이다 — **C에서 C++ 라이브러리를 부르는 일**이 생각보다 큰 주제이기 때문이다.

## 1. 준비

```bash
.venv/Scripts/python tools/get_kiwi.py
```

`third_party/kiwi` 에 약 500MB가 풀린다. 저장소에는 넣지 않는다(`.gitignore`).

받는 것은 셋이다.

| 것 | 자리 | 언제 필요한가 |
|---|---|---|
| 헤더 (`capi.h`) | `include/kiwi/` | **컴파일할 때** |
| import lib (`kiwi.lib`) | `lib/` | **링크할 때** |
| DLL (`kiwi.dll`) | `lib/` | **실행할 때** |

셋이 전부 필요하고, **필요한 시점이 다 다르다.** C 교재 `11.5` 의 분할 컴파일에서 `.h` 와 `.obj` 가 하는 일이 여기서 `.h` / `.lib` / `.dll` 로 늘어난 것이다.

빌드 설정에 추가할 것.

| 설정 | 값 |
|---|---|
| `C/C++` → `일반` → `추가 포함 디렉터리` | `third_party\kiwi\include` |
| `링커` → `입력` → `추가 종속성` | `third_party\kiwi\lib\kiwi.lib` |
| 빌드 후 이벤트 | `copy third_party\kiwi\lib\kiwi.dll $(OutDir)` |

마지막 줄을 빼먹으면 **빌드는 되는데 실행이 안 된다.** 프로그램을 켜는 순간 "kiwi.dll을 찾을 수 없습니다"가 뜬다. 컴파일러도 링커도 잡아주지 못하는 오류다.

## 2. C에서 C++을 부른다는 것

Kiwi 본체는 **C++** 로 쓰여 있다. `include/kiwi/Kiwi.h` 를 열어보면 `namespace kiwi` 안에 클래스가 들어 있다. 우리 코드는 C다. 그대로는 못 부른다.

### 이름 맹글링

C++은 같은 이름의 함수를 인자만 바꿔 여러 개 만들 수 있다(오버로딩). 링커는 이름으로 함수를 찾으므로, C++ 컴파일러는 **인자 타입을 이름에 섞어 넣는다.** 이걸 이름 맹글링(name mangling)이라고 한다.

```
C++ 소스        void Analyze(const char*, int);
MSVC 심볼       ?Analyze@@YAXPEBDH@Z
```

C 컴파일러는 이런 이름을 만들 줄도 찾을 줄도 모른다. 그래서 C++ 라이브러리는 C에서 쓰라고 **창구**를 따로 낸다.

```cpp
#ifdef __cplusplus
extern "C" {
#endif

kiwi_h kiwi_init(const char* model_path, int num_threads, int options, int enabled_dialects);
...

#ifdef __cplusplus
}
#endif
```

`extern "C"` 는 "이 함수들은 C 규칙으로 이름을 지어라"는 지시다. `kiwi_init` 은 `kiwi_init` 그대로 남고, C에서 부를 수 있게 된다. `capi.h` 전체가 이 블록 안에 들어 있다.

`#ifdef __cplusplus` 로 감싼 이유는 **같은 헤더를 C와 C++ 양쪽에서 읽기 때문**이다. C 컴파일러는 `extern "C"` 라는 문법을 모르므로 그때는 통째로 건너뛴다.

### 왜 핸들만 주고받는가

C API를 보면 구조체를 통째로 넘기는 함수가 하나도 없다.

```c
typedef struct kiwi_s* kiwi_h;      // 속이 안 보이는 포인터
```

`struct kiwi_s` 의 정의는 어디에도 없다. 이런 걸 **불투명 포인터**(opaque pointer)라고 한다.

이유는 **ABI** 때문이다. 구조체의 실제 메모리 배치 — 멤버 순서, 채움(padding), 정렬 — 는 컴파일러와 옵션에 따라 달라진다. Kiwi를 빌드한 컴파일러와 우리가 쓰는 컴파일러가 다르면 같은 구조체를 다르게 해석한다. C++ 클래스라면 가상 함수 테이블까지 얽힌다.

그래서 경계에서는 **크기와 배치가 표준으로 정해진 것만** 주고받는다.

- 포인터 (크기가 정해져 있고 내용을 안 들여다본다)
- `int`, `float`, `const char*` 같은 기본 타입
- C에서 정의한 POD 구조체 (`kiwi_token_info_t` 처럼 명시적 타입만 쓴 것)

A7에서 "구조체를 통째로 `fwrite` 하지 말라"고 했던 것과 **똑같은 이야기**다. 파일이든 라이브러리 경계든, 내가 통제하지 못하는 쪽으로 나가는 데이터는 배치를 못박아야 한다.

### Debug와 Release를 섞으면

MSVC에서 가장 흔한 사고다. Kiwi는 Release CRT(`/MD`)로 빌드되어 있다. 우리 프로그램을 Debug CRT(`/MDd`)로 빌드하면 **힙이 두 개**가 된다.

```
Kiwi 안에서 malloc  ->  Release 힙
우리 쪽에서 free    ->  Debug 힙에 반납 시도  ->  죽는다
```

Kiwi의 C API가 `kiwi_res_close`, `kiwi_close` 같은 해제 함수를 **따로 제공하는 이유**가 이것이다. **할당한 쪽이 해제한다.** 우리가 `free()` 를 부를 일이 없게 설계되어 있다.

```c
kiwi_res_h Res = kiwi_analyze(Kiwi, Line, 1, Option, NULL);
...
kiwi_res_close(Res);     // free() 가 아니다
```

### 실패하는 길부터 확인한다

```c
kiwi_h Broken = kiwi_init("third_party/kiwi/models/없는폴더", -1, KIWI_BUILD_DEFAULT, 0);
```

```
  없는 모델 경로 -> handle=0000000000000000, kiwi_error()="Cannot open extract.mdl for WordDetector"
```

`NULL` 을 돌려주고 `kiwi_error()` 에 이유가 남는다. 이것도 C 경계의 규칙이다 — **C++ 예외는 DLL 경계를 넘지 못한다.** 예외를 던지면 그 자리에서 프로그램이 죽는다. 그래서 C API는 예외를 안에서 잡아 오류 코드와 메시지로 바꿔 돌려준다.

우리가 A0에서 "예외를 쓰지 않고 반환 코드와 `CHECK` 로 간다"고 정한 것(결정 15)과 같은 자리에 서 있는 셈이다.

```c
CHECK(Broken == NULL);
```

## 3. 세 번째 해시맵

Kiwi가 돌려주는 형태소는 `"한국어"`, `"를"` 같은 **문자열**이다. 우리 N-그램 코드는 `uint32_t` 토큰만 안다. 문자열마다 번호를 붙여줘야 한다.

해시맵이 또 필요하다. 그런데 지금 가진 둘 다 안 맞는다.

| | 키 | 만든 곳 |
|---|---|---|
| `lib/Map` | `uint64_t` 하나 | A4 |
| `lib/GramMap` | `uint32_t` 배열 (길이 고정) | A6 |
| **`lib/Vocab`** | **문자열** | **A9** |

셋을 나란히 놓으면 **뼈대가 똑같다.**

- 열린 주소, 선형 탐사
- 칸 수는 2의 거듭제곱, `& Mask`
- 적재율 0.7에서 두 배로
- 아레나에 내용을 담고 표에는 번호만
- 해시는 FNV로 굴린 뒤 `MapHash` 로 한 번 더 섞기

다른 것은 **두 줄**뿐이다.

```c
// 비교
Keys[Slot] == Key                                  // Map
memcmp(Stored, Key, KeyLength * sizeof(uint32_t))  // GramMap
strcmp(Text + Offsets[Id], Key)                    // Vocab

// 해시
MapHash(Key)          // Map
GramHash(Key, Length) // GramMap
VocabHash(Text)       // Vocab
```

두 줄이 다르다고 **파일 여섯 개**(`.h`/`.c` × 3)를 따로 썼다. 같은 버그를 고치려면 세 군데를 고쳐야 하고, 적재율을 바꾸려면 세 군데를 고쳐야 한다.

C로 이걸 하나로 묶는 방법이 없지는 않다.

- `void*` 키와 함수 포인터 두 개(비교·해시)를 받는다 → 키 하나 찾을 때마다 **간접 호출 두 번**. A4에서 잰 대로 이 루프는 6억 번 돈다
- 매크로로 코드를 찍어낸다 → 디버거가 못 따라오고 오류 메시지가 지옥이 된다

C++에서는 한 줄이다.

```cpp
std::unordered_map<uint64_t, uint64_t>        Map;
std::unordered_map<std::vector<uint32_t>, uint64_t> GramMap;
std::unordered_map<std::string, uint32_t>     Vocab;
```

템플릿은 **타입마다 코드를 따로 찍어내되 간접 호출을 만들지 않는다.** 우리가 손으로 세 번 쓴 것을 컴파일러가 대신 세 번 쓴다.

이게 B파트로 넘어가는 이유다. 여기까지 오는 동안 **필요해서 손으로 만든 것들**이 C++에는 이미 있고, 게다가 더 빠르다. 직접 만들어봤기 때문에 그 한 줄의 값을 안다.

## 4. 형태소로 바꾸면 무엇이 달라지는가

코퍼스 앞 5만 줄을 형태소로 자른다.

```
[A9-3] 코퍼스 앞 50000줄을 형태소로 자른다
  문장 수        = 50000
  글자 수        = 2427775
  형태소 수      = 1173223
  글자 어휘      = 3780 종
  형태소 어휘    = 53216 종
  글자 하나당    = 0.48 형태소
  걸린 시간      = 12.0 초 (초당 20만 글자)
```

**형태소 하나가 평균 2.07글자**다. 토큰 수가 절반으로 줄었다.

대신 **어휘가 14배로 늘었다.** 글자는 3,780종이면 끝나는데 형태소는 53,216종이다. 그리고 이 숫자는 데이터를 늘리면 계속 늘어난다 — 새 고유명사가 끝없이 나오기 때문이다. 글자는 늘어나지 않는다.

같은 5만 줄로 3그램을 만들어 비교하면,

```
[A9-4] 같은 50000줄로 만든 3그램 두 개

  단위            어휘     토큰 수  서로 다른 그램   한 번만
  글자            3780     2427775          338249     52.6%
  형태소         53216     1173223          706169     84.1%
```

**토큰은 절반인데 서로 다른 그램은 두 배**다. 그리고 한 번만 나온 그램이 52.6%에서 **84.1%** 로 뛴다.

A6에서 본 그 그래프다. 형태소 3그램은 글자로 치면 **6.2글자**를 덮는데, 글자 6그램의 "한 번만" 비율(81.1%)과 거의 같은 자리에 와 있다.

```
[A9-5] 그램 3개가 덮는 실제 길이
  글자 3그램   = 3 글자
  형태소 3그램 = 6.2 글자 (형태소 하나가 평균 2.07글자)
```

**단위를 바꿔도 근본 문제는 그대로다.** 멀리 보려면 표가 희소해진다. 다만 같은 희소함으로 더 멀리 본다는 것이 이득이다.

문장을 보면 이득이 눈에 보인다.

```
  글자 3그램이 쓴 문장
    1.  조카: 인터넷 익스플레인퍽 인류학이 실험은 포함된다. 팜 OS, 물체 질량 자동차 세련된 뒤에는
       컴퓨터과학철학의 협동놀이(文章世界(20대

  형태소 3그램이 쓴 문장 (형태소 사이를 공백으로 이어 붙였다)
    1. 우크라이나 의 국기 는 24 시간 여권 , 차량 등록 , 지역 , 오데사 등 의 소문 에 불과 하 다는 점 도
       비 공식 적 이 ᆫ 미시시피강 - 미주리 강 은 국토 가 아주 넓 은 평야 가 만나 ᆫ ...
```

글자 3그램은 낱말이 깨진다(`익스플레인퍽`). 형태소 3그램은 **낱말이 안 깨진다.** 대신 낱말끼리의 연결은 여전히 엉망이다 — 3그램이 보는 범위가 딱 거기까지다.

> `이 ᆫ`, `만나 ᆫ` 처럼 보이는 것은 Kiwi가 어미를 분석한 결과다. `인` = `이` + `ㄴ`. 원래 형태로 되돌리려면 Kiwi의 `kiwi_joiner_*` 를 써야 하는데, 여기서는 공백으로 이어 붙이기만 했다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Vocab.h` · `.c` | 문자열 → 번호 사전. 이 교재의 **세 번째** 해시맵 |
| `NgramBuildFromTokens` | 파일이 아니라 토큰 배열에서 모델을 만든다 |
| `tools/get_kiwi.py` | Kiwi 배포본 내려받기 (버전 고정) |

알아둘 것.

- **헤더·import lib·DLL 은 필요한 시점이 다 다르다.** DLL을 옆에 안 두면 실행할 때 죽는다
- **`extern "C"` 는 이름 맹글링을 끄는 스위치**다. C++ 라이브러리가 C에 내주는 창구
- **경계에서는 핸들만 주고받는다.** 구조체 배치와 예외는 경계를 못 넘는다
- **할당한 쪽이 해제한다.** `kiwi_res_close` 가 `free` 가 아닌 이유
- **형태소는 멀리 보게 해주지만 어휘가 14배가 된다.** 희소함은 그대로다
- **해시맵을 세 번 쓴 것**이 C의 한계다. 템플릿이 있으면 한 번이면 된다

쓴 문법.

- 분할 컴파일과 외부 라이브러리 링킹 — C 교재 `11.5`
- 불투명 포인터로 구현 감추기
- 문자열 해시와 `strcmp` 비교 — 자료구조 교재 `1.7`

## 연습문제

**1.** `kiwi.dll` 을 실행 파일 옆에서 지우고 돌려보자. 어떤 오류가 나는가? 컴파일러는 왜 못 잡았는가?

<details>
<summary>해답</summary>

프로그램이 **시작조차 못 한다.** 종료 코드가 `0xC0000135` (`STATUS_DLL_NOT_FOUND`) 로 떨어진다. 탐색기에서 켜면 "kiwi.dll을 찾을 수 없기 때문입니다"라는 창이 뜨고, 명령줄에서는 아무 말 없이 그 코드만 남는다.

`main` 이 불리기 전에 죽는다. `printf` 한 줄도 안 나온다. 윈도우 로더가 실행 파일을 메모리에 올릴 때 필요한 DLL을 먼저 찾는데, 그 단계에서 실패하기 때문이다.

컴파일러가 못 잡는 이유는 **컴파일할 때는 DLL이 필요 없기 때문**이다.

| 단계 | 보는 것 | 확인하는 것 |
|---|---|---|
| 컴파일 | `capi.h` | 함수 이름과 인자 타입이 맞는가 |
| 링크 | `kiwi.lib` | 그 함수가 어느 DLL의 몇 번인가 |
| 실행 | `kiwi.dll` | 실제 기계어 |

`kiwi.lib` 는 **import library** 라고 부른다. 안에 코드가 없고 "이 함수는 kiwi.dll에 있다"는 표만 들어 있다. 그래서 링크는 멀쩡히 성공한다.

DLL을 찾는 순서는 정해져 있다. 실행 파일이 있는 폴더 → 시스템 폴더 → `PATH`. 그래서 **빌드 후 이벤트로 DLL을 복사**하는 것이 가장 확실하다.

이게 배포할 때 계속 따라다니는 문제다. E3에서 엔진을 제품에 넣을 때 "무엇을 같이 보내야 하는가"를 다시 다룬다.

</details>

**2.** 형태소 어휘가 53,216종이다. 데이터를 두 배로 늘리면 어휘도 두 배가 될까?

<details>
<summary>해답</summary>

**두 배가 되지는 않지만, 멈추지도 않는다.**

새 문서를 읽을 때마다 새 고유명사가 나온다. 사람 이름, 지명, 회사명, 외래어 표기. 이것들은 아무리 읽어도 바닥이 안 난다. 어휘 크기가 데이터 크기의 제곱근 언저리로 계속 자라는 이 현상을 **힙스의 법칙**(Heaps' law)이라고 부른다.

글자는 반대다. 3,780종에서 거의 멈춘다. A2에서 전체 코퍼스를 셌을 때 27,663종이었고(한자와 각국 문자를 다 포함해서), 5만 줄만 봐도 3,780종이 나온다. **닫힌 집합**이기 때문이다.

여기서 진짜 문제가 나온다. 어휘가 자라면 **모델이 못 본 낱말**(OOV, out-of-vocabulary)이 늘 생긴다. 형태소 모델은 처음 보는 고유명사를 만나면 아무것도 못 한다. 글자 모델은 적어도 글자 단위로는 쓸 수 있다.

그래서 현대 언어모델은 둘의 중간을 택한다. **자주 나오는 덩어리는 한 토큰으로, 드문 것은 조각으로** 쪼갠다. 어휘 크기를 3만~10만 정도로 **고정**해두고 데이터가 늘어도 안 늘어나게 만든다. 그게 BPE(Byte Pair Encoding)이고, 이 교재의 D파트에서 만든다.

- 글자 단위: 어휘 작음, 창이 짧음, OOV 없음
- 형태소 단위: 어휘 큼, 창이 김, OOV 있음
- BPE: 어휘 고정, 창이 중간, OOV 없음

BPE가 **바이트** 쌍을 합치는 방식인 것도 이 때문이다. 바이트는 256종뿐이라 무엇이 들어와도 쪼갤 수 있다. A1에서 UTF-16이 아니라 UTF-8을 고른 결정이 D파트에서 값을 하는 자리다.

</details>

**3.** `lib/Map`, `lib/GramMap`, `lib/Vocab` 을 C에서 하나로 합쳐보자. 어디까지 되는가?

<details>
<summary>해답</summary>

`void*` 키와 함수 포인터로 합칠 수 있다.

```c
typedef struct
{
    size_t KeySize;
    uint64_t (*Hash)(const void* Key);
    int (*Equal)(const void* A, const void* B);
    ...
} FGenericMap;
```

돌아가긴 한다. 값이 얼마인지가 문제다.

**간접 호출 비용.** 키 하나를 찾을 때마다 `Hash` 와 `Equal` 을 함수 포인터로 부른다. 컴파일러가 인라인할 수 없으므로 호출·복귀 비용이 그대로 남고, 분기 예측도 어려워진다. A4에서 잰 대로 이 루프는 6억 번 돈다. A7에서 `lib/Scan` 을 뺐을 때 30%를 잃었던 것과 같은 종류의 손해이고, 그때는 `/GL` 로 되찾았지만 **함수 포인터는 `/GL` 로도 못 되찾는다.**

**타입 안전성이 사라진다.** `void*` 로 받으면 `uint64_t` 키를 넣을 자리에 `uint32_t` 배열을 넣어도 컴파일러가 아무 말을 안 한다. 실행해봐야 안다.

**키가 값인지 포인터인지가 흐려진다.** `lib/Map` 은 키를 슬롯에 직접 담고, 나머지 둘은 아레나에 담는다. 일반화하려면 둘 다 지원해야 하고, 그러면 "키를 누가 소유하는가"가 호출자마다 달라진다.

**매크로로 찍어내는 길**도 있다. 리눅스 커널이나 `sglib` 같은 라이브러리가 쓰는 방식이다. 타입 안전성과 속도는 지키는데, 디버거가 매크로 안으로 못 들어가고 컴파일 오류가 수십 줄로 쏟아진다.

C++의 템플릿이 하는 일이 정확히 **매크로로 찍어내되 디버거와 오류 메시지가 멀쩡한 것**이다. B1에서 세 파일을 지우고 `std::unordered_map` 세 줄로 바꿔본 뒤, 코드량과 속도를 나란히 잰다.

</details>
