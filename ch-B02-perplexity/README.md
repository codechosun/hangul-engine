## 0. A8이 못 답한 질문

A8에서 할인율을 `3/4` 로 정했다. 근거는 "실무에서 흔히 쓰는 값"이었다. `1/2` 가 더 나은지 `7/8` 이 더 나은지는 **말할 수 없었다.**

잴 것이 없었기 때문이다. 가진 숫자는 둘이었는데,

- 베낀 비율 (낮을수록 좋다)
- 평균 문장 길이 (길수록 좋다... 아마?)

**서로 반대로 움직였다.** 할인을 올리면 베끼기는 줄고 문장은 짧아진다. 어느 쪽이 더 중요한지 아무도 안 알려준다.

이 장에서 그 자를 만든다. 그리고 A6과 A8이 남긴 질문에 **숫자로** 답한다.

```
[B2-4] 몇 글자를 보는 것이 좋은가
      차수      퍼플렉서티
        1        167.621
        2         39.313
        3         23.553
        4         21.131      <- 여기가 가장 좋다
        5         21.875
        6         23.549
```

**6그램이 3그램보다 나쁘다.** A6에서 "N을 올리면 문장이 좋아 보인다"고 했던 것이 눈속임이었다는 뜻이다.

## 1. 훈련과 평가를 나눈다

먼저 규칙을 하나 세워야 한다. **평가는 훈련에 안 쓴 글로 한다.**

지금까지 우리는 코퍼스 앞 20만 줄로 모델을 만들고 같은 20만 줄을 봤다. 그러면 A6에서 본 대로 **외운 것**이 그대로 점수가 된다. 6그램의 81%가 한 번짜리이므로, 훈련 데이터에서 재면 6그램이 압도적으로 좋아 보인다.

```c
#define TRAIN_LINES 200000   // 모델을 만드는 데 쓴다
#define TEST_LINES    5000   // 그 다음 5천 줄. 모델은 본 적이 없다
```

```
  평가 5000줄, 토큰 294968개 (훈련에 안 쓴 줄)
```

이 분리가 없으면 이 장의 모든 숫자가 무의미하다. 기계학습에서 가장 기본적이면서 가장 자주 어기는 규칙이다.

## 2. 확률을 곱하면 0이 된다

문장 하나의 확률은 글자마다의 확률을 전부 곱한 것이다.

```
P(문장) = P(첫글자 | BOS) × P(둘째 | 첫째) × ... × P(EOS | 마지막)
```

이걸 그대로 계산하면,

```
[B2-1] 확률을 그냥 곱하면

  글자 하나의 확률을 0.02 로 두고 400번 곱하면
    그냥 곱하기 = 0.000e+00  (191번째에서 0이 되었다)
    로그로 더하기 = -1564.809  (곧 0.000e+00)

  double 이 담을 수 있는 가장 작은 양수는 약 4.941e-324 다.
  0.02 를 191 번 곱하면 거기를 지나간다.
```

**191글자짜리 문장이면 `double` 이 항복한다.** `float` 이면 훨씬 일찍이다.

A0에서 부동소수점이 정확하지 않다는 것을 봤다. 여기서는 **아예 담지 못하는** 경우다. 이걸 **언더플로**(underflow)라고 한다.

해결은 하나뿐이다. **로그로 바꾼다.**

```
log P(문장) = log P(첫글자) + log P(둘째) + ... 
```

곱하기가 더하기가 되고, `-1564.809` 는 `double` 이 여유롭게 담는다. 지수부가 `10^±308` 까지 가는데 우리가 쓰는 건 세 자리 수다.

**언어모델이 로그를 쓰는 이유가 이것이다.** 수학적 우아함이 아니라 **`double` 이 못 담아서**다.

## 3. 퍼플렉서티

로그 확률의 합을 토큰 수로 나누면 "글자 하나당 평균 로그 확률"이 나온다. 부호를 뒤집고 지수를 씌우면 **퍼플렉서티**다.

```c
double Perplexity(const FScore& Score)
{
    return exp(-Score.LogProbSum / (double)Score.TokenCount);
}
```

읽는 법은 간단하다. **"모델이 다음 글자를 고를 때 평균 몇 개 중에서 헷갈리는가."**

| 퍼플렉서티 | 뜻 |
|---|---|
| 1 | 다음 글자를 정확히 안다 |
| 21 | 21개 중에서 고르는 것만큼 헷갈린다 |
| 5,534 | 어휘 전체에서 아무거나 찍는 것과 같다 |

우리 어휘가 5,534종이니, 아무것도 모르는 모델의 퍼플렉서티가 5,534다. 1그램이 167.6, 4그램이 21.1이다.

### 먼저 확률인지부터 확인한다

`BackoffProb` 가 진짜 확률을 돌려주는지 어떻게 아는가. **어휘 전체에 대해 더하면 1이어야 한다.**

```cpp
double Sum = 0.0;
for (uint32_t Token : Vocabulary)
{
    Sum += BackoffProb(&Backoff, Context, TOP_ORDER - 1, Token);
}
CHECK_NEAR(Sum, 1.0, 1e-9);
```

```
  어휘 = 5534 종
  BOS 다섯 개     확률의 합 = 1.000000000000
  " 대한민국"     확률의 합 = 1.000000000000
  "힣힣힣힣힣"    확률의 합 = 1.000000000000
```

**세 번째가 특히 값을 한다.** `힣힣힣힣힣` 은 어느 차수도 모르는 문맥이다. 백오프가 1그램까지 내려가고, 거기서도 합이 정확히 1이 나온다.

이 검사가 통과한다는 것은 **할인해서 떼어낸 몫과 짧은 문맥에 넘긴 몫이 정확히 맞아떨어진다**는 뜻이다. A8에서 분수로 계산한 것이 여기서 확인된다.

```
P(w|c) = max(DEN·count - NUM, 0)/(DEN·T) + (NUM·m)/(DEN·T) · P(w|c')
```

첫 항을 모든 `w` 에 대해 더하면 `(DEN·T - NUM·m)/(DEN·T)`, 둘째 항의 계수는 `NUM·m/(DEN·T)`, 그리고 `P(w|c')` 의 합은 (귀납적으로) 1이다. 더하면 1이다.

**뽑기(`BackoffPick`)와 확률 재기(`BackoffProb`)가 같은 분포를 말한다**는 것도 이 식에서 나온다. 뽑기는 난수로 한 칸을 고르는 일이고, 확률은 그 칸의 너비를 재는 일이다.

## 4. 0을 만나면 전부 무한대가 된다

```
[B2-3] 훈련에서 못 본 글자를 만나면

  받침 없이 잰 퍼플렉서티 = inf
  확률이 0 이었던 토큰     = 193 개 (전체의 0.0654%)
```

**29만 개 중 193개 때문에 전체가 무한대가 됐다.**

백오프는 문맥을 모를 때를 다 처리했는데도 이렇다. 백오프가 못 막는 것이 하나 있기 때문이다 — **글자 자체를 처음 보는 경우**(OOV). 1그램이 0을 주면 물러설 곳이 없다.

`log(0) = -무한대` 이고, 합에 무한대가 한 번 들어가면 **나머지 294,775개가 무슨 값이든** 합은 무한대다. 부동소수점에서 무한대는 전염성이 있다.

### 받침을 댄다

가장 단순한 처방은 바닥값을 정하는 것이다.

```c
if (Prob <= 0.0)
{
    Prob = Floor;   // 1e-6 같은 작은 값
}
```

```
            받침      퍼플렉서티
           1e-03         23.443
           1e-06         23.549
           1e-09         23.655
           1e-12         23.763
```

**받침 값이 결과를 바꾼다.** 0.0654%밖에 안 되는 토큰인데 퍼플렉서티를 1.4% 움직인다.

여기서 중요한 것은 "어느 받침이 옳은가"가 아니라 **"비교할 때는 고정해야 한다"** 는 것이다. 아래 모든 비교는 `1e-6` 으로 고정했다.

> 제대로 하려면 `<UNK>` 토큰을 어휘에 넣고 훈련 때 드문 글자를 거기로 몰아넣는다. 그러면 OOV에 진짜 확률이 생긴다. 여기서는 받침으로 넘어가되 **그 선택이 숫자를 얼마나 흔드는지 보여두는 쪽**을 택했다. 감춰진 임의의 상수가 결과를 좌우하는 것은 실제 논문에서도 흔한 일이다.

## 5. 드디어 답할 수 있다

### 몇 글자를 볼 것인가

```
      차수      퍼플렉서티   확률 0 토큰
        1        167.621           193
        2         39.313           193
        3         23.553           193
        4         21.131           193
        5         21.875           193
        6         23.549           193
```

**4그램이 최적이다.** 그리고 6그램은 3그램보다 나쁘다.

A6에서 N=6 모델이 쓴 문장이 제일 그럴듯해 보였던 것을 떠올려보자.

```
N=6   그는 여성에게도 자유가 없는 것 같은 그의 전역병 약 150 kb 내외이다.
```

읽히는 이유는 **훈련 데이터를 외웠기 때문**이었다. 그 문장의 15글자가 원문 그대로였다. 훈련에 안 쓴 글로 재면 그 능력이 도움이 안 된다 — 아니, **방해가 된다.** 긴 문맥은 대부분 처음 보는 것이고, 백오프로 물러서는 비용만 든다.

이게 **과적합**(overfitting)이다. 훈련 데이터에서의 성적과 처음 보는 데이터에서의 성적이 갈라지는 지점. 기계학습 전체를 관통하는 개념인데, 여기서는 **표를 세기만 했는데도** 나타난다.

> 데이터를 더 주면 최적 차수가 올라간다. 20만 줄이 아니라 전체 1,948만 줄로 훈련하면 5그램, 6그램이 유리해질 것이다. **모델의 크기는 데이터의 크기에 맞춰야 한다** — C파트 이후 계속 돌아올 주제다.

### 할인율은 얼마가 좋은가

```
              할인율      퍼플렉서티
         0/4 = 0.000        273.042
         1/4 = 0.250         42.748
         2/4 = 0.500         28.674
         5/8 = 0.625         25.547
         3/4 = 0.750         23.549
         7/8 = 0.875         22.479
       15/16 = 0.938         22.438
       31/32 = 0.969         22.718
```

**할인이 0이면 재앙이다.** 273.042 — 1그램(167.6)보다도 나쁘다.

이유는 A8에서 본 그대로다. 할인이 0이면 백오프는 "문맥을 못 찾았을 때"만 동작하는데, 한 번밖에 안 본 문맥에서 **한 글자에 100%를 준다.** 평가 데이터에서 그 글자가 아닌 게 나오면 확률이 거의 0이 되고, 로그가 크게 음수가 된다.

**한 번 본 것을 확신하는 대가**가 273 대 22다. 12배다.

0.938 근처가 바닥이고 0.969에서 다시 올라간다. A8에서 고른 0.75는 **나쁘지 않았지만 최선도 아니었다.** 이제 근거를 갖고 고를 수 있다.

### 그런데 퍼플렉서티도 만능은 아니다

A8에서 잰 것과 나란히 놓아보자.

| 할인율 | 베낀 비율 | 평균 문장 길이 | 퍼플렉서티 |
|---|---|---|---|
| 0 | 69.9% | 49.9글자 | 273.042 |
| 0.75 | 47.4% | 33.1글자 | 23.549 |
| 0.938 | 더 낮을 것 | 더 짧을 것 | **22.438** |

퍼플렉서티는 "문장이 짧아지는 것"을 **벌점으로 치지 않는다.** 글자 하나하나를 얼마나 잘 맞히는지만 본다. 할인을 극단으로 올려 거의 1그램이 되면 퍼플렉서티도 나빠지긴 하지만, 그 전까지는 "짧고 안전한 문장"을 만드는 쪽이 유리하다.

실제 언어모델 평가가 퍼플렉서티만으로 안 끝나는 이유가 이것이다. **자 하나로는 부족하다.** 다만 자가 **하나도 없는 것**보다는 압도적으로 낫다.

## 6. 로그로 바꾸면 더하기가 어려워진다

로그 공간으로 옮기면 곱하기는 쉬워지고 **더하기가 어려워진다.**

```
log(a) 와 log(b) 를 아는데 log(a + b) 를 구하려면?
```

그냥 되돌리면 애써 로그로 바꾼 의미가 없다.

```
  log a = log b = -800 일 때 log(a+b) 는 -800 + log 2 = -799.306853 여야 한다
    exp 로 되돌려 더하면 = -inf   <- exp(-800) 이 0 이라 못 구한다
    LogAdd 로 구하면     = -799.306853
```

요령은 **큰 쪽을 뽑아내는 것**이다.

```
log(e^A + e^B) = A + log(1 + e^(B-A))        (A ≥ B)
```

`B - A ≤ 0` 이므로 `e^(B-A)` 는 1을 넘지 않는다. **넘치지도 사라지지도 않는다.**

```c
double LogAdd(double LogA, double LogB)
{
    if (LogA == -INFINITY) return LogB;
    if (LogB == -INFINITY) return LogA;

    double Big = (LogA > LogB) ? LogA : LogB;
    double Small = (LogA > LogB) ? LogB : LogA;

    return Big + log1p(exp(Small - Big));
}
```

`log1p(x)` 는 `log(1 + x)` 인데, `x` 가 아주 작을 때를 위해 따로 있는 함수다. `x = 1e-20` 이면 `1 + x` 는 `double` 에서 정확히 `1.0` 이 되어 `log` 가 0을 돌려주지만, `log1p` 는 `1e-20` 을 제대로 돌려준다.

여러 개를 더하는 `LogSumExp` 도 같은 요령이다. 최댓값을 빼고 더한 뒤 다시 더한다.

손으로 확인되는 값들로 검사를 건다.

```c
CHECK_NEAR(LogAdd(log(1.0), log(1.0)), log(2.0), 1e-12);   // 1+1 = 2
CHECK_NEAR(LogAdd(log(3.0), log(5.0)), log(8.0), 1e-12);   // 3+5 = 8
CHECK_NEAR(LogAdd(log(7.0), -INFINITY), log(7.0), 1e-12);  // 7+0 = 7
```

> **C파트에서 이 코드를 그대로 쓴다.** softmax는 `exp(x_i) / Σ exp(x_j)` 인데, `x` 가 조금만 커도 `exp` 가 넘친다. 최댓값을 먼저 빼면 사라진다. D파트 어텐션의 softmax도 같다. **같은 도구를 세 번 만들지 않으려고 여기서 `lib/LogMath` 로 빼두었다.**

## 정리

만든 것.

| 것 | 내용 |
|---|---|
| `BackoffProb` | 뽑기가 아니라 확률을 재는 함수. `BackoffPick` 과 같은 분포 |
| `BackoffSetDiscount` | 할인율을 실행 중에 바꾼다 (실험하려고) |
| `lib/LogMath` | `LogAdd`, `LogSumExp`. C·D파트에서 다시 쓴다 |
| 훈련/평가 분리 | 앞 20만 줄로 훈련, 그 다음 5천 줄로 평가 |

답한 것.

| 질문 | 답 | 남긴 장 |
|---|---|---|
| 몇 글자를 볼 것인가 | **4그램** (6그램은 3그램보다 나쁘다) | A6 |
| 할인율은 얼마인가 | **약 0.94** (0이면 12배 나빠진다) | A8 |

알아둘 것.

- **평가는 훈련에 안 쓴 글로 한다.** 이게 없으면 나머지 숫자가 전부 거짓말이다
- **확률을 191번 곱하면 `double` 이 0이 된다.** 언어모델이 로그를 쓰는 진짜 이유
- **확률의 합이 1인지부터 확인한다.** 분포가 아닌 것으로 퍼플렉서티를 재면 의미가 없다
- **무한대는 전염된다.** 0.065%의 토큰이 전체를 무한대로 만든다
- **큰 쪽을 뽑아내면** 로그 공간의 더하기가 안전해진다
- **자 하나로는 부족하다.** 퍼플렉서티는 문장이 짧아지는 것을 벌하지 않는다

쓴 문법.

- `std::vector<std::vector<uint32_t>>` — 중첩 컨테이너
- 구조체 멤버 기본값 초기화 (`double LogProbSum = 0.0;`) — C++11
- `std::isinf`, `log1p`, `INFINITY`
- 값으로 구조체 돌려주기 (`FScore ScoreAll(...)`) — 복사가 걱정되면 D1의 이동 시맨틱으로

## 연습문제

**1.** 평가를 **훈련 데이터**로 하면 차수별 퍼플렉서티가 어떻게 바뀌는가?

<details>
<summary>해답</summary>

`TestLines` 를 앞 5천 줄(= 훈련에 쓴 줄)로 바꿔 재면 **순서가 뒤집힌다.** 차수가 올라갈수록 계속 좋아지고, 6그램이 제일 낮게 나온다.

이유는 A6에서 잰 그대로다. 6그램의 81%가 훈련 데이터에 딱 한 번 나온 것이고, 그 문맥에서 다음 글자는 **확률 거의 1**이다. 훈련 데이터를 다시 읽으면 그 예측이 전부 맞는다.

**모델이 좋아진 게 아니라 답을 외운 것**이다.

이게 과적합의 정의이고, 훈련/평가 분리가 기계학습의 첫 규칙인 이유다. 이 규칙을 어긴 채로 "우리 모델이 최고 성능"이라고 쓰는 논문이 지금도 나온다.

한 걸음 더 가면 세 번째 뭉치가 필요해진다. 할인율을 평가 데이터로 고르고 나면, 그 평가 데이터는 더 이상 "처음 보는 글"이 아니다 — 이미 그걸 보고 값을 골랐으니까. 그래서 보통은 셋으로 나눈다.

- **훈련**(train) — 표를 센다
- **검증**(validation) — 할인율·차수 같은 것을 고른다
- **시험**(test) — 마지막에 딱 한 번 쓴다

이 장에서는 둘로만 나눴다. B2-5에서 할인율을 고르는 데 쓴 5천 줄은 엄밀히는 검증 데이터다.

</details>

**2.** 받침(floor) 대신 `<UNK>` 토큰을 쓰면 어떻게 다른가?

<details>
<summary>해답</summary>

받침은 **확률 분포를 망가뜨린다.** 없던 글자에 `1e-6` 을 주면 그 문맥의 확률 합이 1을 넘는다. 퍼플렉서티 숫자는 나오지만 그게 확률론적으로 무슨 뜻인지는 애매해진다.

`<UNK>` 는 제대로 된 방법이다. 훈련할 때 이렇게 한다.

1. 훈련 데이터에서 **드문 글자**(예: 한 번만 나온 것)를 고른다
2. 그것들을 전부 `<UNK>` 라는 토큰 하나로 바꾼다
3. 그 상태로 표를 센다

그러면 `<UNK>` 가 어휘의 정식 구성원이 되고 **진짜 확률**을 갖는다. 평가할 때 처음 보는 글자를 만나면 `<UNK>` 로 바꿔 넣으면 된다. 확률 합은 여전히 1이다.

대가가 있다. 드문 글자를 다 한 덩어리로 뭉쳤으므로 **그것들을 구별하는 능력을 버린 것**이다. A6에서 잰 대로 20만 줄에 5,534종이 있고 그중 1,155종이 한 번만 나왔다. 그 1,155종을 버리는 셈이다.

그리고 **비교가 불공정해진다.** 어휘를 줄이면 퍼플렉서티는 자동으로 내려간다. 5,534종 중에서 고르는 것보다 4,379종 중에서 고르는 게 쉬우니까. **어휘가 다른 두 모델의 퍼플렉서티는 비교할 수 없다.**

이 문제가 D파트에서 다시 나온다. BPE로 토큰을 바꾸면 어휘가 통째로 달라지므로, 글자 모델과 BPE 모델의 퍼플렉서티를 나란히 놓을 수 없다. 그때는 **글자당 비트 수**(bits per character)로 환산해서 비교한다.

</details>

**3.** 퍼플렉서티 21은 좋은 숫자인가?

<details>
<summary>해답</summary>

**비교 대상이 있어야 말할 수 있다.** 절대적인 좋고 나쁨이 없다.

세 가지 기준선을 놓아보자.

| 모델 | 퍼플렉서티 | 뜻 |
|---|---|---|
| 아무거나 찍기 | 5,534 | 어휘 크기 그대로 |
| 글자 빈도만 (1그램) | 167.6 | 공백이 20%라는 것만 안다 |
| 4그램 백오프 | **21.1** | 앞 세 글자를 본다 |
| 완벽한 모델 | 1.0 | 다음 글자를 정확히 안다 |

5,534에서 21까지 왔다. 그런데 21은 **여전히 21개 중에서 헷갈린다**는 뜻이다.

비트로 환산하면 감이 온다. `log2(21.1) = 4.4비트`. 한국어 글자 하나를 적는 데 4.4비트가 필요하다는 뜻이고, UTF-8로 24비트를 쓰는 것보다는 훨씬 낫지만 아직 멀다.

참고로 현대 언어모델은 영어 기준 글자당 **1비트 아래**로 내려간다. 우리 모델과의 차이가 **3배 이상**이다. 그 차이를 메우는 것이 C파트부터 D파트까지의 여정이다.

그리고 이 숫자를 볼 때마다 기억할 것이 하나 있다. **어휘가 다르면 비교할 수 없다.** 영어 글자는 100종 남짓이고 우리는 5,534종이다. 4.4비트와 1비트를 그냥 나란히 놓는 것은 정확한 비교가 아니다. 같은 데이터, 같은 토큰화에서 잰 숫자끼리만 비교한다.

</details>

## 다음 장

**B3. 코사인 유사도.**

자를 하나 더 만든다. 이번엔 **두 벡터가 얼마나 닮았는지** 재는 자다.

지금 우리 모델에서 `가` 와 `나` 는 아무 관계가 없는 번호 두 개다. 44032번과 45208번. 번호가 가깝다고 뜻이 가까운 것도 아니다.

C파트에서 만들 뉴럴 모델은 글자마다 **벡터**를 하나씩 갖는다. 비슷한 자리에 나오는 글자는 비슷한 벡터를 갖게 되고, 그 "비슷함"을 재는 것이 코사인 유사도다. 그게 바로 **임베딩**이다.

C++ 교재 `3.3` 의 연산자 오버로딩이 여기서 처음 쓰인다.

```cpp
Real Similarity = (A * B) / (A.Length() * B.Length());
```

`A * B` 를 내적으로 정의하면 수식이 코드가 된다. D1의 `Tensor` 클래스로 가는 예비 훈련이기도 하다.

그리고 검증이 재미있다. **자기 자신과의 유사도는 정확히 1.0이어야 한다.** 부동소수점에서 이게 생각만큼 쉽지 않다는 것을 그 장에서 본다.
