## 0. 번호와 뜻

지금 우리 모델에서 `을` 과 `를` 은 아무 관계가 없는 번호 둘이다.

```
을 = U+C744 = 51012
를 = U+B97C = 47484
```

번호가 3,528 떨어져 있다. `을` 과 `읁`(U+C741)은 3 떨어져 있다. 번호의 거리는 뜻과 아무 상관이 없다.

그런데 우리는 이미 **뜻에 가까운 것**을 갖고 있다. A5에서 만든 표다.

```
'을' 다음에 온 것   공백(88%), 등(1%), 위(0.5%), ...
'를' 다음에 온 것   공백(89%), 통(0.9%), 위(0.5%), ...
'공백' 다음에 온 것  1(3%), 2(2.5%), 대(1%), ...
```

글자 하나마다 **"다음에 무엇이 얼마나 왔는가"** 를 늘어놓으면 5,534차원 벡터가 된다. `을` 과 `를` 의 벡터는 거의 같고, `공백` 의 벡터는 전혀 다르다.

**두 벡터가 얼마나 닮았는지 재는 자**가 이 장의 주제다. 그리고 이게 그대로 C파트의 **임베딩**으로 이어진다.

```
[B3-4] 유클리드 거리로 재면 어떻게 되는가

  두 글자               코사인     유클리드 거리
  '을' 과 '를'         1.0000             25885
  '을' 과 공백         0.0291            163114
```

## 1. 첫 C++ 클래스

```cpp
class FVector
{
public:
    FVector() = default;
    explicit FVector(size_t Size) : Values(Size, Real(0)) {}

    size_t Size() const { return Values.size(); }

    Real& operator[](size_t Index) { return Values[Index]; }
    const Real& operator[](size_t Index) const { return Values[Index]; }

    FVector& operator+=(const FVector& Other);
    FVector& operator*=(Real Scale);

    Real LengthSquared() const;
    Real Length() const;
    FVector Normalized() const;

private:
    std::vector<Real> Values;
};
```

C++ 교재 `3.2` 와 `3.3` 이 한꺼번에 동원된다. 짚을 것 셋.

### `explicit` 를 붙이는 이유

```cpp
explicit FVector(size_t Size);
```

없으면 이런 일이 생긴다.

```cpp
void Process(const FVector& V);
Process(100);        // FVector(100) 이 슬쩍 만들어진다
```

`100` 을 넘겼는데 컴파일러가 "100차원 영벡터"를 만들어 넘긴다. **의도했을 리가 없다.** `explicit` 는 "이 생성자는 명시적으로 불러야 한다"는 뜻이고, 인자가 하나인 생성자에는 기본적으로 붙인다고 생각하는 편이 낫다.

### `operator[]` 가 둘인 이유

```cpp
Real& operator[](size_t Index);              // 고칠 수 있다
const Real& operator[](size_t Index) const;  // 읽기만 한다
```

`const FVector&` 로 받은 객체에서는 두 번째만 부를 수 있다. 그래서 실수로 고치는 코드가 **컴파일 단계에서** 막힌다.

C에서는 `const FMap*` 를 받아도 멤버 포인터로 안을 고칠 수 있었다. `const` 가 한 겹밖에 안 걸린다. C++은 메서드 자체에 `const` 를 걸 수 있어서 한 겹 더 있다.

### 누적은 `double` 로

```cpp
Real FVector::LengthSquared() const
{
    double Sum = 0.0;   // Real 이 float 이어도 여기는 double

    for (size_t i = 0; i < Values.size(); i++)
    {
        Sum += (double)Values[i] * (double)Values[i];
    }

    return (Real)Sum;
}
```

5,534개를 `float` 에 더하면 뒤쪽 작은 값이 앞쪽 큰 합에 **묻혀 사라진다.** `float` 의 유효숫자가 7자리인데, 합이 `1e7` 을 넘으면 1 이하의 값을 더해도 아무 일이 안 일어난다.

**담는 것은 `float`, 더하는 것은 `double`.** 메모리는 절반만 쓰면서 정확도는 지킨다. C파트의 행렬 곱셈에서 같은 규칙을 다시 쓴다.

## 2. 수식이 코드가 된다

연산자를 오버로딩하면 이렇게 쓸 수 있다.

```cpp
Real Similarity = (A * B) / (A.Length() * B.Length());
```

```
[B3-2] 연산자 오버로딩

  A = (3, 0, 4), B = (1, 0, 0)
    A.Length()          = 5.000000  (손계산 5)
    A * B               = 3.000000  (손계산 3)
    CosineSimilarity    = 0.600000  (손계산 0.6)
    (A + B) * B         = 4.000000  (손계산 4)
    (2 * A) * B         = 6.000000  (손계산 6)
    EuclideanDistance   = 4.472136  (손계산 sqrt(20) = 4.472136)
```

전부 손으로 확인되는 값이다. `(3,0,4)` 의 길이는 3-4-5 직각삼각형이라 5, 내적은 `3·1 = 3`, 코사인은 `3/(5·1) = 0.6`.

### 값으로 받는 이항 연산자

```cpp
FVector operator+(FVector Left, const FVector& Right)   // 왼쪽은 값
{
    Left += Right;
    return Left;
}
```

왼쪽을 **값으로** 받는 것이 관용이다. 이유가 둘이다.

- 함수 안에서 마음대로 고칠 수 있다 (어차피 내 복사본이다)
- 부르는 쪽이 **임시 객체**를 넘기면 복사가 아예 안 일어난다

`A + B + C` 를 쓰면 `A + B` 의 결과가 임시 객체이고, 그게 다음 `+` 의 `Left` 로 **옮겨진다**(move). 복사가 한 번도 안 일어난다. 이게 **이동 시맨틱**(C++ 교재 `11`)이고, D1의 `FTensor` 에서 본격적으로 다룬다.

C로 같은 것을 만들면 이렇게 된다.

```c
FVector Temp1 = VectorAdd(A, B);      // 누가 free 하는가?
FVector Temp2 = VectorAdd(Temp1, C);  // Temp1 은?
VectorFree(&Temp1);                   // 손으로 챙긴다
```

### `operator*` 를 내적으로 쓴 것은 옳은가

```cpp
Real operator*(const FVector& Left, const FVector& Right);   // 내적
FVector operator*(FVector Left, Real Scale);                 // 스칼라배
```

같은 기호가 두 가지 일을 한다. 그리고 **결과 타입이 다르다** — 하나는 `Real`, 하나는 `FVector`.

논쟁거리다. 편을 나눠 보면,

| 찬성 | 반대 |
|---|---|
| 수학 표기(`a·b`)와 닮았다 | 어느 쪽인지 눈으로 바로 안 보인다 |
| 수식이 짧아진다 | `A * B * C` 가 컴파일은 되는데 뜻이 이상하다 |
| | 원소별 곱(`A ⊙ B`)을 쓰고 싶을 때 자리가 없다 |

마지막이 결정적이다. D파트에서 텐서를 다룰 때는 **원소별 곱**이 훨씬 자주 나온다. 그래서 `FTensor` 에서는 `operator*` 를 **원소별 곱**으로 두고 내적은 `Dot(A, B)` 라는 이름을 준다.

**여기서는 일부러 다르게 했다.** 연산자 오버로딩이 무엇을 할 수 있는지 보여주고, 동시에 **그 선택이 나중에 발목을 잡을 수 있다**는 것도 보여주려고. 라이브러리를 설계할 때 연산자를 고르는 일은 되돌리기가 어렵다.

## 3. 자기 자신과의 유사도는 1.0인가

당연히 1.0이어야 한다. 같은 방향이니까 각도가 0이고 코사인이 1이다.

**500개 중 256개만 정확히 1.0이 나온다.**

```
[B3-1] 자기 자신과의 유사도

  500개 글자 각각을 자기 자신과 비교했다 (길이가 0 인 벡터 1개는 뺐다)

  방식                                  정확히 1.0       최대 오차
  float 누적, 제곱근 두 번                    256        1.192e-07
  double 누적, 제곱근 한 번                   499        0.000e+00
```

### 순진한 방식이 하는 일

```cpp
float Dot = 0.0f, LenA = 0.0f, LenB = 0.0f;
for (...)
{
    Dot += A[i] * B[i];
    LenA += A[i] * A[i];
    LenB += B[i] * B[i];
}
return Dot / (std::sqrt(LenA) * std::sqrt(LenB));
```

`A == B` 일 때 `Dot`, `LenA`, `LenB` 는 **같은 값을 같은 순서로 더한 것**이라 셋이 정확히 같다. 그러면 `Dot / (sqrt(L) * sqrt(L))` 인데,

**`sqrt(L) * sqrt(L)` 가 `L` 이 아니다.** 제곱근이 반올림되고, 그 반올림된 값을 제곱하면 원래로 안 돌아온다.

우리 방식은 제곱근을 한 번만 쓴다.

```cpp
return (Real)(Dot / std::sqrt(AA * BB));
```

`A == B` 면 `AA == BB == Dot` 이므로 `sqrt(AA * BB) = sqrt(Dot²) = Dot` 이고, `Dot / Dot = 1.0` 이 **정확히** 나온다. 499개 전부 맞는다.

> **연산을 하나 줄이면 반올림이 끼어들 자리도 하나 준다.** 이 규칙은 C파트의 역전파에서 훨씬 중요해진다. 수치미분과 해석미분을 비교할 때 `1e-5` 수준의 차이로 통과·불통을 가르는데, 불필요한 연산 하나가 그 경계를 넘길 수 있다.

그래도 **"정확히 1.0"을 요구하면 안 된다.**

```cpp
CHECK_NEAR(CosineSimilarity(V, V), 1.0, 1e-6);
```

지금은 우연히 맞지만, 벡터의 값이 달라지거나 차원이 커지면 안 맞을 수 있다. **부동소수점은 `==` 로 비교하지 않는다.** A0에서 세운 규칙이다.

### 길이가 0인 벡터 하나

500개 중 하나는 벡터가 통째로 0이다. 그래서 자기 자신과의 유사도도 1이 아니다 — **정의되지 않는다.** 각도를 말하려면 방향이 있어야 하는데, 영벡터에는 방향이 없다.

무엇인가? **EOS다.** EOS는 문장의 끝이므로 **그 다음에 오는 것이 없다.** "다음에 무엇이 왔는가" 벡터가 전부 0인 게 당연하다.

```c
CHECK(EmptyCount == 1);
```

데이터가 말이 되는지 확인하는 검사 하나가 이렇게 생긴다. 만약 0인 벡터가 둘 이상이면 표를 잘못 만든 것이다.

`CosineSimilarity` 는 이 경우 0을 돌려준다. `NaN` 을 돌려주는 구현도 많은데, **`NaN` 은 한 번 생기면 전파되고 `==` 비교가 전부 거짓이 되어 디버깅이 지옥이 된다.** B2에서 무한대가 퍼플렉서티를 통째로 무한대로 만든 것과 같은 이야기다.

## 4. 실제로 무엇이 비슷한가

```
[B3-3] 다음에 오는 글자가 비슷하면 비슷한 글자인가

  '을'    → 및(1.00000) 를(0.99998) 은(0.99996) ,(0.99993) 될(0.99984)
  '는'    → 큰(0.99896) 은(0.99894) 을(0.99892) 및(0.99892) 를(0.99890)
  '1'     → 9(0.75206) 8(0.56325) 7(0.43815) 4(0.41088) 6(0.40247)
  '한'    → 난(0.84747) 인(0.84302) 른(0.82376) 이(0.81829) 든(0.80886)
  '.'     → )(0.96678) 망(0.83633) 년(0.83022) 일(0.79630) 록(0.79488)
```

**훈련을 한 적이 없다.** 그냥 센 것이다.

- **`을` 과 `를`, `은`, `및`** — 전부 뒤에 공백이 오는 것들이다. 조사와 접속부사
- **`1` 과 숫자들** — 숫자 뒤에는 숫자, 년, 월, 쉼표가 온다
- **`한` 과 `난`, `인`, `른`, `든`** — 종성이 `ㄴ` 인 글자들이다. 뒤따르는 조사·어미가 받침에 따라 달라지기 때문이다
- **`.` 과 `)`** — 둘 다 무언가를 닫는다

네 번째 줄이 특히 흥미롭다. 모델은 한글의 **종성**이라는 개념을 모른다. A1에서 `11,172 = 19 × 21 × 28` 을 계산했지만 그 구조를 코드에 넣은 적은 없다. 그런데 **뒤에 오는 것이 비슷하다는 이유만으로** 받침이 같은 글자들이 한데 모였다.

> **분포 가설**(distributional hypothesis) 이라고 부른다. "같은 자리에 나타나는 것들은 비슷하다." 1950년대 언어학에서 나온 생각이고, word2vec부터 GPT까지 모든 임베딩의 바탕이다. 우리는 그걸 **바이그램 표 하나로** 확인했다.

### 왜 코사인인가

```
  두 글자               코사인     유클리드 거리
  '을' 과 '를'         1.0000             25885
  '을' 과 공백         0.0291            163114
  '를' 과 공백         0.0289            155175
```

유클리드 거리로는 `을`-`를` 이 25,885이고 `을`-공백이 163,114다. 순서는 맞다. 그런데 **이 숫자가 무슨 뜻인지 말할 수가 없다.** 25,885는 가까운 건가 먼 건가?

코사인은 **-1에서 1 사이**로 고정이다. 그리고 **크기에 휘둘리지 않는다.**

```cpp
CHECK_NEAR(CosineSimilarity(A, Real(7) * B), CosineSimilarity(A, B), 1e-6);
```

`를` 은 `을` 보다 자주 나온다. 벡터의 모든 성분이 그만큼 크다. 유클리드 거리는 그 차이를 **거리로 착각**하지만, 코사인은 방향만 보므로 영향받지 않는다.

**빈도가 다른 것들을 비교할 때는 방향을 봐야 한다.** 이게 텍스트 처리에서 코사인이 기본값인 이유다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Vector.hpp` · `.cpp` | 실수 벡터. 연산자 오버로딩, 코사인 유사도 |

`.hpp` 확장자를 쓴 이유 — `lib/*.h` 는 `extern "C"` 창구를 내서 C에서도 읽히지만, 이 파일은 클래스와 연산자를 쓰므로 **C++ 전용**이다. 확장자로 구분한다.

알아둘 것.

- **인자가 하나인 생성자에는 `explicit` 를 붙인다.** 안 그러면 몰래 변환된다
- **`operator[]` 는 `const` 버전을 같이 만든다.** 실수를 컴파일 단계에서 막는다
- **담는 것은 `float`, 더하는 것은 `double`**
- **`sqrt(L) * sqrt(L)` 는 `L` 이 아니다.** 연산을 줄이면 오차도 준다
- **부동소수점은 `==` 로 비교하지 않는다.** 자기 자신과의 코사인도 1.0이 아닐 수 있다
- **영벡터에는 방향이 없다.** `NaN` 대신 0을 돌려주고, 부르는 쪽이 걸러낸다
- **분포가 비슷하면 비슷하다.** 훈련 없이도 임베딩 비슷한 것이 나온다
- **코사인은 크기에 휘둘리지 않는다.** 빈도가 다른 것들을 비교할 때 필수

쓴 문법.

- 클래스, 생성자, `explicit` — C++ 교재 `3.2`
- 연산자 오버로딩 (`+=`, `[]`, `*`) — C++ 교재 `3.3`
- 멤버 함수의 `const` 한정
- 람다를 받는 `std::sort` — C++ 교재 `8.5`

## 연습문제

**1.** `Real` 을 `double` 로 바꿔(`USE_DOUBLE` 정의) 다시 돌려보자. 무엇이 달라지는가?

<details>
<summary>해답</summary>

**B3-3의 순위가 갈라진다.**

`float` 로 돌리면 `'을'` 의 상위 다섯 개가 `1.00000, 0.99998, 0.99996, 0.99993, 0.99984` 로 거의 붙어 있다. `float` 의 유효숫자가 7자리라 이 근처에서 **구별할 수 있는 값이 몇 개 없다.**

1.0 근처에서 `float` 이 표현할 수 있는 값의 간격은 약 `1.2e-7` 이다. 0.9999와 1.0 사이에 800개쯤밖에 없다. `double` 로 바꾸면 그 간격이 `2.2e-16` 이 되어 순위가 또렷해진다.

메모리는 두 배가 된다. 500 × 5,534 × 8바이트 = 22MB. 이 장에서는 문제가 안 되지만 C파트의 가중치 행렬에서는 결정적이다.

**그래서 `Real` 이라는 별칭을 둔 것이다.** 평소에는 `float` 으로 빠르게 돌리고, 정밀도가 필요한 순간에 한 줄로 바꾼다. C2의 gradcheck가 정확히 그 순간이다.

</details>

**2.** 벡터를 만들 때 횟수 대신 **확률**을 쓰면 (각 행을 합이 1이 되게 나누면) 코사인 유사도가 달라지는가?

<details>
<summary>해답</summary>

**안 달라진다.** 각 행을 그 행의 합으로 나누는 것은 벡터에 **양수 상수를 곱하는 것**이고, 코사인은 크기에 영향받지 않는다.

```cpp
CHECK_NEAR(CosineSimilarity(A, Real(7) * B), CosineSimilarity(A, B), 1e-6);
```

이 검사가 그걸 말한다.

그런데 **다른 정규화는 결과를 바꾼다.**

- **각 성분에 `log(1 + count)` 를 씌우면** 달라진다. 큰 값이 눌리면서 드문 조합의 목소리가 커진다
- **TF-IDF** 처럼 "어디에나 나오는 성분"의 가중치를 낮추면 크게 달라진다. 지금 우리 벡터는 **공백 성분이 압도적**이라 거의 모든 글자가 "공백 다음에 온다"는 이유로 비슷해 보인다
- **PMI**(점별 상호정보량)를 쓰면 또 다르다. word2vec이 암묵적으로 계산하는 것이 이것이라는 사실이 2014년에 밝혀졌다

`'을'` 의 상위 목록이 전부 0.999인 것이 그 증거다. 조사들이 **정말로** 비슷한 것도 있지만, 다들 "뒤에 공백이 온다"는 한 가지 성분에 지배당한 탓도 크다. 공백 성분을 빼고 다시 재보면 순위가 훨씬 흥미로워진다.

**무엇을 세느냐보다 어떻게 정규화하느냐가 결과를 더 바꾼다.** 임베딩을 다루다 보면 계속 만나는 이야기다.

</details>

**3.** `FVector` 에 복사 생성자와 소멸자를 직접 쓰지 않았다. 왜 안 써도 되는가?

<details>
<summary>해답</summary>

**멤버가 `std::vector<Real>` 하나뿐이고, 그게 알아서 하기 때문이다.**

컴파일러가 자동으로 만들어주는 것들이 있다.

| 것 | 자동으로 하는 일 |
|---|---|
| 복사 생성자 | 멤버를 하나씩 복사 → `Values` 가 자기 복사 생성자를 부른다 |
| 복사 대입 | 멤버를 하나씩 대입 |
| 이동 생성자 | 멤버를 하나씩 이동 → `Values` 가 버퍼 소유권만 넘긴다 |
| 소멸자 | 멤버를 거꾸로 소멸 → `Values` 가 `free` 한다 |

`std::vector` 가 이미 RAII를 지키고 있으므로, 그걸 멤버로 가진 `FVector` 도 **공짜로** RAII를 지킨다.

이걸 **"0의 규칙"**(Rule of Zero)이라고 부른다. **자원을 직접 들고 있지 않으면 특수 멤버 함수를 아무것도 쓰지 마라.**

반대로 `Real* Values` 와 `size_t Count` 를 직접 들고 있었다면 다섯 개를 전부 써야 한다 — 복사 생성자, 복사 대입, 이동 생성자, 이동 대입, 소멸자. 그게 **"5의 규칙"**(Rule of Five)이고, 하나라도 빠뜨리면 이중 해제나 누수가 난다.

A파트에서 `lib/Map` 을 만들 때 `MapInit`/`MapFree` 짝을 손으로 맞춘 것이 5의 규칙을 C로 흉내낸 것이다. 다만 **복사하면 어떻게 되는지**는 아예 정의하지 않았다. `FMap A = B;` 라고 쓰면 포인터가 그대로 복사되고 둘 다 `MapFree` 를 부르면 이중 해제로 죽는다. C에서는 "그렇게 쓰지 마세요"라고 문서에 적는 수밖에 없다.

D1의 `FTensor` 는 큰 버퍼를 직접 관리해야 해서 5의 규칙 쪽으로 간다. 거기서 이동 시맨틱을 제대로 다룬다.

</details>

## 다음 장

**C1. 뉴런과 순전파.**

B파트가 끝났다. **자를 세 개** 만들었다.

| 자 | 재는 것 |
|---|---|
| `CHECK` / `CHECK_NEAR` (A0) | 코드가 맞는가 |
| 퍼플렉서티 (B2) | 모델이 좋은가 |
| 코사인 유사도 (B3) | 두 벡터가 닮았는가 |

이제 모델을 바꾼다. 지금까지는 **셌다.** C파트부터는 **배운다.**

차이가 무엇인가. N-그램은 `대한민국의 헌` 다음에 `법` 이 온다는 것을 **그 조합을 본 적이 있어서** 안다. 본 적 없는 조합은 모른다. 뉴럴 모델은 글자마다 벡터를 두고 그 벡터들의 **계산 결과**로 답한다. 본 적 없는 조합이어도, 비슷한 벡터를 가진 글자들에서 배운 것이 적용된다.

C1에서는 가장 작은 조각부터 만든다. **입력 벡터에 가중치를 곱해 더하고, 비선형 함수를 한 번 통과시킨다.** 그게 뉴런 하나다. 손으로 계산할 수 있는 크기에서 시작해 `CHECK_NEAR` 로 맞춰본다.

`FVector` 가 여기서 바로 쓰인다. 그리고 곧 답답해진다 — 가중치는 벡터가 아니라 **행렬**이기 때문이다. D1의 `FTensor` 가 필요해지는 이유가 C1에서 이미 보인다.
