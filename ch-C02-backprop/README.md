## 0. 이 장이 특별한 이유

> **추론 버그는 출력이 쓰레기가 되어 명백하다.**
> **훈련 버그는 손실이 *조금* 내려간다. 조용히 틀린다.**

A0에서 "모델보다 자를 먼저 만든다"고 했던 그 이유가 여기서 정점에 달한다.

이 장에서 일부러 버그를 하나 심는다. `tanh` 의 미분을 `1 - y²` 대신 `1 - y` 로 쓰는 것이다. 완전히 틀린 식이다. 그런데,

**손실은 내려간다.** 방향이 대충 맞기 때문이다. 그래프만 보면 "좀 느리게 배우는 모델"로 보인다.

```
[C2-5] 버그를 하나 심으면 잡히는가

  tanh 의 미분을 (1 - y^2) 대신 (1 - y) 로 쓰면
    W1 의 최대 상대 오차 = 6.512e-01
    가장 어긋난 자리 5 번: 역전파 -0.365712970, 수치 -0.127553940
```

**gradcheck 는 즉시 잡는다.** 상대 오차 0.65 — 값이 3배 가까이 틀렸다.

이 도구를 여기서 만들어두면 D파트 끝까지 쓴다. 없으면 트랜스포머 디버깅은 사실상 불가능하다.

## 1. 흔들어 보면 기울기를 알 수 있다

미분의 정의는 이것이다.

```
f'(x) = lim (f(x+h) - f(x)) / h
        h→0
```

컴퓨터에는 `lim` 이 없으니 `h` 를 작게 잡고 계산한다. 그런데 **어느 쪽으로 흔드느냐**로 정확도가 크게 갈린다.

```
[C2-1] 흔들어 보면 기울기를 알 수 있다

  f(x) = x^3, f'(2) = 12 을 수치로 구해본다

           h          앞으로만        오차          양쪽으로        오차
       1e-01     12.610000000     6.10e-01     12.010000000     1.00e-02
       1e-02     12.060100000     6.01e-02     12.000100000     1.00e-04
       1e-03     12.006001000     6.00e-03     12.000001000     1.00e-06
       1e-05     12.000060000     6.00e-05     12.000000000     2.12e-10
       1e-08     11.999999927     7.29e-08     11.999999927     7.29e-08
       1e-12     12.001066807     1.07e-03     12.001066807     1.07e-03
```

읽어낼 것이 셋이다.

**앞으로만 흔들면 오차가 `h` 에 비례한다.** `h` 를 10분의 1로 줄이면 오차도 10분의 1이다.

**양쪽으로 흔들면 `h²` 에 비례한다.** `h` 를 10분의 1로 줄이면 오차가 **100분의 1**이 된다. `1e-3` 에서 이미 `1e-6` 이다.

```
(f(x+h) - f(x-h)) / 2h
```

테일러 전개로 보면 이유가 나온다. `f(x+h) = f + hf' + h²f''/2 + h³f'''/6`, `f(x-h) = f - hf' + h²f''/2 - h³f'''/6`. 빼면 **`h²` 항이 서로 지워진다.** 남는 첫 오차항이 `h²f'''/6` 이다.

**그리고 `h` 를 계속 줄이면 다시 나빠진다.** `1e-8` 에서 `7.29e-08`, `1e-12` 에서 `1.07e-03`.

`f(x+h)` 와 `f(x-h)` 가 거의 같은 값이 되면, 빼는 순간 **유효숫자가 날아간다**(catastrophic cancellation). 12.000000000001 에서 11.999999999999 를 빼면 남는 것은 반올림 오차뿐이다.

| | 줄이면 | 늘리면 |
|---|---|---|
| 잘림 오차(truncation) | 작아진다 | 커진다 |
| 반올림 오차(round-off) | **커진다** | 작아진다 |

둘이 만나는 지점이 최적이고, `double` 에서 대략 `1e-5 ~ 1e-6` 이다. gradcheck 가 `1e-4` 를 쓰는 것도 이 근처를 노린 것이다.

## 2. 연쇄법칙

합성 함수의 미분은 **곱하기**다.

```
s = 2x + 1,  y = tanh(s),  L = y²

dL/dx = dL/dy · dy/ds · ds/dx
```

```
  s = 2x + 1,  y = tanh(s),  L = y^2,  x = 0.5
    s = 2.000000000,  y = 0.964027580,  L = 0.929349175
    dL/dy = 2y      = 1.928055160
    dy/ds = 1 - y^2 = 0.070650825
    ds/dx = 2       = 2.000000000
    dL/dx = 곱하면  = 0.272437375
    수치로 구하면   = 0.272437375
```

**각 단계가 자기 몫의 미분만 알면 된다.** `tanh` 는 자기 미분을 알고, 덧셈은 자기 미분을 알고, 제곱도 안다. 전체는 그것들을 이어 곱한 것이다.

역전파는 이 곱셈을 **뒤에서 앞으로** 한 번에 처리하는 것뿐이다. 왜 뒤에서 앞인가? 손실이 스칼라 하나이기 때문이다. 앞에서 뒤로 가면 입력 개수만큼 따로 계산해야 하지만, 뒤에서 앞으로 가면 **한 번에 전부** 나온다.

```cpp
void Backward(...)
{
    FVector GradScores = SoftmaxCrossEntropyBackward(Trace.Probabilities, Target);
    FVector GradHiddenOut = LinearBackward(Second, Trace.HiddenOut, GradScores, SecondGrad);
    FVector GradHiddenPre = TanhBackward(Trace.HiddenOut, GradHiddenOut);
    LinearBackward(First, Trace.Input, GradHiddenPre, FirstGrad);
}
```

순전파와 **줄 순서가 정확히 반대**다.

```cpp
FTrace Forward(...)
{
    Trace.HiddenPre     = First.Forward(X);
    Trace.HiddenOut     = Tanh(Trace.HiddenPre);
    Trace.Scores        = Second.Forward(Trace.HiddenOut);
    Trace.Probabilities = Softmax(Trace.Scores);
    Trace.Loss          = CrossEntropy(Trace.Probabilities, Target);
}
```

**이 대칭이 역전파 코드를 쓰는 요령이다.** 순전파를 한 줄씩 적고, 거꾸로 읽으며 각 줄의 역함수를 적는다.

### 순전파가 남긴 값이 필요하다

`FTrace` 구조체가 중간값을 전부 들고 있다. 왜인가.

`tanh` 의 미분은 `1 - y²` 인데, 여기서 `y` 는 **순전파 때 계산한 출력**이다. 역전파 시점에 다시 계산할 수도 있지만 그건 낭비다.

그래서 훈련은 추론보다 **메모리를 훨씬 많이 쓴다.** 층마다 중간값을 들고 있어야 하고, 배치 크기만큼 곱해진다. D7에서 "배치를 키우면 왜 메모리가 터지는가"의 답이 이것이다.

### 무엇을 저장할지는 함수마다 다르다

```cpp
FVector TanhBackward(const FVector& Output, const FVector& GradOutput);
FVector ReluBackward(const FVector& PreActivation, const FVector& GradOutput);
```

`tanh` 는 **출력**을 받는다. `1 - y²` 에 입력이 안 나오기 때문이다.

`relu` 는 **입력**을 받아야 한다. 출력이 0일 때 입력이 음수였는지 정확히 0이었는지 구별할 수 없기 때문이다.

이런 차이가 메모리 사용량을 바꾼다. 실제 프레임워크는 "무엇을 저장할지"를 연산마다 최적화해둔다.

## 3. `dL/ds = p - y`

softmax와 교차 엔트로피를 따로 미분하면 지저분하다. softmax의 미분은 **야코비안 행렬**이고, 출력이 `V` 개면 `V × V` 짜리다.

그런데 **둘을 붙여서** 미분하면 이렇게 된다.

```
dL/ds_i = p_i - [i == 정답]
```

```cpp
FVector SoftmaxCrossEntropyBackward(const FVector& Probabilities, size_t Target)
{
    FVector Result = Probabilities;   // 확률을 그대로 복사하고
    Result[Target] -= Real(1);        // 정답 자리에서 1 을 뺀다
    return Result;
}
```

**두 줄이다.**

```
  점수 (1, 2, 3), 정답은 1번
    확률      = (0.090031, 0.244728, 0.665241)
    dL/ds     = (0.090031, -0.755272, 0.665241)
    합        = -0.000000037  (항상 0 이다)
```

뜻이 직관적이다. **"확률을 정답 쪽으로 옮겨라."** 정답에는 음수 그래디언트(= 점수를 올려라), 나머지에는 양수(= 내려라). 그리고 **합이 항상 0**이다 — 확률의 합이 1이고 거기서 1을 빼므로.

> 실제 프레임워크가 `CrossEntropyLoss` 안에 softmax를 **넣어둔** 이유가 이것이다. PyTorch의 `nn.CrossEntropyLoss` 는 로짓을 받지 확률을 받지 않는다. 따로 두면 야코비안을 거쳐야 하고, 수치적으로도 불안정하다. **붙여서 미분하면 짧고 안전하다.**

## 4. gradcheck

```cpp
FGradCheckResult GradCheck(const std::function<double()>& Loss,
                           Real* Parameters, const Real* Analytic,
                           int Count, double Step);
```

가중치를 **하나씩** 흔들어 손실이 얼마나 변하는지 재고, 역전파가 내놓은 값과 비교한다.

```cpp
Real Saved = Parameters[i];

Parameters[i] = Saved + Step;   double Plus = Loss();
Parameters[i] = Saved - Step;   double Minus = Loss();
Parameters[i] = Saved;          // 반드시 되돌려 놓는다

double Numeric = (Plus - Minus) / (2.0 * Step);
```

세 번째 줄을 빼먹으면 검사 자체가 모델을 망가뜨린다. **검사 도구가 대상을 바꾸면 안 된다**는 것이 이런 코드의 첫 규칙이다.

### 상대 오차로 본다

```cpp
double RelativeError(double A, double B)
{
    double Scale = max(|A|, |B|);
    if (Scale < 1e-12) return 0.0;      // 둘 다 0 이면 비교할 게 없다
    return std::fabs(A - B) / Scale;
}
```

절대 오차로 보면 안 된다. 그래디언트가 `1e-8` 인 자리와 `1e+3` 인 자리를 같은 자로 잴 수 없기 때문이다. **비율로 본다.**

### 결과

```
[C2-4] 2층 망 전체를 검사한다

  손실 = 1.229158044
  가중치 50개 + 치우침 9개 = 59개를 전부 검사한다

  대상                개수    최대 상대 오차
  W1                   30          3.987e-02
  b1                    5          1.758e-03
  W2                   20          2.161e-02
  b2                    4          7.776e-04

  전체 최대 상대 오차 = 3.987e-02
  판정 기준 = 1e-01
```

**통과는 했는데 3.987e-02 다.** 4%나 어긋나 있다. 이게 맞는 건가?

## 5. 여기서 `USE_DOUBLE` 이 값을 한다

A0에서 `Real` 이라는 별칭을 만들었다(결정 17). 이유를 이렇게 적어뒀다.

> 나중에 역전파를 수치미분으로 검증할 때는 `float` 의 오차가 너무 커서 통과인지 아닌지 판정이 안 된다. 그때 이 한 줄을 바꿔서 `double` 로 돌린다.

그 순간이 왔다. 전처리기 정의에 `USE_DOUBLE` 을 넣고 다시 빌드하면,

| 대상 | `float` | `double` |
|---|---|---|
| W1 | 3.987e-02 | **2.941e-09** |
| b1 | 1.758e-03 | 3.621e-09 |
| W2 | 2.161e-02 | 5.633e-10 |
| b2 | 7.776e-04 | 1.338e-09 |
| **전체** | **3.987e-02** | **3.621e-09** |

**일곱 자릿수 차이다.**

왜 이렇게 큰가. gradcheck 는 **두 큰 수를 빼서 작은 수를 얻는** 계산이다. `float` 의 유효숫자가 7자리인데, 손실이 `1.229158` 이고 `h` 가 `1e-4` 면 손실 변화가 `1e-5` 수준이다. 7자리 중 **5자리를 빼기에서 날려먹고** 2자리만 남는다.

`double` 은 16자리라 11자리가 남는다. 그래서 `1e-9` 가 나온다.

### 왜 중요한가

`float` 에서 판정 기준을 `1e-1` 로 풀어야 했다. **그 정도 여유로는 진짜 버그도 통과한다.**

예를 들어 그래디언트를 `0.95` 배로 계산하는 버그가 있다고 하자. 상대 오차 `0.05` 다. `1e-1` 기준으로는 **통과**한다. 그런데 그 모델은 학습률이 5% 어긋난 채로 훈련되고, 그 차이는 며칠짜리 훈련에서 결과를 바꾼다.

> **정리하면 이렇다.** 평소에는 `float` 으로 돌린다 — 빠르고 메모리를 절반만 쓴다. **gradcheck 를 할 때만** `double` 로 바꾼다. 역전파를 새로 쓰거나 고칠 때마다 이 스위치를 켜고 확인한 뒤 다시 끈다.
>
> D6에서 트랜스포머의 역전파를 쓸 때 이 절차를 그대로 따른다. 거기서는 야코비안 항과 가중치 공유 때문에 틀릴 자리가 훨씬 많다.

## 6. 일부러 틀려본다

gradcheck 가 진짜 잡는지 확인해야 한다. **검사 도구도 검사해야 한다.**

```cpp
// 틀린 줄: (1 - y^2) 대신 (1 - y)
BadGradPre[i] = GradHiddenOut[i] * (Real(1) - Trace.HiddenOut[i]);
```

```
    W1 의 최대 상대 오차 = 6.512e-01
    가장 어긋난 자리 5 번: 역전파 -0.365712970, 수치 -0.127553940
```

```cpp
CHECK(Check.WorstRelative > 0.01);   // 반드시 잡혀야 한다
```

**세 배 가까이 틀렸다.** `float` 기준(`1e-1`)으로도 확실히 걸린다.

그런데 이 버그로 훈련해도 **손실은 내려간다.** `1 - y` 와 `1 - y²` 는 `y` 가 작을 때 부호가 같고 크기만 다르다. 방향이 대충 맞으면 경사하강은 어쨌든 내려간다.

**그래서 손실 그래프는 증거가 아니다.** "손실이 내려가고 있으니 역전파는 맞다"는 추론은 성립하지 않는다.

        0      1.579433      0.206092

A.Weight.Data()[i] -= Rate * AGrad.Weight.Data()[i];

**그래디언트의 반대 방향으로 조금 움직인다.** 이게 경사하강의 전부다. 한 줄이다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/GradCheck.hpp` · `.cpp` | 중심 차분으로 수치미분, 상대 오차 비교 |
| `lib/Nn` 역전파 | `LinearBackward`, `TanhBackward`, `ReluBackward`, `SoftmaxCrossEntropyBackward` |
| `FLinearGrad` | 가중치와 같은 모양의 그래디언트 통 |

알아둘 것.

- **양쪽으로 흔든다.** 오차가 `h` 가 아니라 `h²` 에 비례한다
- **`h` 를 무한히 줄이면 안 된다.** 잘림 오차와 반올림 오차가 반대로 움직인다
- **역전파는 순전파를 거꾸로 읽는 것이다.** 줄 순서가 정확히 반대다
- **`tanh` 는 출력을, `relu` 는 입력을 저장한다.** 미분식이 다르기 때문이다
- **softmax + 교차 엔트로피 = `p - y`.** 붙여서 미분하면 짧고 안전하다
- **그래디언트는 누적한다.** 같은 가중치가 여러 번 쓰일 수 있다 (D6에서 결정적)
- **`float` 에서는 gradcheck 판정이 안 된다.** `1e-1` 기준으로는 진짜 버그도 통과한다
- **손실이 내려가는 것은 증거가 아니다.** 틀린 그래디언트로도 내려간다

쓴 문법.

- `std::function` 으로 계산을 값처럼 넘기기
- 참조로 받아 고치기 (`FLinearGrad& Grad`) — C++ 교재 `2.7`
- 람다 캡처로 문맥 전달 (`[&]() { return ...; }`)

**1.** `GradCheck` 에서 흔든 값을 되돌려 놓는 줄(`Parameters[i] = Saved;`)을 지우면 어떻게 되는가?

<details>
<summary>해답</summary>

**검사가 통과하면서 모델이 망가진다.** 최악의 조합이다.

가중치를 하나씩 `-Step` 만큼 옮긴 채로 다음 가중치로 넘어가므로, 검사가 끝나면 **모든 가중치가 `1e-4` 씩 작아져 있다.** 59개면 59번 어긋난다.

그런데 gradcheck 자체는 **통과한다.** 각 가중치를 볼 때 앞의 것들이 조금 움직인 상태이긴 하지만, 손실 함수는 연속이고 `1e-4` 는 작으므로 그래디언트가 크게 안 변한다.

증상은 나중에 나온다. "gradcheck 를 돌리면 손실이 조금씩 이상해진다", "검사를 켜고 끄면 결과가 달라진다" 같은 형태로. 원인이 검사 도구라는 것을 의심하기까지 오래 걸린다.

**검사 도구는 대상을 바꾸면 안 된다.** 소프트웨어 테스트의 기본 원칙인데, 수치 코드에서는 특히 어기기 쉽다. 값을 흔들어야 재어지는 종류의 검사이기 때문이다.

안전하게 가려면 검사 전후로 가중치 전체의 체크섬을 재보는 방법도 있다.

```cpp
double Before = Checksum(Parameters, Count);
GradCheck(...);
CHECK_NEAR(Checksum(Parameters, Count), Before, 0.0);
```

</details>

**2.** `LinearBackward` 가 그래디언트를 `=` 로 넣지 않고 `+=` 로 누적하는 이유는?

<details>
<summary>해답</summary>

**같은 층이 한 번의 순전파에서 여러 번 쓰일 수 있기 때문**이다.

지금 우리 망에서는 각 층이 한 번씩만 쓰이므로 `=` 로 해도 똑같다. 그런데 이런 경우들이 곧 나온다.

**배치 훈련(C3).** 예제 여러 개를 처리하고 그래디언트를 모아 한 번에 갱신한다. 예제마다 `+=` 로 쌓고 마지막에 개수로 나눈다.

**가중치 공유(D6).** 트랜스포머는 입력 임베딩과 출력 층이 **같은 행렬**을 쓰는 경우가 많다(weight tying). 그러면 순전파에서 그 행렬이 두 번 쓰이고, 역전파에서 그래디언트가 **두 곳에서** 와서 더해져야 한다.

`=` 로 두면 나중에 온 것이 먼저 온 것을 덮어쓴다. 그러면 그래디언트가 절반만 반영되고 — **손실은 여전히 내려간다.** 조용히 틀리는 전형적인 경우다.

대신 `+=` 를 쓰면 **0으로 비우는 것을 잊으면 안 된다.**

```cpp
FirstGrad.Zero();     // 이걸 빼먹으면 지난 걸음의 그래디언트가 쌓인다
SecondGrad.Zero();
```

PyTorch에서 `optimizer.zero_grad()` 를 매 걸음 부르는 이유가 이것이다. 초보자가 가장 자주 빼먹는 한 줄이고, 빼먹으면 학습률이 점점 커지는 것 같은 이상한 동작을 한다.

**누적하는 설계를 고른 대가로 비우는 책임이 생긴 것**이다. 프레임워크가 자동으로 비우게 만들 수도 있었지만, 그러면 가중치 공유를 못 한다. 설계에는 늘 이런 맞바꿈이 있다.

</details>

**3.** gradcheck 를 실제 크기의 망(가중치 35만 개)에 쓸 수 있는가?

<details>
<summary>해답</summary>

**원리적으로는 되고 실용적으로는 안 된다.**

가중치 하나마다 순전파를 **두 번** 해야 한다. 35만 개면 70만 번이다. 순전파 한 번이 1밀리초라면 **12분**이다. 그리고 한 번의 gradcheck 는 예제 하나에 대한 것이므로, 여러 예제로 확인하려면 그만큼 곱해진다.

실무에서는 이렇게 한다.

**작게 만들어서 검사한다.** 이 장에서 쓴 것이 `6 → 5 → 4` 짜리 망이다. 층의 종류와 연결 구조가 같으면 크기는 상관없다. 버그는 대개 **수식**에 있지 크기에 있지 않다.

**무작위로 몇 개만 뽑아 검사한다.** 35만 개 중 100개를 무작위로 골라 검사하면 1초 안에 끝난다. 버그가 있으면 대개 **많은 자리가 동시에** 틀리므로 100개면 충분히 잡힌다.

**층 단위로 나눠 검사한다.** 새 연산을 하나 추가했으면 그 연산만 따로 떼어 검사한다. 이미 검증된 층은 다시 안 본다.

이 교재는 세 가지를 다 쓴다. C3부터는 층 단위로 검사하고, D6의 트랜스포머는 어텐션·정규화·잔차를 각각 떼어 검사한 뒤 전체를 작은 크기로 한 번 더 본다.

그리고 **한 번 통과했다고 영원히 안 보는 것이 아니다.** 역전파 코드를 한 줄이라도 고치면 다시 돌린다. 이건 단위 테스트를 대하는 태도와 같다.

</details>

## 다음 장

**C3. NPLM 통합.**

조각이 다 모였다. 이제 진짜 모델을 만든다.

**NPLM**(Neural Probabilistic Language Model)은 2003년 벤지오가 제안한 구조다. 지금 기준으로는 아주 단순하다.

```
앞 N-1 글자 → 각각을 임베딩 벡터로 → 이어 붙이기 → 은닉층(tanh) → 출력층 → softmax
```

A파트의 N-그램과 **입력이 똑같다.** 다른 것은 표를 찾는 대신 계산한다는 것뿐이다. 그래서 정확히 비교할 수 있다 — 같은 데이터, 같은 문맥 길이, 같은 평가 집합.

C1에서 본 "원핫 × 행렬 = 열 하나 꺼내기"가 여기서 **임베딩 층**이 된다. 그리고 그 열이 바로 B3에서 코사인 유사도로 쟀던 그 벡터다. 다만 이번엔 **훈련으로 만들어진다.**

새로 필요한 것.

- **미니배치** — 예제를 하나씩 말고 묶어서 처리한다
- **에폭과 셔플** — 데이터를 여러 번 도는데 순서를 섞는다
- **학습률** — 얼마나 크게 움직일 것인가. 너무 크면 발산하고 너무 작으면 안 움직인다
- **손실 곡선** — 훈련 손실과 검증 손실을 나란히 본다. 갈라지는 지점이 과적합이다

검증은 **파이썬 참조 구현과 손실 곡선 대조**다. 같은 씨앗, 같은 데이터, 같은 학습률로 돌려 두 곡선이 겹치는지 본다.
