# C3. NPLM 통합

> **선행** · C++ 교재 `9.9` 모듈 설계 · C1 · C2 전체
> **만드는 것** · `lib/Nplm`, `tools/make_nplm_expected.py`
> **예제** · C3-1 ~ C3-6

---

## 0. 결과부터

같은 데이터, 같은 어휘, 같은 문맥 길이로 두 모델을 세워 붙였다.

```
[C3-5] 같은 어휘, 같은 데이터의 4그램 백오프와 비교

  모델                     검증 손실    퍼플렉서티
  4그램 백오프               3.2113          24.8
  NPLM                       3.4812          32.5

  가중치 개수 : N-그램 349806 항목, NPLM 44608 개
```

**N-그램이 이겼다.**

이 교재는 이런 결과를 감추지 않는다. 오히려 이게 정확한 그림이다 — **2003년의 NPLM은 N-그램을 압도하지 못했다.** 논문에서도 단독으로는 비슷하거나 약간 나은 정도였고, N-그램과 섞어 써야 확실히 이겼다.

그런데 표의 마지막 줄을 보자. **가중치가 8분의 1이다.** 그리고 N-그램이 절대 못 하는 것을 한다.

```
[C3-6] 훈련이 만든 임베딩

  '.'     → :(0.738) ,(0.711) )(0.589) 왕(0.561) N(0.491)
```

마침표가 콜론·쉼표·닫는 괄호와 **한 덩어리로 묶였다.** N-그램에게 `.` 과 `:` 은 아무 관계 없는 번호 둘이다. 이 모델은 둘이 비슷한 자리에 온다는 것을 **16개의 숫자에 압축해 담았다.**

이 차이가 D파트에서 결정적이 된다.

## 1. 구조

```
앞 3개 토큰 → 각각 16차원 임베딩 → 이어 붙여 48차원 → 은닉 64(tanh) → 출력 512 → softmax
```

A파트의 4그램과 **입력이 똑같다.** 앞 셋을 보고 다음 하나를 맞힌다. 다른 것은 표를 찾는 대신 계산한다는 것뿐이다.

### 임베딩은 곱셈이 아니다

C1에서 원핫 벡터로 했던 것을 다시 보자.

```cpp
FVector X(Vocab);                     // 512칸
X[IndexOf[Prev]] = Real(1);           // 한 칸만 1
FVector H = Hidden.Forward(X);        // 512번 곱셈 중 511번이 0 곱하기
```

`W x` 에서 `x` 가 원핫이면 결과는 **`W` 의 한 열**이다. 곱할 필요가 없다.

```cpp
const Real* Row = Embedding.RowData((size_t)Token);
for (size_t d = 0; d < EmbedDim; d++)
{
    Trace.Embedded[k * EmbedDim + d] = Row[d];
}
```

**표에서 줄을 읽어 오는 것이 전부다.** 이게 임베딩 층이고, 별도의 개념이 아니라 **원핫 입력 층의 다른 이름**이다.

그리고 역전파도 대칭이다. 꺼내온 줄에 **되돌려 더한다.**

```cpp
for (size_t k = 0; k < ContextSize; k++)
{
    Real* Row = Grad.Embedding.RowData((size_t)ContextTokens[k]);
    for (size_t d = 0; d < EmbedDim; d++)
    {
        Row[d] += GradEmbedded[k * EmbedDim + d];   // 반드시 누적
    }
}
```

`+=` 여야 하는 이유가 여기서 실물로 나온다. 문맥에 같은 토큰이 두 번 나오면(`그 그` 같은 경우) **같은 줄에 두 번 더해져야** 한다. `=` 로 두면 나중 것이 앞 것을 덮어쓰고, 그래디언트가 절반이 된다. C2 연습문제 2에서 예고한 그 함정이다.

C3-2의 gradcheck에서 문맥을 `{2, 7, 2}` 로 준 것이 이걸 노린 것이다.

### 임베딩을 0으로 초기화하면 안 된다

```cpp
for (size_t i = 0; i < Embedding.Count(); i++)
{
    Embedding.Data()[i] = (Real)RandomRange(&Rng, 0.1);
}
```

전부 0으로 두면 모든 토큰의 벡터가 같아진다. 그러면 순전파 결과도 같고, **역전파로 오는 그래디언트도 같다.** 같은 값에서 같은 만큼 움직이므로 영원히 같은 값으로 남는다.

**대칭을 깨려면 처음부터 달라야 한다.** 신경망 초기화의 첫 번째 규칙이다.

## 2. 파이썬 참조 구현과 비트까지 맞춘다

C2에서 gradcheck를 만들었다. 그런데 gradcheck는 **내 순전파를 기준으로 내 역전파를 검사**한다. 순전파 자체가 틀렸으면 둘 다 사이좋게 틀린다.

그래서 **다른 언어, 다른 사람이 쓴 코드**와 맞춰본다.

```python
# tools/make_nplm_expected.py
Embedded = np.concatenate([Embedding[Token] for Token in CONTEXT_TOKENS])
HiddenPre = HiddenW @ Embedded + HiddenB
HiddenOut = np.tanh(HiddenPre)
...
GradOutputW = np.outer(GradScores, HiddenOut)
GradHiddenOut = OutputW.T @ GradScores
```

NumPy로 쓰면 스무 줄이다. 어휘 7, 문맥 2, 임베딩 3, 은닉 4 짜리 망 하나의 손실과 모든 그래디언트를 계산해 `data/nplm_expected.csv` 로 남긴다.

### 가중치를 난수로 안 채운 이유

C++의 xorshift를 파이썬에서 똑같이 구현하면 되긴 한다. 그런데 그러면 **난수 생성기가 맞는지**까지 이 검사에 얽힌다.

**검사는 한 번에 한 가지만 봐야 한다.** 그래서 정수 나눗셈으로 정해지는 값을 쓴다.

```
((i * 31 + 17) % 41 - 20) / 40.0
```

정수 연산과 나눗셈 한 번이다. 두 언어의 IEEE 754 구현이 같으므로 **비트까지 같은 값**이 나온다.

### 결과

`double` 로 빌드하면,

```
  손실      C++ 1.658953208698782
         파이썬 1.658953208698782
  정답표 85줄 대조 -> 어긋난 줄 0개 (허용 1e-12)
  최대 차이 = 5.551e-17
```

**`5.551e-17`.** `double` 의 기계 엡실론이 `2.2e-16` 이니 **마지막 비트 수준**에서 일치한다.

`float` 로 빌드하면 `1.885e-08` 이다. `float` 의 엡실론이 `1.2e-07` 이므로 이것도 정상이다.

> 이 검사가 잡는 것은 gradcheck가 못 잡는 종류다. 예를 들어 `tanh` 를 실수로 `sigmoid` 로 썼다면 gradcheck는 **통과한다** — 순전파와 역전파가 둘 다 sigmoid이므로 서로 일관되니까. 파이썬 대조는 즉시 잡는다.
>
> **두 검사가 서로 다른 것을 본다.** 둘 다 필요하다.

## 3. 어휘를 줄인다

전체 5,534종을 다 쓰면 출력층이 그만큼 커진다. 이 장의 예제가 몇 분씩 걸리면 아무도 안 돌려본다.

```
[C3-3] 어휘를 512종으로 줄인다

  전체 2684종 중 509종을 남겼다
  남긴 것이 전체 글자의 97.022% 를 덮는다
  나머지는 전부 UNK 한 칸으로 몰아넣는다
```

**509종이 97%를 덮는다.** A1에서 잰 "상위 500자 = 96.6%" 와 거의 같은 숫자다. 한국어 글자 빈도의 성질이 여기서 값을 한다.

B2 연습문제 2에서 예고한 `<UNK>` 방식이다. 그때 적어둔 주의사항이 그대로 적용된다 — **어휘가 다르면 퍼플렉서티를 비교할 수 없다.** 그래서 C3-5의 N-그램 비교도 **같은 512 어휘로 다시 만들어** 잰다.

```cpp
for (int Order = 1; Order <= Backoff.MaxOrder; Order++)
{
    NgramBuildFromTokens(&Backoff.Orders[Order], Converted.data(), ...);
}
```

A9에서 만든 `NgramBuildFromTokens` 가 여기서 쓰인다. 파일이 아니라 **우리가 만든 토큰 배열**로 N-그램을 세야 하기 때문이다. 그때는 형태소용이었는데 지금은 UNK 처리된 글자용이다. **같은 도구가 두 번째 쓰임을 찾았다.**

## 4. 훈련

```cpp
for (size_t Start = 0; Start < Order.size(); Start += BATCH_SIZE)
{
    Grad.Zero();

    for (size_t i = Start; i < Stop; i++)
    {
        FNplmTrace Trace = Model.Forward(Example.Context, Example.Target);
        Model.Backward(Example.Context, Example.Target, Trace, Grad);
    }

    Model.Step(Grad, LEARN_RATE, Real(1) / (Real)(Stop - Start));
}
```

**세 줄이 전부다.** 비우고, 64개를 쌓고, 한 걸음 움직인다.

### 미니배치를 쓰는 이유

예제 하나마다 갱신하면(배치 1) 그래디언트가 너무 흔들린다. 예제 하나는 전체 데이터를 대표하지 않으니까. 전부 모아서 한 번 갱신하면(전체 배치) 안정적이지만 한 걸음에 20만 개를 봐야 한다.

**64개쯤 모으면 둘의 중간이 된다.** 흔들림이 8분의 1로 줄고(표준편차가 `1/√n` 로 준다), 걸음은 여전히 자주 뗀다.

그리고 **`Zero()` 를 빼먹으면 안 된다.** 지난 배치의 그래디언트가 그대로 쌓여서, 학습률이 점점 커지는 것 같은 이상한 동작을 한다. PyTorch의 `optimizer.zero_grad()` 와 같은 자리다.

### 에폭마다 섞는다

```cpp
for (size_t i = Order.size() - 1; i > 0; i--)
{
    uint64_t j = RandomBelow(&Shuffle, (uint64_t)i + 1);
    std::swap(Order[i], Order[(size_t)j]);
}
```

피셔-예이츠 셔플이다. A4에서 해시 실험을 공정하게 만들려고 썼던 그 코드.

섞지 않으면 **같은 문서의 예제들이 연달아 들어온다.** 위키 문서 하나는 한 주제만 다루므로, 배치 하나가 통째로 "축구 선수" 이야기일 수 있다. 그러면 모델이 그쪽으로 끌려갔다가 다음 배치에서 다시 끌려간다.

### 시작 손실부터 확인한다

```cpp
CHECK(std::fabs(StartValid - std::log((double)VOCAB_SIZE)) < 0.5);
```

```
      에폭     훈련 손실     검증 손실      검증 PPL      시간
        0        6.2379        6.2367         511.2         -
```

`log(512) = 6.238`. 잰 값 `6.2367`. C1에서 세운 규칙이 여기서도 통과한다. **훈련을 시작하기 전에 이 숫자를 본다.**

## 5. 과적합을 눈으로 본다

```
      에폭     훈련 손실     검증 손실      검증 PPL      시간
        0        6.2379        6.2367         511.2         -
        1        3.5663        3.7269          41.6      8.1s
        2        3.3720        3.5548          35.0      8.1s
        3        3.2593        3.5117          33.5      8.1s
        4        3.1873        3.4679          32.1      8.1s
        5        3.1272        3.4605          31.8      8.1s    <- 여기가 바닥
        6        3.0929        3.4836          32.6      8.1s
        7        3.0800        3.4627          31.9      8.1s
        8        3.0328        3.4643          32.0      8.2s
        9        3.0454        3.4712          32.2      8.2s
       10        3.0352        3.4812          32.5      8.2s
```

**훈련 손실은 계속 내려가는데 검증 손실은 5에폭에서 멈춘다.**

이게 과적합이다. B2에서 "6그램이 3그램보다 나쁘다"로 봤던 그 현상인데, 여기서는 **시간축에서** 일어난다. 모델이 훈련 데이터의 세부사항을 외우기 시작하고, 그 세부사항은 검증 데이터에 없다.

실무에서는 **조기 종료**(early stopping)를 쓴다. 검증 손실이 몇 에폭 연속 안 내려가면 멈추고, **가장 좋았던 시점의 가중치로 되돌린다.** 우리는 관찰만 하고 끝까지 돌렸다 — 곡선을 보여주는 것이 목적이라서다.

> 훈련 손실만 보고 있으면 이 순간을 놓친다. **검증 집합을 따로 두는 것**이 왜 첫 번째 규칙인지가 여기서 다시 확인된다.

## 6. 8분의 1로 무엇을 샀는가

```
  모델                     검증 손실    퍼플렉서티
  4그램 백오프               3.2113          24.8
  NPLM                       3.4812          32.5

  가중치 개수 : N-그램 349806 항목, NPLM 44608 개
```

퍼플렉서티는 N-그램이 24.8, NPLM이 32.5. **31% 나쁘다.**

그런데 N-그램은 4그램 항목만 **349,806개**를 들고 있다(1~3그램까지 합치면 더 많다). NPLM은 전부 합쳐 **44,608개**다.

그리고 NPLM은 크기가 **데이터와 무관하게 고정**이다. 데이터를 10배 주면 N-그램의 표는 10배 가까이 커지지만 NPLM은 그대로다. 그게 스케일링의 출발점이다.

### 임베딩이 진짜 뭔가를 배웠는가

```
  '을'    → 를(0.975) 럼(0.662) 큰(0.642) 할(0.605) 및(0.593)
  '1'     → 2(0.820) 3(0.766) 5(0.740) 4(0.733) 7(0.705)
  '한'    → 된(0.846) 른(0.770) 든(0.756) 난(0.735) 떤(0.672)
  '.'     → :(0.738) ,(0.711) )(0.589) 왕(0.561) N(0.491)
```

B3에서 잰 것과 비교해보자.

| 질의 | B3 (바이그램 표, 5,534차원) | C3 (훈련한 임베딩, 16차원) |
|---|---|---|
| `을` | 및, 를, 은, `,`, 될 | **를**, 럼, 큰, 할, 및 |
| `1` | 9, 8, 7, 4, 6 | **2, 3, 5, 4, 7** |
| `한` | 난, 인, 른, 이, 든 | **된, 른, 든, 난, 떤** |
| `.` | `)`, 망, 년, 일, 록 | **`:`, `,`, `)`**, 왕, N |

마지막 줄이 눈에 띈다. B3는 `.` 과 `망`, `년`, `일` 을 비슷하다고 했다. 표면적으로는 맞다 — 전부 뒤에 공백이 잘 온다. 그런데 **구두점이라는 공통점**은 못 잡았다.

훈련한 임베딩은 `:`, `,`, `)` 를 위에 올린다. **16차원 안에 "여기서 뭔가 끊긴다"는 성질이 자리를 잡은 것이다.**

`1` 줄도 다르다. B3는 9, 8, 7 순이었는데 여기는 2, 3, 5 순이다. 자릿수가 아니라 **숫자라는 범주**를 잡았다.

**5,534차원이 16차원이 됐고, 그 과정에서 범주가 생겼다.** 이것이 표를 세는 방식으로는 절대 못 하는 일이다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Nplm.hpp` · `.cpp` | 임베딩 + 은닉 + 출력, 순전파·역전파·경사하강 |
| `tools/make_nplm_expected.py` | NumPy 참조 구현 (가중치를 정수식으로 고정) |
| `data/nplm_expected.csv` | 손실 1개 + 그래디언트 84개 |

알아둘 것.

- **임베딩은 곱셈이 아니라 표 읽기다.** 원핫 × 행렬의 다른 이름
- **임베딩 그래디언트는 반드시 누적한다.** 같은 토큰이 문맥에 두 번 나올 수 있다
- **임베딩을 0으로 초기화하면 영원히 같은 값으로 남는다**
- **gradcheck와 참조 구현은 서로 다른 것을 본다.** 둘 다 필요하다
- **검사는 한 번에 한 가지만.** 난수까지 얽히면 무엇이 틀렸는지 못 가린다
- **미니배치는 흔들림과 걸음 수의 절충이다.** `Zero()` 를 빼먹지 않는다
- **훈련 손실과 검증 손실이 갈라지는 지점이 과적합이다**
- **N-그램을 못 이겨도 의미가 있다.** 8분의 1 크기이고, 범주를 배운다

쓴 문법.

- 클래스로 모델 전체를 묶기 — C++ 교재 `9.9`
- `std::vector<FExample>` 로 데이터셋 다루기
- 람다와 `std::sort` 로 빈도순 정렬

<details>
<summary>해답</summary>

**손실이 발산한다.** 그리고 대개 `nan` 으로 끝난다.

경사하강은 "기울어진 방향으로 조금 간다"는 방법이다. **조금**이 핵심이다. 너무 크게 가면 골짜기를 지나쳐 반대편 벽으로 올라가고, 다음 걸음에서 더 크게 지나친다. 진동이 커지다가 값이 넘친다.

증상이 단계적으로 나타난다.

- 조금 크면 → 손실이 내려가다 어느 지점에서 튀고 다시 내려간다 (톱니 모양)
- 더 크면 → 손실이 내려가지 않고 진동한다
- 훨씬 크면 → 몇 걸음 만에 `inf`, 그 다음 `nan`

반대로 너무 작으면 **아무 일도 안 일어나는 것처럼 보인다.** 0.001로 두면 10에폭을 돌려도 손실이 6.2에서 5.9쯤에 머문다.

적당한 값을 찾는 방법이 있다. **학습률을 아주 작은 값에서 시작해 배치마다 조금씩 올리며 손실을 기록한다.** 손실이 가장 빠르게 내려가는 구간의 학습률을 고른다(learning rate range test).

그리고 D7에서는 고정 학습률을 아예 안 쓴다. **처음에는 작게 시작해(warmup) 올렸다가 서서히 줄인다.** 왜 그 모양이어야 하는지는 거기서 다룬다.

</details>

**2.** `Grad.Zero()` 를 배치 루프 밖으로 옮기면(= 에폭당 한 번만 비우면) 어떻게 되는가?

<details>
<summary>해답</summary>

**학습률이 점점 커지는 것과 같아진다.** 그리고 발산한다.

그래디언트가 계속 쌓이므로, 100번째 배치에서는 100개 배치분의 그래디언트가 누적된 상태다. `Step` 이 나누는 것은 **이번 배치의 크기(64)** 뿐이라, 실질 학습률이 배치 번호에 비례해 커진다.

증상이 고약하다. **처음 몇 배치는 정상으로 보인다.** 손실이 내려간다. 그러다 갑자기 튀어 오르고 `nan` 이 된다. 에폭이 바뀌면 다시 정상이었다가 또 터진다.

"에폭 초반에는 괜찮은데 중반에 터진다"는 증상을 보면 이 종류를 의심한다.

더 고약한 변종은 **비우기는 하는데 엉뚱한 곳에서 비우는 것**이다. 예를 들어 `Grad.Zero()` 를 `Step()` 뒤에 두면 논리적으로는 같지만, 마지막 배치 뒤에 한 번 더 비우게 되어 아무 해가 없다. 반대로 `Step()` 앞에 두면 **그래디언트가 전부 0인 채로 갱신**되어 훈련이 아예 안 된다 — 손실이 완전히 평평해진다.

**평평한 손실 곡선은 "안 배운다"가 아니라 "갱신이 0이다"를 의심해야 한다.**

</details>

**3.** 임베딩 차원을 16에서 4로 줄이면?

<details>
<summary>해답</summary>

**퍼플렉서티가 나빠지고, 임베딩의 이웃 목록이 뭉개진다.**

16차원에는 여러 성질이 동시에 들어갈 자리가 있다. "구두점인가", "숫자인가", "받침이 있는가", "조사인가" 같은 것들이 서로 다른 방향을 차지한다.

4차원이면 자리가 모자란다. 가장 손실을 많이 줄여주는 성질 몇 개만 남고 나머지는 섞인다. `.` 의 이웃에 구두점이 아닌 것이 섞여 들어오기 시작한다.

**반대로 늘리면 계속 좋아지는가?** 아니다.

- 64차원쯤까지는 조금씩 좋아진다
- 그 이상은 거의 안 변하거나 **오히려 나빠진다.** 자유도가 늘어난 만큼 외우기 쉬워지므로 과적합이 빨라진다
- 그리고 가중치가 늘어 훈련이 느려진다

적정 차원은 **어휘 크기와 데이터 양**에 달려 있다. 경험칙으로 어휘의 네제곱근 근처(`512^0.25 ≈ 4.8`)에서 시작해 몇 배씩 늘려보라는 말이 있는데, 결국 **재보고 정하는 것**이다.

C6에서 임베딩을 2차원으로 눌러(PCA) 그림으로 그린다. 16차원에 무엇이 들어 있는지를 눈으로 보는 장이다.

</details>

## 다음 장

**C4. 데이터 경계 — `.npy` 리더.**

지금까지 파이썬과 C++은 **CSV로만** 이야기했다. 정답표가 전부 텍스트였다.

그런데 C6에서 임베딩을 그림으로 그리려면 44,608개의 실수를 파이썬으로 넘겨야 한다. CSV로 쓰면 파일이 커지고 파싱이 느리고, 무엇보다 **`float` 을 텍스트로 적었다 읽으면 마지막 비트가 달라진다.**

파이썬 쪽의 표준 형식은 **`.npy`** 다. NumPy 배열 하나를 그대로 담는다. 구조가 단순하다.

```
매직 \x93NUMPY  +  버전 2바이트  +  헤더 길이 2바이트  +  헤더(파이썬 dict 문자열)  +  날것 데이터
```

A7에서 우리가 직접 설계한 `HGNG` 형식과 **판박이**다. 매직 넘버, 버전, 헤더, 데이터. 이번엔 **남이 정한 형식을 읽는** 쪽이다.

C++ 교재 `9.7` 의 고정 폭 정수가 여기서 필수가 된다. 그리고 헤더에 `'<f4'` 같은 문자열이 들어 있는데, `<` 가 리틀 엔디언을 뜻한다 — A7에서 `0x01020304` 로 했던 그 검사를 NumPy는 이렇게 한다.

**파일 포맷이 곧 언어 간 계약**이라는 것을 그 장에서 다룬다.
