> **선행** · C++ 교재 `6.3` 파일 스트림 / `9.7` 고정 폭 정수 · A7 (이진 파일 형식)
> **만드는 것** · `lib/Npy`, `tools/make_npy_expected.py`
> **예제** · C4-1 ~ C4-6

## 0. CSV로는 안 되는 순간

지금까지 파이썬과 C++은 **CSV로만** 이야기했다. 정답표가 전부 텍스트였고, 사람이 열어볼 수 있다는 것이 큰 장점이었다.

그런데 C6에서 임베딩을 그림으로 그리려면 44,608개의 실수를 넘겨야 한다. 텍스트로 적으면 이렇게 된다.

```
[C4-6] .npy 와 CSV, 무엇이 다른가

  2000 x 64 실수 배열 128000개

                          .npy      CSV (%.6f)
  크기                  500 KB         1188 KB
  쓰기                0.001 초        0.025 초
  읽기                0.001 초        0.025 초
  정확히 왕복   128000 / 128000   5075 / 128000
  최대 오차            0.0e+00         5.1e-07
```

크기가 2.4배, 속도가 25배 차이 나는 것보다 **네 번째 줄**이 중요하다.

**12만 8천 개 중 5,075개만 정확히 되돌아온다.** 96%가 달라진다.

`%.6f` 로 적으면 `-0.406253` 같은 값이 `-0.406250` 이 된다. 다시 읽으면 원래 비트가 아니다. 이런 데이터로 파이썬에서 그림을 그리면 **미세하게 다른 것**을 보게 되고, 그 차이가 어디서 왔는지 추적할 방법이 없다.

이 장에서는 파이썬 쪽의 표준 형식인 `.npy` 를 읽고 쓴다.

## 1. `.npy` 는 우리가 만든 것과 닮았다

A7에서 모델 파일 형식을 직접 설계했다.

```
"HGNG" + 바이트순서 표시 + 버전 + 개수들 + 날것 데이터
```

`.npy` 는 이렇다.

```
[C4-1] 파이썬이 쓴 .npy 의 앞부분

    0000  93 4E 55 4D 50 59 01 00 76 00 7B 27 64 65 73 63  |.NUMPY..v.{'desc|
    0016  72 27 3A 20 27 3C 66 34 27 2C 20 27 66 6F 72 74  |r': '<f4', 'fort|
    0032  72 61 6E 5F 6F 72 64 65 72 27 3A 20 46 61 6C 73  |ran_order': Fals|
    0048  65 2C 20 27 73 68 61 70 65 27 3A 20 28 35 2C 20  |e, 'shape': (5, |
    0064  37 29 2C 20 7D 20 20 20 20 20 20 20 20 20 20 20  |7), }           |
```

| 자리 | 크기 | 내용 |
|---|---|---|
| 0 | 6 | `\x93NUMPY` — 매직 넘버 |
| 6 | 2 | 버전 (1, 0) |
| 8 | 2 | 헤더 길이 (리틀 엔디언 `uint16`) |
| 10 | 헤더 길이 | 파이썬 dict 문자열, 공백으로 채우고 줄바꿈으로 끝 |
| ... | | 날것 데이터 (행 우선) |

**판박이다.** 매직 넘버, 버전, 헤더, 데이터.

다른 것은 **우리가 만든 형식이 아니라는 것**뿐이다. 고칠 수 없고, 헤더도 우리 마음대로 읽을 수 없다. **그쪽이 정한 대로** 파싱해야 한다.

### 첫 바이트가 `\x93` 인 이유

ASCII 범위를 벗어난 값이다. 일부러 그렇게 골랐다.

`.npy` 를 텍스트 에디터로 열면 첫 글자부터 깨진다. **"이건 텍스트가 아니다"를 즉시 알린다.** PNG의 첫 바이트가 `\x89` 인 것과 같은 발상이다.

### 헤더 길이가 64의 배수인 이유

```cpp
size_t Total = 10 + BodyLength + 1;
size_t Padded = ((Total + 63) / 64) * 64;
size_t HeaderLength = Padded - 10;
```

```
  헤더 길이      = 118 (전체 128, 64의 배수)
```

데이터가 **64바이트 경계**에 놓이게 하려는 것이다. 요즘 CPU의 캐시 라인이 64바이트이고, SIMD 명령 중에는 정렬된 주소를 요구하는 것이 있다.

**형식에 이런 배려가 박혀 있다는 것 자체가** NumPy가 성능을 염두에 두고 설계됐다는 뜻이다. A7에서 우리 형식을 만들 때는 이 생각을 안 했다 — 남의 형식을 읽으며 배우는 것이 이런 것이다.

### `'<f4'` 의 `<`

```
  descr          = <f4
```

`<` 가 **리틀 엔디언**, `f` 가 부동소수점, `4` 가 바이트 수다. 빅 엔디언이면 `>f4` 다.

A7에서 우리는 `0x01020304` 를 써서 바이트 순서를 확인했다. NumPy는 **타입 이름 안에** 넣었다. 목적은 같다 — **읽는 쪽이 다른 기계여도 안전하게.**

우리 리더는 `<f4` 와 `<f8` 만 받는다. `>f4` 가 오면 `ElementSize` 가 0이 되어 실패한다. **읽을 수 없는 것을 조용히 잘못 읽는 것보다 거절하는 편이 낫다.** A7에서 세운 규칙 그대로다.

## 2. 헤더를 어디까지 파싱할 것인가

헤더는 **파이썬 dict 를 그대로 적은 문자열**이다.

```
{'descr': '<f4', 'fortran_order': False, 'shape': (5, 7), }
```

제대로 하려면 파이썬 표현식 파서를 써야 한다. 그런데,

```cpp
std::string ValueAfter(const std::string& Header, const char* Key)
{
    std::string Needle = "'";  Needle += Key;  Needle += "':";
    size_t At = Header.find(Needle);
    ...
}
```

**문자열 자르기로 끝냈다.** 키가 셋뿐이고 값의 모양도 정해져 있기 때문이다.

한 군데만 신경 썼다. `shape` 의 값 `(5, 7)` 안에 쉼표가 있으므로, **괄호 깊이를 세면서** 값의 끝을 찾는다.

```cpp
if (C == '(') Depth++;
if (C == ')') Depth--;
if (C == ',' && Depth == 0) break;
```

**필요한 만큼만 파싱하는 것도 판단이다.** 완전한 파서를 쓰면 200줄이 되고 버그가 들어갈 자리도 그만큼 는다. 다만 이 결정은 **문서에 적어야 한다** — 나중에 누군가 `'descr': ('<f4', 2)` 같은 구조화 dtype을 넣으면 조용히 틀린 답을 낸다.

## 3. 왕복이 되는가

세 방향으로 확인한다.

**파이썬 → C++**

```
  35개 값 대조 -> 어긋난 것 0개, 최대 차이 0.0e+00
```

파이썬이 `data/npy_values.csv` 에 같은 값을 `%.17g` 로 적어뒀다. 그걸 읽어 `.npy` 에서 읽은 값과 비교한다. **정확히 0** 이어야 한다.

```cpp
CHECK(Bad == 0);   // 이진 파일이므로 **정확히** 같아야 한다
```

이 검사가 `CHECK_NEAR` 가 아니라 `CHECK` 인 것에 주목할 것. 이진 파일은 **근사가 아니다.** 비트가 그대로 넘어온다.

**C++ → C++ (왕복)**

```
  data/npy_from_cpp.npy 를 썼다 (268 바이트)
    0000  93 4E 55 4D 50 59 01 00 76 00 7B 27 64 65 73 63  |.NUMPY..v.{'desc|

  왕복해서 바이트까지 같은가 = 예
```

파일 크기가 **268바이트로 파이썬이 쓴 것과 같다.** 헤더 128 + 데이터 140.

**C++ → 파이썬**

```bash
.venv/Scripts/python tools/make_npy_expected.py --check
```

```
  값이 정확히 같은가 = True
  최대 차이          = 0.000e+00
```

**세 방향이 다 닫혔다.** 이제 두 언어가 실수 배열을 주고받을 수 있다.

## 4. 거절해야 할 것을 거절하는가

```
[C4-5] 우리 파일이 아닌 것

  아무 바이트나 담긴 파일 -> NpyReadInfo = 0
  없는 파일               -> NpyReadInfo = 0
```

A7에서 한 것과 같다. **성공하는 경우만 테스트하면 절반만 테스트한 것이다.**

매직 넘버 검사가 없으면 어떻게 되는지 생각해보자. 헤더 길이를 쓰레기 값으로 읽고, 그 크기만큼 `malloc` 을 시도한다. 운이 나쁘면 수 GB를 잡으려 들고, 더 나쁘면 성공해서 쓰레기를 읽는다.

## 5. 텍스트로는 왜 안 돌아오는가

```
  정확히 왕복   128000 / 128000   5075 / 128000
  최대 오차            0.0e+00         5.1e-07
```

**`%.6f` 는 소수점 아래 6자리**를 적는다. 그런데 `float` 의 정밀도는 자릿수가 아니라 **유효숫자 7자리**다.

- `0.406253` → 유효숫자 6자리. `float` 이 담을 수 있는 것보다 적다
- `-0.000012345` → `%.6f` 로는 `-0.000012`. 유효숫자가 **2자리**로 줄었다

값이 0에 가까울수록 손해가 커진다. 우리 데이터는 `-1 ~ 1` 범위라 그나마 나은 편인데도 96%가 어긋났다.

**정확히 적으려면 몇 자리가 필요한가.**

| 타입 | 왕복을 보장하는 자릿수 | 서식 |
|---|---|---|
| `float` | 9 | `%.9g` |
| `double` | 17 | `%.17g` |

`std::numeric_limits<float>::max_digits10` 이 그 값을 알려준다. `tools/make_nplm_expected.py` 가 `%.17g` 로 적은 이유가 이것이다 — **그건 정답표라서 정확해야 했다.**

> 그럼 CSV를 `%.9g` 로 쓰면 되지 않나? 된다. 크기는 더 커지고 속도는 그대로 느리지만 값은 정확해진다.
>
> 그래서 선택 기준은 정확도가 아니라 **누가 읽는가**다.
>
> - **사람이 검증한다** → CSV. git diff가 되고 눈으로 본다. A2의 정답표가 그렇다
> - **프로그램이 읽는다** → 이진. A7의 모델 파일, C4의 배열
>
> 정확도는 둘 다 만족시킬 수 있다. **목적이 형식을 정한다.**

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Npy.hpp` · `.cpp` | `.npy` 헤더 파싱, 2차원 배열 읽기·쓰기 |
| `tools/make_npy_expected.py` | 파이썬 쪽 쓰기와 확인 |
| `data/npy_from_python.npy` | 5×7 float32 배열 (268바이트) |

알아둘 것.

- **`.npy` 는 A7에서 우리가 만든 것과 같은 모양이다.** 매직 + 버전 + 헤더 + 데이터
- **매직 넘버의 첫 바이트가 ASCII 밖인 것**은 "텍스트가 아니다"를 알리는 관습이다
- **헤더를 64의 배수로 채우는 것**은 데이터를 캐시 라인에 맞추려는 것이다
- **`<f4` 의 `<` 가 바이트 순서**다. A7의 `0x01020304` 와 같은 일을 한다
- **필요한 만큼만 파싱한다.** 대신 그 결정을 문서에 적는다
- **`%.6f` 로는 `float` 이 되돌아오지 않는다.** `%.9g` 가 필요하다
- **형식은 정확도가 아니라 목적이 정한다.** 사람이 읽으면 텍스트, 프로그램이 읽으면 이진

쓴 문법.

- `fread` / `fwrite` / `fseek` — C 교재 `11.2`
- 고정 폭 정수로 형식 못박기 — C++ 교재 `9.7`
- `std::string` 의 `find`, `substr` — C++ 교재 `8.1`

## 연습문제

**1.** `fortran_order` 가 `True` 인 파일이 오면 우리 리더는 0을 돌려준다. 읽으려면 무엇을 해야 하는가?

<details>
<summary>해답</summary>

**전치해서 담으면 된다.**

포트란 순서는 **열 우선**이다. `(3, 2)` 배열을 `a[0][0], a[1][0], a[2][0], a[0][1], ...` 순으로 적는다. 우리 `FMatrix` 는 행 우선이므로 읽으면서 자리를 바꿔야 한다.

```cpp
for (size_t c = 0; c < Cols; c++)
{
    for (size_t r = 0; r < Rows; r++)
    {
        Result(r, c) = (Real)Buffer[c * Rows + r];
    }
}
```

`Buffer` 를 순서대로 읽으면서 `Result` 에 **건너뛰며** 쓴다. 캐시에 나쁘지만 한 번뿐이므로 상관없다. C1의 `TransposedMultiply` 에서 본 것과 같은 상황이다 — 어느 쪽을 순차로 할지 고르는 문제.

그런데 **읽는 것과 거절하는 것 중 무엇이 나은가.**

지금 우리 코드는 거절한다. 이유는 **우리가 만든 파일에는 절대 안 나오기 때문**이다. NumPy가 열 우선으로 저장하는 것은 `np.asfortranarray` 를 명시적으로 부르거나 전치한 배열을 그대로 저장할 때뿐이다.

그런 파일을 받을 일이 생기면 그때 넣으면 된다. 그리고 지금 거절하고 있으므로 **그때가 오면 바로 알게 된다.** 조용히 잘못 읽는 것보다 훨씬 낫다.

**아직 필요 없는 것을 미리 만들지 않되, 마주치면 알 수 있게 막아두는 것** — 이게 A4의 삭제 기능, A7의 엔디언 검사와 같은 판단이다.

</details>

**2.** `.npy` 대신 `.npz` 는 무엇이 다른가?

<details>
<summary>해답</summary>

**`.npz` 는 `.npy` 파일 여러 개를 담은 ZIP 파일**이다. 그게 전부다.

```python
np.savez("model.npz", embedding=E, hidden_w=W1, output_w=W2)
```

압축 여부도 고를 수 있다(`savez_compressed`). 안에는 `embedding.npy`, `hidden_w.npy` 같은 파일이 들어 있다.

C++에서 읽으려면 **ZIP 리더가 필요하다.** 형식 자체는 단순하지만(중앙 디렉터리 + 로컬 헤더 + 데이터) 압축까지 지원하려면 deflate 구현이 있어야 하고, 그러면 zlib 의존성이 생긴다.

그래서 이 교재는 `.npy` 만 쓴다. 배열이 여러 개면 **파일을 여러 개 만든다.** 폴더 하나가 `.npz` 하나와 같은 일을 한다.

이 선택에는 이득도 있다. 배열 하나만 필요할 때 **그것만 읽으면 된다.** `.npz` 는 ZIP 디렉터리를 먼저 읽어야 하고, 압축돼 있으면 풀어야 한다.

D파트에서 모델 가중치를 저장할 때는 A7에서 만든 `HGNG` 형식 쪽을 쓴다. 우리가 정한 형식이라 우리 구조에 딱 맞고, 파이썬이 읽을 일이 없기 때문이다. **경계를 넘는 데이터만 표준 형식을 쓴다.**

</details>

**3.** 크기를 더 줄이려면 어떻게 하는가?

<details>
<summary>해답</summary>

500KB가 문제가 되는 크기는 아니지만, 모델이 커지면 이야기가 달라진다.

**타입을 줄인다.** `float32` 를 `float16` 으로 바꾸면 절반이다. `.npy` 의 `descr` 가 `<f2` 가 된다. 유효숫자가 3~4자리로 줄지만, **임베딩처럼 정밀도가 크게 안 중요한 데이터**에는 충분한 경우가 많다.

더 줄이려면 **정수로 양자화**한다. 값의 범위를 재서 `-1 ~ 1` 을 `-127 ~ 127` 로 옮기면 4분의 1이다.

```
양자화:  q = round(x / scale)
복원:    x ≈ q * scale
```

**D5가 이 주제를 통째로 다룬다.** 거기서는 저장 크기가 아니라 **추론 속도**가 목적이다 — 8비트 정수 곱셈이 32비트 실수 곱셈보다 훨씬 빠르기 때문이다. 그리고 A1 이후 처음으로 비트 연산(C 교재 `2.4`)이 다시 나온다.

**압축을 건다.** `savez_compressed` 나 gzip 을 쓰면 무작위 실수도 10~20%쯤 준다. 규칙성이 있으면 훨씬 많이 준다. 다만 읽을 때 풀어야 하므로 속도를 내준다.

크기·속도·정확도 중 둘만 고를 수 있다고 생각하면 대개 맞다.

</details>

**C5. CPU 최적화.** ★

C3의 훈련이 20만 예제 한 에폭에 **8.1초**였다. 10에폭이면 81초. 데이터를 10배 늘리면 13분이다.

그런데 이 모델은 가중치가 44,608개밖에 안 된다. 요즘 기준으로는 장난감이다. 계산을 세어보면 예제 하나에 곱셈이 약 10만 번이고, 20만 예제면 **200억 번**이다. 8초에 200억 번이면 초당 25억 번 — 요즘 CPU가 낼 수 있는 성능의 **몇 십분의 일**이다.

C5에서 그 격차를 좁힌다. 이 장이 **C++이 파이썬보다 명백히 유리한 유일한 구간**이다.

- **캐시 타일링** — 같은 계산을 다른 순서로. 행렬 곱셈의 세 루프를 어떻게 도느냐로 몇 배가 갈린다
- **SIMD** — 한 명령으로 여덟 개를 곱한다 (AVX2)
- **OpenMP** — 코어를 전부 쓴다
- **리덕션** — 여러 스레드가 같은 값에 더할 때 생기는 문제

원칙은 둘이다.

> **측정 없이 최적화하지 말 것.**
> **효과가 있을 줄 알았는데 없던 사례도 그대로 싣는다.**

두 번째가 이 교재의 태도다. A8에서 "6그램 단독은 자주 막힐 것"이라는 가정이 틀렸던 것처럼, 최적화에서도 예상이 자주 빗나간다. 빗나간 것도 결과다.

마지막에는 직접 최적화한 행렬 곱셈을 **OpenBLAS와 나란히 재본다.** "내가 어디까지 따라갔나"를 아는 것이 이 장의 검증이다.
