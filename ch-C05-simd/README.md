## 0. 두 가지 원칙

이 장은 규칙 두 개 위에 서 있다.

> **측정 없이 최적화하지 말 것.**
> **효과가 있을 줄 알았는데 없던 사례도 그대로 싣는다.**

두 번째가 이 교재의 태도다. A8에서 "6그램 단독은 자주 막힐 것"이라는 가정이 틀렸던 것처럼, 최적화에서도 예상이 자주 빗나간다. **빗나간 것도 결과다.**

실제로 이 장에서 교과서적인 처방 하나가 빗나간다.

```
[C5-5] 해봤는데 오히려 느려진 것

        블록        M,K 만      M,N,K 전부
          32          31.7            24.8
          64          30.6            26.3
```

"캐시 블로킹은 세 축을 다 쪼갠다"가 교과서의 설명인데, **재보니 손해였다.**

## 1. 먼저 어디가 느린지부터

C3의 훈련이 20만 예제에 8.1초였다. 어디를 고쳐야 하는가.

```
[C5-1] 먼저 어디가 느린지부터 본다

  단계                   곱셈 횟수        시간      비중
  은닉층 (48->64)             3072    0.021 초      7.7%
  출력층 (64->512)           32768    0.217 초     79.0%
  softmax (512)                  0    0.036 초     13.4%
```

**출력층이 79%다.** 곱셈 횟수가 은닉층의 10배이니 당연하다.

은닉층을 두 배 빠르게 만들면 전체가 4% 빨라진다. 출력층을 두 배 빠르게 만들면 **40%** 빨라진다. 어디를 고칠지는 이 표가 정한다.

> 이걸 **암달의 법칙**이라고 부른다. 전체의 10%를 차지하는 부분을 무한히 빠르게 만들어도 전체는 11%밖에 안 빨라진다. **재보고 고른다**는 규칙이 여기서 나온다.
>
> 그리고 softmax가 13.4%다. 곱셈이 하나도 없는데 `exp` 를 512번 부르기 때문이다. 초월함수는 생각보다 비싸다.

## 2. 같은 계산, 다섯 가지 방법

행렬 곱셈 `C = A × B` 를 다섯 가지로 쓴다. **답은 전부 같고 속도는 전부 다르다.**

```
[C5-3] 1024 x 1024 x 1024 로 키우면

  방법                            시간     GFLOP/s        배속   최대 차이
  1. 교과서 (i,j,k)          2.1329 초         1.0      1.0 배     0.0e+00
  2. 순서 바꾸기             0.0859 초        25.0     24.8 배     0.0e+00
  3. 블록                    0.0717 초        30.0     29.8 배     0.0e+00
  4. AVX2 + FMA              0.0436 초        49.2     48.9 배     1.9e-05
  5. 스레드                  0.0062 초       348.1    345.7 배     1.9e-05
```

**345배다.** 그리고 코드는 전부 열 줄 안팎이다.

### 1번 → 2번: 루프 순서만 바꿨다 (25배)

교과서에 나오는 그대로 쓰면 이렇다.

```cpp
for (i) for (j)
{
    Real Sum = 0;
    for (k) Sum += A[i*K + k] * B[k*N + j];
    C[i*N + j] = Sum;
}
```

`B[k*N + j]` 를 보자. `k` 가 1 늘 때마다 **`N` 칸씩 건너뛴다.** 캐시 라인 하나(64바이트 = float 16개)를 읽어서 4바이트만 쓰고 버린다. **93%를 버린다.**

순서를 바꾸면,

```cpp
for (i) for (k)
{
    Real Scale = A[i*K + k];      // 안쪽 루프 안에서 안 변한다
    for (j) C[i*N + j] += Scale * B[k*N + j];
}
```

`B` 도 `C` 도 **순차 접근**이다. 캐시 라인을 읽으면 16개를 다 쓴다.

**곱셈 횟수는 똑같다.** 메모리를 어떻게 훑느냐만 바꿨는데 25배다. C++ 교재 `5.5` 의 "배열은 연속된 메모리"라는 사실이 성능으로 환산되는 자리다.

### 2번 → 3번: 블록으로 쪼갠다 (1.2배)

`B` 전체가 4MB다(1024×1024 float). L2 캐시보다 크므로, `i` 가 한 칸 늘 때마다 `B` 를 처음부터 다시 읽는다.

`K` 를 128씩 쪼개면 한 번에 만지는 `B` 는 128행 = 512KB다. 캐시에 들어간다.

```cpp
for (i0) for (k0)                  // 블록
    for (i) for (k)                // 블록 안
        for (j) C[...] += ...;     // N 전체
```

**25.0 → 30.0.** 20% 빨라졌다. 루프 순서 바꾸기(25배)에 비하면 소박하다.

### 3번 → 4번: 한 명령으로 여덟 개 (1.6배)

AVX2는 256비트 레지스터를 가진다. `float` 이면 **여덟 개**가 들어간다.

```cpp
__m256 ScaleVector = _mm256_set1_ps(Scale);      // 같은 값 여덟 개

__m256 CValue = _mm256_loadu_ps(CRow + j);       // 여덟 개 읽고
__m256 BValue = _mm256_loadu_ps(BRow + j);
CValue = _mm256_fmadd_ps(BValue, ScaleVector, CValue);   // 곱하고 더하고
_mm256_storeu_ps(CRow + j, CValue);              // 여덟 개 쓴다
```

`_mm256_fmadd_ps` 가 **FMA**(Fused Multiply-Add)다. `a*b + c` 를 **한 명령**으로 하고, 중간 반올림이 없다. 곱셈과 덧셈을 따로 하는 것보다 빠르고 **정확하다.**

여덟 배가 아니라 1.6배인 이유는, 3번도 이미 컴파일러가 자동 벡터화하고 있었기 때문이다. 우리가 손으로 쓴 것은 **컴파일러가 못 하던 몇 가지**를 추가로 한 것뿐이다.

### 4번 → 5번: 코어를 전부 (7배)

```cpp
#pragma omp parallel for schedule(static)
for (int t = 0; t < Threads; t++)
{
    size_t From = M * t / Threads;
    size_t To = M * (t + 1) / Threads;
    GemmAvx2Core(A, B, C, M, N, K, From, To);
}
```

**겹치지 않게 나누는 것**이 요점이다. 스레드마다 `C` 의 서로 다른 줄만 건드린다. 같은 자리에 두 스레드가 쓰는 일이 없으므로 **잠금이 필요 없다.**

24스레드에서 7배가 나왔다. 24배가 아닌 이유는 물리 코어가 그보다 적고(하이퍼스레딩), 메모리 대역폭이 한계이고, 클럭이 떨어지기 때문이다.

> 만약 `C` 를 여러 스레드가 같은 자리에 더해야 했다면 `reduction` 이나 원자적 연산이 필요하고, 그러면 속도가 절반 이하로 떨어진다. **나누는 방법을 잘 고르면 동기화가 아예 안 필요하다** — 병렬화에서 가장 중요한 판단이다.

## 3. 최적화가 답을 바꾼다

표의 마지막 열을 다시 보자.

```
  1. 교과서 (i,j,k)          0.0e+00
  2. 순서 바꾸기             0.0e+00
  3. 블록                    0.0e+00
  4. AVX2 + FMA              1.9e-05    <- 달라졌다
  5. 스레드                  1.9e-05
```

**AVX2판부터 답이 달라진다.**

부동소수점 덧셈은 **결합법칙이 성립하지 않는다.** `(a+b)+c` 와 `a+(b+c)` 가 다를 수 있다. SIMD는 여덟 개를 동시에 더하므로 더하는 순서가 바뀌고, 결과가 미세하게 달라진다. FMA가 중간 반올림을 생략하는 것도 차이를 만든다.

`1.9e-05` 는 값 자체가 수백 수준인 것에 비하면 상대 오차 `1e-7` 쯤이다. `float` 의 정밀도 한계와 같은 크기다.

```cpp
const double Tolerance = (sizeof(Real) == 8) ? 1e-9 : 1e-2;
CHECK(Simd.WorstGap < Tolerance);
```

그래서 **`==` 로 검사할 수 없다.** 그리고 더 중요한 것은,

> **최적화한 코드와 안 한 코드가 다른 답을 낸다.** 훈련 결과가 재현이 안 되는 원인 중 하나가 이것이다. 스레드 수를 바꾸면 더하는 순서가 바뀌고, 손실 곡선이 미세하게 달라진다.
>
> 그래서 실무에서는 "결정적 모드"를 따로 두는 경우가 많다. 느리지만 **항상 같은 답**을 내는 경로다. 디버깅할 때만 켠다.

## 4. 어디까지 따라갔는가

절대적인 기준이 필요하다. **이 기계가 낼 수 있는 최대치**를 재서 비교한다.

```cpp
for (long long r = 0; r < Rounds; r++)
{
    for (int c = 0; c < Chains; c++)
    {
        Accumulator[c] = _mm256_fmadd_ps(Accumulator[c], One, One);
    }
}
```

FMA 명령만 줄지어 돌린다. 메모리를 아예 안 건드리므로 **연산 능력의 상한**이 나온다. `Chains` 를 8로 둔 것은 의존성을 끊어 파이프라인을 채우기 위해서다 — 연달아 같은 레지스터를 쓰면 앞 명령이 끝날 때까지 기다린다.

```
[C5-4] 이 기계가 낼 수 있는 최대치와 비교

                               GFLOP/s   최대치 대비
  한 스레드 최대치                 109          100%
  우리 AVX2 (1스레드)             49.2         45.0%
  전체 스레드 최대치               579          100%
  우리 병렬판                    348.1         60.1%
```

**한 스레드에서 45%, 전체에서 60%.**

전문 BLAS 라이브러리(OpenBLAS, MKL)는 이런 크기에서 80~90%를 낸다. 우리가 안 한 것들이 있다.

- **패킹** — `A` 와 `B` 를 SIMD가 읽기 좋은 순서로 미리 재배열
- **레지스터 타일링** — `C` 의 4×8 조각을 레지스터에 올려두고 한 번에 갱신
- **프리페치** — 다음에 쓸 데이터를 미리 불러오라고 CPU에 알림
- **어셈블리 손질** — 명령 순서를 직접 배치

**60%면 충분한가.** 답은 목적에 달렸다. 이 교재의 목적은 "왜 빨라지는지 이해하는 것"이고, 제품이 목적이라면 BLAS를 쓰는 게 맞다. **직접 만든 것과 전문가의 것 사이 거리를 아는 것**이 이 절의 소득이다.

> **재는 방식에 대한 고백.** 원래 계획은 OpenBLAS와 나란히 재는 것이었다. 그런데 그러려면 또 하나의 외부 의존성을 받아야 하고, A9에서 Kiwi를 받은 것만으로도 저장소가 무거워졌다. 대신 **기계의 이론 최대치**를 직접 재서 비교했다. 절대 성능은 OpenBLAS 쪽이 더 유용한 기준이지만, "하드웨어를 몇 % 쓰고 있나"는 이쪽이 더 곧바로 말해준다.
>
> 그리고 이 숫자는 **돌릴 때마다 조금씩 다르다.** 109 GFLOP/s가 나온 날도 있고 118이 나온 날도 있다. 노트북 CPU는 발열과 전력 상태에 따라 클럭이 오르내린다. **성능 측정은 원래 이렇게 흔들린다.**

## 5. 교과서가 틀렸던 자리

캐시 블로킹은 보통 **세 축을 다 쪼갠다**고 설명한다. 재보자.

```
[C5-5] 해봤는데 오히려 느려진 것

        블록        M,K 만      M,N,K 전부
          32          31.7            24.8
          64          30.6            26.3
         128          29.8            28.9
         256          29.8            29.8
```

**전부 M,K만 쪼갠 쪽이 낫거나 같다.** 블록이 작을수록 격차가 크다(32에서 28% 차이).

이유는 **안쪽 루프의 길이**다.

```cpp
for (size_t j = j0; j < jStop; j++)   // N 을 쪼개면 32번만 돈다
```

컴파일러는 이 루프를 자동 벡터화한다. 그런데 32번이면 SIMD 4회 + 루프 준비 비용이고, 1024번이면 SIMD 128회 + 같은 준비 비용이다. **준비 비용이 묻히지 않는다.**

그리고 `N` 을 쪼개면 `C` 의 같은 줄을 여러 번 오간다. 쓰기가 늘어난다.

**그럼 교과서가 틀렸는가.** 아니다. 세 축을 다 쪼개는 것이 맞는 전제가 있다.

- 안쪽 루프를 **손으로** 벡터화해서 블록 크기와 무관하게 만들었을 때
- `A`, `B` 를 **패킹**해서 블록 안에서 완전히 순차 접근이 되게 했을 때

그 조건을 안 맞춘 채 축만 쪼개면 손해다. **처방은 조건과 함께 와야 하는데, 조건은 잘 안 적혀 있다.**

이게 "측정 없이 최적화하지 말 것"의 뜻이다. 남의 처방을 그대로 옮기면 **빨라졌다고 착각**하기 쉽다. 재보면 안다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Gemm.hpp` · `.cpp` | 행렬 곱셈 다섯 판, CPUID 검사, 기계 최대치 측정 |

빌드 설정이 하나 늘었다.

| 설정 | 위치 |
|---|---|
| **OpenMP 지원** (`/openmp`) | `C/C++` → `언어` → `OpenMP 지원` = `예` |

알아둘 것.

- **재고 나서 고른다.** 79%를 차지하는 곳을 고쳐야 전체가 빨라진다
- **루프 순서 하나가 25배다.** 곱셈 횟수가 같아도 메모리 훑는 순서가 다르다
- **FMA 는 한 명령으로 곱하고 더한다.** 빠르고 중간 반올림이 없다
- **겹치지 않게 나누면 잠금이 필요 없다.** 병렬화의 첫 판단
- **최적화가 답을 바꾼다.** 부동소수점 덧셈에는 결합법칙이 없다
- **우리는 하드웨어의 45~60%를 쓴다.** 전문 BLAS는 80~90%
- **교과서적 처방에도 전제가 있다.** 전제를 안 맞추면 손해다

쓴 문법.

- 컴파일러 내장 함수(`_mm256_fmadd_ps`) — `<immintrin.h>`
- `__cpuid` / `_xgetbv` 로 CPU 기능 확인
- OpenMP 지시문 (`#pragma omp parallel for`)
- 함수 포인터로 여러 구현을 같은 자리에 꽂기 (C 교재 `7.9`)

## 연습문제

**1.** `CpuHasAvx2()` 가 `_xgetbv` 까지 확인하는 이유는?

<details>
<summary>해답</summary>

**CPU가 지원해도 운영체제가 모르면 못 쓴다.**

AVX는 256비트 YMM 레지스터를 쓴다. 운영체제는 스레드를 전환할 때 레지스터를 전부 저장했다 복원해야 하는데, **YMM이 있다는 걸 모르면 저장을 안 한다.** 그러면 다른 스레드가 끼어들었다 돌아왔을 때 값이 날아가 있다.

증상이 최악이다. 대부분은 잘 돌아가다가, **운 나쁘게 문맥 전환이 낀 순간에만** 틀린 값이 나온다. 재현이 안 되는 버그가 된다.

그래서 검사가 3단계다.

1. `CPUID.1:ECX[28]` — CPU가 AVX를 지원하는가
2. `CPUID.1:ECX[27]` — OS가 `XGETBV` 명령을 허용했는가 (OSXSAVE)
3. `_xgetbv(0) & 0x6 == 0x6` — OS가 XMM과 YMM 상태를 저장하겠다고 표시했는가

세 번째가 핵심이다. **OS가 명시적으로 동의해야** 쓸 수 있다.

요즘 윈도우와 리눅스는 전부 지원하므로 실제로 걸릴 일은 거의 없다. 그래도 넣는 이유는 A7의 엔디언 검사와 같다 — **조용히 틀리는 것보다 안 쓰는 게 낫다.**

</details>

**2.** `float` 대신 `double` 로 (`USE_DOUBLE`) 돌리면 성능이 어떻게 되는가?

<details>
<summary>해답</summary>

**절반 아래로 떨어진다.**

이유가 둘이고, 둘 다 2배씩이다.

**SIMD 레지스터에 절반만 들어간다.** 256비트에 `float` 은 8개, `double` 은 4개다. 같은 명령으로 절반만 처리한다.

**메모리를 두 배 읽는다.** 1024×1024 행렬이 4MB에서 8MB가 된다. 캐시에 들어가는 양이 절반이 되고, 메모리 대역폭도 두 배가 필요하다.

행렬 곱셈은 **메모리에 묶인**(memory-bound) 계산이라 두 번째가 더 아프다. 그래서 실제로는 2배보다 조금 더 느려질 수 있다.

**그럼에도 `double` 이 필요한 순간이 있다.** C2에서 봤듯 gradcheck는 `double` 없이는 판정이 안 된다. 그래서 `Real` 별칭을 둔 것이다 — 평소에는 `float`, 검증할 때만 `double`.

그리고 D5에서는 반대 방향으로 간다. `float` 을 **8비트 정수**로 줄이면 SIMD 레지스터에 32개가 들어간다. 정확도를 내주고 속도를 사는 거래다.

</details>

**3.** C3의 훈련 루프에 이 GEMM을 넣으면 얼마나 빨라지는가?

<details>
<summary>해답</summary>

**생각만큼 안 빨라진다.** 그리고 그 이유가 이 장의 마지막 교훈이다.

C3의 훈련은 예제를 **하나씩** 처리한다. 출력층 계산이 `(512×64) × (64×1)` — 행렬 곱하기 **벡터**다. 여기에는 GEMM의 최적화가 대부분 안 먹는다.

- 블로킹? `B` 가 64개짜리 벡터라 이미 캐시에 있다
- SIMD? 쓸 수 있지만, 읽어온 `A` 를 한 번씩만 쓰므로 **메모리 대역폭에 묶인다**
- 스레드? 일감이 너무 작다

그래서 진짜 이득은 **배치를 묶는 것**에서 온다. 64개 예제를 한꺼번에 처리하면 `(512×64) × (64×64)` 가 되고, `A` 를 한 번 읽어 64번 쓴다.

```
[C5-2] NPLM 출력층을 배치 64개로 묶으면 (512 x 64 x 64)
  1. 교과서 (i,j,k)           10.2 GFLOP/s
  5. 스레드                  154.2 GFLOP/s     15.1 배
```

그런데 그러려면 **훈련 코드를 통째로 고쳐야 한다.** 지금은 `FNplmTrace` 하나가 예제 하나를 담는다. 배치로 가려면 벡터가 행렬이 되고, 역전파도 전부 행렬로 바뀐다.

**이것이 D1에서 `FTensor` 를 만드는 이유다.** 차원 하나를 "배치"로 두고 모든 연산이 그 차원을 자동으로 처리하게 만든다. 그러지 않으면 배치 지원을 코드 곳곳에 손으로 흩뿌리게 된다.

정리하면 이렇다. **최적화의 가장 큰 이득은 코드를 빠르게 만드는 것이 아니라, 빠르게 만들 수 있는 모양으로 바꾸는 것에서 온다.**

</details>

## 다음 장

**C6. 결과 분석.**

C3에서 임베딩 512×16을 얻었다. C4에서 `.npy` 로 내보낼 수 있게 됐다. 이제 **그림으로 본다.**

16차원은 볼 수 없으므로 2차원으로 누른다. **PCA**(주성분 분석)를 쓰는데, 원리는 "가장 많이 흩어져 있는 방향 두 개를 찾는 것"이다. 계산은 파이썬이 하고, C++은 데이터를 내보내고 숫자를 검증한다.

**역할 분담이 이 장의 주제이기도 하다.**

- **C++** — 모델을 만들고, 숫자를 뽑고, 형식을 맞춰 내보낸다
- **파이썬** — 그림을 그린다. matplotlib 한 줄이면 되는 일을 C++로 할 이유가 없다

A파트 초입에 정한 원칙("파이썬은 데이터 준비와 시각화에만")이 여기서 실물이 된다. 그리고 그 경계를 **파일 형식이 지킨다** — C4에서 만든 `.npy` 가 계약서다.

그림에서 무엇이 보일지는 이미 짐작이 간다. C3-6에서 숫자로 본 것 — 숫자끼리, 구두점끼리, 받침이 같은 글자끼리 뭉치는 것 — 이 눈에 보이는 덩어리로 나타날 것이다.
