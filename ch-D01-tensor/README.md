## 0. 왜 `FMatrix` 로는 안 되는가

트랜스포머의 어텐션은 네 축을 동시에 다룬다.

```
(배치, 헤드, 위치, 차원)
```

`FMatrix` 로 하려면 첨자를 손으로 계산해야 한다.

```cpp
Raw[((n * H + h) * T + t) * D + d]
```

이 식을 코드 곳곳에 쓰면 **반드시 한 군데를 틀린다.** 그리고 고약한 것은,

```
[D1-1] 4차원 첨자를 손으로 쓰면

  모양 = (2, 4, 8, 16)
  맞는 식   ((n*H + h)*T + t)*D + d
  틀린 식   ((n*T + h)*H + t)*D + d   <- H 와 T 를 바꿔 썼다

  1024개 자리 중 768개가 어긋난다

  **헤드 수와 위치 수가 같으면 두 식이 같은 답을 낸다.**
  테스트를 (2, 8, 8, 4) 로 짜면 이 버그가 안 잡힌다.
```

**차원 크기가 우연히 같으면 테스트를 통과한다.** C1에서 "정사각 행렬에서는 안 드러난다"고 했던 것의 4차원 판이다.

그래서 첨자 계산을 **한 군데에 가둔다.** 그게 `FTensor` 의 존재 이유다.

```cpp
Real& FTensor::operator()(size_t A, size_t B, size_t C, size_t D)
{
    assert(Rank() == 4);
    assert(A < Shape[0] && B < Shape[1] && C < Shape[2] && D < Shape[3]);
    return Values[((A * Shape[1] + B) * Shape[2] + C) * Shape[3] + D];
}
```

`assert` 가 세 줄 붙어 있다. 범위를 벗어나면 그 자리에서 죽는다. 손으로 쓴 식은 **조용히 엉뚱한 자리를 읽는다.**

> **PyTorch 내부가 실제로 이렇게 생겼다.** `torch.Tensor` 는 데이터 포인터 + 모양 + 보폭(stride)을 들고, 첨자 계산을 안에서 한다. 우리가 만드는 것은 그 축소판이다.

## 1. 5의 규칙

B3의 `FVector` 는 멤버가 `std::vector<Real>` 하나였다. 복사·이동·소멸을 컴파일러가 알아서 했다 — **0의 규칙**.

`FTensor` 는 일부러 **날 포인터**를 든다.

```cpp
private:
    Real* Values = nullptr;
    std::vector<size_t> Shape;
    size_t Total = 0;
```

그러면 다섯 개를 직접 써야 한다.

| 것 | 하는 일 |
|---|---|
| 복사 생성자 | 새 버퍼를 잡고 내용을 옮겨 적는다 |
| 복사 대입 | 내 버퍼를 버리고 새로 잡아 옮겨 적는다 |
| **이동 생성자** | **버퍼를 훔쳐 온다** |
| **이동 대입** | 내 버퍼를 버리고 상대 것을 훔친다 |
| 소멸자 | 버퍼를 반납한다 |

> 실무에서는 `std::vector` 를 멤버로 쓰는 편이 옳다. 여기서 날 포인터를 든 이유는 **이동 시맨틱이 무엇을 하는지 코드에 보이게** 하려는 것이다. 감춰두면 배울 수가 없다.

### 이동은 훔치는 것이다

```cpp
FTensor::FTensor(FTensor&& Other) noexcept
    : Values(Other.Values), Shape(std::move(Other.Shape)), Total(Other.Total)
{
    Other.Values = nullptr;   // 반드시 비워야 한다
    Other.Total = 0;
}
```

포인터를 가져오고 **원본을 비운다.** 안 비우면 둘 다 소멸자에서 같은 버퍼를 해제하고, **이중 해제**로 죽는다.

`&&` 는 "곧 사라질 임시 객체"라는 표시다. 어차피 없어질 것이니 속을 빼가도 된다.

### 자기 대입을 걸러야 한다

```cpp
FTensor& FTensor::operator=(const FTensor& Other)
{
    if (this == &Other) return *this;   // 이 줄이 없으면
    delete[] Values;                    // 내 버퍼를 지우고
    ...
    std::memcpy(Values, Other.Values, ...);   // 그 버퍼에서 읽으려 든다
}
```

`A = A;` 를 누가 쓰겠냐 싶지만, `Bag[i] = Bag[j]` 에서 `i == j` 이면 그 일이 일어난다.

### `noexcept` 가 진짜로 필요하다

이동 생성자에 `noexcept` 를 안 붙이면 어떻게 되는가.

`std::vector` 가 커질 때 원소를 새 버퍼로 옮겨야 한다. 옮기는 도중 예외가 나면 **원본도 새 버퍼도 망가진 상태**가 된다. 그래서 `std::vector` 는 이렇게 판단한다.

> 이동이 예외를 안 던진다고 **약속했으면** 이동하고, 아니면 안전하게 **복사한다.**

```
[D1-3] 복사가 몇 번 일어나는가

                                  할당      복사      이동     복사한 원소
  함수에서 값으로 받기               1         0         0               0
  A 를 B 에 복사                     2         1         0           65536
  A 를 B 로 이동                     1         0         1               0
  vector 에 8개 담기                 8         0        24               0
```

마지막 줄을 보자. **`vector` 에 여덟 개를 담는데 복사가 0이다.** `noexcept` 를 지우면 여기가 복사로 바뀐다. 한 단어가 성능을 가른다.

```cpp
CHECK(BagCopies == 0);
```

> 이동 횟수가 24인 것은 `vector` 가 1 → 2 → 4 → 8 로 커지면서 기존 원소를 옮겼기 때문이다. A4에서 본 **분할 상환**이 여기서도 나온다.

### 값으로 돌려줘도 복사가 없다

```cpp
FTensor MakeTensor(size_t Rows, size_t Cols, Real Value)
{
    FTensor Result({ Rows, Cols });
    Result.Fill(Value);
    return Result;              // 복사? 이동?
}

FTensor A = MakeTensor(256, 256, Real(1));
```

**둘 다 아니다. 복사도 이동도 0이다.**

컴파일러가 `Result` 를 아예 `A` 의 자리에 직접 만든다. 이걸 **복사 생략**(copy elision)이라고 하고, C++17부터는 선택이 아니라 **의무**다.

C로 같은 것을 만들면 이런 고민을 해야 했다.

```c
FTensor* TensorMake(...);        // 힙에 만들어 포인터를 준다. 누가 free?
void TensorMake(FTensor* Out);   // 밖에서 만들어 넘긴다. 초기화는 누가?
```

**C++은 "값으로 돌려준다"가 공짜가 됐다.** 그래서 코드가 수식처럼 읽힌다.

## 2. 값의 차이

```
[D1-4] 복사와 이동의 값 차이

  1024 x 1024 텐서 8개 (32 MB) 를 50번 주고받기

  복사 = 0.438 초, 옮긴 원소 419430400개
  이동 = 0.000 초, 옮긴 원소 0개
  이동 쪽은 아예 재어지지 않는다 (시계 해상도 아래)
```

**4억 개를 옮기는 일과 포인터 여덟 개를 옮기는 일**의 차이다.

이동은 **크기와 무관**하다. 1024×1024든 10000×10000이든 같은 시간이다. 그래서 텐서를 함수에서 돌려주고, 컨테이너에 담고, 다른 함수로 넘기는 것이 전부 공짜가 된다.

D6의 역전파에서 텐서가 함수 사이를 수십 번 오간다. 이게 없으면 **매번 수십 MB를 복사**한다.

## 3. 모양 바꾸기와 축 바꾸기

이름이 비슷해 보이지만 **비용이 전혀 다르다.**

### 모양 바꾸기 — 값을 안 움직인다

```
  (2,3,4) -> (24), (6,4), (2,12)
  값의 순서가 그대로인가 = 예
  T(1,2,3) = 23, Wide(5,3) = 23 (같은 원소)
```

행 우선으로 담아두면 `(2,3,4)` 든 `(6,4)` 든 **메모리에 놓인 순서가 같다.** 모양 정보만 바꾸면 된다.

> 우리 `Reshaped` 는 사실 복사를 한 번 한다. 진짜 프레임워크는 **같은 버퍼를 공유하는 뷰**를 돌려준다. 그러려면 참조 계수(`std::shared_ptr`)가 필요하고, "누가 버퍼를 소유하는가"가 복잡해진다. 이 교재에서는 거기까지 안 간다 — 다만 **왜 PyTorch의 `reshape` 가 때로는 복사하고 때로는 안 하는지**는 이 이야기다.

### 축 바꾸기 — 값을 옮긴다

```
  (2,4,8,16) -> (2,8,4,16)
  Swapped(n,t,h,d) == T(n,h,t,d) 인가 = 예
  두 번 바꾸면 제자리인가 = 예
```

`(배치, 헤드, 위치, 차원)` 을 `(배치, 위치, 헤드, 차원)` 으로 바꾸는 일이다. D2의 어텐션에서 실제로 한다.

이건 메모리 배치가 **정말로** 달라지므로 값을 옮겨야 한다.

```cpp
for (size_t Flat = 0; Flat < Total; Flat++)
{
    // 평평한 번호를 각 축의 첨자로 푼다
    size_t Remaining = Flat;
    for (size_t d = Rank(); d-- > 0; )
    {
        Index[d] = Remaining % Shape[d];
        Remaining /= Shape[d];
    }

    std::swap(Index[DimA], Index[DimB]);
    // 새 자리를 계산해 옮긴다
}
```

`for (size_t d = Rank(); d-- > 0; )` 는 `size_t` 로 역방향 루프를 도는 관용구다. `d >= 0` 은 부호 없는 정수에서 **항상 참**이라 무한 루프가 된다.

**두 번 바꾸면 제자리**라는 것이 좋은 검사다. 되돌아오면 첨자 계산이 양방향으로 맞는 것이다.

## 4. 연산자를 B3과 반대로 정했다

B3에서 `FVector` 의 `operator*` 를 **내적**으로 뒀다. 그때 이렇게 적었다.

> D파트에서 텐서를 다룰 때는 원소별 곱이 훨씬 자주 나온다. 그래서 `FTensor` 에서는 `operator*` 를 **원소별 곱**으로 두고 내적은 이름을 준다.

그대로 했다.

```
  A = [1 2; 3 4], B = [5 6; 7 8]

  A + B      = [6 8; 10 12]
  A * B      = [5 12; 21 32]   (원소별)
  A * 10     = [10 20; 30 40]
  MatMul(A,B)= [19 22; 43 50]  (행렬 곱은 이름 있는 함수)
```

### 왜 이쪽이 맞는가

트랜스포머 코드에서 실제로 나오는 연산을 세어보면,

- 원소별 곱 — 마스킹, 게이팅, 드롭아웃, 활성화 함수와의 곱
- 행렬 곱 — 층마다 몇 번

**원소별이 훨씬 자주 나온다.** 그리고 `A * B` 라고 썼을 때 모양이 안 맞으면 원소별은 **즉시 걸리지만**, 행렬 곱은 `(2,3) × (3,4)` 처럼 우연히 맞아버릴 수 있다.

NumPy도 PyTorch도 같은 선택을 했다. `*` 가 원소별이고 `@` 가 행렬 곱이다. **우리가 독창적인 게 아니라, 실전에서 그쪽이 낫다는 것이 이미 확인됐다.**

### 묶음 행렬 곱

```
  (3,2,4) x (3,4,5) = (3,2,5)
```

앞쪽 축은 **묶음**으로 본다. 3개의 `(2,4) × (4,5)` 를 각각 계산한다. 어텐션에서 배치와 헤드가 이렇게 처리된다.

```cpp
size_t Batches = 1;
for (size_t d = 0; d + 2 < A.Rank(); d++) Batches *= A.Size(d);
```

**뒤 두 축만 행렬로 보고 나머지는 세기만 한다.** 이 규칙 하나로 2차원이든 4차원이든 같은 코드가 돈다.

## 정리

만든 것.

| 파일 | 내용 |
|---|---|
| `lib/Tensor.hpp` · `.cpp` | N차원 텐서. 5의 규칙, 모양 바꾸기, 축 바꾸기, 연산자 |

알아둘 것.

- **첨자 계산은 한 군데에 가둔다.** 차원 크기가 같으면 버그가 안 잡힌다
- **자원을 직접 들면 다섯을 다 쓴다.** 하나만 빠져도 누수나 이중 해제
- **이동은 훔치는 것이다.** 원본을 반드시 비운다
- **`noexcept` 를 빼면 `vector` 가 복사로 되돌아간다.** 한 단어가 성능을 가른다
- **값으로 돌려주는 것이 공짜다.** C++17의 복사 생략은 의무다
- **모양 바꾸기는 공짜, 축 바꾸기는 안 공짜**
- **`operator*` 는 원소별.** 행렬 곱은 이름 있는 함수
- **부호 없는 정수로 역방향 루프는 `for (d = Rank(); d-- > 0; )`**

쓴 문법.

- 5의 규칙 — C++ 교재 `3.2`, `11.3`
- `noexcept` 와 `std::move`
- 연산자 오버로딩 — C++ 교재 `3.3`
- `std::initializer_list` 로 `FTensor({2,3,4})` 쓰기

## 연습문제

**1.** 이동 생성자에서 `Other.Values = nullptr;` 를 지우면 어떻게 되는가?

<details>
<summary>해답</summary>

**이중 해제로 죽는다.** 다만 **언제** 죽는지가 고약하다.

```cpp
FTensor A({1000, 1000});
{
    FTensor B = std::move(A);   // B 와 A 가 같은 버퍼를 가리킨다
}                               // B 가 소멸. 버퍼 해제
// A 도 여전히 그 버퍼를 가리킨다
A.At(0) = 1;                    // 반납한 메모리에 쓴다
```

증상이 셋 중 하나다.

- **바로 죽는다** — 운이 좋은 경우. 디버거가 그 자리를 짚어준다
- **나중에 죽는다** — 반납된 메모리가 다른 할당에 재사용된 뒤 그쪽이 깨진다. 원인과 증상이 멀어진다
- **안 죽는다** — 값이 조용히 틀린다

Debug 빌드에서는 MSVC가 반납된 메모리를 `0xDD` 로 채우므로 죽을 확률이 올라간다. A6 연습문제 1에서 본 것과 같은 이야기다.

이런 버그를 찾는 도구가 있다. Visual Studio의 **주소 소독기**(`/fsanitize=address`)를 켜면 반납된 메모리 접근을 즉시 잡는다. 느려지지만 디버깅할 때는 켤 만하다.

그리고 근본 대책은 **날 포인터를 안 쓰는 것**이다. `std::vector<Real>` 나 `std::unique_ptr<Real[]>` 를 멤버로 두면 이동이 자동으로 올바르게 된다. 우리는 배우려고 손으로 썼다.

</details>

**2.** `Reshaped` 가 복사를 안 하고 같은 버퍼를 공유하게 만들려면?

<details>
<summary>해답</summary>

**버퍼의 소유권을 나눠 가져야 한다.** `std::shared_ptr<Real[]>` 를 쓰면 된다.

```cpp
std::shared_ptr<Real[]> Values;   // 참조 계수가 붙는다
std::vector<size_t> Shape;
```

`Reshaped` 는 같은 `shared_ptr` 를 복사하고 `Shape` 만 바꾼 텐서를 돌려준다. 마지막 참조가 사라질 때 버퍼가 반납된다.

그런데 대가가 셋이다.

**쓰기가 위험해진다.** `A` 를 고치면 `A.Reshaped(...)` 로 만든 `B` 도 바뀐다. 원하는 동작일 때도 있고 아닐 때도 있다. PyTorch가 이것 때문에 `view` 와 `reshape` 를 나눠 뒀다 — `view` 는 반드시 공유, `reshape` 는 필요하면 복사.

**참조 계수 비용이 든다.** 텐서를 복사할 때마다 원자적 증가·감소가 일어난다. 여러 스레드가 같은 텐서를 만지면 그 원자 연산이 병목이 될 수 있다.

**보폭(stride)이 필요해진다.** 진짜 뷰를 지원하려면 "이 축에서 한 칸 가려면 몇 개 건너뛰는가"를 축마다 들고 있어야 한다. 그러면 축 바꾸기도 **값을 안 옮기고** 보폭만 바꾸면 된다 — 대신 모든 연산이 보폭을 고려해야 해서 코드가 두 배쯤 복잡해진다.

이 교재는 거기까지 안 간다. 대신 **왜 PyTorch가 그렇게 생겼는지**는 이제 설명할 수 있다. `tensor.is_contiguous()` 나 `tensor.contiguous()` 를 불러야 하는 상황이 바로 이 보폭 이야기다.

</details>

**3.** `MatMul` 은 앞쪽 축을 "묶음"으로 센다. `(3,2,4) × (4,5)` 는 되는가?

<details>
<summary>해답</summary>

**된다. 그리고 그게 브로드캐스팅의 가장 단순한 형태다.**

```cpp
const Real* Right = B.Data() + ((B.Rank() > 2) ? (b * K * N) : 0);
```

`B` 가 2차원이면 묶음마다 **같은 행렬**을 쓴다. 오프셋이 0으로 고정된다.

이게 실제로 자주 필요하다. 신경망의 층 하나는 `(배치, 위치, 차원) × (차원, 출력)` 인데, 가중치 행렬은 배치마다 같다.

그런데 우리 구현은 **아주 제한적인 브로드캐스팅**만 한다. 이런 것들은 안 된다.

- `(3,2,4) × (1,4,5)` — 첫 축이 1이면 늘려야 한다
- `(3,1,2,4) × (3,7,4,5)` — 중간 축이 1이면 늘려야 한다

NumPy와 PyTorch는 이 규칙을 일반적으로 구현한다. **"크기가 1인 축은 필요한 만큼 늘린다"** 가 규칙이고, 뒤에서부터 축을 맞춰본다.

일반 브로드캐스팅을 구현하려면 각 피연산자의 **보폭**을 0으로 두는 기법을 쓴다. 크기 1인 축의 보폭을 0으로 만들면, 그 축의 첨자가 무엇이든 같은 자리를 읽는다. 늘리는 대신 **제자리를 반복해서 읽는** 것이다.

우아하지만, 그걸 하려면 연습문제 2의 보폭 이야기가 먼저 필요하다. 이 교재의 텐서는 **행 우선 연속 메모리**만 다루고, 필요한 브로드캐스팅은 D2~D4에서 나올 때마다 손으로 처리한다. **범위를 정하고 그 안에서 완결하는 것**도 설계다.

</details>

## 다음 장

**D2. 어텐션 순전파.**

텐서가 생겼으니 어텐션을 만든다. 식은 짧다.

```
Attention(Q, K, V) = softmax(QKᵀ / √d) V
```

한 줄인데 여기 트랜스포머의 전부가 들어 있다.

- `QKᵀ` — 모든 위치가 모든 위치를 본다. `(위치 × 위치)` 행렬이 나온다
- `/ √d` — 차원이 크면 내적이 커진다. 나눠서 softmax가 뾰족해지는 것을 막는다
- `softmax` — C1에서 만든 것을 그대로 쓴다. 각 행의 합이 1이 된다
- `V` 를 곱한다 — 주목한 만큼 섞어 온다

검증이 재미있다.

- **각 행의 합이 정확히 1이어야 한다** (softmax를 제대로 걸었으면)
- **마스크를 씌우면 우상단이 전부 0이어야 한다** (뒤를 못 보게 막았으면)

두 번째가 **인과 마스크**다. 언어모델은 다음 글자를 맞히는 것이 일이므로, 훈련할 때 뒤를 보면 답을 베끼는 것이 된다. 그 한 줄이 빠지면 **손실이 거짓말처럼 잘 내려가고** 생성은 전혀 안 된다. A0에서 말한 "조용히 틀리는" 것의 교과서적 사례다.
