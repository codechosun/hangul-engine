## 0. 여기까지 오면 완성품이 남는다

조각이 다 모였다. 이어 붙이면 트랜스포머다.

```
토큰 → 임베딩 + 위치 → 블록 × N → 최종 정규화 → 출력층 → 점수
```

**훈련을 안 할 독자는 여기서 멈춰도 된다.** 가중치를 어디선가 받아오면 이 코드로 글을 생성할 수 있다. 추론 경로가 완결되는 자리다.

그리고 이 장에서 확인한다.

```
[D4-1] NumPy 참조 구현과 점수 맞추기
  정답표 66줄 대조 -> 어긋난 줄 0개 (허용 1e-04)
  최대 차이 = 2.544e-07
```

**우리 구현이 "그럴듯한 것"이 아니라 맞는 것**임을 확인하는 자리다.

## 1. 위치를 더한다

```cpp
X(b, t, d) = TokenEmbedding(Token, d) + PositionEmbedding(t, d);
```

**한 줄인데 없으면 모델이 순서를 모른다.**

어텐션은 위치에 무관한 연산이다. `Q Kᵀ` 는 내적의 모음이고, 내적은 순서를 안 본다. 입력 순서를 뒤섞어 넣으면 출력도 같이 뒤섞일 뿐 **값은 그대로**다.

그래서 위치 정보를 입력에 **섞어 넣는다.** 우리는 가장 단순한 방법을 쓴다 — 위치마다 학습 가능한 벡터를 하나씩 두고 더한다.

> 요즘 모델은 대개 **RoPE**(회전 위치 임베딩)를 쓴다. 더하는 대신 `Q` 와 `K` 를 위치에 따라 회전시키는 방법인데, 훈련 때 본 것보다 긴 문맥에서도 잘 동작한다. 우리 방식은 `MaxLength` 를 넘으면 아예 못 쓴다.
>
> 여기서 학습 가능한 위치 임베딩을 고른 이유는 **코드가 한 줄**이기 때문이다. 이 교재의 목적은 구조를 이해하는 것이고, 위치 인코딩은 갈아 끼울 수 있는 부품이다.

## 2. NumPy 로 다시 쓴다

C3에서 쓴 방식 그대로다. **같은 계산을 다른 사람이, 다른 모양으로** 쓴다.

```python
Q = (Normed @ W["Q"]).reshape(Length, HEADS, Head).transpose(1, 0, 2)
Scores = (Q @ K.transpose(0, 2, 1)) / np.sqrt(Head)
Scores = np.where(Mask[None, :, :], -1e30, Scores)
Weights = Softmax(Scores)
```

C++ 쪽은 `for` 루프로, 파이썬 쪽은 행렬 연산으로. **모양이 다르게** 쓰는 것이 중요하다. 같은 모양으로 옮겨 적으면 같은 오해를 두 번 쓴다.

```
  정답표 66줄 대조 -> 어긋난 줄 0개 (허용 1e-04)
  최대 차이 = 2.544e-07
```

`float` 의 유효숫자가 7자리이고 점수가 1 정도이므로 `2.5e-07` 은 **정밀도 한계 수준**이다.

이 검사가 잡아주는 것들을 세어보면 놀랍다.

- 위치 임베딩을 안 더했거나 잘못 더했는가
- 헤드를 나누는 자리가 맞는가
- `√d` 로 나눴는가, `√Model` 로 나눴는가
- 마스크의 방향이 맞는가 (위/아래)
- 잔차를 정규화 **전** 값에 더했는가 **후** 값에 더했는가
- RMSNorm 의 `Epsilon` 을 제곱근 안에 넣었는가 밖에 넣었는가
- 최종 정규화를 넣었는가

**하나라도 틀리면 66줄이 전부 어긋난다.**

> **PyTorch 대신 NumPy 를 쓴 이유.** 원래 계획은 PyTorch 와 대조하는 것이었다. 그런데 200MB 짜리 의존성이 하나 더 붙는다. A9에서 Kiwi를 받은 것만으로도 저장소가 무거워졌다.
>
> 대가가 있다. PyTorch는 수많은 사람이 검증한 구현이고, NumPy 참조는 **내가 쓴 것**이다. 같은 사람이 두 번 쓰면 같은 오해를 두 번 쓸 수 있다. 그래서 파이썬 쪽은 C++ 코드를 안 보고 **공개된 수식에서 바로** 썼고, 계산 모양도 다르게 했다. 완벽한 대비책은 아니다 — 이 한계는 적어두는 편이 낫다.

## 3. KV 캐시

생성할 때는 토큰을 하나씩 붙인다. 그런데 **앞의 것들은 안 바뀐다.**

```
"한"        → K₁, V₁ 계산
"한국"      → K₁, V₁ 은 그대로. K₂, V₂ 만 새로
"한국어"    → K₁, V₁, K₂, V₂ 그대로. K₃, V₃ 만 새로
```

들고 있으면 매번 **한 칸만** 계산하면 된다.

```cpp
Cache.Keys[Layer](0, h, Position, d) = K(0, h, 0, d);
Cache.Values[Layer](0, h, Position, d) = V(0, h, 0, d);
```

### 마스크가 필요 없어진다

```cpp
FAttention Attended = Attend(Q, UsedK, UsedV, false);
```

**볼 수 있는 것만 넘겼기 때문**이다. `Position + 1` 개만 잘라 주면 미래를 볼 방법 자체가 없다.

인과 마스크의 본질이 여기서 드러난다. 마스크는 "한꺼번에 계산하려니 어쩔 수 없이 필요한 장치"이지 모델의 일부가 아니다. 하나씩 계산하면 자연스럽게 지켜진다.

### 같은 답이 나오는지 반드시 확인한다

```
[D4-2] 한 번에 vs 한 글자씩
  통째로 넣은 것과 하나씩 넣은 것의 최대 차이 = 0.000e+00
```

```cpp
CHECK(WorstGap < Tolerance);
```

**정확히 0이다.** 같은 순서로 같은 계산을 하므로 비트까지 같아야 하고, 실제로 그렇다.

이 검사가 왜 결정적인가. 캐시 버그는 **증상이 안 보인다.**

- 캐시를 한 칸 밀려 쓰면 → 글자는 계속 나온다. 좀 이상할 뿐
- 위치 임베딩을 `Position` 대신 `0` 으로 주면 → 글자는 계속 나온다
- 캐시를 지우는 것을 잊으면 → 이전 문장의 꼬리가 섞인다

**전부 "돌아가는 것처럼 보인다."** 한꺼번에 계산한 것과 대조하는 검사가 없으면 못 잡는다.

## 4. 얼마나 빨라지는가

```
     생성 길이     캐시 없이        캐시로      배속
            16      0.016 초      0.004 초    3.8 배
            32      0.067 초      0.010 초    6.6 배
            64      0.273 초      0.030 초    9.1 배
           128      1.013 초      0.104 초    9.7 배
```

**길이가 길어질수록 격차가 벌어진다.** 그게 핵심이다.

계산량을 세어보면, 모델차원을 `M`, 생성 길이를 `T` 라 할 때

| | 한 토큰 | 전체 |
|---|---|---|
| 캐시 없이 | `O(t·M² + t²·M)` | `O(T²M² + T³M)` |
| 캐시로 | `O(M² + t·M)` | `O(T·M² + T²M)` |

**전체가 `T` 배 차이난다.** 이론상 `T = 128` 이면 128배여야 한다.

### 그런데 9.7배다

이론과 실제가 13배 차이난다. 왜인가.

`Step` 한 번에 **캐시를 잘라내는 복사**가 들어간다.

```cpp
for (h) for (t < Visible) for (d)
{
    UsedK(0, h, t, d) = Cache.Keys[Layer](0, h, t, d);
}
```

`O(Position × Model)` 을 층마다 복사한다. 그리고 `FDense::Forward` 가 `Reshaped` 를 두 번 부르는데(D3 연습문제 1) 그것도 복사다. 작은 텐서 할당도 수십 번 일어난다.

**계산은 줄었는데 부수적인 복사가 남았다.**

제대로 하려면 D1 연습문제 2의 **뷰**가 필요하다. 캐시의 일부를 복사 없이 그대로 가리킬 수 있어야 한다. 그러려면 텐서에 보폭(stride)과 참조 계수가 들어가야 하고, 구현이 두 배로 복잡해진다.

> **이론상의 배속을 그대로 못 받는 것이 보통이다.** 그리고 그 차이가 어디서 오는지 아는 것이 최적화의 시작이다. C5에서 "하드웨어의 45%를 쓴다"고 잰 것과 같은 자리다.

## 5. 캐시가 먹는 메모리

```
  층 4, 헤드 4, 최대길이 128, 헤드차원 32
  캐시 크기 = 512 KB (가중치는 3652 KB)
```

우리 장난감에서는 캐시가 가중치의 7분의 1이다. 그런데 **실제 크기에서는 뒤집힌다.**

```
  같은 계산을 요즘 크기로 해보면
    층 32, 헤드 32, 헤드차원 128, 문맥 8192, 동시 요청 32
    캐시 = 128.0 GB (fp16 기준)
```

계산은 이렇다.

```
2 (K와 V) × 32층 × 32헤드 × 128차원 × 8192문맥 × 32요청 × 2바이트 = 128 GB
```

같은 규모의 모델 가중치가 대략 **14 GB** 다(70억 개, fp16). **캐시가 아홉 배 크다.**

**추론 서버 메모리의 대부분이 이것**이고, 동시 요청 수를 못 늘리는 이유이기도 하다. GPU 한 장에 80GB가 있어도 가중치 14GB를 빼면 66GB, 그걸로 받을 수 있는 동시 요청 수가 정해진다.

그래서 나온 기법들이 있다.

- **GQA / MQA** — 헤드마다 다른 `K`, `V` 를 쓰지 않고 몇 개가 공유한다. 캐시가 헤드 수만큼 줄어든다
- **페이지드 어텐션** — 캐시를 고정 크기 조각으로 관리한다. 운영체제의 가상 메모리와 같은 발상
- **캐시 양자화** — `K`, `V` 를 8비트로 저장한다. D5의 이야기가 여기에도 적용된다

## 6. 아직 아무것도 안 배운 모델

```
  뽑은 토큰 번호: 0 250 377 12 258 321 384 241 358 381 ...

  평균 손실 = 6.2469, 어휘의 로그 = 6.2383
  퍼플렉서티 = 516.4
```

```cpp
CHECK(Ppl > (double)BIG_VOCAB * 0.5);
CHECK(Ppl < (double)BIG_VOCAB * 2.0);
```

**어휘 크기가 512인데 퍼플렉서티가 516.4다.**

C1에서 세운 그 검사가 트랜스포머에서도 그대로 통과한다. 층이 네 개, 가중치가 93만 개로 늘었는데도 **초기 상태는 여전히 균등 분포**다.

이게 확인해주는 것이 많다.

- 순전파에 폭주하는 곳이 없다 — 있으면 퍼플렉서티가 튄다
- 최종 정규화가 제대로 걸렸다 — 빠지면 점수가 커져 퍼플렉서티가 내려간다
- 라벨이 새지 않는다 — 새면 퍼플렉서티가 훨씬 작다

**훈련을 시작하기 전에 이 숫자를 본다.** C1부터 다섯 장에 걸쳐 같은 검사를 하고 있다.

## 연습문제

**1.** `Step` 에서 위치 임베딩을 `PositionEmbedding(Position, d)` 대신 `PositionEmbedding(0, d)` 로 주면?

<details>
<summary>해답</summary>

**D4-2의 대조 검사가 즉시 잡는다.** 그리고 그 검사가 없으면 **아무도 못 잡는다.**

증상을 생각해보자. 모든 토큰이 "0번 위치"라고 주장하게 된다. 그러면,

- 모델은 글자를 계속 뽑는다
- 문법도 어느 정도 맞는다 — 어텐션이 내용은 제대로 보고 있으므로
- 다만 **순서 감각이 없다.** 문장이 끝날 줄 모르고, 앞뒤가 뒤엉킨다

훈련된 모델에서 이 버그가 있으면 "생성 품질이 좀 이상한데?" 정도로 느껴진다. 손실을 재봐도 (통째 계산 경로로 재면) 정상이다. **생성 경로에만 있는 버그**이기 때문이다.

이런 종류가 특히 위험하다. **훈련과 추론이 서로 다른 코드 경로를 쓰면** 한쪽만 틀릴 수 있고, 그러면 훈련 지표는 멀쩡한데 제품이 이상해진다.

대책은 하나다. **두 경로가 같은 답을 내는지 검사한다.**

```cpp
CHECK(WorstGap < Tolerance);
```

실무에서 이걸 "훈련-추론 일치성 검사"라고 부르고, 모델을 배포하기 전에 반드시 돌린다.

</details>

**2.** 문맥이 `MaxLength` 를 넘으면 어떻게 되는가?

<details>
<summary>해답</summary>

**`assert` 에 걸려 죽는다.**

```cpp
assert(Cache.Length < Config.MaxLength);
```

Release 빌드에서는 `assert` 가 사라지므로 **캐시 배열 밖을 쓴다.** 그러면 인접한 메모리가 깨지고, 어디서 터질지 모른다.

실제 시스템은 이 경우를 처리해야 한다. 방법이 몇 가지다.

**(가) 거절한다.** "문맥이 너무 깁니다" 오류를 돌려준다. 가장 정직하고, 사용자가 무슨 일인지 안다.

**(나) 앞을 버린다**(sliding window). 오래된 토큰의 캐시를 버리고 새 것을 넣는다. 그런데 우리 위치 임베딩은 **절대 위치**라 문제가 생긴다 — 버린 뒤 위치 번호를 어떻게 매길 것인가. RoPE는 상대 위치라 이 문제가 덜하다.

**(다) 요약한다.** 앞부분을 짧게 줄여 넣는다. 품질을 내주고 길이를 산다.

우리 교재는 (가)다. 다만 `assert` 만으로는 부족하다 — E2에서 엔진으로 묶을 때 **공개 API가 오류 코드를 돌려주도록** 고친다. 결정 15에서 정한 "예외 대신 반환 코드"가 거기서 값을 한다.

그리고 이건 라이브러리 설계의 일반적인 이야기이기도 하다. **`assert` 는 프로그래머의 실수를 잡는 것이고, 오류 코드는 사용자의 입력을 처리하는 것이다.** 둘을 섞으면 안 된다.

</details>

**3.** 캐시가 가중치보다 큰 것이 왜 문제인가? 가중치를 줄이는 것과 캐시를 줄이는 것 중 무엇이 급한가?

<details>
<summary>해답</summary>

**둘이 줄어드는 방식이 다르다.**

가중치는 **한 번 올려두면 모든 요청이 나눠 쓴다.** 14GB짜리 모델에 요청이 백 개 와도 가중치는 여전히 14GB다.

캐시는 **요청마다 따로 든다.** 동시 요청이 두 배면 캐시도 두 배다.

그래서 **처리량**(초당 몇 명)을 늘리려면 캐시를 줄여야 한다. 가중치를 절반으로 줄이면 여유 공간이 조금 늘 뿐이지만, 캐시를 절반으로 줄이면 **동시 요청을 두 배로 받는다.**

그런데 가중치를 줄이는 쪽이 훨씬 활발히 연구됐다. 양자화, 가지치기, 증류 — 전부 가중치 이야기다. 캐시 쪽 기법(GQA, 페이지드 어텐션)은 대체로 나중에 나왔다.

이유는 **문맥이 짧았기 때문**이다. 문맥이 512였을 때는 캐시가 작았다. 8192, 128K로 늘어나면서 캐시가 병목이 됐고, 그때서야 처방이 나왔다.

**문제가 실제로 터진 뒤에 처방이 나온다** — D3의 QK-Norm에서도 같은 이야기를 했다. 이 분야가 움직이는 방식이다.

한 가지 덧붙이면, **긴 문맥이 비싼 진짜 이유**가 이것이다. 계산량이 제곱으로 느는 것도 문제지만, 그건 FlashAttention 같은 것으로 상당히 눌렀다. 남은 것은 캐시 메모리이고, 이건 물리적으로 줄일 방법이 제한적이다.

</details>

## 다음 장

**D5. 양자화.**

D4까지 오면 추론이 완결된다. D5는 그 추론을 **더 작고 빠르게** 만드는 장이다.

지금 우리 가중치는 전부 `float` 이다. 93만 개면 3.6MB. 70억 개짜리 모델이면 28GB다.

**8비트 정수로 바꾸면 4분의 1이 된다.**

```
양자화:  q = round(x / scale)
복원:    x ≈ q × scale
```

그런데 `scale` 을 어떻게 정하는가. 행렬 전체에 하나? 줄마다 하나? 그 선택이 정확도를 좌우한다.

그리고 **A1 이후 처음으로 비트 연산이 다시 나온다.** 4비트로 가면 한 바이트에 두 개를 욱여넣어야 하고, 꺼낼 때 시프트와 마스크가 필요하다. C 교재 `2.4` 가 마지막으로 값을 하는 자리다.

검증은 **fp32 대비 출력 차이 측정**이다. 얼마나 틀려지는지를 숫자로 재고, 그 대가로 무엇을 얻는지 — 크기와 속도 — 를 나란히 놓는다.

**KV 캐시와 양자화는 원 강의에 없는 내용**이다. 이 교재의 고유 가치가 되는 자리이기도 하다.
