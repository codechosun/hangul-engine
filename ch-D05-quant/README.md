# D5. 양자화

> **선행** · C 교재 `2.4` 비트 연산 · C 교재 `3.5` 형 변환 · C5 · D4
> **만드는 것** · `lib/Quant`
> **예제** · D5-1 ~ D5-6

---

## 0. 3.6MB를 0.9MB로

D4에서 만든 모델은 93만 개의 `float` 을 들고 있다. 3.6MB다.

같은 구조를 70억 개로 키우면 28GB다. 소비자용 그래픽카드에 안 들어간다. 그런데 사람들은 그 모델을 노트북에서 돌린다.

**어떻게 하는가.** 숫자를 작게 담는다.

```
양자화   q = round(x / scale)     float 하나 -> 정수 하나
복원     x ≈ q × scale
```

`float` 은 4바이트, `int8_t` 는 1바이트다. **4분의 1이 된다.**

값은 틀어진다. 얼마나 틀어지는가. 그 대가로 무엇을 얻는가. 이 장은 전부 **재는 이야기**다.

---

## 1. 여덟 개짜리 줄 하나

말로 하면 안 들어온다. 손으로 세어볼 수 있는 크기부터 본다.

값이 여덟 개 있고 최대 절대값이 `1.0` 이다. 그러면 `scale = 1.0 / 127 = 0.007874016` 이다.

```
      원본      정수          복원          오차
   +1.0000       127  +1.000000000      0.00e+00
   -0.5000       -64  -0.503937006      3.94e-03
   +0.2500        32  +0.251968503      1.97e-03
   +0.0000         0  +0.000000000      0.00e+00
   -1.0000      -127  -1.000000000      0.00e+00
   +0.7500        95  +0.748031497      1.97e-03
   +0.1000        13  +0.102362201      2.36e-03
   -0.3000       -38  -0.299212605      7.87e-04
```

읽는 법.

- `-0.5` 는 `-0.5 / 0.007874 = -63.5` 다. 반올림해서 `-64`. 다시 펴면 `-0.50394`
- 최대값 `±1.0` 은 정확히 `±127` 에 떨어져 **오차가 0** 이다. 눈금을 거기 맞췄으니 당연하다
- 오차는 전부 `scale / 2 = 0.0039` 이하다. 반올림이니 그 이상 틀어질 수 없다

**양자화 오차의 크기는 `scale` 이 결정한다.** 그리고 `scale` 은 그 묶음에서 가장 큰 값이 결정한다. 이 한 줄이 이 장의 나머지를 전부 설명한다.

## 2. 왜 0 이 정확히 0 인가

위 표에서 `0.0` 은 `0` 으로 갔다가 `0.0` 으로 돌아왔다. **오차가 정확히 0 이다.**

우연이 아니다. 우리가 고른 방식이 그렇다.

```
대칭    q = round(x / scale)              0 -> 0
비대칭  q = round(x / scale) + zero       0 -> zero (0이 아니다)
```

비대칭은 값의 분포가 한쪽으로 쏠렸을 때 눈금을 더 촘촘히 쓸 수 있다. `0.0 ~ 1.0` 사이에만 값이 있으면 `-127 ~ 127` 중 절반이 놀고 있으니 아깝다.

그런데 대칭을 골랐다. 이유는 **0 이 특별하기 때문**이다.

- D2의 인과 마스크는 못 보는 자리를 `-1e30` 으로 만든다
- 패딩 자리는 0 이어야 한다
- ReLU 를 지난 값의 상당수가 정확히 0 이다

0 이 `0.003` 으로 틀어지면 이것들이 조용히 새기 시작한다. **틀린 값보다 무서운 것은 틀린 줄 모르는 값**이다.

> 실제 프레임워크는 가중치에 대칭, 활성값에 비대칭을 쓰는 경우가 많다. 가중치는 대체로 0 근처 대칭이고, 활성값은 ReLU 뒤라면 음수가 없어서다.

## 3. `scale` 을 어디 단위로 둘 것인가

여기가 이 장의 핵심이다.

행렬 하나에 `scale` 을 **하나만** 둘 수도 있고, **줄마다 하나씩** 둘 수도 있다. 간단한 쪽이 좋아 보이지만 재보면 다르다.

줄마다 크기가 1000배까지 차이나는 `64 × 128` 행렬로 재봤다. 실제 가중치가 이렇게 생겼다 — 어떤 뉴런은 크게 반응하고 어떤 뉴런은 거의 잠들어 있다.

```
방식                          크기    줄었다     최대 오차      상대 RMS
float (원본)                 32 KB   1.00 배             0            0%
8비트, 전체 scale             8 KB   4.00 배     3.927e-03       1.2890%
8비트, 줄마다 scale           8 KB   3.88 배     3.902e-03       0.3887%
4비트, 줄마다 scale           4 KB   7.53 배     7.119e-02       6.8410%
```

**같은 8비트인데 오차가 3.3배 차이난다.**

이유는 눈금이 어디 맞춰졌느냐다. 전체에 하나만 두면 행렬 전체에서 가장 큰 값에 127 을 맞춘다. 그보다 1000배 작은 줄은 어떻게 되는가.

```
전체 scale 에서 통째로 0 이 된 줄 = 13개 / 64
```

**64줄 중 13줄이 통째로 사라졌다.** 그 줄의 값이 전부 `scale/2` 미만이라 반올림하면 0 이다. 뉴런 13개가 죽은 것이다.

줄마다 두면 각 줄이 자기 최대값에 맞춰 눈금을 새로 잡으므로 이런 일이 없다.

### 공짜는 아니다

줄마다 두면 `scale` 도 64개 필요하다. `float` 64개 = 256바이트가 더 든다.

```
전체 하나    8192 + 4    = 8196 바이트   ->  4.00배
줄마다       8192 + 256  = 8448 바이트   ->  3.88배
```

**4.00배가 3.88배로 줄었다.** 3% 더 쓰고 오차를 3분의 1로 줄인 것이다. 살 만한 거래다.

값의 폭이 넓을수록 잘게 나누는 쪽이 이기고, 나눌수록 `scale` 이 늘어난다. 실제 4비트 양자화가 **줄 전체가 아니라 32개나 128개씩 묶어서** `scale` 을 두는 것이 이 줄다리기의 결과다.

## 4. 4비트 — 비트 연산이 돌아왔다

A1에서 UTF-8을 다룬 뒤로 비트 연산을 쓸 일이 없었다. 여기서 다시 나온다.

4비트 정수를 담을 자료형이 C에 없다. 가장 작은 것이 `uint8_t` 다. **한 바이트에 두 개를 욱여넣는 수밖에 없다.**

### 부호를 옮긴다

4비트 부호 있는 정수의 범위는 `-8 ~ 7` 이다. 대칭으로 쓰려면 `-8` 을 버리고 `-7 ~ 7` 만 쓴다.

그런데 음수를 4비트에 그대로 넣으면 꺼낼 때 부호 확장을 손으로 해야 한다. 간단한 방법이 있다.

```c
uint8_t Nibble = (uint8_t)(Q + 8);   // -7..7  ->  1..15
```

**8을 더해서 전부 양수로 만든다.** 꺼낼 때 8을 빼면 된다. 0 은 8이 된다.

### 담고 꺼내기

```c
const size_t Flat = r * Cols + c;
const size_t Byte = Flat / 2;

if (Flat % 2 == 0)
    Packed[Byte] = (Packed[Byte] & 0xF0u) | (Nibble & 0x0Fu);   // 아래 4비트
else
    Packed[Byte] = (Packed[Byte] & 0x0Fu) | (Nibble << 4);      // 위 4비트
```

읽는 법.

- `& 0xF0` 은 **건드리지 않을 쪽을 살리는** 마스크다. 아래 4비트만 지운다
- `& 0x0F` 은 `Nibble` 이 4비트를 넘지 않게 자르는 안전장치다
- `<< 4` 로 위쪽으로 밀어 올린다

꺼내는 쪽.

```c
uint8_t Nibble = (Flat % 2 == 0) ? (Packed[Byte] & 0x0Fu)
                                 : (Packed[Byte] >> 4);
int32_t Value = (int32_t)Nibble - 8;
```

`>> 4` 는 `uint8_t` 라서 안전하다. **부호 있는 정수를 오른쪽으로 밀면 위쪽에 무엇이 채워지는지 표준이 보장하지 않는다** (C++20 전까지). 비트를 다룰 때 부호 없는 형을 쓰는 이유다. C 교재 `2.4` 에서 한 이야기가 여기서 값을 한다.

### 눈으로 확인

```
원본 = (1, -1, 0.5, 0), scale = 1/7 = 0.142857
정수 = (7, -7, 4, 0)  ->  0 을 8 로 옮겨 (15, 1, 12, 8)

담긴 바이트
  [0] = 0x1F = 31  (아래 4비트 15, 위 4비트 1)
  [1] = 0x8C = 140 (아래 4비트 12, 위 4비트 8)

복원 = (1.000000, -1.000000, 0.571429, 0.000000)
```

`0.5` 가 `0.571429` 로 돌아왔다. `0.5 × 7 = 3.5` 를 반올림하면 4이고 `4/7 = 0.5714` 다.

**4비트로는 이게 최선이다.** 눈금이 15개뿐이니 그 사이 값은 붙잡을 수가 없다.

## 5. 모델 전체에 씌워보면

작은 행렬 하나가 아니라 D4의 트랜스포머 전체를 양자화하고, **점수가 얼마나 달라지는지** 잰다. 이것이 이 장의 검증이다.

`4층 × 128차원 × 어휘 512`, 토큰 32개를 넣었다.

```
무엇을                         최대 오차      상대 RMS
8비트, 블록만                     0.0215        0.862%
8비트, +출력층                    0.0210        0.951%
8비트, 전부                       0.0225        1.022%
4비트, 블록만                     0.4663       18.259%
4비트, +출력층                    0.4574       19.080%
4비트, 전부                       0.4578       20.193%
```

```
가중치 크기  float 3.6 MB -> 8비트 0.9 MB -> 4비트 0.4 MB
```

**8비트는 1%, 4비트는 20%.** 스무 배 차이다.

4비트가 유독 나쁜 이유는 눈금 수가 아니라 **층이 쌓이기 때문**이다. 한 층에서 6% 틀어진 것이 다음 층의 입력이 되고, 거기서 또 틀어진다. 4층이면 네 번 곱해진다.

> 그래서 실제 4비트 양자화는 그냥 반올림하지 않는다. GPTQ 는 한 열을 양자화한 뒤 그 오차를 **남은 열에 보상**하고, AWQ 는 중요한 채널을 미리 키워두고 양자화한다. 우리가 여기서 한 것은 가장 단순한 판이다.

---

## 6. 점수가 아니라 순위

1% 틀어진 것이 큰가 작은가. 판단하려면 **무엇에 쓰는지**를 봐야 한다.

생성에서 우리가 하는 일은 점수를 읽는 게 아니라 **가장 높은 토큰을 고르는 것**이다. 점수가 조금 틀어져도 순서만 안 바뀌면 결과는 같다.

```
위치 32개에서
  1위가 그대로인 자리 = 32개
  원본 1위가 상위 5위 안에 남은 자리 = 32개

점수가 0.951% 틀어져도 순위는 하나도 안 바뀐다.
```

**32개 자리에서 1위가 하나도 안 바뀌었다.**

이것이 양자화가 실용적인 이유다. 점수라는 중간 산물은 1% 흔들렸지만, 우리가 실제로 쓰는 값 — 순위 — 은 그대로다.

거꾸로 말하면 **양자화를 평가할 때 상대 오차만 보면 안 된다.** 재야 할 것은 최종 성능이다. 상대 오차는 그 대리 지표일 뿐이고, 대리 지표는 종종 거짓말을 한다.

> D4의 KV 캐시를 양자화하면 어떻게 되는가. 가중치보다 훨씬 민감하다. 캐시는 층을 건너 계속 재사용되므로 오차가 한 번 들어가면 뒤의 모든 토큰에 남는다. 그래서 캐시는 대개 8비트까지만 간다.

## 7. 정수로 바꾸면 빨라지는가

`(64 × 512) × (512 × 512)` 를 50번씩 재봤다.

```
어떻게                              시간    float 대비
float, i-k-j                    0.054 초       1.00 배
8비트, i-k-j                    0.072 초       0.74 배
8비트, 내적 순서                0.522 초       0.10 배
```

두 가지가 보인다.

### 첫째 — 순서가 또 나왔다

같은 정수 연산인데 **고리 순서만 바꿔서 7.2배**다. C5에서 본 그 문제가 그대로다.

```cpp
// 내적 순서 (i-o-k). 수식을 그대로 옮기면 대개 이렇게 쓴다.
for (o)
    for (i)
        Sum += Row[i] * Values[i * Out + o] * Scales[i];
//                      ~~~~~~~~~~~~~~~~~~ Out 칸씩 건너뛴다
```

```cpp
// C5의 i-k-j
for (k)
{
    const Real Factor = Row[k] * Scales[k];      // scale 을 밖으로 뺐다
    const int8_t* Weights = Values.data() + k * Out;

    for (o)
        OutRow[o] += Factor * (Real)Weights[o];  // 순서대로 읽는다
}
```

여기서 한 가지가 공짜로 따라온다. **줄마다 다른 `scale` 이 `k` 축에 붙어 있다.** 그래서 안쪽 고리 밖으로 뺄 수 있고, 안쪽에는 곱셈이 하나만 남는다.

내적 순서로 쓰면 `scale` 을 안쪽에서 매번 다시 가져와야 한다. **3절에서 "줄마다 두는 것이 거의 공짜"라고 한 말은 이 순서일 때만 참이다.**

두 판의 결과 차이는 `1.914e-07` 이다. 합치는 순서만 다르니 부동소수점 오차뿐이다.

### 둘째 — 순서를 지켜도 float 보다 느리다

`0.74배`. 1.35배 느리다.

당연하다. **곱셈은 어차피 `float` 로 한다.** `int8` 을 `float` 로 바꾸는 변환만 매번 더 붙는 셈이다.

그러면 양자화의 이득은 어디 있는가.

1. **메모리** — 크기가 4분의 1. 이건 확실하다. 안 들어가던 모델이 들어간다
2. **대역폭** — 읽어들일 바이트가 4분의 1. 큰 모델의 추론은 계산이 아니라 **메모리에서 가중치를 끌어오는 것**이 병목이다. 이쪽이 실제 이득의 대부분이다
3. **전용 명령** — VNNI 같은 `int8` 내적 명령을 써야 정수 연산 자체가 빨라진다. 우리는 아직 안 쓴다

우리 예제는 `64 × 512` 짜리라 가중치가 캐시에 다 들어간다. 그래서 2번의 이득이 안 보인다. **28GB짜리 모델에서는 이야기가 완전히 달라진다.**

C5의 교훈이 그대로다. **재보지 않으면 모른다.** 그리고 **무엇을 쟀는지 모르면 잰 것도 모른다.**

## 8. 여기 안 넣은 것들

이 장은 양자화의 뼈대만 세웠다. 실제 도구에 있는 것 중 뺀 것을 적어둔다. 나중에 필요할 때 무엇을 찾아야 하는지 알기 위해서다.

| 뺀 것 | 무엇인가 | 왜 뺐나 |
|---|---|---|
| 그룹 단위 `scale` | 줄 전체가 아니라 32·128개씩 묶어 `scale` | 줄 단위에서 원리는 다 나온다 |
| 비대칭 양자화 | `zero` 를 따로 두어 눈금을 다 쓴다 | 0이 0으로 안 간다 (2절) |
| 활성값 양자화 | 가중치뿐 아니라 중간값도 정수로 | 보정 데이터가 필요하다 |
| GPTQ · AWQ | 오차를 보상하며 양자화 | 4비트를 쓰려면 사실상 필수 |
| QAT | 양자화를 켜둔 채 훈련 | D7 뒤에나 가능하다 |
| VNNI · `dp4a` | int8 내적 전용 명령 | C5의 AVX2 처럼 CPU 확인이 필요하다 |

**뼈대를 직접 써봤으면 이 표의 항목들은 전부 "그 위에 얹는 것"으로 읽힌다.** 처음부터 GPTQ 논문을 읽으면 그렇게 안 읽힌다.

## 정리

- 양자화는 **반올림**이다. `q = round(x / scale)`, `x ≈ q × scale`
- 오차의 크기는 `scale` 이 정하고, `scale` 은 **그 묶음의 최대값**이 정한다
- **대칭**을 쓰면 0이 정확히 0으로 남는다. 마스크와 패딩이 사는 이유다
- `scale` 을 전체에 하나만 두면 작은 줄이 **통째로 0이 된다**. 64줄 중 13줄
- 줄마다 두면 3% 더 쓰고 오차를 **3분의 1** 로 줄인다
- 4비트는 한 바이트에 둘을 담는다. `& 0xF0`, `& 0x0F`, `<< 4`, `>> 4`. **비트 연산이 A1 이후 처음**
- 8을 더해 부호를 없애면 꺼낼 때 부호 확장이 필요 없다
- 모델 전체 기준 **8비트 1.0%, 4비트 20.2%**. 층이 쌓이면서 오차가 곱해진다
- 점수가 1% 흔들려도 **1위는 32/32 그대로**다. 재야 할 것은 최종 성능이지 상대 오차가 아니다
- 정수라고 저절로 빨라지지 않는다. **고리 순서가 7.2배**, `float` 대비는 여전히 0.74배
- 줄 단위 `scale` 이 공짜인 것은 `i-k-j` 순서일 때만이다

## 연습문제

**1.** `Quantize8` 은 `Biggest` 가 0일 때 `Scale = 1.0` 으로 둔다. 이 줄을 지우고 `Biggest / 127.0` 을 그대로 쓰면 무슨 일이 일어나는가. 어떤 텐서에서 실제로 그 상황이 생기는가.

<details>
<summary>답</summary>

`Scale` 이 0이 되고 `T.At(i) / Scale` 이 `0 / 0` 이 되어 **NaN** 이 나온다. 복원할 때도 `0 × 0 = 0` 이 아니라 NaN 이 퍼진다.

실제로 생기는가. 생긴다.

- 훈련 전 모델은 치우침(`Bias`)이 전부 0이다. 0으로 채워둔 텐서를 그대로 양자화하면 바로 만난다
- ReLU 를 지난 활성값에는 통째로 0인 줄이 흔하다 (죽은 뉴런)
- 가지치기(pruning)를 한 모델은 **의도적으로** 0인 줄을 만든다

NaN 은 한 번 생기면 모든 연산을 타고 번진다. 어텐션의 softmax 를 한 번만 지나면 그 위치 전체가 NaN 이다. **그리고 어디서 시작됐는지는 안 알려준다.**

`0.0` 을 특별 취급하는 한 줄은 이런 종류의 방어다. 값싸고, 없으면 디버깅에 반나절이 든다.

</details>

**2.** 4비트에서 `-8` 을 버리고 `-7 ~ 7` 만 썼다. `-8` 까지 쓰면 눈금이 16개가 되어 더 촘촘하다. 왜 안 쓰는가. `-8 ~ 7` 을 다 쓰려면 `scale` 을 어떻게 정해야 하는가.

<details>
<summary>답</summary>

`-8 ~ 7` 은 **대칭이 아니다.** 음수 쪽이 한 칸 더 길다.

대칭으로 쓰려면 `scale = max|x| / 8` 로 잡아야 하는데, 그러면 양수 최대값이 `8` 이 되어 범위를 넘는다. `7` 로 자르면 가장 큰 양수가 `7/8 = 0.875 × max` 로 **눌려버린다.** 최대값을 못 맞추는 양자화는 이상하다.

`scale = max|x| / 7` 로 잡으면 음수 쪽 `-8` 칸은 `-8/7 × max` 여서 원래 값보다 큰 자리다. 쓸 일이 없다.

정리하면 **`-8` 은 대칭을 유지하는 한 쓸 수 없는 칸**이다. 16개 중 15개만 쓰는 손해를 감수하고 0을 가운데 두는 것이다.

비대칭으로 가면 16개를 다 쓴다. `q = round((x - min) / scale)`, `scale = (max - min) / 15`. 대신 2절에서 본 대로 0이 0으로 안 간다. **그리고 복원 식에 덧셈이 하나 더 붙어서 7절의 `Factor` 빼내기가 안 된다.** 공짜가 없다.

</details>

**3.** 7절에서 `int8` 이 `float` 보다 느렸다. 그런데 실제 추론 엔진은 양자화로 **속도**를 얻는다고 말한다. 우리 측정이 틀린 것인가, 아니면 무엇이 다른 것인가. 우리 예제에서 그 차이를 실제로 보이게 하려면 무엇을 바꿔야 하는가.

<details>
<summary>답</summary>

측정은 맞다. **다른 것을 쟀을 뿐이다.**

우리가 쓴 가중치는 `512 × 512 × 4바이트 = 1MB` 다. L2 캐시에 들어간다. 한 번 올려두면 50번 반복 내내 캐시에서 읽는다. 그래서 **메모리에서 끌어오는 비용이 0** 이고, 남은 것은 계산 비용뿐이다. 계산만 보면 `int8 → float` 변환이 붙는 우리 구현이 느린 게 맞다.

실제 LLM 추론은 정반대다. 70억 개짜리 모델의 가중치는 14GB 이고, **토큰 하나를 뽑을 때마다 그걸 전부 한 번씩 읽어야 한다.** 재사용이 없다. 초당 몇 토큰이 나오느냐는 사실상 `14GB ÷ 메모리 대역폭` 이다. 여기서 가중치가 4분의 1이 되면 **거의 그대로 4배**가 된다.

이것을 부르는 이름이 있다. 계산이 병목이면 compute-bound, 메모리가 병목이면 **memory-bound** 다. 배치 하나짜리 LLM 추론은 전형적인 memory-bound 다.

우리 예제에서 보이게 하려면.

- **가중치를 캐시보다 크게 만든다.** `512 × 512` 대신 `8192 × 8192` 면 256MB 라 캐시에 안 들어간다
- **같은 가중치를 반복해서 쓰지 않는다.** 행렬을 여러 개 만들어 돌아가며 쓴다
- 입력 줄 수를 **1로 줄인다.** 64줄이면 가중치 한 번 읽어 64줄을 처리하니 재사용이 64배다. 1줄이면 재사용이 없다

그러면 `int8` 쪽이 빨라진다. **조건을 바꾸면 결론이 뒤집힌다는 것**이 이 문제의 요점이다. C5에서 블록 크기를 바꿔가며 본 것과 같은 이야기다.

</details>

## 다음 장

**D6. 트랜스포머 역전파.**

D5까지 왔으면 **추론은 끝**이다. 작게 만드는 법까지 봤다. 남은 것은 훈련이다.

C2에서 역전파를 손으로 썼다. 층이 세 개였다. 이제 층이 몇 개인가.

```
임베딩 → [ 정규화 → Q,K,V → 어텐션 → 합치기 → 잔차
          정규화 → Up → SiLU → Down → 잔차 ] × 4
        → 최종 정규화 → 출력층
```

D6에서 어려운 것이 둘 있다.

첫째, **softmax 의 야코비안**이다. C2에서는 softmax 바로 뒤에 교차 엔트로피가 붙어 있어서 `p - y` 로 깔끔히 정리됐다. 어텐션 안의 softmax 는 그렇지 않다. 야코비안을 제대로 써야 한다.

둘째, **가중치 공유**다. 잔차 연결은 같은 값을 두 길로 보낸다. 그러면 그래디언트는 **두 길에서 와서 더해진다.** 덮어쓰면 틀린다.

검증은 C2에서 만든 **gradcheck** 다. 손으로 쓴 미분과 수치 미분이 맞아떨어지는지 본다. 그리고 `USE_DOUBLE` 이 여기서 또 필요하다 — C2에서 본 대로, `float` 로는 판단이 안 선다.
