> **선행** · A1 (UTF-8) · A2 (글자 빈도) · D7 (훈련 루프) · D8 (마지막 자리만 채점)

> **예제** · E1-1 ~ E1-6

## 0. 이어 쓰는 것과 대화하는 것은 다르다

D7에서 만든 모델은 글을 **이어 쓴다.** "한국"을 주면 "한국의 대통령..."이 나온다.

대화가 아니다. 대화로 만들려면 둘이 필요하다.

**① 틀.** 누가 말하는 차례인지를 토큰으로 표시한다.

```
<|system|>너는 한글 엔진이다.<|end|><|user|>안녕<|end|><|assistant|>안녕하세요.<|end|>
```

**② 마스킹.** 사용자가 쓴 부분은 **채점하지 않는다.**

②가 이 장의 알맹이다. 그리고 한 줄이면 끝난다.

```
채점 안 할 자리의 상류 그래디언트를 0 으로 둔다.
```

D8에서 마지막 한 자리에만 했던 일이다. 여기서는 자리가 띄엄띄엄 흩어진다.

## 1. 특수 토큰은 글자 뒤에 붙인다

```
글자 81개 + 특수 토큰 4개 = 어휘 85

<|system|>     = 81
<|user|>       = 82
<|assistant|>  = 83
<|end|>        = 84
```

**코퍼스에 없는 번호라 본문과 절대 안 겹친다.**

겹치면 어떻게 되는가. 사용자가 `<|end|>` 라는 **글자**를 입력하면 모델이 멈춘다. 더 나쁘게는 `<|system|>` 을 입력해 시스템 지시를 덮어쓸 수 있다. 실제로 있었던 사고다.

글자 단위 어휘에서는 이게 쉽다. 코드포인트가 아닌 번호를 쓰면 끝이다. 실제 토크나이저도 같은 방식이다 — 특수 토큰을 어휘 끝에 별도로 등록하고, **본문을 토큰화할 때는 절대 그 번호를 내보내지 않는다.**

### `lib/Tokenizer`

D7에서 손으로 하던 일 — 글자를 세고, 번호를 붙이고, 되돌리고 — 을 한 자리에 모았다.

```cpp
void BuildFromText(const char* Text, size_t Bytes, size_t Limit,
                   size_t SpecialCount);
size_t FirstSpecial() const;   // 이 번호부터가 특수 토큰
```

A2에서 글자 빈도를 세던 코드가 여기로 왔다. **엔진이 A파트부터 자란다**는 말의 또 하나의 예다.

> BPE 가 아닌 이유는 결정 26이다. 병합 규칙 학습은 파이썬 쪽 일이고, 남은 분량으로 제대로 다룰 수 없다. 글자 단위는 어휘가 작고 구현이 짧으면서 **특수 토큰과 마스킹이라는 이 장의 주제를 그대로 보여준다.**

## 2. 어디를 채점하는가

`<|user|>안녕<|end|><|assistant|>안녕하세요<|end|>` 를 자리마다 펼쳐보면 이렇다.

```
  자리  토큰              다음에 와야 할 것     채점
     0  <|user|>          안                    .
     1  안                녕                    .
     2  녕                <|end|>               .
     3  <|end|>           <|assistant|>         .
     4  <|assistant|>     안                    O
     5  안                녕                    O
     6  녕                하                    O
     7  하                세                    O
     8  세                요                    O
     9  요                <|end|>               O
```

규칙은 네 줄이다.

- `<|user|>` 뒤의 글자는 **우리가 써 넣은 것**이다. 안 채점한다
- `<|assistant|>` 도 우리가 붙인다. 안 채점한다
- 그 뒤의 글자는 **모델이 써야 한다.** 채점한다
- 마지막 `<|end|>` 도 **채점한다**

마지막 줄이 중요하다. `<|end|>` 를 채점하지 않으면 **모델이 멈추는 법을 못 배운다.** 끝없이 이어 쓴다. 흔한 실수다.

### 자리가 하나 밀린다

우리 모델은 `Tokens[i]` 를 보고 `Tokens[i+1]` 을 맞힌다. 그래서 **채점 여부는 `i+1` 자리의 마스크로 정해진다.**

```cpp
Result.Inputs.push_back(Rendered.Tokens[t]);
Result.Targets.push_back(Rendered.Tokens[t + 1]);
Result.Mask.push_back(Rendered.Loss[t + 1]);   // 한 칸 밀린다
```

여기서 한 칸을 안 밀면 `<|assistant|>` 를 맞히는 것을 채점하고 그 뒤 첫 글자를 안 채점하게 된다. **증상은 "첫 글자만 이상한 모델"**이다. 찾기 어려운 종류의 버그다.

## 3. 검증 — 마스킹된 자리의 그래디언트는 정확히 0

이 장의 검증이다. 두 단계로 한다.

### 첫째, 상류 그래디언트가 0인가

```
자리 63개 중
  채점하는 자리     19개 — 그래디언트가 0 이 아니다
  안 채점하는 자리  44개 — 정확히 0
```

**0 에 가까운 것이 아니라 0 이다.** 애초에 계산을 안 한다.

```cpp
FTensor Result(Logits.GetShape());
Result.Fill(Real(0));

for (r) { if (Mask[r] == 0) continue; ... }
```

D6에서 "안 쓰인 임베딩 줄의 그래디언트는 정확히 0"을 확인한 것과 같은 종류다. **계산 결과가 0 인 것과 계산을 안 한 것은 다르다.**

### 둘째, 정말로 영향이 없는가

상류가 0이라고 해서 **파라미터** 그래디언트에 영향이 없다는 보장은 아니다. 직접 확인한다.

안 채점하는 자리 44곳의 **정답을 일부러 틀리게 바꾸고** 역전파를 다시 돌린다.

```
파라미터 그래디언트 244128개가 전부 그대로다.
```

`==` 로 비교한 결과다. 근사가 아니라 **비트가 같다.**

이게 보증하는 것.

- 마스킹된 자리의 정답이 무엇이든 상관없다
- **패딩을 아무 토큰으로 채워도 된다.** 우리는 `<|end|>` 로 채우지만 아무거나 괜찮다
- 그래서 길이가 제각각인 대화를 한 묶음에 넣을 수 있다

> 주의. 이건 **손실 쪽** 이야기다. 어텐션은 여전히 패딩 자리를 본다. 인과 마스크 덕에 패딩은 자기보다 뒤에만 영향을 주고 그 뒤도 전부 패딩이라 결과적으로 안전하지만, **패딩을 앞이나 가운데 넣으면 깨진다.** 그때는 어텐션 쪽 패딩 마스크가 따로 필요하다.

## 4. 마스킹을 빼면 무슨 일이 생기는가

같은 자료, 같은 초기값, 같은 걸음 수로 두 번 훈련했다. **다른 것은 손실을 어디서 재느냐 하나뿐이다.**

```
마스킹 O  1200걸음 75.2초, 마지막 손실 0.0002
마스킹 X  1200걸음 74.7초, 마지막 손실 0.0454
```

이 두 숫자는 **비교할 수 없다.** 서로 다른 것을 잰 값이기 때문이다. 같은 자로 다시 잰다.

```
무엇을 잰 손실                  마스킹 O      마스킹 X
조수가 쓸 글자                    0.0002        0.0006
사용자가 쓴 글자                  5.9255        0.5518
```

두 줄을 반대로 읽어야 한다.

| | 어느 쪽이 낫나 | 얼마나 |
|---|---|---|
| 조수가 쓸 글자 | **마스킹 O** | 2.6배 |
| 사용자가 쓴 글자 | 마스킹 X | 10.7배 |

**아래 줄이 문제다.** 사용자 글자를 잘 맞힌다는 것은 **사용자의 말투를 외웠다**는 뜻이다. 우리가 시킨 적 없는 일이다.

그리고 용량은 정해져 있다. 시키지 않은 것을 외우는 데 쓰면 시킨 것에 쓸 몫이 준다. **위 줄의 2.6배가 그 값이다.**

> 이 실험은 자료가 16쌍뿐이라 양쪽 다 거의 완벽히 외운다. 그래서 차이가 2.6배로 작게 나왔다. 자료가 크고 모델이 작을수록 이 차이는 커진다.

## 5. 뽑아보기

```
마스킹 O
  "안녕"        -> "안녕하세요. 무엇을 도와드릴까요?"
  "이름이 뭐야" -> "저는 한글 엔진입니다."
  "고마워"      -> "도움이 되어 기쁩니다."
  "날씨 어때"   -> "저는 날씨를 알지 못합니다."
```

생성 절차는 세 단계다.

1. 대화를 펼치고 **끝에 `<|assistant|>` 를 붙인다** (생성 프롬프트)
2. 그 토큰들을 `Step` 으로 밀어넣어 KV 캐시를 채운다 (D4)
3. `<|end|>` 가 나올 때까지 뽑는다

```cpp
FChatRendered Prompt = RenderChat(Turns, Tokenizer, true);
//                                                  ~~~~ 생성 프롬프트
```

`true` 하나가 "이제 네 차례다"라는 뜻이다. 이걸 안 붙이면 모델이 `<|user|>` 를 먼저 쓸 수도 있다.

## 6. 멈추라는 신호를 무시하면

`<|end|>` 에서 안 멈추고 계속 뽑아봤다.

```
마스킹 O
  안녕하세요. 무엇을 도와드릴까요?<|end|>요?<|end|>도와드릴까요?<|end|>요.<|end|> 무엇을 무엇

마스킹 X
  안녕하세요. 무엇을 도와드릴까요?<|end|><|end|><|end|><|end|><|end|><|end|>...
```

첫 `<|end|>` 까지는 같다. 그 뒤가 갈린다.

**마스킹 X 는 `<|end|>` 를 끝없이 찍는다.** 왜? 우리가 길이를 맞추려고 뒤를 `<|end|>` 로 채웠기 때문이다. 마스킹을 빼면 **그 패딩까지 자료로 배운다.**

마스킹 O 는 패딩을 본 적이 없으니 그냥 아무 말이나 잇는다.

둘 다 쓸모없는 출력이지만 **쓸모없어지는 이유가 다르다.** 그리고 요점은 이것이다.

> **마스킹을 빼면 모델은 자료에 우연히 들어 있는 것까지 전부 배운다.** 패딩도, 사용자의 말투도.

대화 프로그램이 할 일은 `<|end|>` 에서 자르는 것뿐이다. 모델은 멈추라는 **신호를 낼 줄만** 알면 된다.

## 7. 여기 안 넣은 것들

| 뺀 것 | 무엇인가 | 왜 뺐나 |
|---|---|---|
| 여러 차례 대화 | 앞 차례를 전부 넣고 이어간다 | 펼치는 코드는 이미 그렇게 돼 있다. 문맥 길이만 문제 |
| 어텐션 패딩 마스크 | 패딩 자리를 못 보게 막는다 | 뒤쪽 패딩만 쓰면 인과 마스크로 충분하다 (3절) |
| 도구 호출 틀 | `<|tool|>` 같은 토큰을 더 둔다 | 특수 토큰 하나 더 다는 일일 뿐이다 |
| 선호 학습 (DPO 등) | 좋은 답과 나쁜 답을 견주어 배운다 | 자료를 만드는 일이 본문보다 커진다 |
| 시스템 지시 주입 방어 | 사용자 입력에 섞인 지시를 막는다 | 특수 토큰 분리가 그 첫 단계다 (1절) |

## 정리

- 대화에는 **틀**과 **마스킹**이 필요하다
- 특수 토큰은 **글자 뒤 번호**로 둔다. 본문과 겹치면 사용자가 모델을 조종할 수 있다
- 채점하는 자리 = **조수가 쓸 글자 + 그 끝의 `<|end|>`**
- `<|end|>` 를 채점 안 하면 **멈추는 법을 못 배운다**
- 마스크는 한 칸 밀린다. `Mask[t] = Loss[t+1]`. 안 밀면 "첫 글자만 이상한 모델"이 된다
- 마스킹된 자리의 상류 그래디언트는 **정확히 0**. 계산을 안 한다
- 그 자리의 정답을 바꿔도 파라미터 그래디언트 **244128개가 비트까지 같다**
- 그래서 **패딩을 아무 토큰으로 채워도 된다**
- 마스킹을 빼면 사용자 말투를 10.7배 더 잘 맞힌다 = **시킨 적 없는 것을 외웠다**
- 그 대가로 조수 글자에서 2.6배 손해를 본다. **용량은 정해져 있다**
- 마스킹을 빼면 **패딩까지 배운다**. 자료에 우연히 들어 있는 것 전부

## 연습문제

**1.** 2절에서 "마스크를 한 칸 안 밀면 첫 글자만 이상한 모델이 된다"고 했다. 정확히 무슨 일이 일어나는지 자리별로 따져보라. 그리고 이 버그가 **손실 값으로는 거의 안 보이는** 이유를 설명하라.

<details>
<summary>답</summary>

`Mask[t] = Loss[t]` 로 쓰면 이렇게 된다.

| 자리 | 입력 | 맞혀야 할 것 | 올바른 채점 | 밀지 않았을 때 |
|---|---|---|---|---|
| 3 | `<|end|>` | `<|assistant|>` | X | X (`Loss[3]`=0) |
| 4 | `<|assistant|>` | `안` | **O** | X (`Loss[4]`=0) |
| 5 | `안` | `녕` | O | **O** (`Loss[5]`=1) |
| … | | | O | O |
| 9 | `요` | `<|end|>` | **O** | O (`Loss[9]`=1) |

두 자리가 어긋난다.

- **자리 4가 빠진다.** `<|assistant|>` 를 본 직후 첫 글자를 맞히는 것을 안 배운다
- 마지막 `<|end|>` 는 우연히 채점된다 (`Loss[9]` 가 1 이므로)

그래서 모델은 답의 **두 번째 글자부터**는 잘 쓰는데 첫 글자를 못 고른다. 생성은 첫 글자부터 시작하므로, 첫 글자가 엉뚱하면 그 뒤가 전부 따라 무너진다.

**손실로는 왜 안 보이는가.** 채점하는 자리 19개 중 1개가 빠진 것이다. 평균 손실에 미치는 영향이 5% 남짓이고, 그마저도 훈련이 진행되면 나머지 18개가 잘 맞아 전체 손실이 내려간다. **숫자는 멀쩡한데 출력만 이상하다.**

이런 버그를 잡는 방법은 하나다. 2절처럼 **자리별로 찍어서 눈으로 보는 것.** 예제 E1-2 가 그 표를 찍는 이유가 이것이다.

</details>

**2.** 3절에서 "패딩을 앞이나 가운데 넣으면 깨진다"고 했다. 왜 그런지 인과 마스크와 함께 설명하고, 그때 무엇을 더 만들어야 하는지 말하라.

<details>
<summary>답</summary>

인과 마스크는 **뒤를 못 보게** 한다. 앞은 다 본다.

패딩이 **뒤쪽에만** 있으면, 패딩 자리는 진짜 토큰들을 보지만 **진짜 토큰은 패딩을 안 본다.** 패딩 자리의 출력은 채점을 안 하니 버려진다. 그래서 아무 영향이 없다.

패딩이 **앞이나 가운데**에 있으면 다르다. 뒤쪽의 진짜 토큰이 앞쪽 패딩을 본다. 어텐션은 그 자리에도 확률을 나눠주고, `V` 를 섞어 온다. **쓰레기가 섞인다.**

정도가 어느 정도인가. 패딩이 절반이면 어텐션 확률의 상당 부분이 패딩으로 샌다. 손실은 조금 나빠지고 — 또 조용히 틀린다.

**무엇을 더 만들어야 하는가.** 어텐션 쪽 패딩 마스크다.

```cpp
// 인과 마스크 + 패딩 마스크
if (Key > Query || IsPadding[Key])
    Scores[...] = GMaskValue;
```

D2의 `ApplyCausalMask` 를 자리별 마스크를 받도록 넓히면 된다. 그리고 D2에서 `-∞` 대신 `-1e30` 을 쓴 이유가 여기서 값을 한다 — **패딩 마스크와 인과 마스크가 겹치면 한 줄이 통째로 막힐 수 있고**, `-∞` 였으면 `0/0 = NaN` 이 난다.

실무에서는 대개 패딩을 아예 안 만드는 쪽을 택한다. 여러 대화를 한 줄로 이어 붙여 길이를 꽉 채우는 방식(packing)이다. 그러면 이번엔 **대화끼리 서로 보는 문제**가 생기고, 그것도 마스크로 막는다. 마스크는 계속 는다.

</details>

**3.** 4절의 실험에서 자료가 16쌍뿐이라 차이가 2.6배로 작게 나왔다고 했다. 자료를 1000쌍으로 늘리고 모델 크기를 그대로 두면 이 두 줄의 숫자가 어떻게 변할 것 같은가. 세 경우로 나눠 예상하라.

<details>
<summary>답</summary>

**① 조수가 쓸 글자 — 양쪽 다 나빠지고, 격차는 벌어진다.**

16쌍은 그냥 외워진다. 1000쌍은 모델 용량(24만 파라미터)에 비해 크므로 외우는 것만으로는 안 되고 일반화해야 한다. 양쪽 다 손실이 `0.0002` 보다 훨씬 커진다.

그리고 **마스킹 X 쪽이 더 나빠진다.** 같은 용량으로 조수 말투와 사용자 말투를 **둘 다** 배워야 하기 때문이다. 배워야 할 양이 대략 두 배가 된다. 2.6배였던 격차가 더 벌어진다.

**② 사용자가 쓴 글자 — 격차가 줄어든다.**

마스킹 O 의 `5.9255` 는 "전혀 안 배웠다"는 뜻인데, 사실 완전히 못 맞히지는 않는다. 사용자 문장에도 한국어의 일반적인 글자 이어짐이 있고, 그건 조수 글자를 배우면서 부수적으로 배운다.

자료가 늘면 그 부수 효과가 커져서 마스킹 O 쪽 사용자 손실도 내려간다. 마스킹 X 쪽은 이미 낮으니 덜 내려간다. **10.7배가 줄어든다.**

**③ 가장 중요한 변화 — 생성 품질에서 차이가 드러난다.**

16쌍 실험에서는 두 모델의 **생성 결과가 똑같았다.** 둘 다 답을 통째로 외웠으니까. 1000쌍이면 외울 수 없고, 그때 마스킹 X 쪽의 병이 눈에 보인다.

- 답을 쓰다 말고 `<|user|>` 로 넘어가 **스스로 질문을 지어낸다**
- 사용자 말투가 답에 섞여 나온다

**즉, 이 장의 실험은 현상의 방향은 보여주지만 크기는 못 보여준다.** 자료가 작아서 그렇다. 실제로 마스킹을 빼먹은 채 미세조정을 하면 훨씬 험한 꼴을 본다.

솔직하게 말하면, 교재용 예제가 5분 안에 끝나야 한다는 제약에서 온 한계다. 방향은 `5.9255` 대 `0.5518` 로 분명히 잡혔다.

</details>

## 다음 장

**E2. 엔진으로 묶기.** ★

이 교재의 종착점이다.

지금까지 `lib/` 에 스물몇 개 모듈이 쌓였다. `Utf8` 부터 `Chat` 까지, A1에서 E1까지 자란 것이다. 그런데 아직 **엔진이 아니다.**

```
lib/Backward.hpp  ->  #include "Types.h"   <- common/ 에 있다
```

`common/` 은 **교재 도구**다. `CHECK` 매크로와 표 찍는 함수가 들어 있다. 엔진이 거기 의존하면 안 된다. 이런 것이 몇 개 더 있다.

E2에서 할 일.

- **공개 API 정하기** — 밖에 내놓을 헤더와 안에 감출 헤더를 가른다
- **경계 정리** — `common/` 의존을 끊는다
- **소스 배포 준비** — 어떤 빌드 시스템에도 들어가게
- **빈 프로젝트에서 붙여 돌리기** — 이게 검증이다

검증은 **빈 폴더에 엔진 파일만 복사해 넣고, `main.cpp` 하나로 한국어를 생성하는 것**이다. 교재 코드를 한 줄도 안 가져가고 되어야 한다.
