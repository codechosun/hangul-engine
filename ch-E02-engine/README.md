## 0. 이 교재의 종착점

A1에서 `Utf8.c` 하나로 시작했다. 지금 `lib/` 에 파일이 60개 넘는다.

그런데 **아직 엔진이 아니다.** 떼어낼 수가 없기 때문이다.

이 장에서 할 일 네 가지.

| | 무엇 |
|---|---|
| **경계** | 엔진이 교재 코드에 기대고 있던 자리를 끊는다 |
| **현관** | 밖에서 포함할 헤더 하나를 정한다 |
| **파일** | 모델을 굽고 다시 읽는다 |
| **배포** | 딸려오는 파일만 골라 내보낸다 |

그리고 검증은 하나다.

> **빈 폴더에 엔진 파일만 복사하고, `main.cpp` 하나로 한국어를 생성한다.**
> 교재 코드를 한 줄도 안 가져간다.

## 1. 경계를 거꾸로 밟고 있었다

A0에서 폴더를 셋으로 나눴다.

```
common/   교재 도구 (CHECK 매크로, 표 찍기) — 엔진에는 안 들어감
lib/      엔진이 될 코드
ch-XXX/   그 장 실습
```

`common/` 이 `lib/` 를 쓰는 것은 괜찮다. 반대는 안 된다. 그런데 세어보니 이랬다.

```
lib/Attention.hpp:22:#include "Types.h"
lib/Backward.hpp:29:#include "Types.h"
...
lib/Vector.hpp:16:#include "Types.h"     ← 15곳
```

`Types.h` 가 `common/` 에 있었다. **엔진 헤더 15개가 교재 도구를 포함하고 있었던 것이다.**

빌드는 잘 됐다. `-I common -I lib` 로 컴파일하니까. **경계는 컴파일러가 아니라 우리가 지킨다.**

고치는 방법은 파일 하나를 옮기는 것이었다.

```
common/Types.h  ->  lib/Types.h
```

### 두 번째 자리

하나 더 있었다. `Engine.cpp` 가 가중치를 파일에 적으려면 파라미터 목록이 필요한데, 그게 `Backward.hpp` 에 있었다.

```cpp
void CollectParameters(FTransformer& Model, std::vector<Real*>& Out);
```

그러면 **추론만 하려는 사람도 역전파를 통째로 링크해야 한다.** 그리고 `Backward.hpp` 는 `GradCheck.hpp` 를 포함하고 있었다 — 검증 도구가 제품에 실린다.

둘 다 옮기고 끊었다.

```
CollectParameters   Backward.hpp -> Model.hpp   (파라미터를 세는 건 모델의 일)
GradCheck.hpp       Backward.hpp 에서 뺌        (쓰는 쪽이 직접 포함)
```

**"어디에 두는 것이 맞는가"는 배포할 때가 되어야 답이 나온다.** 그 전에는 다 그럴듯해 보인다.

## 2. 현관 하나

```cpp
#include "Engine.hpp"

FEngine Engine;
Engine.Load("model.hgen");
Engine.Reply(Turns, {});
```

`lib/` 에 60개가 넘게 있지만 **밖에서 볼 것은 이것뿐이다.**

왜 가르는가. 전부가 공개 API 라면 `FTensor` 의 필드 이름 하나 바꾸는 것도 남의 코드를 깨는 일이 된다. **고칠 수 있는 자리를 남겨두는 것**이 경계를 긋는 이유다.

공개로 정한 헤더는 다섯이다.

| 헤더 | 왜 공개인가 |
|---|---|
| `Engine.hpp` | 현관 |
| `Chat.hpp` | `FChatTurn` 을 만들어 넘겨야 하니까 |
| `Tokenizer.hpp` | 어휘를 직접 만들 수 있어야 하니까 |
| `Model.hpp` | `FModelConfig` 로 크기를 정하니까 |
| `Types.h` | `Real` |

나머지는 안쪽이다. 포함해도 되지만 보증하지 않는다.

### 감출 것과 열 것

```cpp
FTransformer& MutableModel() { return Model; }
FTokenizer& MutableTokenizer() { return Tokenizer; }
```

가중치를 감추지 않는다. **감추면 이 엔진으로 미세조정을 못 한다.**

"캡슐화"를 기계적으로 적용하면 여기서 틀린다. 무엇을 감추고 무엇을 열지는 **이 엔진으로 무엇을 할 것인가**가 정한다. 추론만 시킬 거면 감추는 게 맞고, 훈련까지 시킬 거면 열어야 한다.

이 교재의 답은 **연다**이다. E2-2에서 실제로 그 문으로 훈련한다.

```
900걸음 58.9초, 마지막 손실 0.0004
```

## 3. 모델 파일 — 헤더 + 날 배열

결정 25 그대로다. 포맷 파싱이 주제를 가리지 않게.

```
"HGEN"    4바이트
판 번호   4바이트
Real 크기 4바이트
설정      uint64 6개  (어휘, 모델차원, 헤드, 앞먹임, 층, 최대길이)
어휘      글자 수 + 특수 토큰 수 + 코드포인트 배열
가중치    Real 244128개
```

실제로 구워보면 이렇다.

```
data/chat.hgen  954.0 KB
가중치만 953.6 KB — 나머지 408바이트가 머리말이다.
```

**99.96% 가 가중치다.** 모델 파일은 원래 그렇다.

### 머리말의 두 줄이 중요하다

**`Real` 크기 4바이트.** `float` 로 구운 파일을 `double` 빌드가 읽으면 전부 쓰레기가 된다. 그리고 그게 **조용히** 일어난다 — 크래시도 안 나고, 그냥 이상한 글자가 나온다.

적어두면 `Load` 가 실패한다. **실패하는 편이 낫다.**

**숫자는 전부 `uint64`.** `size_t` 를 그대로 적으면 32비트 빌드와 64비트 빌드가 서로 못 읽는다. 파일 형식에서는 **컴파일러가 정하는 크기를 쓰지 않는다.**

### 가중치의 순서는 계약이다

```cpp
CollectParameters(Mutable, Parameters);
for (i) fwrite(Parameters[i], sizeof(Real), 1, File);
```

`CollectParameters` 의 순서가 **파일 형식의 일부**가 된다. 나중에 파라미터를 하나 더 붙이면 판 번호를 올려야 한다.

그리고 그 순서는 이미 다른 계약에도 쓰이고 있다 — D6의 gradcheck 이 `CollectGradients` 와 짝을 맞춰 쓴다. **한 함수가 두 곳에서 계약이 된 것**이다. `Model.hpp` 의 주석에 그걸 적어뒀다.

## 4. 검증 ① 굽고 다시 읽으면 같은가

```
다시 읽은 가중치 244128개 중 244128개가 비트까지 같다.

물어본 것         구운 뒤 답                        같나
안녕              안녕하세요. 무엇을 도와드릴까요?  O
이름이 뭐야       저는 한글 엔진입니다.             O
고마워            도움이 되어 기쁩니다.             O
잘 가             안녕히 가세요.                    O
```

가중치가 비트까지 같으면 답도 같은 게 당연해 보이지만, **확인해야 한다.** 어휘가 빠졌거나 설정이 하나 틀어져도 가중치는 멀쩡하다.

### 잘못된 파일

```
없는 파일              -> 실패
마법 문자 한 글자 틀림 -> 실패
```

그리고 더 중요한 것.

> **실패했을 때 엔진이 반쯤 채워지지 않는다.**

`Load` 는 다 읽고 검사가 끝난 뒤에야 자기 것을 바꾼다.

```cpp
FTransformer Fresh(Loaded);       // 새 것에 읽는다
... 검사 ...
if (!bOk) return false;           // 여기서 나가면 this 는 그대로다

Config = Loaded;                  // 다 통과한 뒤에야
Model = std::move(Fresh);
bReady = true;
```

중간에 갈아 끼우면 실패한 엔진으로 생성이 되고, **그건 쓰레기를 내놓으면서 성공한 척하는 것이다.**

D1에서 만든 이동 시맨틱이 여기서 값을 한다. `Fresh` 를 복사가 아니라 이동으로 넘긴다. 954KB 짜리 복사 하나가 사라진다.


`Gemm` 은 조금 아깝다. C5에서 AVX2까지 써가며 만든 것인데 `Tensor::MatMul` 이 쓰지 않는다. 엔진이 그걸 쓰게 만드는 것은 좋은 다음 작업이고, 연습문제로 남긴다.

## 7. 상용 제품에 싣는다는 것

결정 23과 36이 여기서 회수된다.

**소스 배포.** 헤더와 소스를 그대로 넘긴다. 어떤 빌드 시스템에도 들어가고, 쓰는 사람이 속을 읽고 고칠 수 있다. `.lib` 를 넘기면 컴파일러 판, 런타임 판, `/MT` 대 `/MD` 가 전부 문제가 된다. **43개 소스 파일이 그 문제를 통째로 없앤다.**

**MIT.** 코드가 MIT 이므로 상용 이용에 걸림돌이 없다. 교재 본문은 CC BY-NC 지만 코드는 아니다.

**외부 의존성 0.** 표준 라이브러리 12개 헤더가 전부다. 게임에 넣든 데스크톱 앱에 넣든 따라 들어가는 것이 없다.

그리고 이 엔진의 강점은 **오프라인**이다.

- 953KB 짜리 모델이 프로세스 안에서 돈다
- 네트워크가 없다. 서버 비용도, 지연도, 사용량 제한도 없다
- 사용자가 입력한 것이 밖으로 안 나간다

게임 NPC 대화 생성이 자연스러운 용례다. 953KB 모델로 셰익스피어를 쓰지는 못하지만, **정해진 어조로 짧게 답하는 일**은 이 크기로도 된다 — E2-3의 답 네 개가 그 증거다.

큰 모델이 필요한 일은 어차피 이 엔진의 일이 아니다. **그 경계가 어디인지**가 E3의 주제다.

## 정리

- 경계는 컴파일러가 아니라 **우리가** 지킨다. `-I` 두 개면 위반해도 빌드된다
- `Types.h` 가 `common/` 에 있어 엔진 헤더 15개가 교재 도구를 포함하고 있었다
- `CollectParameters` 는 역전파가 아니라 **모델**의 일. 추론만 하는 사람이 역전파를 링크하면 안 된다
- 현관은 `Engine.hpp` 하나. 공개 헤더 다섯, 나머지는 안쪽
- **가중치는 감추지 않는다.** 감추면 미세조정을 못 한다. 무엇을 열지는 용도가 정한다
- 모델 파일 = 머리말 408바이트 + 가중치 953.6KB. **99.96% 가 가중치**
- `Real` 크기와 `uint64` 고정 — **조용히 틀리는 대신 실패하게** 만드는 장치
- `Load` 는 다 읽고 검사가 끝난 뒤에 갈아 끼운다. 실패하면 **엔진이 그대로 남는다**
- 왕복 검증: 가중치 244128개가 비트까지 같고, 답 4개가 글자까지 같다
- 추론 엔진 = **19개 파일 67.7KB.** 전부 실으면 43개 181.4KB
- 엔진에서 빠지는 것과 **교재에서 지우는 것은 다르다**
- 검증 = `dist/` 만 보고 빌드한 `app/main.cpp` 가 한국어로 답한다

## 연습문제

**1.** 5절에서 `Gemm` 이 엔진에 안 들어간다고 했다. C5에서 AVX2까지 써가며 만든 것인데 `Tensor::MatMul` 이 쓰지 않기 때문이다. `MatMul` 이 `Gemm` 을 쓰게 하려면 무엇을 확인해야 하는가. 그리고 **그렇게 하지 않은 것이 왜 합리적인 선택이었는지**도 말해 보라.

<details>
<summary>답</summary>

**확인할 것 셋.**

① **모양이 맞는가.** `GemmAvx2` 는 `(M,K) × (K,N)` 2차원을 받는다. `MatMul` 은 배치 축이 앞에 붙은 4차원도 받는다. 묶음마다 `Gemm` 을 부르면 된다 — `MatMul` 이 이미 그렇게 나눠 돌고 있으므로 어렵지 않다.

② **결과가 같은가.** `Gemm` 의 블록 분할은 **더하는 순서를 바꾼다.** D7의 정답표 대조가 `6.661e-15` 로 맞았던 것은 순서가 고정이었기 때문이다. 순서가 바뀌면 그 숫자가 달라진다. 틀린 건 아니지만 **기준선을 다시 잡아야 한다.**

③ **빨라지는가.** C5에서 잰 대로 `Gemm` 이 빠른 것은 큰 행렬에서다. E1·E2에서 쓰는 행렬은 `(504, 96) × (96, 384)` 정도다. D5-6에서 본 대로, **작으면 재보기 전에는 모른다.**

**왜 안 했는가.**

한 줄로 답하면 — **재보지 않았기 때문이다.**

C5에서 `Gemm` 을 만들 때 목표는 "행렬 곱을 빠르게 하는 법을 배운다"였고, 그건 달성했다. D1에서 `Tensor` 를 만들 때는 배치와 축이 주제였고, `MatMul` 은 그 안에서 가장 단순한 판으로 썼다. **두 장의 목표가 달랐고, 잇는 것은 어느 쪽의 목표도 아니었다.**

실무에서도 이런 일이 생긴다. 좋은 조각을 만들어놓고 안 쓰는 것. 나쁜 것은 **안 쓰는 것**이 아니라 **안 쓰는 줄 모르는 것**이다. `check_engine.py` 가 "Gemm 은 안 딸려온다"고 찍어주는 것이 그래서 값을 한다.

잇겠다면 순서는 이렇다. 먼저 재고(현재 `MatMul` 대비 몇 배인지), 빨라지면 D7의 정답표를 다시 굽고, 그 다음에 바꾼다. **재기 → 기준선 → 교체.** 순서를 바꾸면 무엇이 좋아졌는지 모르게 된다.

</details>

**2.** 4절에서 `Load` 가 "다 읽고 검사가 끝난 뒤에 갈아 끼운다"고 했다. 이것을 어기면, 즉 읽으면서 바로 `this` 에 채우면 어떤 일이 생기는지 구체적인 시나리오로 설명하라. 그리고 이 원칙에 이름이 있는지 생각해 보라.

<details>
<summary>답</summary>

**시나리오.** 게임이 돌고 있다. NPC 대화용 엔진이 이미 메모리에 올라가 있고 잘 답하고 있다. 사용자가 "다른 말투 팩"을 골라 새 모델을 불러오는데, 그 파일이 다운로드 중에 잘렸다.

읽으면서 바로 채우는 구현이면.

1. 설정을 읽어 `Config` 를 덮어쓴다 — 어휘 크기가 달라졌다
2. 어휘를 읽어 `Tokenizer` 를 덮어쓴다
3. 가중치를 읽다가 파일이 끝난다. `Load` 가 `false` 를 돌려준다
4. 게임이 "불러오기 실패" 를 띄우고 **원래 엔진으로 계속 돌린다**
5. 그런데 원래 엔진은 없다. `Config` 는 새 것, 가중치는 절반만 새 것이다

증상은 NPC 가 갑자기 이상한 소리를 하는 것이다. 그리고 **`Load` 는 분명히 실패를 알렸다.** 부른 쪽은 잘못한 게 없다.

**이름이 있다.** 예외 안전성(exception safety)의 **강한 보장**(strong guarantee)이다. "연산이 성공하거나, 아니면 아무 일도 안 일어난 것과 같다."

이 교재는 예외를 안 쓰지만(결정 15) **원칙은 같다.** 반환값으로 실패를 알리든 예외를 던지든, 실패했을 때 객체가 성한 상태여야 한다는 것은 바뀌지 않는다.

구현 요령도 정해져 있다. **새 것을 다 만든 뒤 맞바꾸기**(copy-and-swap). `FTransformer Fresh(Loaded)` 를 따로 만들고 다 통과한 뒤에 `std::move` 로 옮긴다. C++ 교재 `10.4` 의 대입 연산자에서 같은 요령이 나온다.

</details>

**3.** 이 엔진을 게임에 넣는다고 하자. 지금 구조에서 **바로 문제가 될 것** 셋을 짚고, 각각 무엇을 고쳐야 하는지 말하라.

<details>
<summary>답</summary>

**① 생성이 게임 프레임을 멈춘다.**

`Reply` 는 토큰을 40개 뽑을 때까지 돌아온다. 한 토큰에 몇 ms 면 답 하나에 100ms 넘게 걸린다. 60fps 면 16.7ms 안에 끝나야 하는데 여섯 프레임을 통째로 먹는다.

고칠 것: **한 토큰씩 돌려주는 API.** `Step` 은 이미 그렇게 돼 있으니 그걸 밖으로 내면 된다.

```cpp
FStream Stream = Engine.Begin(Turns, Options);
while (!Stream.bDone) { Stream.Next(); }   // 프레임마다 한 번
```

덤으로 **글자가 하나씩 나타나는 효과**가 공짜로 생긴다. 대화창에 어울린다.

**② 메모리를 매번 새로 잡는다.**

`Run` 안에서 `FKvCache Cache(Config)` 를 만든다. 대화 한 번마다 캐시를 새로 할당한다. `std::vector<double> Weight(Config.Vocab)` 도 **토큰마다** 새로 잡는다.

게임에서는 프레임 중 할당이 프레임 끊김의 흔한 원인이다.

고칠 것: 캐시와 버퍼를 **엔진이 들고 있게** 한다. `Begin` 이 재사용하고, 필요하면 미리 잡아둘 수 있는 `Reserve` 를 연다.

**③ 여러 NPC 가 동시에 말한다.**

`Reply` 는 `const` 라 여러 스레드에서 불러도 될 것 같지만, 캐시를 스택에 만드니 **메모리가 NPC 수만큼 는다.** 문맥 64에 96차원이면 캐시 하나가 작지만, 문맥이 길어지면 D4에서 본 대로 커진다.

그리고 가중치는 953KB 하나로 **모두가 나눠 쓸 수 있다.** D4-5에서 본 그림 그대로다 — 가중치는 공유, 캐시는 요청마다.

고칠 것: **엔진과 대화 상태를 분리한다.** 엔진은 하나, `FStream` 은 NPC 마다. 위 ①의 API 가 그 모양이다.

**공통점.** 셋 다 "한 번 부르면 답이 나온다"는 모양에서 온다. 그 모양은 예제로는 좋지만 **실시간 프로그램에는 안 맞는다.** 이 엔진은 아직 예제에 맞춰져 있다.

그리고 그게 정직한 상태다. 실제 제품에 넣을 때 무엇을 고쳐야 하는지 **아는 것**과, 다 되어 있다고 믿는 것은 다르다.

</details>
