# E3. 규모의 벽

> **선행** · 없다. 지금까지 잰 숫자를 모아 판단하는 장이다
> **만드는 것** · 없다. `tools/` 도 `lib/` 도 늘지 않는다
> **예제** · E3-1 ~ E3-6

## 0. 마지막 장은 판단이다

E2에서 엔진이 떨어져 나갔다. 953KB 모델이 한국어로 답한다.

그러면 **이제 무엇을 할 수 있고 무엇을 할 수 없는가.**

이 질문에 "C++로 다 할 수 있다"도 "그건 파이썬이 하는 일이다"도 답이 아니다. 각각이 맞는 자리가 있고, **그 경계를 숫자로 아는 것**이 이 교재의 마지막 목표다.

그래서 이 장은 재는 것으로 시작한다.

## 1. 크기만 바꿔서 다섯 번 훈련한다

같은 코퍼스, 같은 걸음 수, 같은 묶음 순서. **모델 차원만 바꾼다.**

```
코퍼스 앞 2048KB -> 어휘 256자로 89.43% 를 덮었다
토큰 836317개
```

```
    차원    파라미터      손실   글자당 비트  그림
      24       27000    3.5308         5.094  ################################
      32       42144    3.4567         4.987  ###############################
      48       81648    3.3998         4.905  ###############################
      64      133440    3.3831         4.881  ###############################
      96      273888    3.3710         4.863  ##############################
```

**파라미터를 10배로 키웠는데 손실이 0.16 밖에 안 내려갔다.**

막대 그림을 보면 거의 안 움직인다. 이게 이 장의 첫 번째 사실이다.

> 걸음 수를 600으로 고정했으므로 큰 모델은 덜 훈련된 상태다. 실제 스케일링 실험은 크기마다 최적 걸음 수를 따로 잡는다. 우리 숫자는 **"같은 예산에서"** 의 비교다.

## 2. 기울기를 재고, 일부러 틀리게 외삽해 본다

다섯 점에 직선을 맞춘다. C6에서 쓴 최소제곱 그대로다.

```
손실 = 4.1789 + (-0.1530) x log10(파라미터)

파라미터를 10배로 하면 손실이 0.1530 내려간다. 글자당 0.221 비트다.
```

이 직선을 그대로 늘려보면 이렇게 된다.

```
    파라미터  이 식의 예측   글자당 비트
       1e+05        3.4140         4.925
       1e+06        3.2610         4.705
       1e+07        3.1080         4.484
       1e+08        2.9550         4.263
       7e+09        2.6727         3.856
       1e+12        2.3430         3.380
```

**이 표는 틀렸다.** 그리고 어떻게 틀렸는지가 중요하다.

### 직선은 언젠가 0을 뚫는다

손실은 음수가 될 수 없다. 이 직선을 계속 늘리면 `10^27` 쯤에서 0을 지난다. 말이 안 된다.

글자를 완벽히 맞히더라도 **한국어 자체의 불확실성**이 남는다. "안녕하" 다음이 "세"일 확률이 아무리 높아도 1은 아니다. 그 한계를 **되돌릴 수 없는 손실**(irreducible loss)이라 부른다.

실제 스케일링 법칙은 이렇게 생겼다.

```
손실 = 바닥 + 계수 / 파라미터^알파
```

직선이 아니라 **바닥을 향해 눕는 곡선**이다. 우리가 잰 다섯 점은 그 곡선의 아주 왼쪽 끝이라 직선으로 보일 뿐이다.

### 다섯 점으로 12자릿수를 외삽하는 것

우리가 잰 범위는 `2.7만 ~ 27만` 이다. **한 자릿수**다. 그걸로 `10^12` 까지, **일곱 자릿수를 더 뻗은** 것이다.

그런 외삽은 과학이 아니다. 위 표의 값은 "이 정도 방향"이지 예측이 아니다.

> 그런데 실제 스케일링 법칙 논문도 비슷한 일을 한다. 다만 **여섯 자릿수 이상**을 재고, 곡선 형태를 가정하고, 그 가정이 맞는지를 따로 검증한다. 차이는 외삽을 하느냐 마느냐가 아니라 **얼마나 정직하게 하느냐**다.

## 3. 시간의 벽

파라미터가 늘면 한 걸음이 얼마나 느려지는가.

```
    파라미터     한 걸음      파라미터당
       27000       9.6ms         357.4ns
       42144      10.9ms         258.4ns
       81648      16.2ms         198.0ns
      133440      22.2ms         166.3ns
      273888      33.1ms         120.8ns
```

**파라미터당 시간이 오히려 줄어든다.** 작은 행렬에서는 고정 비용(할당, 함수 호출, 스레드 깨우기)이 크기 때문이다. C5에서 본 그대로다.

가장 큰 판 기준 **파라미터당 120.8ns**. 이걸로 계산해 본다.

```
70억 파라미터면 한 걸음에 845.4초 (묶음 8 x 32 = 토큰 256개)
토큰 1조 개를 보려면 걸음이 3.91e+09번.

1.05e+05 년이다.
```

**10만 5천 년.** 기록된 인류 역사가 5천 년쯤이니 그 스무 배다.

### 이 계산에서 정직해야 할 것

**① 묶음이 너무 작다.** 실제로는 백만 토큰짜리 묶음을 쓴다. 묶음을 키우면 걸음 수가 줄지만 걸음당 시간이 그만큼 는다. **총 계산량은 안 변한다.**

**② GPU 는 훨씬 빠르다.** 이 CPU 코드 대비 1000배쯤이고, 카드를 수천 장 쓴다.

```
1000배 (하드웨어) × 수천 배 (대수) = 백만 배
```

10만 년이 **한 달**이 된다. 그게 실제로 하는 일이다.

**그 백만 배가 규모의 벽이다.** 우리 코드가 나쁜 게 아니라, 저쪽이 백만 배 큰 것이다.

## 4. 메모리는 더 단단한 벽이다

D6과 D7에서 잰 비율을 그대로 쓴다.

```
무엇                       우리 것          70억
파라미터                 1069.9 KB         26 GB
그래디언트               1069.9 KB         26 GB
AdamW 상태               2139.8 KB         52 GB
합                       4279.5 KB        104 GB
```

여기에 D6의 자취가 더 붙는다. 배치와 길이에 비례해서.

**시간은 기다리면 되지만 메모리는 안 그렇다.** 안 들어가면 안 도는 것이다.

그래서 훈련 쪽 기법의 대부분이 메모리 이야기다.

| 기법 | 무엇을 아끼나 | 이 교재 어디서 봤나 |
|---|---|---|
| 혼합 정밀도 | 파라미터·그래디언트를 16비트로 | D5 (양자화의 사촌) |
| 8비트 옵티마이저 | AdamW 상태를 양자화 | D5 + D7 |
| ZeRO · FSDP | 상태를 카드 여러 장에 쪼갠다 | — |
| gradient checkpointing | 자취를 버리고 다시 계산 | D6 |

**네 줄 중 셋이 이 교재에 나온 것**이다. 규모가 커지면 새로운 마법이 나오는 게 아니라, **같은 문제가 더 세게 나온다.**

## 5. 그래서 어디서 갈아타는가

```
무엇을                        이 엔진       왜
글자·낱말 N-그램             맞다          A파트로 끝난다
100만 이하 모델 추론          맞다          953KB, 의존성 0
100만 이하 모델 훈련          맞다          이 장이 그 증거
1억 모델 추론                 된다          느리지만 돈다. 양자화 필요
1억 모델 훈련                 아니다        CPU 로 몇 주
70억 모델 추론                아니다        28GB. 메모리부터 안 된다
70억 모델 훈련                아니다        백만 배 모자란다
남이 훈련한 모델 싣기         맞다          형식 변환만 하면 된다
```

**경계는 대략 백만에서 1억 사이**다.

그 위로는 이 코드가 틀린 게 아니라 **도구가 다르다.** 망치로 나사를 박을 수도 있지만 드라이버가 있다.

### 마지막 줄이 중요하다

**남이 훈련한 가중치를 싣는 것**은 이 엔진이 가장 잘하는 일이다.

훈련은 파이썬과 GPU 가 한다. 그건 저쪽이 백만 배 유리하다. 그런데 **제품에 실려 도는 것**은 이야기가 다르다.

| | 파이썬 런타임 | 이 엔진 |
|---|---|---|
| 의존성 | 수백 MB | **0** |
| 시작 시간 | 초 단위 | 즉시 |
| 배포 | 인터프리터를 같이 넣거나 서버를 띄운다 | **소스 43개 파일** |
| 오프라인 | 가능하지만 무겁다 | **기본** |
| 게임 엔진 안에 | 어렵다 | **넣으면 된다** |

`.gguf` 나 `.safetensors` 를 읽어 우리 `FEngine` 에 채우는 것은 **형식 변환 문제**다. E2에서 만든 `Load` 를 하나 더 쓰면 된다. 그게 이 엔진의 가장 실용적인 쓰임이고, 이 교재 다음의 첫 작업으로 자연스럽다.

## 6. 30장을 지나 남은 것

### 숫자로 남은 것

```
UTF-8 글자 세기부터 트랜스포머 훈련까지 C/C++ 로
엔진 43개 파일, 외부 의존성 0
gradcheck 6.787e-07, NumPy 곡선 대조 6.661e-15
한국어 글자당 4.863 비트
```

### 숫자가 아닌 것

**재보지 않으면 모른다.**
C5에서 블록 크기를 나눴더니 오히려 느려졌다. D5에서 정수로 바꿨더니 느려졌다. 둘 다 "당연히 빨라질" 것이었다.

**조용히 틀리는 것이 무섭다.**
A6의 창 초기화 한 칸, D6의 잔차 한 줄. 둘 다 프로그램이 돌고, 숫자가 나오고, 손실이 내려간다. 다만 틀린다.

**못 재는 것과 틀린 것은 다르다.**
D6의 `float` gradcheck 이 `1.470` 을 내놨을 때, 답은 "실패"가 아니라 **"판단 불가"** 였다. 기준을 느슨하게 풀어 "통과"라고 찍는 것이 더 나쁜 거짓말이다.

**도구를 먼저 맞춰놓는다.**
D8의 그로킹은 5000걸음 동안 아무 일도 안 일어나는 구간을 견뎌야 볼 수 있었다. 그걸 버그가 아니라고 말할 수 있었던 것은 D6과 D7이 통과했기 때문이다.

## 마치며

이 교재가 한 일은 **판단할 근거를 만든 것**이다.

트랜스포머가 무엇인지는 글로도 읽을 수 있다. 그런데 "이 크기면 되는가", "이건 왜 안 되는가", "여기서 무엇을 의심해야 하는가"는 **자기가 만들고 재봐야 생긴다.**

세 권의 교재에서 배운 것 — 포인터, 자료구조, 클래스 — 이 여기서 전부 값을 했다.

| 어디서 | 무엇이 |
|---|---|
| A2 | 해시맵을 직접 짜서 `std::unordered_map` 보다 2.85배 빠르게 |
| A4 | `/GL /LTCG` 로 모듈 분리의 대가 30%를 되찾고 |
| B1 | Rule of Five 로 `FVector` 의 소유권을 잡고 |
| C5 | 고리 순서 하나로 GEMM 을 몇 배 빠르게 |
| D1 | 이동 시맨틱으로 32MB 복사를 없애고 |
| D5 | 비트 연산으로 한 바이트에 두 값을 담고 |
| E2 | 헤더 경계를 그어 953KB 엔진을 떼어냈다 |

**"C를 배우면 뭘 할 수 있나요"에 대한 대답이 이것이다.**

그리고 끝이 아니다. 이 저장소의 `dist/hangul-engine/` 에 43개 파일이 있고, 그것은 MIT 다. 무엇을 만들든 가져다 쓰면 된다.

<details>
<summary>답</summary>

무엇을 고정하느냐가 **무슨 질문에 답하는지**를 바꾼다.

**① 걸음 수 고정** (지금 우리가 한 것)
- 재는 것: "같은 횟수만큼 갱신했을 때 어느 쪽이 나은가"
- 문제: 큰 모델은 걸음당 계산이 많은데 그 값을 안 쳐준다. **큰 모델에 유리한 쪽으로 편향**된다 (계산을 공짜로 준다)

**② 총 계산량 고정** (파라미터 × 걸음 수)
- 재는 것: "같은 연산 예산에서 어느 크기가 나은가"
- 이게 실제 스케일링 법칙이 쓰는 기준이다. 예산이 정해져 있을 때 **모델을 키울지 오래 돌릴지**를 정하는 것이 핵심 질문이기 때문이다
- 우리 실험에 적용하면 차원 96은 600이 아니라 약 60걸음만 돌게 된다. 손실이 훨씬 높게 나온다

**③ 벽시계 시간 고정**
- 재는 것: "한 시간 주면 어느 크기가 나은가"
- 가장 실무적이지만 **기계에 따라 답이 달라진다.** 3절에서 본 대로 작은 모델은 고정 비용 때문에 손해를 본다. 다른 CPU 에서는 다른 답이 나온다

**어느 게 맞는가.** 질문에 따라 다르다. 그런데 **무엇을 고정했는지 밝히지 않은 비교는 읽을 수가 없다.** 논문에서 "같은 설정으로" 라고만 쓰여 있으면 그 표는 못 믿는다.

이 교재가 ①을 고른 이유는 솔직히 말해 **돌리는 시간 때문**이다. ②로 하면 작은 모델을 수천 걸음 돌려야 해서 예제가 10분을 넘긴다. 그리고 본문에 그렇게 적어뒀다.

**2.** 5절에서 "1억 모델 추론은 된다(느리지만)"고 했다. 정말 그런지 이 교재의 숫자로 따져보라. 문맥 512에서 토큰 하나를 뽑는 데 얼마나 걸리는가. 그리고 무엇을 하면 쓸 만해지는가.

<details>
<summary>답</summary>

**계산.** D4에서 본 대로 KV 캐시를 쓰면 토큰 하나당 계산은 **파라미터 수에 비례**한다. 대략 `2 × N` 번의 곱셈-덧셈이다.

1억 파라미터면 토큰당 2억 FLOP. D5-6에서 잰 우리 속도가 float 기준 약 `1 GFLOP/s` (i-k-j, 단일 스레드) 였다.

```
2e8 FLOP / 1e9 FLOP/s = 0.2초/토큰
```

100글자짜리 답이면 **20초**다.

`/openmp` 로 8배 빨라진다고 치면 2.5초. 여전히 대화용으로는 답답하다.

**무엇을 하면 쓸 만해지나.**

① **메모리 대역폭을 줄인다.** 토큰 하나마다 가중치 400MB(fp32)를 전부 읽는다. D5에서 본 대로 이게 진짜 병목이다. **8비트로 바꾸면 100MB.** 여기서 가장 큰 이득이 난다

② **GEMM 을 제대로 쓴다.** E2 연습문제 1에서 본 대로 `MatMul` 은 C5의 `Gemm` 을 안 쓴다. AVX2 + 멀티스레드로 바꾸면 몇 배

③ **묶어서 처리한다.** 토큰 하나씩 뽑으면 행렬-벡터 곱이라 대역폭만 먹는다. 여러 요청을 묶으면 행렬-행렬 곱이 되어 가중치 한 번 읽고 여러 개를 처리한다

셋을 다 하면 `0.2초` 가 `0.01초` 근처까지는 갈 만하다. 초당 100토큰이면 쓸 만하다.

**정리하면 "된다"는 말은 정확히 이런 뜻이다.** 지금 코드로는 답답하지만, 이 교재에서 이미 본 기법들을 적용하면 실용 범위에 들어온다. **새로운 것을 배울 필요가 없다는 것이 요점이다.**

정답은 없다. 참고로 셋을 적어둔다.

**① 남의 가중치 싣기** — `lib/Engine.cpp`

`.gguf` 나 `.safetensors` 를 읽어 `FTransformer` 에 채운다. E2의 `Load` 옆에 형식 하나를 더 붙이는 일이다.

걸림돌은 **구조가 다르다는 것**이다. 대부분의 공개 모델은 RoPE(회전 위치 임베딩)를 쓰는데 우리는 학습된 위치 임베딩이다. D2의 `Attend` 에 RoPE 를 하나 더 다는 작업이 먼저다.

가장 실용적인 방향이고, 이 엔진을 **당장 쓸 물건**으로 만든다.

**② 토크나이저를 BPE 로** — `lib/Tokenizer`

글자 단위는 문맥을 낭비한다. 한글 한 자가 토큰 하나면 32토큰에 32글자밖에 안 들어간다. BPE 면 두세 배가 된다.

학습은 파이썬으로 하고(결정 26) 인코딩만 C++ 로 옮긴다. `tools/` 에 스크립트 하나, `lib/Tokenizer` 에 병합 규칙 적용 하나.

①과 짝이 된다. 남의 모델을 실으려면 남의 토크나이저도 필요하다.

**③ 실시간 API** — `lib/Engine.hpp`

E2 연습문제 3에서 짚은 셋 — 한 토큰씩 돌려주기, 버퍼 재사용, 대화 상태 분리. 게임이나 앱에 넣으려면 반드시 필요하다.

코드 양은 가장 적은데 **API 설계를 다시 하는 일**이라 생각할 거리가 많다.
